# Checkpoint (Контрольная точка)

Заменяет прежнюю сущность «Перекличка» (Roll Call) — переименована, модель
пересмотрена. Старый механизм (Kopfzählung + `reset_events`, кнопки «Tag
starten»/«Soft Reset») полностью удалён — описан в [[Переклички]] как
историческая заметка, здесь не переиспользуется.

## Зачем нужна перекличка

Система обеспечивает оперативный контроль местонахождения детей во время
поездки и сопровождает процессы посадки/высадки, передислокации групп и
промежуточных проверок. Контрольная точка (Checkpoint) — не сам процесс
сканирования, а **зафиксированный результат** на определённый момент
времени, на основании которого принимается решение: можно продолжать
движение, нужно подождать или нужно искать отсутствующих детей.

## Основные понятия (глоссарий)

| Термин | Значение | Где подробнее |
|---|---|---|
| **Roster** (реестр) | полный список всех зарегистрированных детей, включая отсутствующих сегодня | [[children]] |
| **Daily Roster** (`presentRoster`) | часть Roster, участвующая в сегодняшней поездке; `absentRoster = Roster − presentRoster` | [[Первая-регистрация-дня]] |
| **Group Roster** (`groupRoster`) | список детей группы; `presentGroupRoster`/`absentGroupRoster` — присутствующие/отсутствующие сегодня в группе | [[Группы-и-рабочий-день]] |
| **Bus Roster** (`busRoster`) | список детей, едущих в конкретном автобусе; автобус — временная группа с посадочным составом, не меняющимся в течение поездки | [[Учёт-автобусов]] (историческая — админ-экран удалён, автобус теперь только тип Checkpoint) |
| **Betreuer** / **HauptBetreuer** | воспитатель группы / главный администратор | [[Роли-пользователей]] |
| **ScanEvent** | одиночная отметка присутствия ребёнка (`child_id` + время) | [[scans]] |
| **ScanPacket** | пакет из произвольного числа ScanEvent, отправляемый воспитателем за один раз | [[scan_packets]] |
| **Checkpoint** (бывш. RollCall) | сама контрольная точка — не хранит детей напрямую, только ссылки на свои пакеты | эта страница |
| **checkedRoster** / **missingRoster** | дети, присутствующие / временно отсутствующие на контрольной точке; `missingRoster = presentRoster − checkedRoster` | см. «Missing/Extra» ниже |

Иерархия вложенности: `Checkpoint → ScanPacket (ScanBatch) → ScanEvent →
Child`. Ребёнок не принадлежит Checkpoint напрямую — только через цепочку
пакетов.

## Три типа

| Тип | Назначение | Стратегия агрегирования |
|---|---|---|
| **BUS** | подсчёт детей по автобусам при посадке/высадке; обычно две BUS-точки в день (утренняя и вечерняя) | `Union` всех пакетов (накопление, повторный скан не портит результат) |
| **GROUP** | подсчёт детей по группам непосредственно до/после каждой передислокации всей группировки; пересчёт группы обычно ведёт один закреплённый за ней воспитатель (10-12 детей в группе) | `Last Packet Wins` (каждый пакет — полная фотография группы, замена предыдущего) |
| **LAZY** | перекличка в середине дня (например, 13:00) без сбора всей группировки — вместо этого каждый ребёнок обязан появиться «на базе» в заданном временном окне и отметиться | `Union` всех пакетов, как BUS |

Особенность BUS: в одном автобусе может быть до 60 детей из разных групп —
разделение идёт по автобусам, а не по группам. Два воспитателя могут
сканировать один автобус параллельно (например, каждый — свой ряд сидений,
для ускорения, либо оба — весь автобус, для взаимной проверки) — `Union`
корректно обрабатывает оба сценария.

## Aggregation Model

Воспитатели никогда не изменяют результат контрольной точки напрямую — они
только отправляют **ScanPacket**, неизменяемый снимок состояния со своего
устройства. Всё остальное вычисляется автоматически на сервере:

```
Scanner → ScanPacket (immutable) → Aggregation Strategy → текущее состояние Checkpoint → UI
```

Пакет не редактируется и удаляется с большими ограничениями (см.
`remove_checkpoint()` в [[checkpoints]]). Все изменения происходят только на
уровне агрегирования пакетов, не самих пакетов. Это даёт: полную историю
(кто что прислал и когда), возможность пересчитать результат другим
алгоритмом без изменения данных, видимость вклада каждого воспитателя и
возможность восстановить состояние на любой момент времени.

### Почему GROUP использует другую стратегию, чем BUS/LAZY

Во время автобусной переклички невозможно понять, закончил ли воспитатель
сканирование — он может прислать частичный пакет, затем ещё один с
оставшимися детьми. Поэтому пакеты **накапливаются** (`Union`).

Во время групповой переклички воспитатель видит всю группу сразу — повторная
отправка означает не «вот ещё несколько детей», а «предыдущий пакет содержал
ошибку, используйте этот». Поэтому применяется `Last Packet Wins`: более
поздний пакет полностью заменяет более ранний по этой группе (но не удаляет
его — см. `remove_checkpoint()`/история пакетов в [[checkpoints]]).

| Тип | Aggregation |
|---|---|
| BUS | `Union` всех пакетов |
| GROUP | `Last Packet Wins` |
| LAZY | `Union` всех пакетов |

### Порядок детей

Хотя агрегирование выполняется как операция над множествами, результат
показывается в виде **упорядоченного списка** (порядок группы/автобуса
сохраняется, а не сортируется каждый раз заново) — это привычный порядок
бумажной переклички, ускоряет поиск конкретного ребёнка и даёт одинаковый
порядок на всех экранах.

## Missing/Extra/Comparison

Список отсутствующих детей никогда не хранится отдельно — вычисляется на
лету как разница между списком-эталоном и текущим списком присутствующих:

- `missing = Reference − Current` (кого не хватает по сравнению с эталоном);
- `extra = Current − Reference` (кто появился сверх эталона — например,
  ребёнок посчитан в двух автобусах одновременно, признак ошибки).

Реализовано в `useCheckpoints.js`:

- `summarizeCheckpoint()` — поля `missing`/`extra` против дневного
  `baseline_children_count` (см. «Baseline присутствия» ниже);
- `getBusDelta()`/`getGroupDelta()` — отклонение конкретного автобуса/группы
  от того же автобуса/группы в базовой (baseline) точке дня;
- `getBusChildrenBreakdown()`/`getGroupChildrenBreakdown()` — полный
  `{present, absent}` относительно всего Roster (`checkedRoster`/
  `missingRoster` из глоссария выше, буквально).

Если два воспитателя независимо пересчитали один и тот же автобус и
результаты разошлись — расхождение видно через сравнение пакетов
(`packets` внутри `buses[]`, [[Checkpoint]]-детали), решение принимает
HauptBetreuer (повторный пересчёт или ручная сверка).

## Принципы интерфейса

Заложены при редизайне администраторского интерфейса (сущностные экраны
Child/Betreuer/Group вместо табличного Kopfzählung, признанного неудачным
экспериментом):

1. Каждая сущность имеет собственный экран — избегать экранов «смешанного
   назначения».
2. Краткое представление (Widget, кликабельный) внутри списков + полное
   представление (View) при переходе.
3. Списки виджетов вместо табличного отображения там, где это возможно.
4. Навигация строится переходом между сущностями, а не разрастанием одной
   страницы.
5. Действия выполняются над сущностями (Checkpoint, Child, Betreuer, Group),
   а не над таблицами базы данных напрямую.

## Гибридная модель жизненного цикла

1. **Создаётся автоматически** — первый пакет своего типа/дня создаёт точку
   без участия администратора; воспитатели никогда не блокируются
   ожиданием (`submit_scan_packet()`, см. [[checkpoints]]).
2. **Завершается только явно** — администратор нажимает Finish
   (`finish_checkpoint()`); авто-завершения нет ни для одного типа, включая
   LAZY.
3. **Точки разных типов независимы** — BUS и GROUP могут быть открыты
   одновременно, это штатный режим, не конфликт.
4. **Не более одной открытой точки одного типа в день** — явное создание
   при уже открытой отклоняется (`ALREADY_OPEN`). **Должно быть** по
   изначальному замыслу — программная проверка на уровне API; **реализовано
   сильнее**: частичный уникальный индекс `(day, type) WHERE status = 1`
   в БД делает второй одновременный открытый Checkpoint одного типа/дня
   технически невозможным даже в обход приложения (прямой SQL), а не только
   отклоняемым интерфейсом — см. [[checkpoints]].
5. **Reopen/Remove** — `reopen_checkpoint()` отменяет Finish,
   `remove_checkpoint()` удаляет точку целиком вместе с её пакетами
   (каскадно). Отмены отдельных уже принятых пакетов без удаления всей
   точки не существует — сознательное ограничение, см. [[checkpoints]].

## Baseline присутствия (`presentRoster`)

При **первой за день завершённой контрольной точке** (любого типа —
`finish_checkpoint()`) фиксируется `baseline_children_count` — это и есть
`presentRosterCount` из глоссария: жёстко зафиксированное число детей,
участвующих сегодня. Все последующие точки дня отображают отклонение
(`missing`/`extra`) от этого числа, а не пересчитывают его заново.

## Автоматическая граница дня

Дня как отдельного явного действия («Tag starten»/«Tag schließen») не
существует. [[children_today]]/[[groups_today]] date-scoped — уникальные
ограничения на `(child_id, date)`/`(group_id, date)` вместо единственной
строки на сущность; новый день начинается сам собой с первым сканом с новой
датой, никакого `pg_cron`/scheduled job нет. Заменяет весь диапазон
Reset-событий старого `reset_events`, см. [[reset_events]] (историческая).

## Экраны администратора

Единая точка входа — кнопка «Checkpoints» в `MainView.vue`:

- `CheckpointListView.vue` (`/admin/checkpoints`) — список/история, явное
  создание, различает точки «создана автоматически (Betreuer X)» от
  «создана администратором».
- `CheckpointBusView.vue` (`/admin/checkpoints/bus/:id`) — детали BUS-точки.
- `CheckpointGroupView.vue` (`/admin/checkpoints/group/:id`) — детали
  GROUP-точки, со сворачиванием «чистых» групп (без отклонений).
- `CheckpointLazyView.vue` (`/admin/checkpoints/lazy/:id`) — прогресс LAZY
  (кто отметился / ещё нет).

Все три детальных экрана обновляются по Realtime (`postgres_changes` на
`checkpoints`+`scan_packets`) без ручной кнопки «Aktualisieren».
Дополнительно — сущностные экраны (Child/Betreuer/Group card) — см.
`useBetreuerEntity`, `useChildren`.

- `useScanPacket.js` — сборка/отправка пакета со стороны воспитателя.
