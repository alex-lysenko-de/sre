# Инвайты, сессии, WebAuthn

> Источники: `backup/database/schema.sql` (реальный `pg_dump`, тикет 111),
> `supabase/functions/auth/index.ts`, `supabase/functions/invite-generate/index.ts`,
> `supabase/functions/invite-accept/index.ts`. Добавлено по итогам ревью
> тикета 108 (`tickets/108/REVIEW_REPORT.md`, Critical 2) — раздел
> «Модель аутентификации» изначально не покрывал этот слой.

[[Модель-аутентификации]] описывает основной путь входа — обычный
`supabase.auth.signInWithPassword()`/`getSession()`/`signOut()`. Но схема
БД содержит более широкий слой таблиц/функций, относящихся к
аутентификации, который не сводится к этому основному пути. По факту в
проекте одновременно присутствуют два разных, несовместимых друг с другом
механизма — **боевой** (используется) и **отдельный, судя по всему
нерабочий** (код есть, но не вызывается).

## Боевой путь: приглашения (`invites`) + обычный Supabase Auth

Регистрация новых пользователей идёт не через открытую самостоятельную
регистрацию, а через приглашение от admin:

1. `InviteGeneratorView.vue` → Edge Function `invite-generate` — проверяет,
   что вызывающий admin (по `users.role` через `service_role`-клиент),
   создаёт строку в `public.invites` (`invite_token`, `role`, `expires_at`).
2. Ссылка с токеном передаётся новому пользователю; `InviteAcceptView.vue`/
   `WelcomeView.vue` → Edge Function `invite-accept` — проверяет токен
   (`invite_token`, `used = false`, `expires_at`), создаёт **настоящего**
   пользователя `auth.users` через `supabase.auth.admin.createUser({email,
   password, ...})`, затем строку в `public.users` (обычный email+пароль
   аккаунт, не passkey), помечает `invites.used = true`.
3. Дальше — обычный вход через `supabase.auth.signInWithPassword()`
   (`LoginView.vue`/`WelcomeView.vue`), сессия хранится штатным механизмом
   Supabase Auth поверх LocalForage (см. [[Кэширование-LocalForage]]).

`public.invites` в реальной схеме: `id uuid`, `invite_token text`, `role
text` (`admin`/`user`, CHECK), `expires_at timestamptz`, `used boolean
default false`, `used_by_email text`, `created_at`. Эти имена колонок
совпадают с тем, что использует `invite-generate`/`invite-accept`.

## Отдельный слой: WebAuthn/passkey + кастомный JWT — код есть, но не используется

В `schema.sql` также есть:

- `public.sessions` — кастомные токены сессий (`token_hash`, `device_id`,
  `expires_at`, `revoked`, `last_activity`) и функция
  `is_session_valid(token_hash)`, проверяющая их.
- `public.webauthn_challenges` + `auth.webauthn_credentials` — таблицы для
  WebAuthn/passkey-регистрации и входа (challenge/response, credential_id,
  public_key, counter).
- Edge Function `supabase/functions/auth/index.ts` (~413 строк) — реализует
  `register/prepare`, `register/finish`, `login/prepare`, `login/finish`
  поверх WebAuthn, плюс `generateJWT()` — собственный HMAC-подписанный JWT
  (`Deno.env.get('JWT_SECRET') || 'your-secret-key'` — значение по
  умолчанию `'your-secret-key'` взято прямо из кода, это не секрет, а
  fallback-заглушка; реальный `JWT_SECRET` в этой ревизии не читался).

**Проверено:** `grep` по `src/` на вызовы `functions/auth`,
`sessions`/`is_session_valid`/`token_hash` — ноль совпадений. Единственные
вызываемые из `src/` Edge Functions — `invite-generate`, `invite-accept`,
`delete-user` (см. [[Обзор-Edge-Functions]]). Ни один компонент не
обращается к `/auth/register/*` или `/auth/login/*`, и ни один composable
не читает/пишет `public.sessions`.

Более того, у `auth/index.ts` есть внутренние нестыковки с реальной схемой,
из-за которых он в текущем виде не мог бы работать против неё:

- Вставляет в `invites` через колонку `token`, тогда как реальная колонка —
  `invite_token`.
- Вставляет в `webauthn_challenges` колонку `user_data`, которой в
  `schema.sql` нет.
- Создаёт `public.users` со своим `id: crypto.randomUUID()` (`uuid`), тогда
  как в реальной схеме `users.id` — `bigint generated by default as
  identity` (сгенерированный сервером, не задаётся клиентом).

**Вывод:** это, судя по всему, код от более раннего или параллельного
варианта дизайна аутентификации (WebAuthn/passkey вместо email+пароль),
оставленный в репозитории, но не подключённый к текущему фронтенду и не
согласованный с текущей схемой `public.invites`/`public.users`. Функции
`has_role()`/`is_admin()` из той же группы SQL-функций, наоборот, активно
используются — `has_role()` в RLS-политиках [[users]]
(`users_delete_admins_only` и др., см. [[RLS-политики]]); `is_admin()` и
`is_session_valid()` в проверенных источниках (RLS-политики, `src/`) не
встретились ни разу.
