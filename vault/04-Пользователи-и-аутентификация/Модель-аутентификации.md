# Модель аутентификации

> Источники: `doc/useUser.md` (обновлён в тикете 107 под реальную
> 3-слойную архитектуру; файл удалён в тикете 118, содержание перенесено сюда), `src/router/index.js`.

Аутентификация — через **Supabase Auth** (email+пароль). Приложение
поддерживает две прикладные роли поверх `auth.users`: `admin` и `user`
(Betreuer), хранимые в таблице [[users]] (см. [[Роли-пользователей]]).
Регистрация закрытая — по приглашению admin, без открытой формы
самостоятельной регистрации. В схеме БД дополнительно есть отдельный
слой invite/session/WebAuthn-таблиц — см. [[Инвайты-сессии-WebAuthn]] для
разбора, какая часть из этого реально используется, а какая — нет.

## Вход в систему выполняется один раз

По задумке (`doc/selectGroupAndBus.md`, удалён в тикете 118), `LoginView.vue` пользователь видит
только один раз — при первой регистрации. Дальше сессия сохраняется, и вход
выполняется автоматически («в тихом режиме»). Токен сессии хранится через
адаптер `supabaseStorageAdapter` поверх LocalForage (см.
[[Кэширование-LocalForage]]), а не в обычном `localStorage`.

### Флаг `sre_user_registered` — подсказка для гейта, не источник истины (тикет 112)

До тикета 112 `router.beforeEach`/`App.vue.initializeApp()` вызывали
`supabase.auth.getSession()` **только если** `sre_user_registered === 'true'`
в LocalForage — при негативном флаге сессия вообще не проверялась. На iPhone
(Safari/установленное PWA) ровно одна ненадёжная запись этого флага (в
`WelcomeView.vue` он писался сразу после `invite-accept`, до подтверждения
входа) навсегда «ломала» устройство — оно вело себя как незарегистрированное
при каждом следующем запуске, даже если сессия Supabase на самом деле
восстанавливалась нормально. Начиная с тикета 112:

- `getSession()` вызывается **всегда**, независимо от значения флага.
- Флаг используется только как подсказка для выбора страницы в одном
  случае — сессии сейчас нет: `true` → `/login` (устройство уже когда-то
  логинилось), отсутствует/не `'true'` → `/info` (гость).
- `WelcomeView.vue` пишет флаг только **после** подтверждённого
  `signInWithPassword()`, а не сразу после `invite-accept`.
- Флаг самовосстанавливается (fire-and-forget) в `App.vue`
  (`handleAuthentication()`/`checkAuth()`) при каждой подтверждённой активной
  сессии — по аналогии с уже существующим обновлением `last_seen_date` в
  `router/index.js`.

## Реализация в три слоя

Изначально задание (`doc/useUser.md`, удалён в тикете 118) предполагало один модуль
`src/modules/useUser.js`. По факту реализовано как три отдельных слоя:

```
Components (UI)
     ↓
useUser.js       — бизнес-логика: кэш (LocalForage, TTL), оркестрация
     ↓
useSupabaseUser.js — только запросы к Supabase (getSession, fetchUserFromDB,
                      fetchScheduleForDate, updateScheduleRecord, signOut, ...)
     ↓
stores/user.js   — Pinia store: только реактивное состояние (userInfo) +
                    геттеры (isAdmin, isCheckInRequired, userEmail); методы
                    делегируют в useUser()
```

Подробности каждого слоя — [[useUser]], [[useSupabaseUser]], [[stores-user]].

## Navigation guard (`src/router/index.js`)

`router.beforeEach` (с тикета 112 — сначала всегда сессия, флаг только для
редиректа при её отсутствии):

1. Читает флаг `sre_user_registered`, затем **всегда** вызывает
   `supabase.auth.getSession()` — независимо от значения флага.
2. Публичные страницы (`meta.public`) пропускаются без проверок в любом
   случае — есть сессия или нет.
3. Если активной сессии нет: флаг `!== 'true'` (гость, никогда не
   логинился) → разрешены только `Welcome`, `Main`, `Info`, иначе редирект
   на `/info`; флаг `'true'` (устройство уже когда-то логинилось) → редирект
   на `/login`.
4. Если сессия есть и `meta.requiresAuth` — проверка `role`/`active` из
   [[users]]; неактивный аккаунт — принудительный `signOut()` и редирект на
   `/login`.
5. Для `meta.requiresAdmin` — доп. проверка `role === 'admin'`, иначе
   редирект на `/main` с алертом.
6. Обновление `users.last_seen_date` (fire-and-forget).
7. Перехват `?id=`/`?n=` в query-параметрах маршрутов без `public`/
   `requiresAuth` → редирект на `/armband/:id` (см. [[QR-код-URL]]).

Это дублирует часть логики RLS на клиенте (UX — быстрый редирект без
обращения к серверу), но не заменяет её — реальное ограничение доступа к
данным обеспечивается [[RLS-политики]] на стороне БД.

## Выход из системы: подтверждение + опциональная полная очистка (тикет 112)

Кнопка «Abmelden» в `App.vue` открывает `LogoutConfirmModal.vue` (по образцу
`GroupChangeModal`/`BusChangeModal`) вместо немедленного `signOut()`. Порядок
при подтверждении:

1. `supabase.auth.signOut()` — сначала, пока сессия ещё на месте (SDK должен
   успеть прочитать refresh-токен для server-side revoke).
2. `userStore.clearUserCache()` — как раньше.
3. Только если отмечен чекбокс «Auch lokale Daten löschen» —
   `clearAllAuthStorage()` (см. [[Кэширование-LocalForage]]): полностью
   очищает `authLocalForage`, включая `sre_user_registered`. Без чекбокса
   флаг остаётся — устройство при следующем запуске всё ещё считается
   «известным» и ведёт на `/login`, а не на `/info`.
