# `checkpoints`

> Источник: `doc/db/checkpoints.sql` (тикет 132, применена к боевой БД —
> подтверждено побайтовым совпадением со свежим дампом
> `backup/database/schema.sql`). Доменное обоснование модели (гибридный
> жизненный цикл, зачем нужен именно такой) — [[Checkpoint]].

Заменяет старый механизм «перекличка через `reset_events`» (см.
[[reset_events]], помечена исторической). Контрольная точка — фиксация
результата пересчёта детей на момент времени, а не сама история сканов
(историю хранят [[scans]]/`scan_packets`, `checkpoints` — только ссылки на
них через `scan_packets.checkpoint_id`).

```sql
create table public.checkpoints (
  id bigint generated by default as identity not null,
  type smallint not null,                -- 1=BUS, 2=GROUP, 3=LAZY
  day character varying not null,        -- формат scans.date/scan_packets.date
  status smallint not null default 1,    -- 1=OPEN, 2=FINISHED
  created_by bigint not null references users(id),
  created_at timestamptz not null default now(),
  finished_at timestamptz null,
  finished_by bigint null references users(id),
  baseline_children_count smallint null,
  constraint checkpoints_pkey primary key (id),
  constraint checkpoints_type_check check (type in (1, 2, 3)),
  constraint checkpoints_status_check check (status in (1, 2))
);

create unique index checkpoints_open_type_per_day
  on public.checkpoints (day, type) where status = 1;
```

Частичный уникальный индекс `(day, type) WHERE status = 1` — центральный
механизм гибридной модели: не более одной открытой контрольной точки на
тип в день. Используется дважды: `create_checkpoint()` явно отклоняет
конфликт, `submit_scan_packet()` (см. ниже) использует его как
`ON CONFLICT`-таргет для гонки двух воспитателей, отправляющих первый
пакет дня одновременно — оба сходятся к одной и той же контрольной точке,
ни один пакет не отклоняется.

Статуса `CANCELLED` нет намеренно — вместо него `reopen_checkpoint()` (отмена
Finish) и `remove_checkpoint()` (полное удаление), см. ниже.

## RPC-функции (все `SECURITY DEFINER`, проверка `role='admin' AND active=true` внутри)

| Функция | Действие |
|---|---|
| `create_checkpoint(type, day)` | Явное создание администратором. В отличие от авто-создания в `submit_scan_packet()` — **отклоняет** конфликт (`ALREADY_OPEN` + id существующей через Postgres `DETAIL`), не создаёт молча. |
| `finish_checkpoint(id)` | Единственный способ закрыть точку (авто-завершения нет ни для одного типа, включая Lazy). Два раздельных шага: 1) закрыть саму точку; 2) если это первая за день завершённая точка любого типа — зафиксировать `baseline_children_count` (`COUNT(DISTINCT child_id)` по `scans`/`scan_packets` этой точки). |
| `reopen_checkpoint(id)` | Отмена Finish (`status 2→1`). Отклоняет, если тем временем открылась другая точка того же типа/дня (`ALREADY_OPEN`, та же форма ошибки). |
| `remove_checkpoint(id)` | Полное удаление точки + каскадное `DELETE` `scan_packets`/`scans` (явными запросами, не `ON DELETE CASCADE` — чтобы не менять поведение удаления `scan_packets` в остальных сценариях). Явное следствие: `client_packet_id` удалённых пакетов освобождается — повторная офлайн-отправка того же пакета после `remove_checkpoint()` принимается как новый (осознанный риск, `tickets/131/MIGRATION_PLAN_REVIEW_RESPONSE.md`). |

Контракт ошибок: `RAISE EXCEPTION '<CODE>'` без интерполяции для
плоских кодов (`NOT_OPEN`, `NOT_FINISHED`, `NOT_FOUND`, `NOT_ADMIN`); для
`ALREADY_OPEN` id существующей точки передаётся через `DETAIL`
(`error.details` в `supabase-js`) — без второго round-trip. Та же форма
ошибок используется клиентским composable-слоем (`useCheckpoints.js`,
`translateRpcError()`).

## `submit_scan_packet()` — авто-создание/поиск контрольной точки

Функция (тикеты 120/122) расширена `CREATE OR REPLACE`, не переписана — тело
для `scan_packets`/`scans` не менялось. Перед вставкой пакета: `INSERT INTO
checkpoints ... ON CONFLICT (day, type) WHERE status = 1 DO NOTHING`, затем
`SELECT` открытой точки этого типа/дня — если пакет пришёл без открытой
точки, она создаётся автоматически; воспитатель никогда не получает отказ
по этой причине (центральное свойство гибридной модели, см. [[Checkpoint]]).
`scan_packets.checkpoint_id` заполняется найденным/созданным id.

## RLS

`SELECT` — любой `authenticated` (`USING (true)`). Ни одной
`INSERT`/`UPDATE`/`DELETE`-политики для `authenticated` — запись только
через перечисленные выше `SECURITY DEFINER`-функции и через
`submit_scan_packet()` (вызывается Edge Function под `service_role`, RLS не
применяется). Спроектирована без антипаттерна «неотозванных широких
legacy-политик» с самого начала, см. [[RLS-политики]], раздел
«[[checkpoints]] (тикет 132)».
