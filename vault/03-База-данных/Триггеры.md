# Триггеры

> Источники: `doc/db_triggers.sql` (исходная построчная версия, историческая),
> `doc/db/scan_packets.sql` (тикет 122 — переход на `FOR EACH STATEMENT` +
> transition tables, batch-версии функций), `doc/db/date_scoped_daily_tables.sql`
> (тикет 138 — date-scoped `ON CONFLICT`-таргеты, подтверждено применённой к
> боевой БД, см. [[children_today]]), `doc/db/remove_reset_events_trigger.sql`
> (тикет 137 — `DROP FUNCTION on_reset_event_insert()`), `doc/db/
> headcount_presence_morning.sql` (тикет 106).

Вся логика пересчёта агрегированных счётчиков присутствия находится **в
БД** (PL/pgSQL-функции + триггеры), а не в клиентском коде — клиент только
вставляет строки в `scans`/[[scan_packets]] (через `submit_scan_packet()`),
остальное происходит автоматически.

## `on_scan_insert_batch()` (`AFTER INSERT ON scans`, `FOR EACH STATEMENT`)

Живая версия с тикета 122 (заменила построчную `on_scan_insert()`, см.
«Историческая версия» ниже) — `REFERENCING NEW TABLE AS new_table`, срабатывает
один раз на весь INSERT-стейтмент независимо от числа строк, а не по разу на
строку. Так один пакет из N детей ([[scan_packets]], тикет 122) даёт один
цикл пересчёта, а не N.

- Guard: если среди вставленных сканов есть ребёнок без `group_id` —
  `RAISE EXCEPTION` на весь батч целиком, ничего не пишется молча
  (безгруппный ребёнок — невозможное состояние домена, см. `[[children]]`).
- `DISTINCT ON (s.child_id)` (по `s.created_at DESC`) — защита от двух строк
  одного ребёнка в одном стейтменте: клиент дедуплицирует внутри раунда
  (`isDuplicate()`), но `INSERT ... ON CONFLICT` падает, если в самом
  стейтменте есть два конфликтующих ряда на один ключ, поэтому сервер не
  полагается на клиентскую дедупликацию.
- `INSERT ... ON CONFLICT (child_id, date) DO UPDATE` в [[children_today]]
  (таргет — `(child_id, date)` с тикета 138, до этого был просто `child_id`).
  `date` берётся из `s.date` самого скана, не из `DEFAULT`/`now()` сервера.
  - INSERT-ветка (первая строка ребёнка **за эту дату**): `presence_today=1`,
    `presence_now=1`, `bus_today=s.bus_id`, `bus_now=s.bus_id`,
    `presence_morning = CASE WHEN s.bus_id IS NOT NULL THEN 1 ELSE 0 END`
    (тикет 106).
  - `DO UPDATE`-ветка (повторный скан того же дня): только `presence_now=1`,
    `bus_now=EXCLUDED.bus_now`, `user_id=EXCLUDED.user_id`.
    **`presence_morning` сюда сознательно не входит** — разовый снимок,
    который не должен «мигать» при повторных сканах (см. [[children_today]]).

## `on_children_today_change_batch()` (`AFTER INSERT` / `AFTER UPDATE ON children_today`, `FOR EACH STATEMENT`)

Живая версия с тикета 122 (заменила построчную `on_children_today_change()`).
Postgres не разрешает transition-таблицу на триггере с более чем одним
событием, поэтому это два отдельных триггера (`trg_on_children_today_insert`/
`trg_on_children_today_update`), делящих одну функцию.

Пересчитывает [[groups_today]] для затронутых **пар** `(group_id, date)` (с
тикета 138 — раньше группировка была только по `group_id`, без даты): `COUNT(*)
FILTER (WHERE presence_today = 1)` и `... presence_now = 1`, `GROUP BY
ct.group_id, ct.date`, ограничено `WHERE (ct.group_id, ct.date) IN (...
new_table ...)`. Затем `ON CONFLICT (group_id, date) DO UPDATE`. Полный
пересчёт по группе-и-дате, а не инкремент/декремент — проще и устойчивее к
гонкам, дороже при больших группах (не проблема при масштабах проекта).

## `on_reset_event_insert` — историческая, функция физически удалена (тикет 137)

> **Историческая заметка (тикет 139):** функция `DROP FUNCTION`-нута
> (`doc/db/remove_reset_events_trigger.sql`), подтверждено отсутствие в живом
> дампе схемы. Механизм Hard/Normal/Soft Reset, который она реализовывала,
> заменён автоматической date-scoped границей дня (тикет 138) — см.
> «Граница дня» в [[children_today]] и [[Checkpoint]]. Раздел ниже сохранён
> как есть, без изменений, для истории решений (правило с ревью тикета 131),
> но **описывает удалённый код**, не действующий.

`CASE NEW.event_type`:

- `0` (Total reset) — `DELETE FROM children_today; DELETE FROM groups_today;`
- `1` (Normal reset) — если это первый reset дня (`event_type=1`) —
  `groups_today.children_today = children_now`, затем `children_now = 0`;
  иначе только `children_now = 0`. В обоих случаях —
  `children_today.presence_now = 0`.
- `2` (Soft reset) — `presence_now`/`children_now` обнуляются без сохранения
  снимка.

См. [[reset_events]] (историческая) для таблицы событий.

## `on_children_today_delete` (`AFTER DELETE ON children_today`) — неактивна с тикета 137

Пересчитывала/удаляла строку [[groups_today]] для группы удалённой записи —
на случай явного `DELETE FROM children_today` вне общего `event_type=0`.
Единственный источник таких `DELETE` был `on_reset_event_insert`
(`event_type=0`, «Total reset») — с его удалением в тикете 137 триггер не
срабатывает ни при каком живом сценарии. Не удалена, оставлена как мёртвый
код (вне объёма тикетов 137/138/139).

## `on_scan_insert()` / `on_children_today_change()` (построчные, историческая версия) — не действуют с тикета 122

Оригинальные `FOR EACH ROW`-версии `on_scan_insert_batch()`/
`on_children_today_change_batch()` выше — по одному вызову на строку вместо
одного на весь батч. Заменены в тикете 122 при переходе на пакетную отправку
сканов ([[scan_packets]], `useScanPacket.js`). Функции физически не удалены
(нет живого триггера, который бы их вызывал), оставлены как мёртвый код —
вне объёма тикетов 122/137/138/139.

## `recalculate_groups_today()` — вспомогательная функция, обновлена под date-scoping (тикет 138)

Полный пересчёт [[groups_today]] по всем **парам** `(group_id, date)` сразу
(было — по всем `group_id`, без даты) — на случай рассинхронизации счётчиков;
не вызывается никаким триггером, ручной инструмент восстановления
(запускается вручную из Supabase SQL editor). Подтверждено грепом: не
используется ни триггером, ни `src/`.

`idx_scans_child_date(child_id, date)`, `idx_scans_band_date(band_id, date)`,
`idx_scan_packets_bus_date`/`idx_scan_packets_group_date`,
`idx_scans_packet_id` — под характерные запросы подсчёта присутствия и
истории сканов. `idx_reset_events_day_type(day, event_type)` — таблица и
индекс не удалены (решение пользователя на ревью 131), но триггер, ради
которого он был нужен, отсутствует с тикета 137.
