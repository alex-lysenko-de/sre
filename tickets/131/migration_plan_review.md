## 1. Главный вывод

Текущий план (13 тикетов, Phase 1 / Gate 141 / Phase 2) спроектирован как
**безопасная поэтапная миграция боевой системы с живыми пользователями**:
Phase 1 работает рядом со старыми экранами, Phase 2 (date-scoped
`children_today`/`groups_today`) отложена и защищена ручным gate-тикетом.

По вводным задачи это неверная оптимизация: пользователей нет, ценных данных
нет, обратная совместимость не нужна, временная нерабочесть между тикетами
допустима. Критерий качества — минимальное время до чистой конечной
архитектуры, а не отсутствие риска. Вся конструкция Phase 1/Gate/Phase 2
существует только ради того, чтобы `AdminBusView.vue`/`ChildrenView.vue`
продолжали работать во время Phase 1 — если это требование снять, разделение
не нужно.

## 2. Подтверждено по свежему дампу БД (`backup/database/schema.sql`, обновлён 2026-08-02)

- **`groups_today_user_id_key UNIQUE(user_id)` не существует** — в реальной
  схеме только `groups_today_group_id_key UNIQUE(group_id)`. Пункт «сверить
  перед Phase 2» (`131/MIGRATION_PLAN.md`, §1.3 п.4) закрыт: соответствующий
  `DROP CONSTRAINT` в DDL тикета 142 нужно просто убрать, а не «сверять на
  живой БД» как написано в 142.txt.
- **`scan_packets` присутствует** в дампе — подтверждает, что тикет 122
  применён к боевой БД (как и указано в памяти проекта).
- **`children_today`/`groups_today` глубже вплетены в БД, чем видно по
  `src/`**: триггеры `on_children_today_change`/`_batch`/`on_children_today_delete`
  синхронизируют агрегаты в `groups_today`, плюс отдельная функция
  `recalculate_groups_today()`. Ни один из тикетов 132–144 не упоминает эти
  функции явно — при миграции их нужно учитывать, а не только колонки и
  индексы (см. решение по вопросу 2 ниже — миграция, не удаление).
- **Уже существующий пример «неотозванной широкой legacy-политики»**
  (антипаттерн, задокументированный в `vault/03-База-данных/RLS-политики.md`)
  реально присутствует на `children_today`: permissive-политика
  `"Allow authenticated users to ... USING (true)"` сосуществует с более узкой
  `own_group_insert_presence_now`/`own_group_update_presence_now` —
  PostgreSQL объединяет permissive-политики через OR, поэтому узкая политика
  сегодня ничего не ограничивает. Раз `children_today` мигрируется, а не
  удаляется (вопрос 2) — стоит почистить эту политику заодно, а не переносить
  антипаттерн в date-scoped версию.
- **`useChildPresence.js.setPresentNow()` пишет в `children_today` напрямую**,
  без Packet — нарушает Aggregation Model и Принцип 5 `decision.md`
  («воспитатели никогда не изменяют состояние переклички напрямую» /
  «все действия выполняются над сущностями, не над таблицами БД»). Это и есть
  причина, по которой Kopfzählung признана не вписывающейся в новую
  архитектуру (см. решение по вопросу 1).

## 5. Новая находка вне текущего охвата 132–144: обход Packet-модели в `ChildDetailView.vue`

Кнопка «Präsenz registrieren» на `ChildDetailView.vue` вызывает
`useScan.js`.`createScan()` — **прямой `INSERT` в `scans`, без `packet_id` и
без обращения к `submit_scan_packet()`/`scan_packets` вообще**. Экран
достижим через реальный, живой маршрут: физический QR/NFC на браслете →
`?id=123` в URL → редирект на `/armband/:id` (`ArmbandView.vue`) → при уже
привязанном браслете сразу на `/child/:id` (`ChildDetail`, `ChildDetailView.vue`).
Это не мёртвый код и не прототип — это отдельный, третий по счёту канал
регистрации присутствия (помимо камерного `Scanner.vue`/пакетного потока
тикета 120 и `useChildPresence.js`/Kopfzählung).

**Практическое следствие**: ребёнок, отмеченный присутствующим через эту
кнопку, получит строку в `scans` без `checkpoint_id` — она никогда не попадёт
ни в один Checkpoint-экран (Bus/Group/Lazy), так как все три считают
присутствие через `scans ⋈ scan_packets.checkpoint_id`. Администратор увидит
через Checkpoint, что ребёнок отсутствует, хотя по факту он уже отмечен через
этот альтернативный путь — расхождение в данных, которое новая архитектура
не обнаружит и не предупредит о нём.

Это нарушает тот же принцип Aggregation Model, что и Kopfzählung, но **не
упомянуто ни в одном документе (130/131/132–144)** — вероятно, потому что
`ChildDetailView.vue`/`ArmbandView.vue`/`useScan.js` относятся к более старому
слою функциональности (привязка браслетов), не пересматривавшемуся с момента
тикета 120/121/122.

**решение пользователя** 
Переделать кнопку «Präsenz registrieren» из `ChildDetailView.vue` так, чтобы она тоже создавала запись через
   `submit_scan_packet()` (CHECKIN-подобный пакет с одним ребёнком) без сохранения
   UX «сразу после привязки браслета — отметить присутствие»;
Такой вариант достаточно простой (уже есть готовая функция
`submit_scan_packet()`, нужно только сформировать однопакетный payload типа
LAZY/CHECKIN на клиенте)

## 6. Предлагаемая структура тикетов (обновлено с учётом решений §3)

13 тикетов → 6:

1. **DB — вся новая схема разом**: `checkpoints`+RLS, RPC ×4,
   расширение `submit_scan_packet()` (бывшие 132+133+134). Прецедент проекта
   (121→122) уже объединял таблицу+триггеры+функцию+RLS+Edge Function+UI в
   один тикет для сравнимого объёма — разделение здесь не добавляет пользы.
2. **DB — date-scoped `children_today`/`groups_today`** (бывший 142, без
   изменений в замысле — пользователь подтвердил миграцию, не удаление).
   Поскольку единственный потребитель в коде (`useChildPresence.js`) уходит
   вместе с Kopfzählung (см. §3), фактический объём тикета — только схема:
   колонка `date`, новые unique-констрейнты, обновлённые `ON CONFLICT`-цели
   в `on_children_today_change_batch`/`on_scan_insert_batch`, плюс чистка
   найденной в §2 неотозванной широкой RLS-политики на `children_today`. Не
   зависит от тикета 3 (удаление UI) и может идти параллельно/сразу за
   тикетом 1.
3. **Удаление устаревшего UI**: `AdminBusView.vue`, `ChildrenView.vue`,
   `HeadcountView.vue` (Kopfzählung, решение 1), `ResetHistoryPanel.vue`,
   `BusDetailModal.vue`, `GroupDetailModal.vue`, `useChildPresence.js`,
   мёртвые функции `useDays.js`, `on_reset_event_insert`, старые
   маршруты/кнопки `MainView.vue` — без промежуточной 4-й кнопки, сразу
   финальное меню. **Добавлено по итогам аудита (§4)**: убрать кнопку
   «Kopfzählung» из `GroupEditView.vue` (`goToHeadcount()`/`/headcount`,
   иначе мёртвая ссылка) — не упомянуто ни в одном из тикетов 132–144.
4. **Composable + Entity слой** на реальных данных (бывшие 135+136).
5. **Экраны Checkpoint**: List+Bus+Group одним тикетом (однородны, прямые
   аналоги старых экранов), Lazy — отдельным (единственный содержательно
   новый экран; критерий Finish уже решён — простой список, см. §3 вопрос 4).
6. **Сквозная проверка на устройстве + документация** (бывшие 141+144).

Отдельно от этой серии тикетов — открытый вопрос §5 (обход Packet-модели в
`ChildDetailView.vue`) требует решения пользователя и, вероятно, отдельного
тикета (нумерация вне 132–144, так как это не часть Checkpoint-функциональности
как таковой, а независимо обнаруженный архитектурный разрыв).
