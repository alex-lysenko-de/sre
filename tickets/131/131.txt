# Тикет 131: Реализация «Контрольная точка» (Checkpoint) — БД и интерфейс администратора

Тикет реализации для 130, по аналогии с парой 121 (research/архитектура) →
122 (реализация). 130 был явно ограничен дизайн-этапом ("БД/код в рамках
этого тикета не меняются") — 131 применяет принятую в нём концепцию к
реальной БД и клиентскому коду.

Входные документы, на которых основан этот тикет и которые он **не
дублирует**: `tickets/130/130.txt` (исходные требования, часть которых
позже скорректирована), `tickets/130/decision.md` (итоговое архитектурное
решение по модели — гибридная модель авто-создания/явного завершения,
имеет приоритет там, где расходится с `130.txt`) и
`tickets/130/IMPLEMENTATION_PLAN.md` (архитектурная спецификация — схема
БД, RPC-функции, новые компоненты, план внедрения, уже приведённая в
соответствие с `decision.md`). Точные DDL, псевдокод функций, раскладка
экранов — уже зафиксированы там и здесь не переписываются; 131 ссылается
на конкретные разделы вместо дублирования.

Сущность переименована из «Перекличка (Roll Call)» в «Контрольная точка
(Checkpoint)» — таблица `checkpoints`, RPC `create_checkpoint`/
`finish_checkpoint`/`cancel_checkpoint`, колонка `scan_packets.
checkpoint_id`, композабл `useCheckpoints.js`, компоненты
`CheckpointListView.vue`/`CheckpointBusView.vue`/`CheckpointGroupView.vue`/
`CheckpointLazyView.vue`.

# Назначение задачи

Сегодня администратор работает с перекличкой через разрозненные экраны
(`AdminBusView.vue`: сводка/Aktualisieren/Tag starten/Soft Reset/таблица
автобусов/история сбросов; `ChildrenView.vue`: отдельная сводка групп и
предупреждение о недостающих детях) и нет ни одной сущности "раунд
запущен/завершён" на уровне данных. 130 спроектировал замену: новая
таблица `checkpoints` с гибридной моделью (`tickets/130/decision.md`) — контрольная
точка создаётся автоматически по первому пакету соответствующего типа
(воспитатели никогда не ждут администратора), завершается только явным
действием администратора, типы (Bus/Group/Lazy) полностью независимы и
могут быть открыты одновременно; автоматическая граница дня взамен Hard/
Soft/Total Reset; три новых экрана мониторинга + общий список/история.

131 переводит эту концепцию в работающий продукт: миграции БД, RPC,
расширение `submit_scan_packet()`, композаблы, экраны, пересмотр меню и
маршрутов.

# Зависимости — что уже решено и не пересматривается этим тикетом

Ниже перечислены решения, принятые в 130, на которые 131 опирается как на
данность. Обоснования и рассмотренные альтернативы — в
`tickets/130/decision.md` и `tickets/130/IMPLEMENTATION_PLAN.md`, здесь не
воспроизводятся.

- **Новая таблица, не адаптация `reset_events`/`admin_logs`** —
  `130.txt:93`, обоснование в `IMPLEMENTATION_PLAN.md` "Анализ текущей
  архитектуры".
- **Схема `checkpoints`** — поля, constraints, unique-индекс "не более
  одной открытой контрольной точки на тип в день" (`(day, type) WHERE
  status = 1`) — `IMPLEMENTATION_PLAN.md`, "Новая таблица `checkpoints`".
  Не пересматривается без явной причины.
- **Гибридная модель создания/завершения** (`decision.md`, целиком) —
  центральное решение, не подлежит пересмотру в 131:
  - контрольная точка создаётся **автоматически** по первому пакету
    своего типа (в `submit_scan_packet()`, `ON CONFLICT DO NOTHING` +
    чтение, без отказов воспитателю);
  - завершается **только явным действием администратора**
    (`finish_checkpoint()`) — авто-завершения нет ни для одного типа,
    включая Lazy (это отменяет более раннее правило `130.txt:240`,
    "авто-завершение Lazy при старте Bus/Group" — `decision.md` заменяет
    его симметричной моделью для всех трёх типов);
  - контрольные точки **разных типов** могут быть открыты одновременно —
    это нормальный режим работы, не конфликт (`decision.md`, п.3);
  - конфликт возможен только между двумя открытыми точками **одного**
    типа; явное создание (`create_checkpoint()`) в этом случае
    отклоняется — администратор должен сначала завершить существующую
    (`decision.md`, п.4);
  - при аварийном состоянии "две открытые одного типа" (ручное
    вмешательство в БД) входящие пакеты относятся к последней открытой
    (`decision.md`, п.6).
- **`scan_packets.checkpoint_id`** и правило приёма (авто-создание/поиск
  открытой контрольной точки того же типа, без `RAISE EXCEPTION`) —
  `IMPLEMENTATION_PLAN.md` "Расширение `scan_packets`"/"`submit_scan_
  packet()` — правило приёма". Клиентский контракт `useScanPacket.js`
  (тикет 120) не меняется.
- **Отмена Hard Reset/Soft Reset/Tag starten** — `130.txt:206`, заменяются
  автоматической границей дня (date-scoped `children_today`/`groups_today`,
  без `pg_cron`) + baseline-снимком присутствия, привязанным к первой
  завершённой контрольной точке дня (`finish_checkpoint()`, переносит
  логику первой ветки `on_reset_event_insert` `event_type=1`,
  `doc/db_triggers.sql:150-157`).
- **RPC, не Edge Function** для `create_checkpoint`/`finish_checkpoint`/
  `cancel_checkpoint` — вызывается напрямую через `supabase.rpc()`
  аутентифицированной admin-сессией, `SECURITY DEFINER` с проверкой роли
  внутри; в отличие от `submit_scan_packet()`, которому нужен
  `service_role` из-за недоверенного вызывающего (воспитателя), но который
  теперь **тоже** пишет в `checkpoints` (авто-создание) — см.
  «Ограничения».
- **Три детальных экрана и их основа** — `CheckpointBusView.vue` (на
  основе `AdminBusView.vue`/`BusDetailModal.vue`), `CheckpointGroupView.vue`
  (на основе `ChildrenView.vue`), `CheckpointLazyView.vue` (новый экран) —
  `IMPLEMENTATION_PLAN.md` "Новые компоненты"/"UI изменения".

# Что реализует этот тикет (охват)

Порядок соответствует "План реализации" в
`tickets/130/IMPLEMENTATION_PLAN.md` (10 шагов) — здесь не переписан
дословно, см. тот раздел за деталями по каждому пункту:

1. Миграция БД: таблица `checkpoints`, колонка `scan_packets.
   checkpoint_id`, функции `create_checkpoint`/`finish_checkpoint`/
   `cancel_checkpoint`, расширение `submit_scan_packet()` (авто-создание/
   поиск), узкие RLS-политики для обоих путей `INSERT` (см. «Ограничения»).
2. Миграция `children_today`/`groups_today` на date-scoped схему (колонка
   `date`, новые unique-констрейнты) — заменяет `daily_rollover()`/
   `pg_cron`, которые исключены из архитектуры полностью (не требуют
   проверки доступности — см. `IMPLEMENTATION_PLAN.md`, «Автоматическая
   граница дня»).
3. `useCheckpoints.js` + `useLazyCheckpointProgress.js`.
4. `CheckpointListView.vue` + опциональное явное создание (тип-селектор).
5. `CheckpointBusView.vue`.
6. `CheckpointGroupView.vue` (со сворачиванием "чистых" групп).
7. `CheckpointLazyView.vue`.
8. Обновление `router/index.js`, объединение кнопок в `MainView.vue`
   ("Busse"/"Admin Übersicht" → одна точка входа на Checkpoints).
9. Удаление мёртвого кода после подтверждения, что он больше не читается:
   `AdminBusView.vue`, `ChildrenView.vue`, `ResetHistoryPanel.vue`,
   `useDays.startNewDay/softReset/closeDay/isDayStarted/isDayClosed`,
   `useBusData.getResetHistory`, триггер `on_reset_event_insert`.
   `BusDetailModal.vue`/`GroupDetailModal.vue` — удаляются только если
   полностью замещены, а не переиспользованы как основа новых экранов.
10. Ручная проверка на устройстве (браузерной автоматизации в проекте нет
    — по аналогии с 120/122/123/126).

# Открытые вопросы, требующие решения при реализации

`IMPLEMENTATION_PLAN.md` (раздел «Риски») сознательно оставляет их
нерешёнными до старта 131 — начинать реализацию без явной фиксации
ответов на них нельзя. Часть вопросов, ранее числившихся здесь как
открытые, уже разрешена `decision.md` и ниже не повторяется (конфликт
Bus/Bus — блокируется явным `create_checkpoint()`, авто-создание никогда
не конфликтует; авто-завершение Lazy — отменено, Finish везде только
явный).

- **`cancel_checkpoint()` не откатывает уже принятые `scan_packets`** —
  зафиксировано как сознательное ограничение (нет механизма отмены даже
  сегодня, `doc/db/scan_packets.sql:39`). Подтвердить, что это приемлемо
  для 131, или явно расширить охват, если нет.
- **Финальные пути маршрутов** (`/admin/checkpoints`, `/admin/checkpoints/:id`
  и т.п.) — предложены в плане как пример, не как обязательные значения.
- **Семантика "Finish" для Lazy** — явно поставленный, не решённый в 130
  вопрос (`130.txt:229-238`): явная кнопка Finish есть, но нет чёткого
  критерия "все данные собраны"; решается по месту в рамках реализации
  `CheckpointLazyView.vue`, ориентируясь на описание в 130.txt (постепенная
  фиксация в течение дня). Важно: критерий не может опираться на
  "авто-завершение при старте следующей Bus/Group" — этот механизм
  отменён `decision.md`, Lazy закрывается исключительно по кнопке.
- **Отображение авто-созданных контрольных точек в списке/истории** —
  `created_by` для них — автор триггерящего пакета (воспитатель), не
  администратор; UI должен явно отличать "создана автоматически" от
  "создана администратором" (`IMPLEMENTATION_PLAN.md`, «Риски»). Точный
  текст/индикатор — на усмотрение реализации, но не может отсутствовать
  полностью.

# Ограничения, которые нужно соблюдать

- **RLS для `checkpoints`** — только узкие политики с самого начала
  (`SELECT` любому `authenticated`; `INSERT`/`UPDATE` только через
  `SECURITY DEFINER`-функции — и `submit_scan_packet()` для авто-создания,
  и `create_checkpoint`/`finish_checkpoint`/`cancel_checkpoint` для
  явного управления). Не повторять задокументированную ошибку проекта
  (`vault/03-База-данных/RLS-политики.md`, "Неотозванные широкие
  legacy-политики" у `reset_events`/`children_today`/`groups_today`) —
  "добавить временную широкую политику, потом сузить" не работает,
  PostgreSQL объединяет permissive-политики через OR.
- **Клиентский контракт `useScanPacket.js` (тикет 120) не меняется** —
  сервер сам находит или создаёт контрольную точку по `type`+`date` из уже
  отправляемых полей, без нового поля в теле запроса воспитателя, и без
  новых кодов ошибок (пакет не отклоняется по этой причине никогда).
- **Кнопки сканирования воспитателя не блокируются** и не меняют
  доступность в зависимости от статуса контрольной точки
  (`130.txt:274-282`) — с гибридной моделью это тем более не требуется:
  воспитатель никогда не получает отказ из-за отсутствующей контрольной
  точки.
- **`finish_checkpoint()` — два разных по смыслу шага в одной функции**
  ("закрыть раунд" + "иногда зафиксировать baseline дня") — реализовать
  как отдельные, ясно разделённые шаги внутри функции, не как
  непрозрачную транзакцию без комментариев (см.
  `IMPLEMENTATION_PLAN.md`, «Риски»).

# Definition of Done

- Таблица `checkpoints` создана по спецификации `IMPLEMENTATION_PLAN.md`;
  unique-индекс `(day, type) WHERE status = 1` гарантирует не более одной
  открытой контрольной точки на тип в день.
- `scan_packets.checkpoint_id` добавлена и заполняется
  `submit_scan_packet()`; при отсутствии открытой контрольной точки
  соответствующего типа/дня она создаётся автоматически, пакет никогда не
  отклоняется по этой причине.
- `create_checkpoint`/`finish_checkpoint`/`cancel_checkpoint` реализованы и
  развёрнуты; `create_checkpoint()` отклоняет создание при уже открытой
  точке того же типа; `finish_checkpoint()` фиксирует baseline присутствия
  только при первой завершённой контрольной точке дня (независимо от
  типа); авто-завершения нет ни для одного типа.
- Контрольные точки разных типов могут быть одновременно открыты; ни
  один UI-путь не блокирует и не считает это ошибкой.
- Автоматическая граница дня реализована через date-scoped
  `children_today`/`groups_today` (без `pg_cron`); Hard Reset/Soft
  Reset/Tag starten удалены из UI.
- `CheckpointListView.vue` (список/история/создание), `CheckpointBusView.vue`,
  `CheckpointGroupView.vue`, `CheckpointLazyView.vue` реализованы и
  подключены; все три экрана обновляются по Realtime без ручной кнопки
  "Aktualisieren"; список отличает авто-созданные точки от созданных
  администратором.
- `MainView.vue`, `router/index.js` обновлены согласно принятому решению
  по пересмотру меню (`/admin-busses`/`/children` заменены новыми
  маршрутами).
- Мёртвый код из шага 9 удалён после подтверждения отсутствия
  потребителей.
- Все открытые вопросы из раздела «Открытые вопросы, требующие решения
  при реализации» либо разрешены явным решением (задокументированным в
  `IMPLEMENTATION_REPORT.md`), либо, если решение невозможно принять
  самостоятельно, реализация по соответствующему пункту остановлена и
  описана как отклонение — не решена самостоятельно в обход требования
  "не принимай архитектурные решения самостоятельно".
- Сквозная ручная проверка на устройстве: авто-создание контрольной точки
  по первому пакету каждого типа, параллельная работа Bus и Group
  контрольных точек, явное создание при уже открытой (должно отклоняться),
  Finish/Cancel, смена дня.
