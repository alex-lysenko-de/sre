# основная идея для UI
Переделывая интерфейс, стоит перестать думать экранами и начать думать **сущностями**. Сейчас одна и та же информация отображается разными способами в разных местах. Это усложняет интерфейс, увеличивает объем кода и делает навигацию нелогичной. Нужно перейти к единой модели, где каждая сущность имеет собственный компонент отображения и может использоваться повторно в любом месте системы.

В целом текущий интерфейс выглядит значительно лучше, однако остается фундаментальная архитектурная проблема:
Сейчас каждый экран проектируется практически независимо от остальных. В результате одна и та же информация отображается разными способами. Особенно это заметно на списках детей, автобусов и групп.

Необходимо перейти к проектированию интерфейса вокруг **сущностей**, а не вокруг отдельных страниц.

## Общий принцип

Каждая сущность должна иметь:

* единый визуальный компонент отображения;
* собственную страницу просмотра (при необходимости);
* собственный URL (если используется навигация);
* единый способ открытия;
* единый способ детализации.

Это позволит многократно использовать уже готовые компоненты и сделает интерфейс значительно более последовательным.

Основной принцип работы интерфейса:

> **Сначала показывается общая информация. Затем пользователь постепенно переходит к более детальным данным, открывая связанные сущности.**

Каждый следующий экран является уточнением предыдущего.

---

# Пример навигации

```
Список перекличек
        ↓
Выбираем Конкретную перекличку
        ↓
все данные по перекличке (Время начала, время конца, статус, результаты пересчета) / Автобусы / группы / общие списки
        ↓
Выбираем Конкретный автобус
        ↓
все данные по автобусу (в контексте переклички) + Список детей + список воспитателей 
        ↓
Выбираем конкретного ребенка из списка отсутстующих детей 
		↓
Карточка ребенка (имя, возраст, телефон родителей) + история сканирований ребенка за день
        ↓
Выбираем конкретный скан
		↓
Все данные по скану (Имя ребенка, время сканирования, имя воспитателя)		
        ↓
Карточка Betreuer (Имя, номер телефона, e-mail, номер группы)
        ↓
Карточка группы
```

Таким образом пользователь постепенно «погружается» в данные, а не пытается увидеть всю информацию сразу на одном экране.

---

# Сущность «Перекличка»

На **Page 1** отображается список перекличек.

Однаиз них, обычно первая помечена как "базовая". В ней зафиксирован список детей участвующих сегодня. Все остальные переклички должны показывать отличия от базовой (список отсутствующих детей, список появившихся детей)

Каждая перекличка представлена кликабельной карточкой. Карточка содержит только наиболее важные данные:
- время начала и конца
- тип (BUS, Group, ...)
- статус
- отметка "Base"

При выборе карточки открывается страница просмотра конкретной переклички (**Page 2**, **Page 3** или **Page 4**, в зависимости от типа).

На странице переклички должна отображаться **полная информация** о ней:

* тип;
* статус;
* время начала;
* время окончания;
* итоговые результаты (итоговое количество детей / итоговое количество Betreuer)
* все связанные сущности.

Например, для BUS-переклички это:

* список автобусов;
* список принятых пакетов


---

# Сущность «Автобус»

Автобус является самостоятельной сущностью.

На странице BUS-переклички отображается список автобусов в виде кликабельных карточек.

Каждая карточка содержит:

* номер автобуса;
* количество присутствующих детей;
* количество Betreuer;
* количество отсутствующих детей (по сравнению с первой перекличкой дня);
* количество появившихся детей.

Например:

```
Bus 3

36 Kinder
5 Betreuer

−2 Kinder
+1 Kind
```

Все количественные показатели являются ссылками.

Например:

```
36 Kinder
```

или

```
5 Betreuer
```

При нажатии открывается соответствующий список.

---

# Сущность «Список детей»

Это новый универсальный компонент интерфейса.

Любой список детей должен использовать один и тот же экран.

Не имеет значения, каким образом пользователь попал в этот список:

* через автобус;
* через группу;
* через перекличку;
* через список отсутствующих;
* через список присутствующих.

Во всех случаях используется один и тот же экран.

Например:

**EL1**

```
← Назад
Присутствующие дети

```

**EL2**

Информация о родительской сущности:

Например:

```
Bus 3
BUS Checkpoint #5
```

или

```
Group 10
GROUP Checkpoint #8
```

**EL3**

Список детей.

Каждый ребенок отображается одинаково.

Например:

```
Иванов Иван (G-10)
```

или

```
<button>Иванов И. (G-10)</button>
```

Нажатие открывает карточку ребенка.

---

# Сущность «Ребенок»

Карточка ребенка должна содержать всю доступную информацию:

* имя;
* фамилию;
* возраст;
* группу;
* родителей;
* телефоны;
* привязанный бейдж;
* дополнительные сведения.

Также здесь должна находиться кнопка **Edit**, открывающая экран редактирования ребенка.

Дополнительно отображается история всех сканирований за текущий день.

---

# Сущность «История сканирований»

История представляет собой список событий.

Для каждого сканирования отображается:

* время;
* тип переклички;
* результат;
* Betreuer, выполнивший сканирование.

Каждая запись является кликабельной.

Нажатие на имя Betreuer открывает его карточку.

---

# Сущность «Betreuer»

Карточка Betreuer должна содержать:

* имя;
* e-mail;
* телефон (при наличии);
* сегодняшнюю группу;
* текущий автобус (если применимо).

Группа отображается как ссылка.

Например:

```
Group-10
```

При нажатии открывается страница группы.
Номер телефона кликабельный, позволяет осуществить звонок
Рядом с телефоном стоит кнопка для оправки сообщения через Whatsup
---

# Сущность «Группа»

Страница группы содержит:

* номер группы;
* полный список детей;
* список Betreuer которые сегодня имеют привязку к группе
* список пакетов отправленых сегодня в ходе групповых перекличек (обычно один пакет за перекличку) 
* историю изменений за день.

Все списки используют тот же универсальный компонент отображения.

---

# Основной принцип проектирования

Каждая сущность должна иметь собственный экран просмотра и единый способ отображения.

Интерфейс должен строиться по принципу последовательной детализации:

```
Переклички
    ↓
Перекличка
    ↓
Автобусы / Группы
    ↓
Список детей
    ↓
Ребенок
    ↓
История сканирований
    ↓
Betreuer
    ↓
Группа
```

Такой подход дает несколько преимуществ:

* повторное использование компонентов;
* единообразный внешний вид интерфейса;
* отсутствие дублирования логики отображения;
* простая и понятная навигация;
* возможность постепенно углубляться в данные, не перегружая экран лишней информацией.

Фактически интерфейс превращается в дерево взаимосвязанных сущностей, где каждый экран отвечает только за отображение одной конкретной сущности и предоставляет переходы к связанным объектам.
