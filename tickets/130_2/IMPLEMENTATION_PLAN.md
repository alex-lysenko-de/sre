# Тикет 130_2 — Архитектурный план: UI-прототип экрана управления контрольными точками (mock-данные)

Роль: Software Architect. Документ описывает решение, но не применяет его —
код не пишется и не изменяется в рамках этого документа. Аналог по духу —
`tickets/116/IMPLEMENTATION_PLAN.md` (UI-прототип сканера перед 120): здесь
то же самое отношение между 130_2 и 131 — 130_2 согласовывает UX, 131
подключает реальные данные и бизнес-логику.

Входные данные: `tickets/130_2/130_2.txt`, `tickets/130/decision.md`
(гибридная модель контрольной точки — единственный источник истины по
поведению сущности), `tickets/130/IMPLEMENTATION_PLAN.md` (спецификация
будущей боевой реализации — таблица `checkpoints`, RPC
`create_checkpoint`/`finish_checkpoint`/`cancel_checkpoint`, composables
`useCheckpoints.js`/`useLazyCheckpointProgress.js`, экраны
`CheckpointListView.vue`/`CheckpointBusView.vue`/`CheckpointGroupView.vue`/
`CheckpointLazyView.vue`), `tickets/116/IMPLEMENTATION_PLAN.md` (структурный
прецедент "прототип на mock-данных до боевой реализации").

# Цель

Спроектировать изолированный, полностью автономный UI-прототип экрана
управления контрольными точками (Checkpoint) для главного администратора:
список, создание, детальный просмотр по трём типам (Bus/Group/Lazy),
демонстрация всех предусмотренных состояний — целиком поверх локальных
mock-данных в памяти приложения, без единого обращения к серверу и без
изменения существующей боевой функциональности (`AdminBusView.vue`,
`ChildrenView.vue`, `useDays.js`, схема БД).

Ключевое архитектурное требование, отличающее этот прототип от полностью
одноразового кода: экраны и mock-composable должны быть спроектированы под
тот же контракт (имена функций, форма возвращаемых данных), что уже
специфицирован для боевой реализации в `tickets/130/IMPLEMENTATION_PLAN.md`
(`useCheckpoints.js`, `useLazyCheckpointProgress.js`). Это прямое следствие
цели тикета, сформулированной в `130_2.txt` ("Что это даёт"): после
согласования UX "интеграция сведётся к подключению API" — то есть 131
должен иметь возможность заменить *источник данных* (mock → Supabase),
не переписывая экраны заново, аналогично тому, как `Scanner.vue` из 116
был перенесён в 120 без изменений.

# Анализ текущей архитектуры

## Что уже спроектировано (130) и что из этого актуально для прототипа

- Модель данных сущности зафиксирована в `decision.md` и не пересматривается
  здесь: контрольная точка (1) создаётся автоматически по первому пакету
  своего типа **или** явно администратором; (2) завершается только явным
  действием администратора (Finish), авто-завершения нет ни для одного
  типа, включая Lazy; (3) типы Bus/Group/Lazy независимы и могут быть
  открыты одновременно — это нормальное состояние, не конфликт; (4) не
  более одной ОТКРЫТОЙ контрольной точки на тип в день — конфликт возможен
  только между двумя точками одного типа, и создание второй через
  интерфейс администратора запрещается интерфейсом; (5) авария "две
  открытые одного типа" теоретически возможна (ручное вмешательство в БД),
  UI не должен позволять её создать, но должен уметь её отобразить, если
  она есть в данных.
- `tickets/130/IMPLEMENTATION_PLAN.md` уже специфицирует форму объекта
  `checkpoints` (`id`, `type` 1=BUS/2=GROUP/3=LAZY, `day`, `status`
  1=OPEN/2=FINISHED/3=CANCELLED, `created_by`, `created_at`, `finished_at`,
  `finished_by`, `cancelled_at`, `cancelled_by`,
  `baseline_children_count`) и контракт будущего `useCheckpoints.js`
  (`createCheckpoint(type)`, `finishCheckpoint(id)`, `cancelCheckpoint(id)`,
  `fetchCheckpointsForDay(day)`, `fetchCheckpointDetail(id)`). Прототип
  использует ровно эти имена и форму данных для своего mock-слоя — не
  придумывает параллельную модель.
- Порядковый номер контрольной точки за день — не хранимое поле, а
  вычисляемое (`ROW_NUMBER() OVER (PARTITION BY day ORDER BY id)`,
  `130/IMPLEMENTATION_PLAN.md`, "Новая таблица `checkpoints`"). В
  mock-данных — аналогично: вычисляется на чтении, не хранится в объекте.

## Существующие экраны-доноры вёрстки (только для визуального ориентира,
не переиспользуются как код)

- `AdminBusView.vue` (`/admin-busses`) — таблица автобусов, сводка
  Kinder/Betreuer, статус-точки.
- `ChildrenView.vue` (`/children`, компонент `AdminGroupView`) — таблица
  групп, предупреждение о недостающих детях, `Differenz`
  (Morgen/Aktuell).
- `BusDetailModal.vue` / `GroupDetailModal.vue` — список пакетов/детей по
  сущности.

Эти компоненты **не импортируются и не рефакторятся** прототипом (см.
«Затрагиваемые модули») — `130/IMPLEMENTATION_PLAN.md` уже отметил, что
прямое переиспользование этих модалок "как есть" сомнительно, так как в
новом дизайне это не второстепенная деталь, а основной рабочий экран.
Прототип пишет вёрстку заново, ориентируясь на их раскладку визуально —
тот же осознанный компромисс, что был принят в 116 для `Scanner.vue`
относительно `ScannerView.vue`.

## Существующие паттерны, которые прототип обязан соблюдать

- Слоистая структура `stores/useXXX` → `composables/useXXX` →
  `composables/useSupabaseXXX` (CLAUDE.md) — прототип **не встраивается**
  в эту иерархию как боевой слой: его composables работают только с
  in-memory данными, не имеют `useSupabaseXXX`-аналога и explicitly не
  предназначены жить в этой форме после 131 (см. «Риски»). Чтобы это было
  очевидно на уровне имён файлов, не только по комментарию в коде,
  используется суффикс `Mock`/`Prototype` — соглашение, уже применённое в
  116 (`ScannerPrototypeView.vue`).
- Меню (`MainView.vue`) добавляет новую кнопку, не трогая существующие
  ("Busse", "Admin Übersicht") — прецедент 116 (`goToScannerPrototype()`
  рядом с `goToScanBus()`), явно разрешено `130_2.txt` ("не обязан сразу
  заменять `/admin-busses`/`/children`").
- Guard в `router/index.js` — все admin-экраны используют
  `meta: { requiresAuth: true, requiresAdmin: true }` (см. `/admin-busses`,
  `/children`); прототип — тоже admin-only функциональность по смыслу
  задачи ("интерфейс главного администратора"), поэтому наследует тот же
  guard, хотя технически ничего не пишет и не читает из Supabase.

# Новые компоненты

Все новые файлы — в новом изолированном пространстве имён (суффикс/подпапка
`prototype`/`Mock`), чтобы (а) визуально сигнализировать "это не боевой
код" при просмотре дерева файлов и (б) не создавать заранее коллизию имён
с реальными компонентами, которые специфицированы в
`tickets/130/IMPLEMENTATION_PLAN.md` под теми же "чистыми" именами
(`CheckpointListView.vue` и т.д.) — эти имена зарезервированы за 131.

## Mock-слой данных (аналог будущего `useCheckpoints.js`)

- **`src/composables/useCheckpointsMock.js`** — module-level реактивный
  singleton (`reactive([])`, не Pinia-стор: состояние осознанно не
  персистентное, не проходит через слой `stores/useXXX`, чтобы не
  создавать видимость боевого домена — см. «Анализ», «Риски»). Экспортирует
  функции с той же сигнатурой, что и специфицированный в 130
  `useCheckpoints.js`, все — `async`, возвращают `Promise` (без реальной
  задержки сети — резолвятся сразу же), чтобы вызывающий код (View) не
  отличался от будущего кода на реальном API:
  - `fetchCheckpointsForDay(day)` — список за день (включая вычисляемый
    `seq`).
  - `createCheckpoint(type)` — та же семантика, что у будущего RPC
    `create_checkpoint`: если уже есть открытая точка этого типа — не
    создаёт новую, а возвращает объект ошибки (например, `{ error:
    'ALREADY_OPEN', existingId }`), который View показывает как inline
    сообщение (демонстрация состояния "ошибка", `130_2.txt`, "различные
    состояния интерфейса").
  - `finishCheckpoint(id)` — переводит в `FINISHED`, проставляет
    `finished_at`/`finished_by`; если это первая `FINISHED` точка за день
    (любого типа) — проставляет `baseline_children_count` (мок-число) —
    демонстрирует правило baseline из `decision.md`/130-плана, полностью
    в памяти.
  - `cancelCheckpoint(id)` — переводит в `CANCELLED`.
  - `fetchCheckpointDetail(id)` — возвращает точку + синтетические
    type-специфичные данные (список автобусов/групп/детей, см. ниже).
  - Инициализация: при первом обращении composable сам засеивает
    правдоподобный набор точек — например, одна `FINISHED` Bus (сегодня
    утром), одна `OPEN` Bus, параллельно одна `OPEN` Group (демонстрация
    п.3 `decision.md` — два разных типа открыты одновременно), одна
    `FINISHED` Lazy. Дополнительно — одна запись, специально
    демонстрирующая аварийное состояние "две открытые одного типа"
    (`decision.md`, п.6): она **только** засеивается на старте, не
    создаётся ни одним действием пользователя ни при каких условиях — это
    прямое следствие требования "интерфейс администратора не должен
    позволять создавать подобные состояния".
- **`src/composables/useLazyCheckpointProgressMock.js`** — аналог будущего
  `useLazyCheckpointProgress.js`: по `checkpointId` возвращает списки
  "отметились"/"ещё нет" + время последней отметки, вычисленные из
  синтетического набора "детей группы"/"детей без группы" (Lazy не
  привязан к конкретной группе).

## Presentational-компоненты (переиспользуются между Bus/Group/Lazy экранами)

- **`src/components/checkpoints-prototype/CheckpointStatusBadge.vue`** —
  цветная точка+текст по `status` (OPEN/FINISHED/CANCELLED), включая
  визуальную пометку "просрочена" для `day < today() && status === OPEN`
  (косметическое правило из 130-плана, "Единственный оставшийся хвост").
- **`src/components/checkpoints-prototype/CheckpointTypeBadge.vue`** —
  иконка+подпись по `type` (Bus/Group/Lazy).
- **`src/components/checkpoints-prototype/CheckpointOriginBadge.vue`** —
  инкапсулирует различение "создана автоматически (Betreuer X)" vs
  "создана администратором" по `created_by`/флагу автора (`130_2.txt`,
  явное требование; риск, зафиксированный в 130-плане).
- **`src/components/checkpoints-prototype/CheckpointCreateModal.vue`** —
  выбор типа при явном создании + отображение блокировки, если тип уже
  открыт (состояние "ошибка").

## Экраны

- **`src/views/CheckpointListPrototypeView.vue`** — список/история за
  день + кнопка "Neuen Checkpoint erstellen" (открывает

# Изменения БД

Нет. Прототип не создаёт, не читает и не пишет ни одной таблицы. Форма
mock-объектов сознательно скопирована со спецификации `checkpoints` из
`tickets/130/IMPLEMENTATION_PLAN.md` (см. «Новые компоненты»), но это
только соглашение об именах полей в JS-объекте, не миграция.

# API изменения

Нет. Ни одного вызова `supabase.from(...)`, `supabase.rpc(...)` или
`supabase.channel(...)` в новом коде. Realtime-обновление между списком и
детальным экраном не нужно и не имитируется через сеть — оба экрана
читают один и тот же module-level реактивный singleton
(`useCheckpointsMock.js`), поэтому изменение состояния в детальном экране
(Finish/Cancel) мгновенно видно в списке без какой-либо подписки — сам
факт использования общего reactive-объекта уже даёт нужный эффект.

Обязательные демонстрируемые состояния списка (`130_2.txt`, "Что должно

## Детальные экраны (Bus/Group/Lazy)

Каждый — клик по строке списка ведёт на соответствующий маршрут по
`type`+`id`. Общее для всех трёх: заголовок с `CheckpointTypeBadge` +
`CheckpointStatusBadge` + `CheckpointOriginBadge`, кнопки Finish/Cancel
(активны только при `status === OPEN`), кнопка "Zurück" на список.
Type-специфичная часть — по макетам из `130/IMPLEMENTATION_PLAN.md` («UI
изменения», разделы Bus/Group/Lazy Checkpoint).

Обязательные демонстрируемые состояния детального экрана: "нет детей"
(пустой автобус/группа — например, автобус без назначенных детей),
"недостающие дети" (Differenz > 0), "полностью чисто" (Differenz = 0,
группа сворачивается), "ошибка" (попытка Finish уже завершённой точки —
кнопка задизейблена, либо попытка создать вторую открытую точку того же
типа из списка — inline-сообщение из `createCheckpoint()`).

10. Обновить `tickets/130_2/state.txt` и `tickets/dashboard.md`.

Порядок 1→2→3 можно вести параллельно (независимы друг от друга), 4-7

# Риски

- **Общий reactive-singleton вместо Pinia-стора** — сознательное
  отклонение от слоистой конвенции проекта (`stores/useXXX` →
  `composables/useXXX`, CLAUDE.md). Обоснование: если оформить
  mock-данные как настоящий Pinia-стор, это создаст видимость боевого
  домена (`stores/checkpoints.js`) в дереве файлов, которую 131 придётся
  явно демонтировать/переименовывать, а не просто удалить. Суффикс
  `Mock`/`prototype` в имени и месте (composables, не stores) должен
  держать эту границу явной на протяжении жизни прототипа.
- **Дублирование информации о будущей форме данных** — mock-объекты
  копируют форму `checkpoints`/контракт `useCheckpoints.js` из
  `tickets/130/IMPLEMENTATION_PLAN.md` вручную; если 130-план изменится
  по итогам обсуждения 131 (например, другая форма ошибки
  `createCheckpoint`), прототип не узнает об этом автоматически — это
  нормально и ожидаемо (`130_2.txt`, "Зачем это нужно": UX может меняться
  свободно), но означает, что рассинхронизация имён полей между
  прототипом и итоговым 130-планом не является дефектом реализации, а
  штатной частью итеративного согласования.
- **Осознанный отказ от чтения `useConfigStore` (`total_groups`/
  `total_buses`)** — эти значения реальные и требуют сетевого запроса
  (даже с кэшем `CONFIG_CACHE_TTL`, стор всё равно инициализируется через
  Supabase). Чтобы полностью исключить любую сетевую зависимость
  прототипа (буквальное требование `130_2.txt`: "никаких обращений к
  серверу"), количество автобусов/групп в mock-данных — захардкоженная
  константа внутри `useCheckpointsMock.js`, не читается из реального
  конфига. Цена решения — мок может разойтись с реальным числом
  автобусов/групп конкретного мероприятия; это не важно для цели тикета
  (проверка UX, не проверка чисел).
- **Имена файлов-прототипов не совпадают 1:1 с именами из
  `130/IMPLEMENTATION_PLAN.md`** (суффикс `Prototype`/`Mock`) — намеренно,
  чтобы избежать коллизии, пока оба тикета не примирены. Явное следствие
  для 131: при боевой реализации прототипные файлы должны быть либо
  удалены и заменены "чистыми" именами (как это произошло с
  `ScannerPrototypeView.vue` в 120), либо явно переименованы с заменой
  mock-composable на боевой — выбор фиксируется в тикете реализации, не
  здесь.
- **Соблазн развить прототип сверх запрошенного** (реальные задержки
  сети, персистентность mock-данных между перезагрузками страницы и
  т.п.) — прямо противоречит `130_2.txt` ("не отправляются реальные
  запросы", "хранится просто в памяти приложения"); реактивный singleton
  сбрасывается при перезагрузке страницы — это ожидаемое поведение, не
  дефект.
- **`CheckpointOriginBadge`/аварийное состояние "две открытые одного
  типа" — легко забыть при вёрстке**, так как оба случая не встречаются
  в существующих экранах-донорах (`AdminBusView.vue`/`ChildrenView.vue`
  этого не показывают, у них нет понятия "раунда"/"создателя раунда").
  Явно вынесены в DoD ниже, чтобы не быть случайно упущенными.

# Definition of Done

- Новый изолированный маршрут (`/admin/checkpoints-prototype` и
  вложенные `bus/group/lazy/:id`) открывает прототип; ни один
  существующий маршрут/экран (`/admin-busses`, `/children`, и т.д.) не
  изменён ни в одной строке.
- Сущность в интерфейсе называется «Контрольная точка»/«Checkpoint» — не
  «Перекличка»/«Roll Call» (`130_2.txt`, явное требование, наследуемое из
  `decision.md`).
- Реализованы: список контрольных точек, создание новой (с блокировкой
  при уже открытой того же типа), просмотр детального экрана, переключение
  между типами Bus/Group/Lazy, синтетические результаты, кнопки Finish/
  Cancel.
- Продемонстрированы все перечисленные в `130_2.txt` состояния: идёт
  (OPEN), завершена (FINISHED), ошибка (blocked create / Finish
  недоступен), отсутствуют дети (пустой автобус/группа).
- Продемонстрировано явно как штатное состояние: несколько одновременно
  открытых контрольных точек разных типов (`decision.md`, п.3).
- Продемонстрировано явное визуальное отличие "создана автоматически
  (Betreuer X)" от "создана администратором" (`created_by`,
  `CheckpointOriginBadge.vue`).
- За всё время работы прототипа (создание/Finish/Cancel/навигация между
  экранами) в Network-панели браузера не появляется ни одного запроса к
  Supabase — проверяется вручную на шаге 9 плана реализации.
- Mock-composables (`useCheckpointsMock.js`,
  `useLazyCheckpointProgressMock.js`) используют те же имена
  функций/форму данных, что специфицированы для боевого
  `useCheckpoints.js`/`useLazyCheckpointProgress.js` в
  `tickets/130/IMPLEMENTATION_PLAN.md` — так, чтобы 131 мог заменить
  источник данных, не переписывая View-слой с нуля.
- Код прототипа изолирован по именам файлов (суффикс/подпапка
  `prototype`/`Mock`) от зарезервированных за 131 "чистых" имён.
