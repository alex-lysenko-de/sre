# Итог

CHANGES_REQUIRED

Реализация в целом точно следует утверждённому архитектурному плану и
закрывает большинство пунктов Definition of Done (структура стора,
`markRaw()`, ранняя инициализация в `main.js`, глобальное монтирование
компонентов в `App.vue` вне `<nav v-if="isAuthenticated">`, триггеры в
`WelcomeView.vue`/`LoginView.vue`). Обнаружена одна функциональная ошибка
в основном Android-сценарии (см. Major), которую необходимо исправить
перед завершением задачи.

# Critical

Не обнаружено.

# Major

1. **`promptInstall()` не защищён от повторного вызова и не обрабатывает
   ошибки нативного API** (`src/stores/installPrompt.js:57-65`).

   ```js
   async promptInstall() {
     if (this.platform === 'android' && this.deferredPrompt) {
       await this.deferredPrompt.prompt()
       await this.deferredPrompt.userChoice
       this.deferredPrompt = null
     } else if (this.platform === 'ios') {
       this.showIosInstructions = true
     }
   },
   ```

   `BeforeInstallPromptEvent.prompt()` по спецификации бросает исключение
   при повторном вызове ("...`prompt()` may not be called more than
   once"). Пока пользователь не принял решение в нативном диалоге,
   `await this.deferredPrompt.userChoice` ещё не выполнен, `deferredPrompt`
   всё ещё не `null`, а значит `showButton` (и, соответственно, сама
   кнопка) остаётся активной. `InstallAppButton.vue` не имеет `disabled`/
   `loading`-состояния и вызывает `promptInstall()` напрямую по клику
   (`@click="installPromptStore.promptInstall()"`, без `await`/`.catch()`).
   Повторный клик по кнопке, пока пользователь ещё не ответил на первый
   нативный диалог (обычный сценарий на мобильном экране — двойное
   касание или нетерпеливый повторный тап), вызовет `.prompt()` второй
   раз на том же событии → необработанное исключение (unhandled promise
   rejection), при этом код никогда не доходит до `this.deferredPrompt =
   null`. В результате `deferredPrompt` навсегда остаётся "протухшим"
   валидным-по-форме, но нерабочим объектом, и кнопка "Установить
   приложение" перестаёт работать до конца сессии (до перезагрузки
   страницы) — без какой-либо диагностики в UI.

   Это прямо затрагивает основной сценарий, явно описанный в тикете
   ("После нажатия на кнопку… Вызывается `beforeinstallprompt.prompt()`"),
   и является реальной, легко воспроизводимой функциональной ошибкой, а
   не гипотетическим краевым случаем.

   Также стоит отметить расхождение с принятым в проекте паттерном:
   `LoginView.vue`/`WelcomeView.vue` используют флаг `loading` и
   `:disabled="loading"` на кнопках отправки форм именно для защиты от
   повторного клика во время async-операции — в `InstallAppButton.vue`
   этот паттерн не применён.

# Minor

1. **Именование `platform === 'android'` вводит в заблуждение**
   (`src/stores/installPrompt.js:35-39`): бакет определяется через
   `'onbeforeinstallprompt' in window`, что верно и для десктопных
   Chromium-браузеров (Chrome/Edge на Windows/macOS), не только для
   Android. Функционально не является ошибкой (кнопка одинаково корректно
   отработает и на десктопе), но название состояния расходится с
   реальным охватом и может ввести в заблуждение при дальнейшей
   поддержке кода.

2. **Кнопка смонтирована глобально на всех маршрутах без исключений**
   (`src/App.vue:142-145`, `position: fixed; bottom: 1rem; right: 1rem`).
   `src/views/ScannerView.vue` использует полноэкранный
   camera/QR-scanner интерфейс (`#qr-reader`, `.scanner-overlay`) —
   основной пользовательский сценарий приложения согласно предметной
   области (сканирование браслетов, CLAUDE.md). Плавающая кнопка в
   правом нижнем углу поверх видео-превью камеры может визуально
   перекрывать элементы сканера на небольших мобильных экранах. Тикет
   не запрещает такое размещение, но стоит проверить реальное наложение
   вручную на маршруте `/scanner` (или аналогичном).

3. **Детект iOS не покрывает iPadOS 13+** (`src/stores/installPrompt.js:27`,
   `/iphone|ipad|ipod/i.test(userAgent)`). Начиная с iPadOS 13, Safari по
   умолчанию отправляет desktop-подобный User-Agent ("Macintosh..."),
   поэтому iPad не будет определён как `platform === 'ios'` и попадёт в
   `'other'` — кнопка не появится и на iPad, даже в Safari. Тикет
   формально требует только iPhone, поэтому это не нарушение DoD, но
   стоит зафиксировать как известное ограничение (в проекте есть и другие
   iPad-совместимые сценарии, судя по общей направленности приложения).

4. **Баннер не переиспускается для восстановленных сессий** — `triggerBanner()`
   вызывается только из явных `handleLogin()`/`handleRegister()`. Если
   пользователь уже был аутентифицирован ранее и просто открывает
   приложение заново (авто-восстановление сессии через
   `App.vue.initializeApp()/handleAuthentication()`, минуя
   `LoginView.vue`), кнопка "Установить приложение" не покажется вообще,
   даже если PWA всё ещё не установлено. Буквальная формулировка DoD
   ("сразу после первого успешного логина") этому не противоречит, но это
   расходится с мотивацией из тикета, п.3 ("на случай, если пользователь
   уже давно работает через браузер и просто ещё не установил
   приложение") — именно эта категория пользователей чаще всего заходит
   через восстановленную сессию, а не через форму логина.

# Архитектурные замечания

- Паттерн "стор с логикой внутри, без отдельного composable-слоя"
  (`stores/installPrompt.js`) корректно повторяет прецедент
  `stores/config.js` и обоснованно не вводит лишний слой — соответствует
  и плану, и CLAUDE.md ("слоистая структура для **доменной** логики").
- Монтирование `InstallAppButton`/`InstallIosInstructionsModal` в
  `App.vue` как siblings существующих модалок, вне `<nav
  v-if="isAuthenticated">`, полностью соответствует плану и корректно
  устраняет риск размонтирования компонента при переходе
  `WelcomeView → /main` (авто-логин через 1.5с) — момент, отдельно
  выделенный в разделе "Риски" плана.
- `markRaw()` применён к `deferredPrompt` в точности как предписано
  планом; ранняя, неблокирующая инициализация в `main.js` (до
  `await configStore.initConfigModule()`) корректно устраняет риск
  пропуска события `beforeinstallprompt`.
- Точки вызова `triggerBanner()` в `WelcomeView.vue` (до `setTimeout`/
  `signInWithPassword()`) и `LoginView.vue` (после проверки роли/
  `active`, до `setAuthItem(...)`) соответствуют плану буквально.
- Отклонение от буквального требования тикета "до первой записи в
  LocalForage" для `LoginView.vue` осознанно зафиксировано и в плане, и
  в отчёте, с корректным обоснованием (ограничение архитектуры Supabase
  JS SDK, дополнительно смягчённое решением тикета 112 о
  самовосстановлении сессии) — не требует исправления.

# Рекомендации

1. Обязательно: добавить `try/catch`/`.catch()` вокруг
   `deferredPrompt.prompt()`/`userChoice` в `promptInstall()` и защитить
   от повторного вызова, пока предыдущий вызов не завершён (например,
   локальный флаг `installing`, аналогичный `loading` в
   `LoginView.vue`/`WelcomeView.vue`, с `:disabled` на кнопке).
2. Проверить вручную (или согласовать как принятое ограничение)
   поведение плавающей кнопки на `ScannerView.vue` — не перекрывает ли
   она элементы управления камерой на мобильных экранах.
3. Рассмотреть, нужно ли вызывать `triggerBanner()` также при
   авто-восстановлении сессии (`App.vue`), чтобы полнее закрыть
   мотивацию тикета (п.3) для давно работающих через браузер
   пользователей — решение можно принять как осознанное ограничение, но
   стоит явно зафиксировать.
4. Ручная проверка по плану (раздел "План реализации", п. 7) не была
   выполнена в рамках реализации (см. IMPLEMENTATION_REPORT.md, раздел
   "Проверки") — необходимо выполнить её перед мержем, обратив особое
   внимание на сценарий двойного клика/тапа по кнопке "Установить
   приложение" на Android (см. Major, п.1).
