# Цель

Дать пользователю ненавязчивую возможность установить PWA-приложение
(«Установить приложение») сразу после первого успешного входа в систему —
как после регистрации по invite-ссылке (`WelcomeView.vue`), так и после
обычного логина (`LoginView.vue`) — на Android (через нативный
`beforeinstallprompt.prompt()`) и на iPhone (через инструкцию «Поделиться →
На экран «Домой» → Добавить», на немецком). Отказ от установки не должен
блокировать или редиректить пользователя — работа в браузере продолжается
как обычно. Если PWA уже установлено (standalone-режим), баннер/кнопка не
показывается.

Для сценария регистрации по инвайту (`WelcomeView.vue`) кнопка должна быть
видна **до** первой записи в LocalForage, которую делает авто-логин —
см. «Анализ текущей архитектуры» о том, что конкретно это означает на
практике в данном кодовом решении.

# Анализ текущей архитектуры

## Стек PWA уже настроен

- `vite.config.js:13-66` — `VitePWA({ registerType: 'autoUpdate', ... })` уже
  подключён, манифест (`name`, `icons`, `display: 'standalone'` и т.д.) уже
  заполнен, `workbox` уже кеширует статику и Supabase API. Service Worker
  уже регистрируется в `src/main.js:5,117-125` через
  `registerSW()` из `virtual:pwa-register`.
- Это значит, что базовая «инсталлируемость» приложения (валидный manifest +
  зарегистрированный SW + HTTPS) уже обеспечена существующей конфигурацией.
  Задача 113 добавляет только **UI-триггер** (`beforeinstallprompt.prompt()`
  на Android, инструкция на iOS) — сама возможность установки уже
  существует независимо от этой задачи.

## Ключевой факт: `signInWithPassword()` сам пишет в LocalForage

`src/supabase.js:7-9`:

```js
export const supabase = createClient(supabaseUrl, supabaseKey, {
  auth: { storage: supabaseStorageAdapter }
})
```

`supabaseStorageAdapter` (`src/modules/storage.js:52-56`) — это прямой
passthrough к `authLocalForage` (`localforage.createInstance({name:
'sre-app', storeName: 'auth'})`). Supabase JS SDK **сам**, внутри вызова
`supabase.auth.signInWithPassword()`, синхронно с успешным ответом от Auth
API записывает `access_token`/`refresh_token`/сессию через этот адаптер —
то есть **первая запись в LocalForage происходит внутри самого
`signInWithPassword()`, ещё до того, как наш код (`then`/`await`
продолжение) успевает что-либо сделать**.

Практическое следствие для требования тикета («показать предложение об
установке до первой записи в LocalForage»): единственный способ буквально
это выполнить — показать кнопку/баннер **до вызова `signInWithPassword()`**,
а не «после него, но до чего-то ещё». В текущем коде `WelcomeView.vue`
(`handleRegister()`, строки 234-262) для этого уже существует ровно нужный
момент: `success.value = true` (строка 231, сразу после успешного ответа от
`invite-accept`) наступает **раньше**, чем `setTimeout(..., 1500)` вызывает
`signInWithPassword()` (строка 237). Значит, кнопку установки нужно
показывать в success-блоке шаблона (строки 121-125), а не где-то после
авто-логина.

Для `LoginView.vue` (`handleLogin()`, строки 116-168) такого «окна ожидания»
нет — `signInWithPassword()` вызывается сразу по сабмиту формы, и первая
запись в LocalForage в этом сценарии неизбежно происходит раньше, чем можно
было бы показать любой UI. Тикет требует показывать кнопку «и при обычном
логине» (`113.txt`, пункт 3), но без формулировки «до первой записи» — там
это условие не ставится, оно специфично для сценария регистрации (комментарий
в тикете явно привязывает его к проблеме тикета 112 о раздельном хранилище
Safari/PWA на iPhone). Поэтому для `LoginView.vue` требование трактуется как
«кнопка видна сразу после успешного входа», без искусственной задержки
самого входа ради UI.

## Тикет 112 уже решил корневую проблему, ради которой введено условие «до записи»

`tickets/112/IMPLEMENTATION_REPORT.md` документирует, что `router/index.js`
и `App.vue.initializeApp()` теперь **всегда** вызывают
`supabase.auth.getSession()` независимо от флага `sre_user_registered`, а
сам флаг самовосстанавливается (`fire-and-forget setAuthItem(...)`) при
каждой подтверждённой сессии. Это значит, что даже если что-то в
LocalForage браузера не «переехало» в установленное PWA (проблема тикета
112), реальная активная сессия Supabase всё равно будет обнаружена и
восстановлена при следующем запуске PWA — повторный логин не потребуется.
Формулировка «до первой записи» в тикете 113, таким образом, не является
жёстким техническим требованием (её буквальное выполнение и так невозможно
для `LoginView.vue`, см. выше), а скорее пожеланием «показать как можно
раньше» — что и реализуется размещением кнопки в success-блоке
`WelcomeView.vue`, до вызова `signInWithPassword()`.

## Существующие паттерны, на которые опирается решение

- **Store с логикой внутри (без отдельного composable-слоя)** —
  `src/stores/config.js` уже показывает прецедент: Pinia-стор, который сам
  делает Supabase-запросы и работает с `localStorage`-кешем, без
  промежуточного `composables/useConfig.js`. Для задачи 113 предлагается
  тот же паттерн: вся логика PWA-install (захват `beforeinstallprompt`,
  детект платформы/standalone, вызов `.prompt()`) не является доменной
  бизнес-логикой (группы/дети/пользователи), а инкапсулирует чисто
  браузерный API — отдельный composable-слой поверх стора не добавляет
  ценности и не требуется архитектурной конвенцией проекта (см. CLAUDE.md:
  «Слоистая структура для **доменной** логики»).
- **Глобальные модалки, монтируемые в `App.vue`** — `DailyCheckInModal`,
  `GroupChangeModal`, `BusChangeModal`, `LogoutConfirmModal` уже монтируются
  как siblings в корневом `<div>` `App.vue` (строки 1-146), видимость
  управляется `v-if` на реактивном состоянии. Новые компоненты следуют
  этому же паттерну.
- **Инициализация стора при старте приложения до `app.mount()`** —
  `src/main.js:104-109` уже делает `await configStore.initConfigModule()`
  после `app.use(pinia)`, но до `app.mount('#app')`. Для перехвата
  `beforeinstallprompt` нужен аналогичный, но **синхронный** (не
  `await`-блокирующий) вызов инициализации в этом же месте — событие может
  быть выпущено браузером в любой момент после загрузки страницы, и если
  слушатель не навешан достаточно рано, событие будет безвозвратно
  пропущено (браузер не повторяет `beforeinstallprompt` в рамках одной
  загрузки страницы).

# Новые компоненты

## `src/stores/installPrompt.js` (Pinia store)

State:
- `deferredPrompt` — сохранённое событие `beforeinstallprompt` (хранить
  через `markRaw()`, чтобы Vue не пытался сделать его реактивным —
  нативный `Event`-объект и его метод `.prompt()`/поле `.userChoice` не
  должны оборачиваться в Proxy).
- `platform` — `'android' | 'ios' | 'other'`, определяется один раз при
  инициализации по `userAgent`/фиче-детекту.
- `isStandalone` — `boolean`, определяется один раз при инициализации через
  `window.matchMedia('(display-mode: standalone)').matches ||
  window.navigator.standalone === true` (последнее — нестандартное
  свойство Safari, обращение только через `'standalone' in
  window.navigator` guard).
- `bannerTriggered` — `boolean`, `false` по умолчанию, выставляется в
  `true` вызовом `triggerBanner()` из `WelcomeView.vue`/`LoginView.vue`.
- `showIosInstructions` — `boolean`, управляет модалкой с инструкцией.

Getters:
- `canInstall` — `!isStandalone && (platform === 'android' ?
  !!deferredPrompt : platform === 'ios')`.
- `showButton` — `canInstall && bannerTriggered`.

Actions:
- `init()` — вызывается один раз из `main.js`. Определяет `platform` и
  `isStandalone`; регистрирует `beforeinstallprompt` (`e.preventDefault()`,
  `this.deferredPrompt = markRaw(e)`) и `appinstalled` (сбрасывает
  `deferredPrompt = null`, `isStandalone = true`) слушатели на `window`.
- `triggerBanner()` — `this.bannerTriggered = true`.
- `async promptInstall()` — на Android: `await
  this.deferredPrompt.prompt()`, дождаться `userChoice`, затем
  `this.deferredPrompt = null` (событие одноразовое, повторно
  использовать нельзя); на iOS: `this.showIosInstructions = true`.
- `closeIosInstructions()` — `this.showIosInstructions = false`.

## `src/components/InstallAppButton.vue`

Небольшая кнопка/бейдж («📲 App installieren» или аналогично, на немецком),
`v-if` на `installPromptStore.showButton`. По клику — вызывает
`installPromptStore.promptInstall()`. Не содержит собственной логики
платформы — вся ветвление (Android prompt vs iOS-модалка) инкапсулировано
в сторе.

## `src/components/InstallIosInstructionsModal.vue`

Модалка по образцу `LogoutConfirmModal.vue` (структура `modal fade
show d-block`, `modal-header`/`modal-body`, кнопка закрытия). Текст — три
шага на немецком, как указано в `tickets/113/113.txt`:

1. Tippen Sie auf **Teilen** (⬆️)
2. Wählen Sie **Zum Home-Bildschirm**
3. Tippen Sie auf **Hinzufügen**

`v-if="installPromptStore.showIosInstructions"`, закрытие вызывает
`installPromptStore.closeIosInstructions()`. Чисто информационная модалка,
не блокирует и не редиректит — только `@close`.

# Риски

- **`beforeinstallprompt` может не сработать даже при технически корректной
  реализации**: Chrome применяет собственную эвристику вовлечённости
  (engagement heuristics) и может не выпускать событие при первом визите
  независимо от кода приложения. Это не баг реализации — тестировать нужно
  либо через принудительный вызов в Chrome DevTools (Application → Manifest
  → «Add to home screen»), либо после накопления реального пользовательского
  взаимодействия.
- **Необходим `markRaw()` для `deferredPrompt`**: если сохранить нативный
  `BeforeInstallPromptEvent` в реактивном state стора без `markRaw()`, Vue
  обернёт его в реактивный Proxy, что может сломать внутренние
  предположения браузера о типе объекта при вызове `.prompt()`. Если это
  упущено при реализации — кнопка на Android перестанет работать без
  явной ошибки в консоли, которую легко пропустить при ревью.
- **Ранняя инициализация обязательна**: если `useInstallPromptStore().init()`
  в `main.js` будет вызван позже (например, перенесён внутрь
  `App.vue.onMounted()` или после `await configStore.initConfigModule()`),
  есть риск пропустить событие `beforeinstallprompt`, если браузер выпустит
  его до того, как слушатель будет навешан — событие в рамках одной
  загрузки страницы не повторяется.
- **Компонент кнопки должен жить в `App.vue`, а не в `WelcomeView.vue`**:
  если кнопку/модалку по ошибке смонтировать локально внутри
  `WelcomeView.vue` (что кажется естественным местом, так как именно там
  формально должна появиться кнопка), пользователь, начавший установку
  через нативный диалог (Android) в течение success-окна, рискует получить
  размонтированный компонент в момент, когда авто-логин (через 1.5с)
  переключит `<router-view/>` на `/main` — диалог браузера может продолжать
  висеть, но Vue-обработчик `userChoice` в размонтированном компоненте
  либо не сработает, либо вызовет предупреждение. Монтирование на уровне
  `App.vue`, управляемое стором, устраняет этот риск.
- **iOS: невозможно программно проверить исход** («добавил ли пользователь
  приложение на самом деле») — Safari не даёт такого API. Кнопка на iOS
  всегда доступна, пока не обнаружен standalone-режим; это ограничение
  платформы, а не недоработка реализации.
- **`navigator.standalone`** — нестандартное, специфичное для iOS Safari
  свойство; обращение к нему без guard (`'standalone' in
  window.navigator`) на других платформах не вызовет ошибку (просто
  `undefined`), но код должен явно это учитывать при ревью, чтобы не
  выглядеть как забытый platform-specific хак.
- **Буквальное требование «до первой записи в LocalForage» недостижимо для
  `LoginView.vue`** (см. «Анализ текущей архитектуры») — это ограничение
  архитектуры Supabase JS SDK, а не решения этой задачи. Зафиксировано как
  осознанно принятое отклонение от буквальной формулировки тикета, не
  требующее дальнейшего решения.
- **Отсутствие автоматических тестов** для PWA install flow — проверка
  целиком ручная (см. «План реализации», п. 7); большая часть сценариев
  (реальный Android-телефон, реальный iPhone) требует физических
  устройств, эмуляция в DevTools покрывает не всё.

# Definition of Done

- Кнопка «Установить приложение» видна пользователю, работающему в браузере
  без установленного PWA, начиная с success-блока `WelcomeView.vue` (для
  регистрации по инвайту, до вызова `signInWithPassword()`) и сразу после
  успешного `LoginView.vue`-логина, и продолжает быть видна в шапке
  приложения (`App.vue`) на всём протяжении сессии, пока PWA не
  установлено.
- На Android нажатие кнопки вызывает нативный `deferredPrompt.prompt()`.
- На iPhone нажатие кнопки открывает модалку с пошаговой инструкцией на
  немецком («Teilen → Zum Home-Bildschirm → Hinzufügen»).
- Отказ от установки (любой исход `userChoice`, закрытие iOS-модалки) не
  блокирует и не редиректит пользователя — работа с приложением в браузере
  продолжается как обычно.
- Если PWA уже установлено (`display-mode: standalone` или
  `navigator.standalone === true`), кнопка не показывается ни в одном из
  сценариев.
- `beforeinstallprompt` перехватывается максимально рано (`main.js`, до
  `app.mount()`), чтобы не пропустить событие.
- Существующий функционал (`vite.config.js` PWA-конфигурация,
  групп/автобус-индикаторы в `App.vue`, поток логина/регистрации) не
  затронут регрессией.
