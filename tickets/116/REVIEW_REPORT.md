# Major

1. **Ошибки БД/сети при резолве браслета маскируются под "браслет не
   найден"** (`src/components/scanner/Scanner.vue:334-351`).

   ```js
   let child = null
   try {
     child = await armband.getBraceletStatus(bandId)
   } catch (error) {
     console.error('❌ Fehler beim Abrufen des Armband-Status:', error)
   }
   if (!child) {
     result = { status: 'not-found', bandId }
     ...
   }
   ```

   Любое исключение из `getBraceletStatus` (сбой сети, недоступность
   Supabase, RLS-ошибка) проглатывается и приводит к тому же исходу,
   что и "браслет действительно не привязан ни к одному ребёнку":
   сигнал "notFound", красный экран "Kein Kind mit dem Verband
   verbunden". Оператор в этом случае получает недостоверную
   информацию — вместо "не удалось проверить, попробуйте ещё раз" видит
   сообщение, означающее "у этого ребёнка нет браслета в системе", что
   в контексте предметной области (учёт присутствия детей) может вести
   к ложному заключению об отсутствии ребёнка/браслета.

   Существующий `ScannerView.vue` (`src/views/ScannerView.vue:440-488`)
   различает эти два случая: `!child` → "Kein Kind ist mit dem Armband
   verbunden", а исключение из `getBraceletStatus` перехватывается
   отдельным внешним `catch` → "Fehler beim Verarbeiten" — то есть в
   проекте уже есть принятая конвенция различать "не найдено" и
   "ошибка запроса". Новый код эту конвенцию не воспроизводит, хотя
   контракт `onChildResolved` (план, раздел "Слои прототипа", п.1) и не
   предусматривает третьего статуса `error` — это пробел уже на уровне
   плана, не только реализации.

   Ручное тестирование это отдельно не проверяло (оно фокусировалось на
   UX-эргономике), но находка остаётся в силе: во время реальной работы
   сетевая нестабильность может быть ошибочно интерпретирована как
   "сканер работает некорректно с браслетами".

# Minor

1. **Незакрытый шаблонный `ref`** — `qrReaderEl` (`Scanner.vue:10, 86`)
   объявлен и привязан к `<div>`, но нигде не используется в скрипте
   (`Html5Qrcode` работает по строковому `id="qr-reader-proto"`).
   Мёртвый код, оставшийся от рефакторинга/копирования шаблона.

2. **Гонка "unmount во время инициализации" унаследована из
   `ScannerView.vue`, но теперь продублирована** — `onBeforeUnmount`
   (`Scanner.vue:392-397`) вызывает `stopScanning()`, которая
   реально останавливает камеру только если `scannerActive.value ===
   true`. Если пользователь нажимает "Beenden" до того, как
   `html5QrCode.start()` внутри `initScanner()`/`startScanningWith*`
   успел резолвиться (например, ожидание разрешения на камеру),
   `scannerActive` ещё `false`, `stop()` не вызывается — а когда
   `start()` всё же резолвится уже после размонтирования компонента,
   `scannerActive.value = true` присваивается на уничтоженном
   инстансе, и камера продолжает работать без отображения интерфейса
   до перезагрузки страницы. Тот же паттерн уже существует в
   `ScannerView.vue:542-547`, поэтому это не регрессия, а
   унаследованный и теперь задублированный риск — стоит иметь в виду
   при планировании 120/122, если прототип станет основой боевого кода.

3. **`packet.group_id` может быть `null`** (`ScannerPrototypeView.vue:59`,
   из `userStore.userInfo.group_id`) — если у пользователя не выставлена
   группа на сегодня (см. `CLAUDE.md`: `group_id` — поле "на сегодня" из
   `user_group_day`, не всегда заполнено), собранный `PresencePacket`
   типа `GROUP` будет содержать `group_id: null`. Для прототипа это не
   критично (пакет никуда не отправляется), но стоит держать в уме как
   пример, который не следует напрямую копировать в 120 без валидации
   контекста пользователя.

4. **`Kamera wählen` открывает пустой селектор при незагруженном
   списке камер** — если `Html5Qrcode.getCameras()` в `initScanner()`
   упал (поймано, залогировано предупреждением) и `cameraList` осталась
   пустой, кнопка "Kamera wählen" всё равно активна и по клику покажет
   `<select>` с одним disabled-плейсхолдером без реальных опций, без
   какой-либо подсказки пользователю, что список не загрузился. По факту
   должно естественным образом закрыться реализацией пункта 2 из
   "Результаты ручного тестирования" ниже (состояния "камера не
   выбрана" не должно существовать вообще).

# Результаты ручного тестирования

Ручное тестирование на реальных устройствах выполнено (закрывает пункт
Definition of Done, ранее отмеченный как незакрытый в
`IMPLEMENTATION_REPORT.md`). Требование "область сканирования
максимально близко к объективу камеры" (116.txt, п.3, см. также
"Архитектурные замечания" прежней версии этого отчёта) **подтверждено
выполненным** — навбар `App.vue` фактическому расположению области
сканирования относительно объектива не мешает. По итогам тестирования
зафиксированы следующие замечания, требующие исправления:

1. **Область сканера не квадратная — под видео остаётся пустое чёрное
   пространство.** Изображение с камеры квадратное (`SCANNER_CONFIG.
   aspectRatio: 1.0`, `Scanner.vue:96`), как и задумано, но контейнер
   `.proto-scan-area` (`flex: 1 1 auto` внутри `.proto-scanner` с
   `min-height: 100vh`, `Scanner.vue:409-415`) занимает всю оставшуюся
   высоту экрана, а не только высоту, равную его ширине. В результате
   под квадратным видео остаётся значительная пустая чёрная область до
   блока управления внизу — часть экрана используется неэффективно.
   Требуется: область сканера — квадрат шириной во весь экран (высота =
   ширина экрана), в котором размещается и видео, и все визуальные
   элементы сканирования (оверлей инициализации, экран подтверждения).
   Не выяснено, специфично ли это для тестового устройства (Samsung)
   или это общая особенность рендеринга камеры на Android — проверить
   на нескольких устройствах/платформах при исправлении.

2. **Интерфейс выбора камеры слишком громоздкий для редко используемой
   функции.** Текущая реализация (`Scanner.vue:28-61`) — это три
   отдельных визуальных блока (индикатор `.proto-camera-indicator`, две
   кнопки `.proto-camera-buttons`, раскрывающийся `<select>`
   `.proto-camera-selector`), что неоправданно занимает место в нижнем
   блоке управления. Требуется свести к одной кнопке, которая всегда
   отображает текущее значение (название конкретной камеры либо
   "Автоматический выбор камеры") и по нажатию открывает единый список
   всех камер устройства **вместе с** пунктом "Автоматический выбор
   камеры" как равноправным вариантом (не отдельным элементом
   интерфейса), с поддержкой прокрутки для устройств с большим числом
   камер (iPhone). Промежуточное состояние "камера не выбрана" /
   плейсхолдер "Kamera auswählen…" (`Scanner.vue:56`) быть не должно —
   камера всегда либо конкретно выбрана, либо в автоматическом режиме.
   Это отменяет прежнее допущение плана/реализации о раздельных
   элементах индикатора и селектора (`IMPLEMENTATION_PLAN.md`, раздел
   "Слои прототипа", п.1) и попутно закрывает Minor-находку выше о
   пустом `<select>` при незагруженном списке камер.

3. **Время показа экрана подтверждения (0.8 с для всех исходов,
   `wait(800)`, `Scanner.vue:367`) недостаточно для восприятия.**
   Пользователь не успевает прочитать текст, особенно в случае ошибки.
   Требуется: не менее 1.5 с для успешного исхода, не менее 3 с для
   любого неуспешного исхода (`invalid`/`not-found`) — таким образом,
   разным вариантам исхода нужна разная длительность показа, а не одна
   общая константа, как сейчас. Более длительный показ успеха попутно
   снижает риск случайного повторного считывания того же браслета,
   пока пользователь не убрал его от объектива.

4. **Повторное сканирование в рамках захода трактуется как ошибка,
   хотя таковой не является.** Текущая реализация
   (`ScannerPrototypeView.vue:76-80`) при повторном скане уже
   зарегистрированного ребёнка возвращает `variant: 'error'` — красный
   экран "Bereits gescannt", тот же визуальный/звуковой класс, что и
   для `invalid`/`not-found` (это соответствовало таблице сигналов
   `IMPLEMENTATION_PLAN.md`, но по факту тестирования признано
   неверным поведением). Требуется: повторное успешное считывание
   должно давать **зелёный** экран и звук успеха (браслет считан
   корректно), с текстом о том, что ребёнок уже зарегистрирован в
   текущем пакете, и дополнительной визуальной индикацией повтора
   (например, двойная галочка — если количество повторов не
   отслеживается, достаточно фиксированной "двойной" индикации для
   любого повтора). Ребёнок по-прежнему не должен добавляться в пакет
   повторно — в этой части текущая логика дедупликации верна и не
   меняется.

5. **Реакция интерфейса на "Отправить" неполная.** После нажатия
   "Senden" (`ScannerPrototypeView.vue:93-97`) состояние `packet`/
   `scannedList` не сбрасывается — список "отсканировано в этом
   заходе" продолжает показывать предыдущий заход, а обратная связь об
   отправке — это мелкий `alert alert-info` под кнопками
   (`ScannerPrototypeView.vue:22`), легко теряющийся в полевых
   условиях. Требуется: (а) после успешной отправки сразу очищать
   список отсканированных детей и состояние пакета, возвращая экран в
   исходное состояние для нового захода; (б) использовать саму область
   сканера (ту же зону, что и экран подтверждения скана) для показа
   результата отправки — зелёный экран с крупным сообщением/иконкой
   при успехе, красный с сообщением и кратким описанием причины при
   ошибке — вместо мелкого текстового уведомления. Кроме того, кнопку
   "Senden" (и по аналогии другие основные кнопки интерфейса) следует
   сделать выше за счёт увеличения вертикальных отступов (`padding`) —
   удобнее для нажатия на ходу, меньше промахов.

1. **Дублирование кода со `ScannerView.vue`** — сознательный и
   задокументированный компромисс плана (раздел "Риски"), не является

   `pause()/resume()`, работы с `localStorage` и резолва камеры теперь
   существует в двух местах и должна поддерживаться синхронно до тех
   пор, пока прототип не станет либо боевым, либо не будет удалён.
   Пункты 1-5 раздела "Результаты ручного тестирования" выше добавляют
   к этому списку ещё один слой логики (раскладка области сканера,
   единая кнопка выбора камеры, длительности показа экрана,
   трактовка повтора, обратная связь отправки), который при
   дальнейшем развитии стоит либо перенести в общий переиспользуемый
   код, либо явно принять решение не переносить.
