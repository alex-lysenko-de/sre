# Цель

Улучшить интерфейс и поведение модуля сканирования (`/scanner`,
`src/views/ScannerView.vue`) по семи пунктам тикета 116:

1. Сохранение выбранной камеры между визитами.
2. Информативный индикатор текущей камеры + возможность в любой момент
   вернуться к автоматическому выбору.
3. Поддержка фронтальной камеры + расположение области сканирования как
   можно выше (близко к объективу).
4. Индустриальная логика после скана: звук всегда при успешном считывании
   QR, короткая пауза распознавания (~0.5–1 с), крупный экран
   подтверждения вместо мелкого текста.
5. Разные звуковые сигналы для разных исходов обработки.
6. Разная вибрация (короткая/длинная) + визуальное подтверждение
   (зелёный/красный экран) после каждого скана.
7. Кнопки управления — вниз экрана.

**Дополнительное архитектурное требование пользователя (уточнение к
исходному тикету)**: реализовать сканер как композицию слоёв-"врапперов"
("матрёшка"), где каждый слой отвечает только за свою область
ответственности и расширяет поведение нижнего слоя, не изменяя его
напрямую. Это прямо меняет решение из предыдущей версии плана (всё в
одном файле `ScannerView.vue`) — изменение обосновано пользователем
явно: подготовка к дальнейшей миграции приложения и к тикету 120
(дальнейшее развитие сканера, например автобусный режим), где ожидается
добавление ещё одного враппера поверх уже созданных без изменения их
кода.

Явно вне зоны действия (по тексту тикета 116): различение режимов
сканирования (автобус / перекличка группы / произвольное сканирование-
привязка) как бизнес-логика — отдельный будущий тикет (120). Текущий
тикет закладывает архитектуру, позволяющую такие режимы добавлять как
новые врапперы, но сам ни одного из них не реализует — сегодняшний
`ScannerView.vue` продолжает реализовывать ровно один сценарий (групповая
перекличка), просто выраженный теперь как верхний слой композиции.

## Модель слоёв (по требованию пользователя)

Три слоя для этого тикета (дальнейшие слои — предмет будущих тикетов,
например 120):

1. **Базовый (промышленный) сканер** — ничего не знает о детях,
   браслетах, группах. Отвечает за: экран камеры, рамку сканирования,
   декодирование QR, выбор/сохранение камеры (пункты 1-3, 7 тикета
   целиком принадлежат этому слою), стандартный сигнал+короткую
   вибрацию при самом факте успешного считывания QR (независимо от
   бизнес-исхода), паузу распознавания на ~0.5-1 с после каждого скана,
   отображение результата (зелёный/красный экран с иконкой и текстом) —
   причём **содержимое текста и, при необходимости, весь экран
   результата может быть переопределено вышестоящим слоем**.
2. **Враппер сканера браслетов** — использует слой 1 для получения
   декодированного текста, проверяет по БД, привязан ли QR-код (браслет)
   к ребёнку (`useArmband`), отображает сведения о ребёнке или ошибку
   "не найден"/"не привязан", добавляет **собственный** отдельный
   звуковой сигнал успеха/ошибки и более длинную вибрацию при ошибке
   "не найден" — поверх (в дополнение к, не вместо) базового сигнала
   слоя 1.
3. **Верхний слой конкретного сценария использования** — сегодня это
   сам `ScannerView.vue` в роли "враппера групповой переклички": держит
   список уже отсканированных в этом заходе детей, решает, что повторный
   скан того же ребёнка — не новая бизнес-запись, добавляет свой
   собственный сигнал/вибрацию для этого случая и красный экран
   "Bereits gescannt". Именно этот слой пользователь иллюстрирует
   примером "автобусного сканера" для будущего тикета 120 — по аналогии,
   гипотетический `BusScannerView` будущего тикета переиспользовал бы
   слои 1 и 2 без изменений, реализуя свою собственную (отличную от
   групповой) логику "что считать повторным сканированием" — что и
   требует размещения этой логики на верхнем, а не на среднем слое.

**Уточнение по итогам обсуждения тикета 120** (см. `tickets/120/120.txt`):
задача 120 явно формулирует "Scanner не содержит бизнес-логики" и
описывает будущую модель, где ни один слой сканера сам не пишет в БД —
вместо этого каждый режим формирует пакет и отправляет его целиком по
кнопке "Отправить" (офлайн-надёжность, возможность проверить/отменить
перед отправкой — решение принято в обсуждении тикета 116/120, не будет
дублироваться здесь). Чтобы слой 2 (`BraceletScanner`) остался
переиспользуемым для будущих пакетных режимов без изменений, **решение о
том, писать ли что-либо и когда**, выносится из слоя 2 полностью на слой
3 — то есть уже в этом тикете `BraceletScanner` не вызывает
`useArmband.recordChildPresence()` сам. Он только резолвит QR в ребёнка
(найден/не найден) и передаёт результат вверх; текущий `ScannerView.vue`
(сегодняшний единственный режим, ещё не пакетный — пакетная отправка
остаётся предметом тикета 120) выполняет запись в БД сам, немедленно —
то есть видимое поведение приложения сегодня не меняется, меняется
только то, в каком слое живёт код, отвечающий за запись.

Контракт между слоями — не события "в одну сторону", а **асинхронный
callback, передаваемый вниз и возвращающий результат вверх**: каждый
слой предоставляет нижнему свою функцию-обработчик декодирования,
которая (а) выполняет действия своего уровня ответственности, (б) при
необходимости вызывает аналогичный callback, полученный от слоя ещё
выше, чтобы дать ему шанс переопределить исход, (в) возвращает
итоговый/скорректированный результат вниз. Это позволяет верхнему слою
"выключить" побочный эффект нижнего (например, не создавать вторую
запись в `scans` при повторном сканировании) — то, чего не позволил бы
простой однонаправленный emit-механизм. Подробности контракта — в
разделе "Новые компоненты".

Существующее взаимодействие с БД/бизнес-логикой (`useArmband`, триггер
`on_scan_insert` → `children_today`, см. [[Триггеры]],
[[Учёт-автобусов]]) тикетом по-прежнему не меняется — только код,
вызывающий `recordChildPresence()`, переезжает из старого
`processScannedData()` в `ScannerView.vue` (слой 3, см. уточнение выше),
и вызывается ровно в тех же случаях, что и сейчас (валидный браслет,
найден ребёнок, не является дублем в рамках этого захода).

# Изменения существующих компонентов

## `src/views/ScannerView.vue`

Практически полностью переписывается, но по объёму кода — существенно
**сокращается**: вся механика камеры и вся логика браслетов переезжают в
новые компоненты (см. ниже). Остаётся:

- Разметка страницы верхнего уровня: заголовок/кнопка "Beenden", счётчик
  (`counter-bar`), список "Gescannte Kinder" (без изменений в составе
  данных).
- Монтирование `<BraceletScanner :onChildFound="handleChildFound" />`.
- `scannedChildren` (список детей, отсканированных в этом заходе) —
  без изменений по смыслу, заполняется напрямую внутри
  `handleChildFound()` (см. ниже) — отдельный emit `child-recorded` от
  `BraceletScanner` не нужен, так как запись теперь и происходит именно
  здесь.
- **`handleChildFound(child, bandId)`** — обязательный проп-callback,
  единственное место, где сегодня выполняется запись в БД (перенесено
  из старого `processScannedData()`/новой версии `BraceletScanner`, см.
  "Уточнение по итогам обсуждения тикета 120" выше):
  1. Если `child.id` уже есть в `scannedChildren` — проигрывает свой
     сигнал "duplicate" + короткую вибрацию (через
     `useScannerFeedback`), **не** вызывает `recordChildPresence()`,
     возвращает `{status: 'duplicate', title: 'Bereits gescannt',
     subtitle: child.name}` — этот объект используется слоем 2 как
     финальный результат для экрана подтверждения (переопределяет
     дефолтный "успех" слоя 2).
  2. Иначе — вызывает `useArmband.recordChildPresence(userStore.userInfo.id,
     child.id, bandId, userStore.userInfo.bus_id)` (перенесено без
     изменений семантики из старого кода), добавляет `child` в
     `scannedChildren`, возвращает `{status: 'success', title: child.name,
     subtitle: 'Gruppe ' + child.group_id}`.
  Именно эта функция — единственное место, которое в будущем тикете 120
  для пакетных режимов заменяется на "добавить в локальный пакет" вместо
  прямой записи в БД; сигнатура и место вызова (`onChildFound` пропа
  `BraceletScanner`) не меняются.
- `exitScanner()` — без изменений в сути (`router.push('/main')`), но
  остановка сканера (`stopScanning()`) теперь инкапсулирована в
  `BaseQrScanner` — вызывается через `ref` на дочерний компонент
  (`defineExpose` в `BaseQrScanner`, например метод `stop()`), либо через
  `onBeforeUnmount` внутри самого `BaseQrScanner` при размонтировании
  (что естественно происходит при уходе с маршрута `/scanner`) —
  выбор конкретного механизма делается на этапе реализации, оба
  варианта совместимы с текущим поведением "Beenden".

## 2. `src/components/scanner/BraceletScanner.vue`

Враппер вокруг `BaseQrScanner`. Содержит:

- `<BaseQrScanner :onDecode="handleDecode" ref="baseScannerRef" />` —
  прозрачно прокидывает разметку/слот наружу при необходимости (для
  этого тикета — не требуется, `ScannerView.vue` монтирует
  `BraceletScanner` напрямую).
- `createQrCodePattern()`/`getBaseDomain()` — переносятся сюда из
  текущего `ScannerView.vue` без изменений: разбор формата URL браслета —
  это знание о том, как выглядит QR-код именно браслета, то есть
  ответственность этого слоя, а не базового сканера.
- `handleDecode(rawText)`:
  1. Не соответствует формату URL браслета → свой сигнал ошибки
     "invalid" + длинная вибрация → возврат `{status: 'error', title:
     'Ungültiger QR-Code'}`. **Не вызывает `onChildFound`** — нет
     найденного ребёнка, персистить нечего.
  2. `useArmband.getBraceletStatus(bandId)` не находит ребёнка → свой
     сигнал "not-found" + длинная вибрация → возврат `{status: 'error',
     title: 'Kein Kind mit dem Verband verbunden'}`. Тоже не вызывает
     `onChildFound`.
  3. Ребёнок найден → проигрывает свой сигнал "success" (сам факт, что
     браслет валиден и привязан — это успех уровня ответственности
     слоя 2, независимо от того, что решит слой 3) → вызывает
     `const outcome = await props.onChildFound(child, bandId)`
     (**обязательный** проп, единственное место во всём компоненте,
     которое умеет что-либо делать с найденным ребёнком дальше — сам
     `BraceletScanner` **не вызывает `useArmband.recordChildPresence()`
     и вообще не содержит логики персистентности**, см. "Уточнение по
     итогам обсуждения тикета 120" выше) → возвращает `outcome` как
     финальный результат для экрана подтверждения слоя 1 (слой 3
     полностью определяет `status`/`title`/`subtitle` — например,
     помечает результат как `'duplicate'` вместо `'success'`).
- Props: `onChildFound: (child, bandId) => Promise<{status: 'success'|
  'duplicate', title?, subtitle?}>` — обязательный, без значения по
  умолчанию: без него компонент не может ничего сделать с найденным
  ребёнком, и это осознанное архитектурное ограничение (решение
  "писать/копить/игнорировать" не может приниматься на этом слое).
- Emits: не требуются — весь необходимый слою 3 результат передаётся
  через возврат `onChildFound`, отдельного события не нужно.

## 3. `src/composables/useScannerFeedback.js`

Не бизнес-логика, а маленькая техническая утилита — вынесена из
существующего `ScannerView.vue` без изменений механики (Web Audio API,
`navigator.vibrate`), чтобы не дублировать boilerplate между тремя
слоями. Экспортирует примитивы, не привязанные к конкретному звуку/
паттерну — конкретные частоты/длительности/паттерны каждый слой задаёт
сам при вызове:

- `getAudioContext()`, `unlockAudioContext()` (для вызова из
  `onMounted`/первого жеста пользователя — как сейчас, критично для iOS
  Safari), `playTone(frequencies, duration)`.
- `vibrate(pattern)` (обёртка над `navigator.vibrate` с проверкой
  `'vibrate' in navigator`).

Каждый слой (`BaseQrScanner`, `BraceletScanner`, `ScannerView`) вызывает
`playTone(...)`/`vibrate(...)` с собственными параметрами (см. таблицу
ниже) — сама утилита не содержит пресетов и не знает о "успехе"/
"ошибке".

Это единственное сознательное отклонение от принципа "каждый слой
полностью независим": композабл не содержит поведения, только
переиспользуемый технический примитив (аналогично тому, как несколько
composables проекта используют общий `src/supabase.js` — см.
[[Обзор-composables]]), поэтому не нарушает изоляцию слоёв по бизнес-
смыслу.

# Риски

- **`pause(true)`/`resume()` — не проверено на реальных устройствах** в
  рамках архитектурного планирования (код не запускался). Основной
  риск: если `pause(true)` (сохранение последнего кадра) визуально даёт
  "подвисшую" картинку до появления экрана результата — может
  потребоваться `pause(false)` или мгновенная подмена экраном результата
  без паузы видео. Проверяется на шаге 5 плана реализации.
- **Взаимодействие `pause()`/`resume()` (слой 1) с `isTransitioning`
  (тоже слой 1, при смене камеры)**: если пользователь выберет новую
  камеру ровно во время активной паузы после скана, возможна гонка
  между отложенным `resume()` (по таймеру cooldown) и `stop()`/`start()`
  (по смене камеры). Поскольку оба механизма теперь целиком внутри
  одного компонента (`BaseQrScanner`), это локальная задача этого
  файла — не распространяется на слои 2-3; решается, например, токеном
  текущей операции, проверяемым перед вызовом отложенного `resume()`.
- **Стоимость нового многослойного контракта**: три файла и явный
  callback-контракт (`onDecode`/`onChildFound`) — больше движущихся
  частей, чем в изначальном (однофайловом) варианте плана. Оправдано
  явным требованием пользователя и целью тикета 120 (переиспользование
  слоёв 1-2 без изменений при добавлении, например, автобусного
  сценария) — риск в том, что если тикет 120 в итоге не потребует
  переиспользования в описанном виде, часть этой декомпозиции окажется
  избыточной для тикета 116 самого по себе.
- **Длительность окна паузы (0.5-1 с)** — тикет указывает диапазон, не
  точное число; план фиксирует единое значение (рекомендация: 800 мс)
  без отдельной настройки/конфигурации.
- **iOS Safari mute switch** (задокументированное в коде ограничение из
  тикета 103) — по-прежнему не решается кодом ни для одного из
  сигналов; визуальный экран результата — единственный надёжный канал
  обратной связи в этом случае.
- **Регресс защиты `isTransitioning`** (тикет 103) — при переносе в
  `BaseQrScanner` нужно сохранить её в точности, включая `:disabled` на
  кнопке/селекторе камеры.
- **Отсутствие автоматических тестов** для сканера — вся проверка, как и
  в тикете 103, только ручная и требует физических устройств.

# Definition of Done

- Функциональность полностью соответствует пунктам 1-7 тикета (как в
  предыдущей версии DoD): камера сохраняется между визитами; индикатор
  показывает активную камеру; "Automatisch" всегда доступен для выбора;
  фронтальные камеры доступны, область сканирования — вверху экрана;
  кнопки — внизу; при любом успешном считывании QR всегда сразу
  срабатывает базовый сигнал+короткая вибрация, распознавание
  приостанавливается на ~0.5-1 с и автоматически возобновляется; после
  каждого скана — крупный зелёный/красный экран с иконкой и текстом;
  разные исходы (успех/неверный QR/не найден/повторный скан) звучат
  по-разному; повторный скан в рамках захода не создаёт новую запись в
  БД, но слышен/виден оператору (короткая вибрация, "Bereits gescannt");
  ошибки — длинная вибрация; защита от гонки состояний при смене камеры
  не регрессирует.
- **Архитектурное требование**: код разделён на три независимых слоя —
  `BaseQrScanner.vue` (ничего не знает о детях/браслетах),
  `BraceletScanner.vue` (резолвит QR в ребёнка, но **не пишет в БД и не
  содержит логики персистентности** — ничего не знает о группах/
  списках/дублях в рамках захода/пакетах), `ScannerView.vue` (реализует
  специфику групповой переклички, включая единственный в тикете вызов
  `recordChildPresence()`). Нижние два слоя не содержат кода,
  специфичного для верхнего — переиспользуемы без изменений в
  гипотетическом будущем сценарии (например, автобусном или пакетном,
  тикет 120), где верхний слой заменит немедленную запись на накопление
  в пакет, не трогая `BaseQrScanner.vue`/`BraceletScanner.vue`.
- Ручная проверка на реальных Android- и iPhone-устройствах (включая
  режим "Бесшумный" на iPhone) выполнена и подтверждает пункты выше.
