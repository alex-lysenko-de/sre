# Тикет 116 — архитектурный план (прототип нового сканера)

Заменяет предыдущую версию этого файла целиком — та описывала
переписывание боевого `ScannerView.vue` на 3 слоя, что отменено по
итогам ревью (см. `tickets/116/DECISIONS.md`). Ниже — план под новую
цель тикета: отдельный, не подключённый к продовой логике UI-прототип.

Входные данные: `tickets/116/116.txt` (обновлён), `tickets/116/DECISIONS.md`
(решение о смене цели + разрешённая развилка "2 или 3 слоя"),
`tickets/120/120.txt` (формат `PresencePacket`, диаграмма
«Scanner → режим → пакет», раздел «Общая архитектура»).

# Цель

Новый, не связанный с боевым кодом экран-прототип, реализующий
интерфейсные и поведенческие требования 116.txt (пункты 1-7:
сохранение камеры, индикатор камеры с возвратом к "Automatisch",
фронтальная камера с областью сканирования вверху, индустриальная
логика после скана, разные звуковые сигналы, вибрация+визуальный экран
подтверждения, кнопки внизу) и накапливающий результаты сканирования в
объект по форме `PresencePacket` (`tickets/120/120.txt`). Кнопка
"Отправить" — заглушка: ничего не пишет в БД, никуда не обращается.
Цель прототипа — проверить удобство интерфейса до того, как под него
пишется боевая логика режимов/сервера (тикеты 120/122).

**Явно не входит** (см. 116.txt, "Что не входит"): различение режимов
сканирования (автобус/перекличка группы/свободные отметки) как
бизнес-логика, реальная отправка пакета, любая интерпретация
результатов, автоматизированные тесты сверх необходимого минимума.

# Анализ существующей архитектуры и контекста

- **`ScannerView.vue` не трогается** ни в каком виде — ни рефакторинг,
  ни извлечение общего кода из него. Новый прототип пишется с нуля;
  часть механики (выбор/сохранение камеры, `pause()`/`resume()`,
  Web Audio/vibration) неизбежно **повторяет** уже существующие в
  `ScannerView.vue` паттерны — это осознанный, принятый компромисс для
  одноразового прототипа (дублирование дешевле, чем трогать боевой
  экран ради временного кода). Если прототип впоследствии станет
  постоянным (решение — по итогам UX-проверки, вне рамок 116), общий
  код можно будет выделить отдельным шагом.
- Технические находки тикета 103, полезные как референс при написании
  нового кода (не как код для переноса): `Html5Qrcode.getCameras()` не
  фильтрует по типу камеры (фронтальные уже видны); `pause(shouldPauseVideo)`/
  `resume()` — способ приостановить распознавание без полного
  `stop()`/`start()`; параллельный вызов `start()`/`stop()` до
  завершения предыдущего перехода кидает синхронное исключение —
  нужна защита по образцу `isTransitioning`.
- **`tickets/120/120.txt`, раздел «Общая архитектура», прямо описывает
  двухуровневую модель**: единый `Scanner`, который «отвечает только за
  получение идентификатора ребёнка» и «не знает, какой режим сейчас
  используется» — режимы (Bus/Перекличка/Отметки) находятся выше и
  сами решают, что показывать и как формировать пакет. Это и есть
  готовый ответ на открытый вопрос `DECISIONS.md` («2 или 3 слоя»):
  раз даже в описании самого 120 «получение идентификатора ребёнка»
  (то есть включая резолв браслета в ребёнка, а не только сырой
  декодированный текст) — обязанность одного и того же нижнего слоя,
  контрпримера для отдельной прослойки "сырой декод без резолва
  браслета" нет. **Решение: 2 слоя**, как и предполагалось по
  умолчанию в `DECISIONS.md`.
- Следствие: нижний слой прототипа **не свободен от доменных понятий**
  полностью (в отличие от прежнего плана, где `BaseQrScanner` ничего не
  знал о браслетах) — он читает статус браслета через
  `useArmband.getBraceletStatus()` (доступ на чтение). Это осознанно —
  не write-логика и не режимо-специфичная бизнес-логика, а именно
  «получение идентификатора ребёнка», как описано в 120.txt.

# Слои прототипа

## 1. `src/components/scanner/Scanner.vue` — переиспользуемый базовый слой

Отвечает за пункты 1-3, 7 тикета 116 целиком и за базовую часть пунктов
4-6 (сам факт успешного считывания QR, включая резолв в ребёнка):

- Механика камеры: инициализация, запуск/остановка, выбор камеры,
  защита от параллельных переходов состояния (по аналогии с
  `isTransitioning` из 103) — реализуется заново, без переноса кода.
- Сохранение выбранной камеры в `localStorage` (пункт 1). Ключ
  хранения — решение на этапе реализации: можно переиспользовать тот
  же ключ, что и у `ScannerView.vue` (выбор камеры — предпочтение
  устройства, а не конкретного экрана, так что общий ключ логичен и не
  требует изменений в `ScannerView.vue`, так как это чтение общего
  `localStorage`, а не изменение его файла), либо завести отдельный —
  окончательный выбор не архитектурно значим, фиксируется в 122/при
  реализации.
- Индикатор текущей камеры вместо статус-бейджа + опция "Automatisch"
  всегда доступна для повторного выбора (пункт 2).
- Раскладка: область сканирования вверху, кнопки/индикатор/селектор —
  внизу (пункты 3, 7).
- При каждом успешном считывании QR: `pause()`, базовый сигнал +
  короткая вибрация (через `useScannerFeedback`), резолв QR → браслет →
  ребёнок (`useArmband.getBraceletStatus()`), пауза ~0.5-1 с, затем
  `resume()`.
- Результат резолва передаётся наверх через обязательный проп-callback
  `onChildResolved(result)`, где `result` — один из:
  - `{ status: 'invalid' }` — текст не похож на URL браслета;
  - `{ status: 'not-found', bandId }` — браслет не привязан ни к
    одному ребёнку;
  - `{ status: 'found', child, bandId }` — ребёнок найден.
  Callback — `async`, возвращает `{ title, subtitle }` для экрана
  подтверждения (слой 2 решает, что показать — например, "уже
  отсканирован в этом заходе" вместо дефолтного "успех"). Компонент
  сам проигрывает сигнал/вибрацию, специфичные для исхода резолва
  (`invalid`/`not-found`/`found`) — эта часть таблицы сигналов ниже.
  Слой 2 может добавить **дополнительный** сигнал/вибрацию поверх (не
  вместо), если решит переопределить исход (например, "уже
  отсканирован").
- Не содержит: `recordChildPresence()`, сборки `PresencePacket`,
  списка отсканированных детей "в рамках захода" — всё это выше.

## 2. `src/views/ScannerPrototypeView.vue` — экран-прототип

- Монтирует `<Scanner :onChildResolved="handleResolved" />`.
- **Дедупликация "в рамках этого захода"** — базовое поведение
  процесса сканирования (явно требуется 116.txt, п.4-5: "повторное
  сканирование" — отдельный тип ошибки/сигнала), не режимо-специфичная
  бизнес-логика, поэтому остаётся в прототипе, а не откладывается в
  120: если `child.id` уже есть в локальном списке — свой сигнал
  "duplicate" + короткая вибрация, экран "Bereits gescannt", **не**
  добавляется вторая запись в накапливаемый пакет.
- **Сборка `PresencePacket`** (локально, в памяти, ничего не пишется
  на сервер): при первом успешном (не дублирующемся) резолве
  фиксируется `started_at`; при каждом — добавляется элемент
  `children[]` в форме `{ child_id, timestamp, method: 'SCAN' }`
  (`method` всегда `'SCAN'` — ручная отметка вне рамок прототипа);
  `finished_at` обновляется на каждый скан или фиксируется в момент
  нажатия "Отправить". Раз различение режимов вне рамок 116 (см.
  «Цель»), пакет собирается в форме, ближайшей к режиму GROUP
  (`tickets/120/120.txt`, «Режим 2»): `type: 'GROUP'`, `author_id` —
  `userStore.userInfo.id`, `group_id` — `userStore.userInfo.group_id`
  (уже доступный контекст пользователя, не новая бизнес-логика режима).
  Это сознательное упрощение для демонстрации формата, не решение о
  реальном режиме — при реализации 120 может быть выбран другой пример
  или несколько.
- **Кнопка "Отправить" — заглушка**: не выполняет `fetch`/Supabase-
  вызовов, не пишет в БД. Допустимо (не обязательно) чисто
  косметическое локальное подтверждение для тестировщика (например,
  кратковременная надпись "Отправлено (заглушка)"), но никакого
  сетевого/DB-эффекта быть не должно.
- Список "отсканировано в этом заходе" — аналог текущего "Gescannte
  Kinder" в `ScannerView.vue`, для наглядности тестировщику.
- Кнопка выхода/возврата на главный экран (`router.push('/main')`),
  останавливающая сканер (`Scanner.vue` предоставляет `defineExpose({
  stop })`, либо остановка через `onBeforeUnmount` внутри самого
  `Scanner.vue`).

## 3. `src/composables/useScannerFeedback.js`

Новый, не связан с существующим `ScannerView.vue`. Технические
примитивы без пресетов (аналогично прежней версии плана):
`getAudioContext()`/`unlockAudioContext()` (вызов на первом жесте
пользователя — важно для iOS Safari), `playTone(frequencies, duration)`,
`vibrate(pattern)` (обёртка над `navigator.vibrate`). Конкретные
частоты/паттерны для каждого исхода задаёт вызывающий код (`Scanner.vue`
и `ScannerPrototypeView.vue`) — сам композабл не знает про "успех"/
"ошибку".

# Риски

- **Дублирование кода с `ScannerView.vue`** (камера/decode/feedback) —
  осознанный компромисс прототипа (раздел «Анализ»); если прототип
  впоследствии станет боевым экраном, общий код можно будет выделить
  отдельным шагом — не в рамках 116.
- **`pause(true)`/`resume()` не проверены на реальных устройствах** в
  рамках архитектурного планирования — тот же риск, что был в прежней
  версии плана; проверяется на шаге 5.
- **Упрощение формы пакета до GROUP-подобной** (раздел «Слои», п.2) —
  при реализации 120 реальный набор режимов может потребовать другой
  иллюстративный пример; это не блокирует цель 116 (проверка UX
  интерфейса сканирования, а не корректности конкретного формата
  пакета).
- **Отсутствие автоматических тестов** — осознанно, по цели тикета
  (116.txt, п.5 DECISIONS.md): только ручная проверка UX.
- **iOS Safari mute switch** — как и в 103/прежнем плане, не решается
  кодом ни для одного сигнала; визуальный экран подтверждения — тот же
  единственный надёжный канал в этом случае.

# Definition of Done

- Существующий `/scanner` (`ScannerView.vue`) не изменён ни в одной
  строке.
- Новый маршрут/пункт меню открывает прототип, реализующий пункты 1-7
  тикета 116 (камера сохраняется и переключается на "Automatisch" в
  любой момент; фронтальная камера доступна, область сканирования
  вверху; при каждом успешном считывании — сигнал+короткая вибрация,
  пауза ~0.5-1 с, автоматическое возобновление; крупный зелёный/
  красный экран с иконкой и текстом после каждого скана; разные исходы
  звучат по-разному; повторный скан в рамках захода не добавляется в
  пакет повторно, но слышен/виден оператору; кнопки — внизу экрана).
- Прототип накапливает результаты в объект по форме `PresencePacket`
  (`tickets/120/120.txt`) — проверяется вручную (например, через
  консоль/Vue devtools), что объект формируется и растёт с каждым
  успешным сканом.
- Кнопка "Отправить" не выполняет ни одного сетевого запроса и ни
  одной записи в БД — подтверждается вручную (сетевые логи/Supabase
  logs пусты после нажатия).
- `useArmband.recordChildPresence()` не вызывается прототипом ни при
  каких условиях.
- Ручная проверка на реальных Android- и iPhone-устройствах выполнена.
