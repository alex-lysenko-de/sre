# LocalForage ↔ Supabase: архитектура обмена данными

## Проблема

Сейчас часть важных пользовательских данных хранится только в LocalForage и отсутствует в Supabase. На iOS это не очень надёжное решение: невозможно гарантировать сохранность локальных данных после выхода пользователя из приложения или при переходе между браузером и установленным PWA-приложением (два разных хранилища, см. тикеты 105 и 112).

Например, пользователь сначала работает с приложением в браузере Safari — в LocalForage сохраняются его настройки (выбранная камера для сканирования, номер группы, различные предпочтения и т.д.). Затем пользователь устанавливает PWA — на iOS это приложение использует уже другое локальное хранилище, не связанное с хранилищем браузера (в отличие от Android, где поведение предсказуемее). В результате приложение запускается без ранее сохранённых настроек.

Данные о детях, в свою очередь, хранятся в Supabase, но для быстрого доступа и работы при нестабильном интернете кэшируются локально в LocalForage.

Отсюда вопрос: нужен ли между LocalForage и Supabase полноценный механизм двусторонней синхронизации?

## Рекомендация (архитектурная, для обсуждения/уточнения перед реализацией)

Единого "sync-движка" на все данные заводить не стоит — это источник конфликтов и лишних запросов без явной необходимости. Вместо этого предлагается разделить данные по природе и обращаться с каждой группой по-своему:

1. **Персональные/расписательные данные пользователя** (группа, автобус, роль и т.п.) — Supabase уже является источником истины (таблицы `users`, `user_group_day`). Тут не нужна "синхронизация" в полном смысле — на новом устройстве/после переустановки эти данные просто заново подгружаются из Supabase. LocalForage для них остаётся тем, чем уже является в `useUser.js`, — read-through кэшем с TTL (сейчас 60 сек), а не независимым хранилищем истины. Отдельная синхронизация не требуется — требуется только гарантировать, что кэш всегда можно безопасно перечитать из Supabase.
2. **Чисто клиентские настройки устройства** (выбранная камера для сканера и т.п., см. тикет 116) — это свойство конкретного устройства/браузера, а не пользователя. Их не стоит переносить в Supabase вообще: смысл этих настроек как раз в том, что они привязаны к физическому устройству (на новом устройстве камеру всё равно надо выбирать заново). Хранить только локально (LocalForage/localStorage), без синхронизации.
3. **Кэш данных о детях** — уже правильно организовано как локальный кэш поверх Supabase-источника истины; изменений не требует, только явное документирование источника истины и стратегии инвалидации кэша (TTL/force-reload по аналогии с `useUser.js`).

## Открытые вопросы к обсуждению перед реализацией

* Согласны ли мы с делением "источник истины = Supabase для всего, что касается личности/расписания пользователя, LocalForage только для устройство-специфичных настроек"? Если да — задачи по синхронизации как таковой не остаётся, остаётся только ревизия существующих мест хранения (что из уже сохранённого в LocalForage реально должно быть отнесено к пользователю, а что — к устройству).
* Если всё же требуется полноценная синхронизация (например, для оффлайн-режима с изменениями, которые нужно применить к Supabase позже) — нужно отдельно спроектировать разрешение конфликтов (какая сторона "выигрывает" при расхождении) и механизм очереди отложенных изменений. Это отдельный, более сложный сценарий, выходящий за рамки простого read-through кэша.

## Definition of Done

* Принято архитектурное решение по разделению данных (см. рекомендацию выше) — зафиксировано в документации (`vault/`).
* Составлен полный список текущих ключей LocalForage/localStorage с классификацией "пользовательские / устройство-специфичные" (аудит, без немедленной реализации).
* Для данных, ошибочно хранимых только локально, но по природе являющихся пользовательскими, — определён путь переноса в Supabase.
