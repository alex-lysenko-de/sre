# Архитектурные замечания

Сам план (`tickets/124/IMPLEMENTATION_PLAN.md`) ревью не подвергался
предметно, так как задача — ревью реализации, а не повторное ревью уже
принятого плана. Отмечу только для последующего разработчика: план
самостоятельно называет два пункта как непроверенные архитектурные
допущения, которые нужно подтвердить именно на шаге реализации, а не
считать решёнными заранее:
- необходимость `SECURITY DEFINER` у `set_client_log_user_id()` —
  зависит от фактических RLS-политик `users` на момент реализации;
- обоснованность двух отдельных INSERT-политик (`authenticated`/`anon`)
  вместо одной общей — план это не разбирает явно.

Оба пункта корректно adressuются на этапе реализации/следующего
ревью, а не блокируют начало работы.
