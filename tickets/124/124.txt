# Тикет 124: Клиентское логирование ошибок + версионность приложения

## Проблема

В приложении сегодня нет структурированного логирования: ошибки и
непредвиденные исключения на клиенте попадают только в
`console.error()`/`console.warn()` (см., например, `useArmband.js`,
`useChildren.js`, `useChildPresence.js`) — то есть видны только если
разработчик в момент возникновения проблемы смотрит в devtools того же
устройства. Выделенного бэкенда, кроме Supabase, у проекта нет
(`CLAUDE.md`: "фронтенд обращается к Supabase напрямую").

Из-за этого повторяющаяся проблема: тестер/пользователь сообщает
"что-то не сработало", а разработчик не может понять ни точную
последовательность действий (какой роут, какое меню, какой composable/
action вызывался), ни даже версию приложения, с которой тестер работал
(есть ли риск, что баг уже исправлен, но у тестера просто не обновилось
PWA).

## Часть 1 — Клиентский лог ошибок

Реализовать логирование по гибридной схеме (комбинация серверного и
локального хранения, без полноценного отдельного backend-а):

1. **Ring-buffer "хлебных крошек" в памяти** — последние N (порядок
   величины 200–500) событий: переходы роутера, вызовы Pinia-экшенов,
   вызовы/результаты обращений к Supabase (включая коды ошибок API, не
   только исключения), значимые пользовательские действия. Не полноценный
   лог всего подряд постоянно — только контекст, который пригодится при
   разборе конкретной ошибки.
2. **Перехват необработанных ошибок**: `app.config.errorHandler` (Vue),
   `window.onerror`, `window.addEventListener('unhandledrejection', ...)`.
   При срабатывании — текущий ring-buffer + сама ошибка сохраняются одной
   записью в персистентный лог.
3. **Персистентное локальное хранение** — через LocalForage (в проекте
   уже есть прецедент отдельного instance для конкретной области данных,
   `authLocalForage` в `src/modules/storage.js`; лог должен использовать
   свой собственный instance/store, не пересекаясь с авторизационными
   данными). Работает полностью офлайн — ничего не теряется при
   отсутствии сети.
4. **Best-effort отправка на сервер** — новая таблица в Supabase (лог
   ошибок), запись только через `INSERT` собственных строк
   аутентифицированного пользователя (RLS `user_id = auth.uid()`), без
   широких permissive-политик "на всякий случай" (в проекте уже
   зафиксирован антипаттерн такой политики, см.
   `vault/03-База-данных/RLS-политики.md`). Отправка — периодическая
   попытка выгрузить накопленное из LocalForage при наличии сети; при
   отсутствии сети запись остаётся локально до следующей попытки, ничего
   не блокирует основной сценарий работы приложения.
5. **Экран просмотра лога** (для тестера/администратора) — показывает
   содержимое локального лога, с возможностью поделиться содержимым
   через `navigator.share()` (Web Share API — на мобильных сама
   предложит WhatsApp/почту и т.п. как получателя) и запасным вариантом
   "скопировать в буфер обмена" для сред без Web Share API.
6. **Приватность/данные детей** — в проекте обрабатываются персональные
   данные несовершеннолетних (имена, группы и т.п.); нужно явно
   определить, что в лог не попадает ни при каких обстоятельствах
   (токены, пароли — однозначно) и насколько допустимо присутствие в
   логе имён детей/групп ради диагностической ценности.

## Часть 2 — Версионность приложения

Сегодня номер версии нигде не используется во время выполнения:
`package.json` содержит `"version": "0.0.1"`, но это значение не
прокидывается в собранный клиентский код и нигде не отображается
пользователю. При этом PWA уже настроен на автообновление
(`vite.config.js`: `VitePWA({ registerType: 'autoUpdate' })`,
`src/main.js`: `registerSW({ onNeedRefresh() { ... updateSW(true) } })`)
— то есть механизм обновления уже есть, но нет способа проверить, что
конкретное устройство реально работает с ожидаемой версией.

Требуется:

1. Единый источник истины для номера версии — `package.json` (`version`),
   пробрасываемый в клиентский бандл через `vite.config.js` (`define`),
   без дублирования значения в нескольких файлах вручную.
2. Номер версии должен присутствовать в **каждой** записи клиентского
   лога из Части 1 — чтобы по логу сразу было понятно, с какой версией
   приложения он получен.
3. Экран/окно "About" (сегодня в проекте отсутствует) — минимально,
   отображает текущий номер версии приложения. Точка входа в этот экран
   и его прочее содержимое (кроме номера версии) — вне рамок этой
   задачи, определяется при реализации.
4. **Соглашение о нумерации версии** (принимается как рабочее, не
   окончательное — можно пересмотреть после практики использования):
   третий (patch) сегмент версии по схеме `0.1.<номер тикета>` совпадает
   с номером тикета, в рамках которого было последнее изменение,
   затрагивающее клиентский код. Например, после реализации этого тикета
   — `0.1.124`. Негласное правило на будущее: каждый тикет, меняющий
   клиентский код, обновляет `package.json.version` на номер своего
   тикета. Не throw-away — если правило окажется неудобным на практике
   (например, для тикетов, не затрагивающих клиент, или при
   параллельной работе над несколькими тикетами), его можно
   скорректировать отдельным решением, не пересматривая остальную часть
   этой задачи.

## Definition of Done

- Необработанные исключения (ошибки рендера Vue, `window.onerror`,
  необработанные rejected promises) сохраняются в персистентный
  локальный лог вместе с предшествующими "хлебными крошками"
  (маршруты/экшены/вызовы Supabase) и номером версии приложения.
- Лог переживает отсутствие сети — запись работает полностью офлайн,
  накопленное позже (best-effort) отправляется в Supabase.
- Новая серверная таблица лога защищена RLS так, что пользователь может
  вставлять только собственные записи (не более широкая политика).
- Есть экран просмотра локального лога с возможностью поделиться его
  содержимым (Web Share API) или скопировать в буфер обмена.
- Лог не содержит токенов/паролей; решение о допустимости имён детей в
  логе явно задокументировано (не оставлено умолчанием "как получится").
- Номер версии приложения берётся из `package.json` без дублирования,
  виден в UI (экран About) и присутствует в каждой записи лога.
- Обновление версии при выпуске тикетов, затрагивающих клиент,
  задокументировано как рабочее соглашение (где именно — определяется
  при архитектурном планировании, например `CLAUDE.md` или
  `tickets/dashboard.md`).
