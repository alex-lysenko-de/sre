# Цель

Дать разработчикам инструмент для разбора клиентских ошибок без
выделенного backend-а: перехватывать необработанные исключения вместе с
контекстом, предшествующим им (маршруты, экшены сторов, уже существующие
`console.error`/`console.warn` во всех composables), сохранять это
локально (переживает офлайн) и по возможности догружать на сервер —
плюс дать пользователю и разработчику возможность в любой момент
проверить, с какой версией приложения он сейчас работает.

Явно вне цели этого тикета (зафиксировано в переписке до архитектурного
этапа, не пересматривается здесь): всплывающие toast-уведомления о
бизнес-событиях (пересчёт автобуса/группы завершён), push-уведомления,
двусторонние сообщения администратор↔бетройр. Схема данных этого тикета
проектируется так, чтобы не создавать связей с этими будущими
(пока не заведёнными) фичами — см. «Риски».

# Анализ текущей архитектуры

## Сегодняшнее состояние логирования

Логирования, переживающего перезагрузку страницы или недоступного
разработчику иначе как через devtools конкретного устройства, в проекте
нет. Единый, уже задокументированный паттерн (`vault/05-API-Composables/
Обзор-composables.md`): каждый composable оборачивает вызовы
`supabase.from(...)` в `try/catch`, делает `console.error(...)` и
перебрасывает `Error` дальше. Это верно для всех проверенных composables
(`useArmband.js`, `useChildren.js`, `useChildPresence.js`,
`useBusData.js`, `useGroups.js`, `useUser.js` и др.) — единообразие,
которое можно использовать: **если обернуть сам `console.error`/
`console.warn`, breadcrumb-покрытие всех уже существующих точек
логирования ошибок в проекте достаётся бесплатно, без изменения ни
одного из этих файлов.**

## Слои приложения, которые нужно затронуть для сбора контекста

- **Роутер** (`src/router/index.js`) — уже содержит единственный
  `router.beforeEach` с логикой аутентификации/авторизации. Точка для
  breadcrumb "переход на маршрут X" — одна дополнительная строка в начале
  существующего guard'а, без изменения его логики.
- **Pinia-сторы** (`src/stores/user.js`, `config.js`, `installPrompt.js`)
  — состояние приложения меняется через `actions`. Pinia поддерживает
  глобальные плагины (`pinia.use(plugin)`), которые могут подписаться на
  `store.$onAction(...)` для **любого** стора автоматически — не нужно
  вручную оборачивать действия в каждом сторе.
- **Необработанные исключения** — сегодня ничем не перехватываются:
  `app.config.errorHandler` (Vue) не установлен, `window.onerror`/
  `unhandledrejection` не слушаются.
- **`src/modules/storage.js`** — уже существующий прецедент отдельного
  named-instance LocalForage (`authLocalForage`, явно скоупнут в
  комментарии файла как "Auth-Daten"). Для лога нужен свой собственный
  instance, не подмешанный в этот — по той же причине, по которой
  auth-данные не должны разрастаться посторонним содержимым.
- **`vite.config.js`/`package.json`** — версия (`"version": "0.0.1"` в
  `package.json`) сегодня нигде не используется в рантайме и не
  прокидывается в клиентский бандл.
- **PWA автообновление уже есть** (`vite.config.js`:
  `VitePWA({ registerType: 'autoUpdate' })`, `src/main.js`:
  `registerSW({ onNeedRefresh() { ... updateSW(true) } })`) — механизм
  обновления не нужно строить заново, нужна только видимость текущей
  версии.
- **`InfoView.vue`** (маршрут `/info`) — проверено чтением файла: это не
  универсальный "About"-экран, а специализированный экран для случайного
  прохожего, нашедшего ребёнка ("Falls Sie ein Kind gefunden haben...").
  Смешивать номер версии туда — неверно по смыслу; нужен отдельный новый
  экран.
- **Модель ролей** — в `users.role` сегодня только `'admin'`/`'user'`
  (`stores/user.js`, `router/index.js`'s `requiresAdmin`). Отдельной роли
  "специалист/для отладки" не существует — упомянутая в обсуждении идея
  "видно только специалистам" в этом тикете не реализуется как отдельная
  роль (см. «Изменения БД» — решение сделать серверную таблицу лога
  нечитаемой из приложения вообще, не только для не-специалистов).
- **Гостевой режим** — `App.vue`/`router/index.js` уже поддерживают
  неаутентифицированных "гостей" (`isRegistered`/`session` может
  отсутствовать). Значит клиентский лог должен уметь писаться и без
  Supabase-сессии (`user_id` — nullable, см. «Изменения БД»), это не
  гипотетический, а уже существующий в проекте случай.
- **`users.id` (bigint) vs `users.user_id` (uuid)`** — та же развилка,
  что уже была явно учтена в 122 (`author_id`): `client_logs.user_id`
  должен ссылаться на `users.id`, а определяться на сервере из
  `auth.uid()` (uuid), не приниматься от клиента как есть.

# Новые компоненты

## `src/modules/clientLog.js`

Обычный JS-модуль (singleton), не Vue-composable и не Pinia-стор — по
образцу уже существующего `src/modules/storage.js` (тоже
module-level singleton, используется напрямую компонентами/сторами без
обёртки-composable). Ring-buffer breadcrumbs — состояние в замыкании
модуля, не реактивное (реактивность нужна только экрану просмотра, он
читает снимок массива при монтировании).

Отвечает за:
- Ring-buffer последних N (порядок величины 300) breadcrumb-записей в
  памяти: `{ ts, kind: 'route'|'action'|'console', ... }`.
- Регистрация обработчиков (`registerGlobalHandlers()`, вызывается один
  раз из `main.js`): `app.config.errorHandler`, `window.onerror`,
  `unhandledrejection`, патч `console.error`/`console.warn`.
- Pinia-плагин (`clientLogPiniaPlugin`) — на каждый `$onAction`
  добавляет breadcrumb с именем стора/экшена и (усечёнными/
  сериализуемыми) аргументами.
- При срабатывании необработанной ошибки — формирует запись-инцидент
  (текущий ring-buffer + сама ошибка + `APP_VERSION` из `src/version.js`
  + текущий маршрут) и сохраняет в собственный instance LocalForage
  (`localforage.createInstance({ name: 'sre-app', storeName: 'client_log' })`
  — свой store в том же LocalForage-namespace `sre-app`, что и
  `authLocalForage`, но не тот же store, см. «Анализ архитектуры»),
  список инцидентов — с жёстким верхним пределом (FIFO-вытеснение
  старых при переполнении).
- Best-effort отправка накопленных инцидентов на сервер: попытка сразу
  после сохранения нового инцидента + периодически + по событию
  `window.addEventListener('online', ...)`; неудача не блокирует
  ничего в приложении и не удаляет запись из LocalForage (следующая
  попытка позже).
- Публичное API для экрана лога: получить список локальных инцидентов,
  очистить их, собрать текстовое представление для `navigator.share()`/
  копирования в буфer.

Сознательно **не реализуется** в этом тикете (см. «Риски»): обёртка
самого `supabase.from(...)` для breadcrumb-логирования содержимого
каждого запроса/ответа — самый чувствительный, самый разделяемый модуль
проекта (`src/supabase.js`), трогать его ради дополнительного, не
обязательного для DoD, покрытия — риск несоразмерный пользе на этом
этапе.

## `src/version.js`

```
export const APP_VERSION = __APP_VERSION__
```

`__APP_VERSION__` — глобальная константа, определяемая `vite.config.js`
(`define`) из `package.json`. Используется и в `DiagnosticsView.vue`, и
в `clientLog.js` (штамп версии на каждой breadcrumb-записи/инциденте).

## `src/views/DiagnosticsView.vue`

Один новый экран (объединяет то, что 124.txt описывал как два разных
пункта — "About" и просмотр лога — в один, чтобы не плодить два новых
маршрута и два пункта меню ради, по сути, одного диагностического
назначения; 124.txt явно оставлял точку входа и содержимое экрана "вне
рамок задачи, определяется при реализации", это не отступление от
требований):

- Вверху — текущий номер версии приложения (`APP_VERSION`).
- Ниже — список локально сохранённых инцидентов (время, сообщение,
  разворачиваемый breadcrumb-трейл), кнопки "Teilen" (`navigator.share()`,
  где доступно) и "Kopieren" (буфer обмена, запасной вариант), кнопка

Маршрут — по аналогии с `/info`: `meta: { requiresAuth: false }` (не
обязательно логиниться, чтобы посмотреть версию/локальный лог этого
устройства).

# Изменения БД

Новая таблица `client_logs` (только для лога инцидентов — **не**
переиспользует и не связана со схемой `scan_packets`/`scans`, и не
закладывается заранее под отложенную идею toast/push/чат-сообщений,
см. «Риски»):

```sql
CREATE TABLE IF NOT EXISTS public.client_logs (
  id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
  client_log_id uuid NOT NULL,               -- сгенерирован на клиенте, якорь идемпотентности при повторной попытке отправки
  user_id bigint NULL REFERENCES public.users(id), -- перезаписывается триггером, NULL = гость (нет сессии)
  app_version text NOT NULL,
  occurred_at timestamptz NOT NULL,          -- клиентское время возникновения ошибки
  received_at timestamptz NOT NULL DEFAULT now(),
  route_path text NULL,
  message text NOT NULL,
  stack text NULL,
  breadcrumbs jsonb NOT NULL DEFAULT '[]'::jsonb,
  CONSTRAINT client_logs_pkey PRIMARY KEY (id),
  CONSTRAINT client_logs_client_log_id_key UNIQUE (client_log_id)
);

CREATE INDEX IF NOT EXISTS idx_client_logs_received_at ON public.client_logs(received_at);
```

Идентичность автора определяется сервером, не клиентом — тот же принцип,
что `author_id` в `submit_scan_packet()` (122), но здесь через триггер, а
не Edge Function (обоснование — см. «API изменения»):

```sql
CREATE OR REPLACE FUNCTION set_client_log_user_id()
RETURNS TRIGGER AS $$
BEGIN
  IF auth.uid() IS NULL THEN
    NEW.user_id := NULL; -- Gastmodus, keine Supabase-Auth-Session
  ELSE
    SELECT id INTO NEW.user_id FROM public.users WHERE user_id = auth.uid();
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER trg_set_client_log_user_id
  BEFORE INSERT ON public.client_logs
  FOR EACH ROW EXECUTE FUNCTION set_client_log_user_id();
```

`SECURITY DEFINER` — чтобы функция могла прочитать `users` независимо от
собственных прав вызывающей роли на эту таблицу; нужно проверить на
момент реализации, действительно ли это необходимо при текущих RLS
`users` (не проверено в рамках этого архитектурного прохода).

RLS:

```sql
ALTER TABLE public.client_logs ENABLE ROW LEVEL SECURITY;

CREATE POLICY "client_logs_insert_authenticated" ON public.client_logs
  FOR INSERT TO authenticated WITH CHECK (true);

CREATE POLICY "client_logs_insert_anon" ON public.client_logs
  FOR INSERT TO anon WITH CHECK (true);

-- Сознательно НЕТ SELECT-политики ни для authenticated, ни для anon:
-- никакой ролью из приложения строки не читаются вообще. Разработчики
-- читают лог напрямую через Supabase Studio/SQL (service_role, RLS не
-- применяется). Это проще и приватнее, чем вводить отдельную "роль
-- специалиста" ради экрана внутри приложения, которого DoD этого тикета
-- не требует (см. «Анализ текущей архитектуры», «Модель ролей»).
```

Применяется вручную через Supabase SQL Editor, по той же конвенции, что
`doc/db/scan_packets.sql`/`doc/db_triggers.sql` (в проекте нет папки
миграций) — `CREATE TABLE IF NOT EXISTS`, функция/триггер
пересоздаваемые, безопасно перезапускать.

# API изменения

Новых Edge Function/HTTP-эндпоинтов нет. Отправка — прямой
`supabase.from('client_logs').insert(...)` с текущим анонимным/
аутентифицированным клиентом, как обычные вызовы во всех composables
проекта.

Отличие от подхода 122 (`submit-scan-packet`, привилегированная Edge
Function) — осознанное и обоснованное: там Edge Function была нужна
из-за атомарной многотабличной записи (заголовок + результаты по детям
одной операцией) и бизнес-валидации. Здесь — одна таблица, одна
строка, а серверное определение автора решается дешевле — триггером
`BEFORE INSERT` плюс RLS. Заводить Edge Function только ради
переиспользования уже знакомого паттерна было бы неоправданным
усложнением best-effort, fire-and-forget записи диагностики.

   зафиксировать в `vault/`, не оставлять как "получилось само".

# Риски

- **Патч `console.error`/`console.warn`** — самое чувствительное
  изменение этого тикета: эти функции вызываются буквально из каждого
  composable проекта. Обязательное требование к реализации: оригинальная
  функция вызывается первой и без изменений; любая ошибка внутри
  дополнительной логики логирования перехватывается локально и никогда
  не долетает до вызывающего кода/консоли пользователя.
- **Неограниченный рост лога на длительной сессии** — приложение может
  оставаться открытым много часов/дней подряд (лагерная смена). И
  ring-buffer в памяти, и персистентный список инцидентов в LocalForage
  обязаны иметь жёсткий верхний предел с вытеснением старых записей —
  не факультативная оптимизация, а обязательное условие корректности.
- **Приватность/данные детей** — breadcrumbs с аргументами
  Pinia-действий могут содержать персональные данные (например,
  `saveChild(childData)` с именем ребёнка). Нужно осознанное, явно
  задокументированное решение о том, что усекается/маскируется перед
  сохранением, а не то, что случайно попало в сериализацию.
- **`SECURITY DEFINER`-функция `set_client_log_user_id()`** —
  необходимость именно `SECURITY DEFINER` (а не обычной функции) нужно
  подтвердить на реальных RLS-политиках `users` на момент реализации;
  архитектурный план фиксирует намерение, не проверенный факт.
- **Надёжность LocalForage на iOS** — тот же класс риска, что уже
  задокументирован для `authLocalForage` (тикеты 105/112): новый
  instance логов подвержен той же потенциальной ненадёжности
  локального хранилища на iOS PWA/Safari, отдельного решения в рамках
  этого тикета не предлагается.
- **Осознанно не реализуется в этом проходе**: обёртка `supabase.from()`
  для breadcrumb-логирования содержимого запросов (см. «Новые
  компоненты») — можно добавить позже отдельным шагом, если
  router+Pinia+перехваченные `console.error/warn` окажутся на практике
  недостаточными.
- **Границы с отложенной идеей сообщений/уведомлений** (см. «Цель») —
  схема `client_logs` намеренно не пересекается со `scan_packets`/
  `scans` и не проектируется как будущая таблица сообщений; если позже
  появится тикет на toast/push/чат, для него потребуется отдельная
  схема, а не расширение `client_logs`.

# Definition of Done

- Необработанные исключения (ошибки Vue, `window.onerror`,
  `unhandledrejection`) сохраняются локально вместе с предшествующими
  breadcrumbs (маршруты, Pinia-действия, перехваченные `console.error`/
  `console.warn` из уже существующих composables) и номером версии
  приложения — без изменения кода самих composables/сторов.
- Ring-buffer в памяти и персистентный список инцидентов в LocalForage
  оба ограничены по размеру (продемонстрировано на длительной сессии).
- Таблица `client_logs` создана; проверено вручную: `user_id`
  проставляется сервером через триггер (не из данных клиента), NULL для
  гостя; ни `authenticated`, ни `anon` не могут прочитать ни одной
  строки через обычный клиент (RLS).
- Локальные инциденты, накопленные офлайн, реально долетают до сервера
  после восстановления сети (best-effort, без блокировки других
  действий приложения).
- Номер версии берётся из `package.json` через `vite.config.js`
  (`define`), без ручного дублирования в нескольких местах, виден на
  новом экране `DiagnosticsView.vue` и присутствует в каждой
  сохранённой breadcrumb/инцидент-записи.
- Экран `DiagnosticsView.vue` доступен из меню, позволяет поделиться
  локальным логом (`navigator.share()` или копирование в буфer) и
  очистить его.
- В сохранённых breadcrumbs/инцидентах нет токенов/паролей; решение по
  именам детей явно принято и задокументировано.
- Проверено на реальном устройстве, включая офлайн→онлайн переход.
