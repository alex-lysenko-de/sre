# Тикет 121 — Research: архитектура серверной обработки пакетов сканирования

Это не план разработки (тикет 121 не содержит кода и не описывает
детальную техническую реализацию — по явному требованию `121.txt`). Это
документ архитектурного решения: рассмотренные варианты, их сравнение и
рекомендация — входные данные для `tickets/122/IMPLEMENTATION_PLAN.md`,
где рекомендованный здесь вариант получит детальную техническую
проработку (точные DDL, код Edge Function и т.д.).

# Контекст

Тикет 120 меняет клиентское поведение: вместо отдельных `INSERT` в
`scans` по каждому скану мобильное приложение копит результаты локально
и по кнопке «Отправить» отправляет один `PresencePacket` целиком (модель
зафиксирована в `tickets/120/DECISIONS.md`, п.1). Три подрежима — BUS,
GROUP, CHECKIN (см. `tickets/120/120.txt`). Серверная сверка (объединение
нескольких пересчётов, расхождения, отсутствующие, итоговый экран
Hauptbetreuer) **не входит** ни в 120, ни в 122 — вынесена в отдельный,
ещё не заведённый тикет (`DECISIONS.md`, п.2). Задача этого документа —
спроектировать только приём/хранение/идемпотентность пакетов так, чтобы
сверку можно было добавить позже без переделки схемы.

**Решение принято**: вариант A (раздел 3) с двумя оговорками,
согласованными отдельно от первой версии документа:

- Начиная с 120/122, `scans` пополняется **только** через пакеты — не
  останется сканеров/путей, кроме перечисленных в 120.txt, и каждый из
  них формирует пакет. «Голого» скана без пакета в системе не возникает.
  Отсюда — целевое ограничение `packet_id NOT NULL`, вводимое **позже**
  (раздел 9), а не в рамках самой миграции 122.
- Обязательна пакетная (не построчная) обработка триггеров при вставке
  результатов пакета — раздел 6.

# 1. Требования к новой серверной логике

Явно заданы `121.txt`, дополнены по итогам обсуждения:

- Пакет применяется **атомарно**: либо весь пакет (заголовок + все
  результаты по детям), либо ничего — частично применённого пакета быть
  не должно.
- Повторная отправка того же пакета (после потери ответа, обрыва сети)
  **идемпотентна** — не создаёт дубликатов и не искажает счётчики.
- `children_today`/`groups_today` и всё, что от них зависит
  (Kopfzählung, экраны групп/детей), продолжают корректно обновляться —
  новая логика не должна создавать второй, потенциально
  рассогласованный источник истины о присутствии.
- Обновление `children_today`/`groups_today` при вставке пакета должно
  происходить **пакетно**, а не по разу на каждого ребёнка — пакет по
  автобусу (35+ детей) не должен вызывать 35 отдельных каскадов
  пересчёта (раздел 6).
- Чувствительные поля (`author_id`) сервер определяет сам из
  аутентифицированной личности вызывающего, не доверяя телу запроса.
- Админ-интерфейс должен получить возможность видеть «кто/когда/что
  прислал» на уровне пакета, а не только на уровне отдельных сканов.
- Схема не должна исключать в будущем: (а) серверную сверку (раздел 12),
  (б) отмену последнего отправленного пакета, если это понадобится
  (раздел 10) — обе возможности не реализуются сейчас, но не должны
  требовать переделки уже принятой здесь схемы.

# 2. Анализ существующей архитектуры

- `scans` — append-only журнал (`id, created_at, date, user_id, child_id,
  band_id, bus_id, type`). Каждый `INSERT` синхронно триггерит
  `on_scan_insert` → upsert `children_today` (`presence_today`,
  `presence_now`, `bus_today`, `bus_now`, `presence_morning` — последнее
  пишется один раз и никогда не перезаписывается). `on_children_today_change`
  пересчитывает `groups_today` (`children_today`, `children_now`) полным
  `COUNT(*) FILTER` по группе.
- Оба триггера сегодня объявлены **построчно** (`FOR EACH ROW`) — это
  важно для раздела 6: при вставке N строк они срабатывают N раз, а не
  один.
- Вся бизнес-логика пересчёта живёт в БД (PL/pgSQL + триггеры), не в
  клиенте — устоявшийся принцип проекта (`vault/03-База-данных/Триггеры.md`).
  Ниже это не принимается как обязательное ограничение (см. требование
  121.txt не консервировать текущую архитектуру) — но при прочих равных
  вариант, не ломающий этот принцип, снижает риск.
- Записывают в `scans` сегодня: `useArmband.recordChildPresence()`
  (единичный скан) и `useScan.createScan()`. Оба — прямой `INSERT` через
  Supabase JS SDK, без Edge Function/RPC. После 120/122 оба пути
  заменяются пакетной отправкой (см. «Решение принято» выше) — это и
  есть основание для будущего `packet_id NOT NULL`.
- Единственные существующие Edge Functions (`auth`, `delete-user`,
  `invite-generate`, `invite-accept`) все работают с `auth.users`/
  `service_role` — ни одна не занимается бизнес-логикой сканов.
  Прецедента «Edge Function для обычной пользовательской записи» в
  проекте нет.
- `AdminBusView.vue` держит живую Realtime-подписку (`postgres_changes`)
  на `children_today` (весь стрим), `user_group_day` (по `day`) и
  `reset_events` (`INSERT`, по `day`) — см. `tickets/120/DECISIONS.md`, п.1.
- RLS — по ревью тикета 108 (`RLS-политики.md`) для `children_today`,
  `groups_today`, `reset_events`, `children` рядом с корректными узкими
  политиками остались широкие legacy-политики `USING(true) TO authenticated`,
  которые благодаря OR-семантике PostgreSQL сводят реальное ограничение
  доступа к «любой authenticated». Действующая проблема — важно **не
  повторить** её для новых таблиц.

# 3. Варианты хранения пакетов и результатов сканирования

По требованию 121.txt существующая модель (`scans`) не считается
обязательной основой — ниже три реалистичных варианта на равных
основаниях.

## Вариант A — новая таблица-заголовок + переиспользование `scans`

Идея: добавить таблицу-заголовок пакета (id, `client_packet_id`, тип,
`author_id`, `bus_id`/`group_id`, `date`, время начала/конца,
`children_count`). Существующая `scans` дополняется ссылкой на пакет и
полем способа получения результата (скан/ручная отметка). Каждый
результат внутри пакета — обычная строка `scans`, как и сегодня.

- **Плюсы**: `children_today`/`groups_today` продолжают обновляться уже
  существующими, проверенными триггерами без единой строчки новой
  бизнес-логики пересчёта — риск рассинхронизации минимален. Миграция
  обратно совместима (новые колонки nullable на переходный период —
  см. раздел 9). История отдельных сканов (когда именно отсканирован
  конкретный ребёнок) сохраняется на прежнем уровне детализации.
- **Минусы**: `scans` приобретает два смысла одновременно — «единичное
  событие сканирования» и «строка внутри пакета» — до момента, пока
  пакет не станет единственным источником (раздел 9), когда это
  фактически станет одним смыслом.
- **Риск (принят к устранению, не оставлен как есть)**: без изменений
  триггер `on_scan_insert` выполняется N раз за пакет (по разу на
  ребёнка) — для автобуса с 35+ детьми это 35 каскадов пересчёта на один
  «Отправить». Это неприемлемо и требует пакетной переработки триггеров
  — решение см. раздел 6; без него вариант A принимать нельзя.
- **Влияние на существующее**: `HeadcountView`, `ChildrenView`, `useGroups`
  — без изменений. `AdminBusView` может делать точечный запрос к таблице
  заголовков вместо агрегации по `scans`.

## Вариант B — полностью отдельная модель (заголовок + дочерние строки), `scans` не трогается

Идея: новая пара таблиц (заголовок пакета + дочерние результаты внутри
пакета), независимая от `scans`.

- **Плюсы**: `scans` и всё, что от неё зависит, гарантированно не
  затрагивается вообще. Чистое концептуальное разделение «сырое событие»
  vs «пакет».
- **Минусы**: `children_today`/`groups_today` перестают обновляться
  автоматически для данных из пакетов — нужно либо продублировать логику
  `on_scan_insert`/`on_children_today_change` для новых таблиц, либо
  вызывать её вручную из серверного кода приёма пакета. Проблема N-кратных
  каскадов (см. вариант A) здесь тоже присутствует и тоже требует
  пакетной обработки — просто в заново написанной логике, а не в
  существующей.
- **Риски**: два независимых места, где нужно поддерживать одну и ту же
  бизнес-логику пересчёта присутствия — существенно повышает вероятность
  их расхождения со временем.
- **Влияние на существующее**: минимальное на `scans`-потребителей, но
  максимальное на разработку 122 — почти вся логика пересчёта
  присутствия пишется заново.

## Вариант C — пакет как единый документ (JSONB), без нормализации в строки

Идея: одна таблица пакетов, где результаты по детям хранятся не
отдельными строками, а одним JSONB-полем внутри строки заголовка.

- **Плюсы**: минимальная схема (одна новая таблица, `scans` не меняется
  вовсе), вставка пакета — вставка одной строки; побочный эффект —
  проблема N-кратных триггеров варианта A здесь **не возникает вовсе**
  (вставляется всегда одна строка заголовка, `children_today` пересчитать
  можно одним пакетным проходом внутри одного нового триггера).
- **Минусы**: теряется построчная гранулярность `scans` (запросы вида
  «когда именно отсканирован ребёнок X» требуют разбора JSONB по всем
  пакетам, без пригодного индекса, аналогичного текущему
  `idx_scans_child_date`). Обновление `children_today`/`groups_today`
  всё равно требует новой логики, разворачивающей JSONB-массив — то есть
  дублирования той же бизнес-логики, что и в варианте B, только в другой
  форме.
- **Риски**: нарушает устоявшуюся конвенцию «одна строка `scans` = одно
  событие сканирования», на которую неявно может полагаться другой код
  или будущие отчёты.
- **Влияние на существующее**: похоже на вариант B по объёму новой
  логики пересчёта, но с дополнительной потерей детализации истории.

## Сравнение

| Критерий | A: заголовок + `scans` | B: отдельные таблицы | C: JSONB-документ |
|---|---|---|---|
| Риск рассинхронизации `children_today`/`groups_today` | Минимальный (триггеры не меняются по сути, только по гранулярности вызова — раздел 6) | Высокий (логика дублируется) | Высокий (логика дублируется) |
| N-кратные каскады триггеров на пакет | Есть, требует явного устранения (раздел 6) | Есть, требует явного устранения (в новой логике) | Не возникает (один пакет = одна строка) |
| Размер миграции/новой логики для 122 | Малый + переработка 2 триггеров (раздел 6) | Большой | Средний, но с новой PL/pgSQL-логикой |
| Гранулярность истории сканов | Сохранена | Сохранена (для не-пакетных) | Потеряна |
| Атомарность вставки | Один составной оператор (раздел 5) | Один составной оператор | Тривиальна (одна строка) |

## Рекомендация

**Вариант A**, с обязательным устранением N-кратных каскадов (раздел 6)
как частью, а не факультативным дополнением решения. Он единственный не
создаёт второй источник истины для пересчёта присутствия — это
перевешивает более чистую изоляцию вариантов B/C, поскольку
`children_today`/`groups_today` являются данными, от которых напрямую
зависит корректность работы уже существующих и активно используемых
экранов (Kopfzählung, группы, автобусы). Смешение смысла колонок `scans`
(минус варианта A) — управляемый, временный (раздел 9) недостаток; риск
рассинхронизации бизнес-логики (минус B/C) — нет. Вариант C был бы
привлекателен именно отсутствием проблемы N-кратных каскадов, но
проигрывает по гранулярности истории и всё равно требует новой
пересчётной логики — то же усилие, что и устранение каскадов в
варианте A (раздел 6), но с потерями, которых у варианта A нет.

# 4. Нужна ли сущность ScanPacket (заголовок пакета)

Альтернатива заголовку — не заводить отдельную сущность вовсе, а
хранить метаданные пакета (client_packet_id, время, тип, bus/group)
продублированными на каждой дочерней строке `scans`.

- **Без заголовка**: невозможна атомарная проверка идемпотентности до
  вставки дочерних строк — уникальность `client_packet_id` пришлось бы
  проверять по агрегату из потенциально ещё не существующих строк, а
  пустой пакет (0 детей) вообще не оставил бы следа для дедупликации.
  Запрос «сколько пакетов получено по автобусу №2 сегодня» требовал бы
  `GROUP BY` по `scans` при каждом обращении вместо чтения одной таблицы.
  Отмена пакета (раздел 10) тоже стала бы невозможной без заголовка —
  нечего было бы помечать отменённым.
- **С заголовком** (рекомендуется, согласуется с вариантом A раздела 3):
  идемпотентность проверяется одним `SELECT` по независимой от
  количества детей строке; пакетно-ориентированные запросы и будущая
  отмена пакета становятся прямыми, без агрегации по `scans`.

Вывод: сущность ScanPacket нужна.

# 5. Приём и интерпретация пакета сервером

Два реалистичных варианта точки входа.

## Вариант 1 — PL/pgSQL RPC-функция

- **Плюсы**: атомарность многострочной вставки — встроенное свойство
  функции/транзакции в Postgres, без дополнительных ухищрений.
- **Минусы**: PL/pgSQL менее привычен команде, чем TypeScript; в проекте
  нет прецедента такого объёма бизнес-логики в хранимой функции (только
  триггеры).
- **Риски/влияние**: сложнее unit-тестировать логику валидации пакета
  изолированно от БД.

## Вариант 2 — новая Edge Function (`submit-scan-packet`)

- **Плюсы**: прямой прецедент в проекте — `delete-user`/`invite-generate`
  уже используют привилегированный `service_role`-клиент с проверкой
  личности/роли вызывающего по `Authorization`-токену в TypeScript, а не
  через RLS. TypeScript/Deno привычнее команде. Задел на будущее — если
  сверке (раздел 12) понадобятся внешние вызовы, Edge Function не нужно
  будет вводить заново.
- **Минусы**: атомарность многотабличной вставки не даётся бесплатно —
  требует одного составного SQL-оператора вместо нескольких
  последовательных вызовов через SDK. Технически решаемо, но требует
  аккуратности при реализации в 122.
- **Риски/влияние**: минимальны при соблюдении «один оператор — вся
  вставка».

## Важное уточнение: выбор между RPC и Edge Function не решает проблему N-кратных триггеров

Оба варианта одинаково подвержены проблеме раздела 6 и одинаково от неё
избавляются: количество срабатываний триггера — свойство самого
триггера (`FOR EACH ROW` vs `FOR EACH STATEMENT`) и того, вставляются ли
все строки пакета одним SQL-оператором, а не свойство того, что именно
инициировало этот оператор — Edge Function или RPC-функция. Поэтому
выбор в пользу Edge Function (ниже) не нужно пересматривать из-за
проблемы триггеров — она решается отдельно, на уровне схемы (раздел 6),
и одинаково применима к обоим вариантам приёма.

## Решение (согласовано с пользователем)

**Edge Function `submit-scan-packet`.** Обоснование: переиспользование
уже принятого в проекте паттерна привилегированного кода с проверкой
токена, привычность TypeScript команде, задел на будущие внешние вызовы.
Атомарность обеспечивается одним составным оператором вставки заголовка
и дочерних результатов (деталь реализации — в 122).

# 6. Пакетная (batch) обработка триггеров — устранение N-кратного срабатывания

Проблема поднята отдельно от выбора хранения: при вставке пакета с
35+ детьми (автобус) построчный триггер `on_scan_insert` (раздел 2)
сработает 35 раз, каждый раз делая upsert `children_today`, что
дополнительно 35 раз (или меньше, если несколько детей — из одной
группы) вызывает построчный `on_children_today_change` с полным
пересчётом `groups_today`. Один «Отправить» — потенциально десятки
избыточных кас­кадов вместо одного.

**Не устраняется выбором Edge Function vs RPC** (раздел 5) — оба
инициируют один и тот же `INSERT` в `scans`, а срабатывание триггера
зависит только от того, как объявлен сам триггер.

**Решение — перевести оба триггера с построчных (`FOR EACH ROW`) на
постатементные (`FOR EACH STATEMENT`) с доступом ко всем вставленным
строкам сразу (механизм transition tables, доступен в Postgres, начиная
с версии 10).** Смысл: если весь пакет вставляется одним SQL-оператором
(это уже требование атомарности, раздел 5) — постатементный триггер
сработает **один раз на весь пакет**, получит все вставленные строки
целиком и сможет сделать один пакетный `UPSERT` в `children_today`
вместо N отдельных. Аналогично `groups_today` пересчитывается не по
разу на ребёнка, а по разу на каждую **отличную** затронутую группу
(для одного автобуса — обычно одна, максимум несколько групп) — тоже
кратное сокращение по сравнению с N.

Рассматривался и отклонён более грубый обходной путь — временное
отключение триггеров на время вставки (например, через параметр сессии,
подавляющий срабатывание всех триггеров). Отклонён: действует на уровне
всей сессии/операции, а не точечно на нужный триггер, легко забыть
включить обратно, и подавляет заодно любые другие триггеры на тех же
таблицах — структурно более рискованный вариант, чем целевая переработка
конкретных двух триггеров.

Эта переработка нужна **независимо от того, какой вариант хранения
выбран** (раздел 3) — при вариантах B/C та же по сути логика просто
пишется заново, а не переиспользуется из существующих триггеров.
Единственный вариант, где проблема не возникает по построению — C
(раздел 3), но он отклонён по другим причинам.

Для потребителей `children_today`/`groups_today` эта переработка
**незаметна** — меняется количество срабатываний триггера и его
объявление, а не набор колонок или итоговые значения; `HeadcountView`,
`ChildrenView`, `useGroups` не нуждаются в изменениях.

# 7. Формат пакета — предлагаемые уточнения формата из тикета 120

Тикету 121 явно разрешено пересматривать формат из 120.txt. Предлагаю
**сохранить форму** `PresencePacket { type, author_id, started_at,
finished_at, children[] }` и **добавить**:

| Поле | Где | Зачем |
|---|---|---|
| `client_packet_id` (UUID) | корень пакета | Идемпотентность повторной отправки (раздел 8) — в 120.txt отсутствует вовсе, без него нет способа отличить ретрай от нового пакета. |
| `date` (`YYYY-MM-DD`) | корень пакета | Совпадает с существующей конвенцией `scans.date` — фильтрация «пакеты за сегодня» без приведения `timestamptz→date` на каждый запрос. |
| `method` (`SCAN`\|`MANUAL`) | у каждого ребёнка, всегда | В 120.txt `method` упомянут явно только в примере Режима 2 (группа), но уже перечислен как общее поле в структуре `PresencePacket` — закрепляю как обязательное для всех трёх типов пакетов (для BUS/CHECKIN всегда `SCAN`). |

Остальное — `bus_id` для BUS, `group_id` для GROUP — без изменений, как
в 120.txt.

**`author_id`, присланный клиентом, сервер игнорирует.** Если сервер
доверится этому полю пакета, любой пользователь сможет отправить пакет
от чужого имени. Сервер обязан подставлять `author_id` из
аутентифицированной личности вызывающего самостоятельно, а присланное
клиентом значение — игнорировать (или использовать только для сверки:
несовпадение = отказ, не подмена).

# 8. Идемпотентность и повторная отправка

Рассматривался альтернативный подход — дедупликация по хэшу содержимого
пакета вместо клиентского `client_packet_id`. Отклонён: хэш содержимого
не отличает намеренный повторный пакет от ретрая после сбоя, а
`client_packet_id`, генерируемый клиентом один раз на попытку отправки,
различает их правильно и является стандартным решением для этой задачи.

**Выбранный подход**: `client_packet_id` — уникальный на стороне БД.
Перед вставкой — проверка существования пакета с этим id:

- Найден → пакет уже обработан (ретрай после потерянного ответа) →
  возвращается тот же результат, ничего не создаётся заново.
- Не найден → выполняется вставка заголовка и всех дочерних результатов
  одним составным оператором. Если оператор падает — откатывается
  целиком, включая заголовок; `client_packet_id` не считается «занятым»,
  повторный вызов после исправления данных отработает как первая
  попытка.

**Повтор одного и того же ребёнка внутри одного пакета** специально
**не блокируется на сервере** — `scans` append-only, `on_scan_insert` и
так идемпотентно обновляет `children_today` через `ON CONFLICT`, а для
BUS-режима расчёт актуального автобуса и так берёт «последний скан»
(`useScan.getChildBusForToday`). Дедуп внутри пакета — ответственность
клиентского слоя режима (уже решено на уровне тикета 116/120).

# 9. Структура данных (описание, без DDL — детали в 122)

Заголовок пакета (новая сущность, раздел 4): идентификатор,
`client_packet_id` (уникален), тип пакета, `author_id`, `bus_id`/
`group_id` (в зависимости от типа), `date`, время начала/окончания
сбора, время получения сервером, количество результатов, **время
отмены** (нужно для раздела 10 — nullable, заполняется только если
пакет отменён).

Изменения существующей `scans` (вариант A, раздел 3): добавляется ссылка
на заголовок пакета и поле способа получения результата (скан/ручная
отметка).

**Переходный период vs целевое состояние для `packet_id`.** На момент
миграции 122 колонка должна остаться nullable — если в 122 сохранится
хоть один путь единичной вставки без пакета (например, код 120 ещё не
полностью выкатан). Целевое состояние, зафиксированное решением в начале
документа: как только все сканы гарантированно приходят через пакет,
`packet_id` переводится в `NOT NULL` — отдельным, последующим шагом
(не в рамках 122), формализующим уже действующий на практике инвариант.
До этого момента инвариант не гарантирован схемой, только соглашением
на уровне кода — это стоит явно держать в уме при ревью 122.

RLS для заголовка пакета: только чтение для аутентифицированных
пользователей (свой пакет или admin); прямая запись от имени обычной
роли не разрешается вовсе — запись только через `service_role` внутри
Edge Function (раздел 5), которая сама проверяет личность вызывающего.
Это осознанно строже действующей практики проекта (предупреждение в
разделе 2 про legacy-permissive-политики).

# 10. Расширяемость — отмена последнего пакета

Не требуется для 122, но схема не должна её исключать — рассмотрено по
запросу.

Идея: у автора пакета появляется возможность отменить последний
отправленный им пакет (например, ошибочно указан не тот автобус).

**Совместимость с append-only `scans`.** Удаление строк `scans`
недопустимо — append-only является действующей конвенцией проекта
(раздел 2). Поэтому отмена не может означать «удалить строки»; она должна
означать «пометить заголовок пакета отменённым» (поле `cancelled_at`,
раздел 9) — сами строки `scans` остаются в истории как есть.

**Что это меняет в пересчёте.** Раздел 6 предполагает пакетный upsert
`children_today` на основе вставленных строк. Если отмена пакета когда-
либо будет реализована, логика «текущее присутствие ребёнка» должна
брать «последний **не отменённый** результат», а не просто «последний
результат» — то есть учитывать статус пакета (через `packet_id`) при
определении, какая строка `scans` актуальна. Это не требует новой
колонки на самих строках `scans` — достаточно join к заголовку пакета
по `packet_id`.

**Почему это дёшево уже сейчас.** Раз каждая строка `scans` уже
ссылается на `packet_id` (вариант A, раздел 3), а заголовок пакета уже
существует как отдельная сущность (раздел 4) — отмена не требует новой
таблицы или связи, только: (а) поле `cancelled_at` в заголовке (уже
добавлено в раздел 9 заранее), (б) правило учёта статуса пакета в
пересчёте (раздел 6), когда/если
функция отмены будет реализована. Сама функция (эндпоинт «отменить
последний пакет», логика пересчёта после отмены) — не проектируется
здесь, это задача отдельного будущего тикета при необходимости.

# 11. Влияние на существующие компоненты и экраны администратора

- **Триггеры `on_scan_insert`/`on_children_today_change`** — меняется
  гранулярность срабатывания (раздел 6), но не итоговый результат
  пересчёта — для потребителей (`HeadcountView`, `ChildrenView`,
  `useGroups`) это не видно.
- **`AdminBusView.vue`** — требует переработки (объём зафиксирован в
  `tickets/120/DECISIONS.md`, реализуется в 122 вместе с серверной
  частью, см. `122.txt`, раздел «UI главного администратора»):
  - Существующая Realtime-подписка на `children_today`/`user_group_day`/
    `reset_events` формально продолжит работать, но перестанет быть
    осмысленной как «живой» индикатор — числа будут скачками меняться в
    момент отправки пакета, а не по одному скану.
  - Нужен новый источник для «кто что прислал»: запрос к заголовкам
    пакетов (по дате+автобусу/группе) — список пакетов с автором,
    временем, количеством результатов, статусом отмены (раздел 10).
  - Сама реализация экрана — за рамками этого документа, решается в 122.
- При выборе варианта B или C (раздел 3) влияние на `AdminBusView` было
  бы тем же по объёму, но потребовало бы дополнительно проверять
  корректность новой, независимой логики пересчёта присутствия.

# 12. Вне рамок этого документа (сознательно)

Соответствует `tickets/120/DECISIONS.md`, п.2 — не проектируется здесь:

- Объединение нескольких пересчётов одного автобуса/группы, выявление
  расхождений, вычисление отсутствующих.
- Итоговый экран для Hauptbetreuer.
- Сама функция отмены пакета (раздел 10) — только совместимость схемы с
  её будущим добавлением.
- Перевод `packet_id` в `NOT NULL` (раздел 9) — целевое состояние,
  формализуется отдельным шагом после полного перехода на пакетную
  отправку.

Хранение спроектировано так, чтобы всё перечисленное можно было добавить
позже без изменения уже описанной здесь схемы.

# 14. Перечень изменений для тикета 122

1. Миграция: новая сущность-заголовок пакета, включая поле отмены
   (раздел 4, 9, 10), новые поля в `scans` (nullable, раздел 9), индексы
   под пакетные запросы, RLS (раздел 9) — точные DDL прорабатываются в
   122.
2. Переработать `on_scan_insert` и `on_children_today_change` с
   построчных на постатементные (transition tables) — раздел 6. Это
   отдельная, обязательная часть миграции, не факультативная оптимизация.
3. Реализовать Edge Function `submit-scan-packet` (раздел 5, 8) —
   проверка токена, идемпотентность, один атомарный составной оператор
   вставки.
4. Переработать клиентский слой отправки пакета (тикет 120) под
   финальный формат (раздел 7) — согласовать с планом 120 конкретные
   имена полей.
5. Переработать `AdminBusView.vue` — новый запрос к заголовкам пакетов
   (раздел 11), пересмотр смысла Realtime-индикатора.
6. Проверить остальные экраны, читающие `scans`/`children_today`/
   `groups_today` (`ChildrenView`, `HeadcountView`, история сканов
   ребёнка) — по разделу 11 изменений не требуется, но нужна ручная
   регрессионная проверка после миграции (особенно после переработки
   триггеров, п.2).
7. Не входит в 122, зафиксировать как известный следующий шаг: перевод
   `packet_id` в `NOT NULL` (раздел 9) после подтверждения, что все
   пути записи в `scans` идут через пакет; реализация отмены пакета
   (раздел 10), если понадобится.
