# Тикет 121 — Research: архитектура серверной обработки пакетов сканирования

Это не план разработки в обычном смысле (тикет 121 не содержит кода) —
это результат исследования, который сам является входными данными для
`tickets/122/IMPLEMENTATION_PLAN.md`. Структура документа следует не
стандартным 11 секциям архитектора, а перечню задач исследования из
`tickets/121/121.txt`.

# Контекст

Тикет 120 меняет клиентское поведение: вместо отдельных `INSERT` в
`scans` по каждому скану мобильное приложение копит результаты локально
и по кнопке «Отправить» отправляет один `PresencePacket` целиком (модель
зафиксирована в `tickets/120/DECISIONS.md`, п.1). Три подрежима — BUS,
GROUP, CHECKIN (см. `tickets/120/120.txt`). Серверная сверка
(объединение нескольких пересчётов, расхождения, отсутствующие,
итоговый экран Hauptbetreuer) **не входит** ни в 120, ни в 122 — вынесена
в отдельный, ещё не заведённый тикет (`DECISIONS.md`, п.2). Задача этого
документа — спроектировать только приём/хранение/идемпотентность
пакетов так, чтобы сверку можно было добавить позже без переделки схемы.

# 1. Анализ существующей архитектуры

- `scans` — append-only журнал (`id, created_at, date, user_id, child_id,
  band_id, bus_id, type`). Каждый `INSERT` синхронно триггерит
  `on_scan_insert` → upsert `children_today` (`presence_today`,
  `presence_now`, `bus_today`, `bus_now`, `presence_morning` — последнее
  пишется один раз и никогда не перезаписывается). `on_children_today_change`
  пересчитывает `groups_today` (`children_today`, `children_now`) полным
  `COUNT(*) FILTER` по группе.
- Вся бизнес-логика пересчёта живёт в БД (PL/pgSQL + триггеры), не в
  клиенте — это явный, устоявшийся принцип проекта (`vault/03-База-данных/Триггеры.md`),
  и предлагаемая ниже архитектура ему следует, а не вводит новый паттерн.
- Записывают в `scans` сегодня: `useArmband.recordChildPresence()`
  (единичный скан) и `useScan.createScan()` (используется реже). Оба —
  прямой `INSERT` через Supabase JS SDK, без Edge Function/RPC.
- Единственные существующие Edge Functions (`auth`, `delete-user`,
  `invite-generate`, `invite-accept`) все работают с `auth.users`/`service_role`
  — ни одна не занимается бизнес-логикой сканов. Прецедента «Edge Function
  для обычной пользовательской записи» в проекте нет.
- `AdminBusView.vue` держит живую Realtime-подписку (`postgres_changes`)
  на `children_today` (весь стрим), `user_group_day` (по `day`) и
  `reset_events` (`INSERT`, по `day`) — см. `tickets/120/DECISIONS.md`, п.1,
  «известное следствие».
- RLS — по ревью тикета 108 (`RLS-политики.md`) для `children_today`,
  `groups_today`, `reset_events`, `children` рядом с корректными узкими
  политиками остались широкие legacy-политики `USING(true) TO authenticated`,
  которые благодаря OR-семантике PostgreSQL сводят реальное ограничение
  доступа к «любой authenticated». Это действующая проблема, не гипотеза —
  важно **не повторить** её для новых таблиц.

# 2. Приём и интерпретация пакетов сервером

**Решение (подтверждено пользователем — см. раздел 10): новая Edge
Function `submit-scan-packet`, не PL/pgSQL RPC.**

Обоснование выбора Edge Function:

- Прецедент такого паттерна в проекте уже есть — `delete-user` и
  `invite-generate` тоже привилегированный код (`service_role`-клиент),
  который сам проверяет личность/роль вызывающего по `Authorization`-
  токену в TypeScript, а не полагается на RLS. `submit-scan-packet`
  делает то же самое: не новый паттерн для проекта, а переиспользование
  уже принятого.
- TypeScript/Deno привычнее команде, чем PL/pgSQL — проще писать и
  тестировать логику валидации пакета.
- Задел на будущее (сверка/уведомления, вынесенные за рамки 120/122,
  раздел 9) — если там понадобятся внешние вызовы, Edge Function не
  придётся вводить заново.

**Атомарность без PL/pgSQL-функции.** Заголовок пакета + N строк `scans`
всё равно должны создаваться одной транзакцией (раздел 6) — просто
несколько последовательных `INSERT` через PostgREST/JS SDK внутри Edge
Function эту гарантию не даёт (сеть/ошибка между вызовами оставит
частично вставленный пакет). Решение: Edge Function не делает N+1
отдельных запросов, а отправляет **один SQL-оператор** — `INSERT INTO
scan_packets ... RETURNING id`, объединённый через CTE с `INSERT INTO
scans (...) SELECT ... FROM jsonb_array_elements($1) JOIN <id пакета>`.
Один SQL-оператор атомарен в Postgres сам по себе, без явного
`BEGIN`/`COMMIT` и без PL/pgSQL-обёртки — Edge Function собирает этот
SQL (или вызывает его через `service_role`-клиент как один `rpc()`/
`sql()`-вызов), а вся валидация/резолюция `author_id` остаётся в
TypeScript-коде функции, как и хотелось.

Каждая вставка в `scans` внутри этого оператора всё равно проходит через
существующий `on_scan_insert` как обычный `INSERT` — `children_today`/
`groups_today` обновляются без каких-либо изменений в триггерах
(это решение не зависит от выбора RPC/Edge Function, см. раздел 4).

# 3. Формат пакета — предлагаемые уточнения формата из тикета 120

Тикету 121 явно разрешено пересматривать формат из 120.txt. Предлагаю
**сохранить форму** `PresencePacket { type, author_id, started_at,
finished_at, children[] }` и **добавить**:

| Поле | Где | Зачем |
|---|---|---|
| `client_packet_id` (UUID) | корень пакета | Идемпотентность повторной отправки (раздел 6) — в 120.txt отсутствует вовсе, без него нет способа отличить ретрай от нового пакета. |
| `date` (`YYYY-MM-DD`) | корень пакета | Совпадает с существующей конвенцией `scans.date` — фильтрация «пакеты за сегодня» без приведения `timestamptz→date` на каждый запрос (см. `idx_scans_child_date`). |
| `method` (`SCAN`\|`MANUAL`) | у каждого ребёнка, всегда | В 120.txt `method` явно упомянут только в примере Режима 2 (группа); в разделе «Presence Packet» (общая структура) он уже перечислен как общее поле для всех детей — просто закрепляю это как обязательное для всех трёх типов пакетов (для BUS/CHECKIN всегда `SCAN`, поле не лишнее — дешевле, чем два разных формата строки). |

Остальное — `bus_id` для BUS, `group_id` для GROUP — без изменений, как
в 120.txt.

**`author_id`, присланный клиентом, сервер игнорирует.** В 120.txt
`author_id` — поле пакета, как если бы клиент его указывал. Если
функция доверится этому полю, любой пользователь сможет отправить пакет
от чужого имени. RPC должен подставлять `author_id` из `auth.uid()`
(→ `users.id`) самостоятельно, а присланное клиентом значение —
игнорировать или использовать только для валидации (несовпадение = отказ,
не подмена). Это не изменение формата, а уточнение семантики поля,
важное закрепить явно, раз оно нигде пока не описано.

# 4. Изменения БД

Новая таблица-заголовок пакета:

```sql
create table public.scan_packets (
  id bigint generated by default as identity primary key,
  client_packet_id uuid not null,
  type smallint not null,        -- 1=BUS, 2=GROUP, 3=CHECKIN
  author_id bigint not null references users(id),
  bus_id smallint null,          -- только для type=BUS
  group_id smallint null,        -- только для type=GROUP
  date character varying not null,     -- 'YYYY-MM-DD', как scans.date
  started_at timestamptz not null,
  finished_at timestamptz not null,
  received_at timestamptz not null default now(),
  children_count smallint not null default 0,
  constraint scan_packets_client_packet_id_key unique (client_packet_id)
);

create index idx_scan_packets_date_type on scan_packets(date, type);
create index idx_scan_packets_bus on scan_packets(bus_id) where bus_id is not null;
create index idx_scan_packets_group on scan_packets(group_id) where group_id is not null;
```

Изменения существующей `scans` (обратно совместимые — новые колонки
nullable, старые единичные вставки продолжают работать без изменений):

```sql
alter table public.scans
  add column packet_id bigint null references scan_packets(id),
  add column method smallint null default 1;  -- 1=SCAN, 2=MANUAL

create index idx_scans_packet_id on scans(packet_id) where packet_id is not null;
```

**Почему не отдельная таблица `scan_packet_children` вместо переиспользования `scans`:**
рассматривался вариант с полностью отдельной моделью (`scan_packets` +
`scan_packet_children`), не трогающей `scans`. Отклонён: тогда
`children_today`/`groups_today` не обновлялись бы существующими
триггерами автоматически — пришлось бы либо дублировать в них логику
`on_scan_insert`, либо вызывать её вручную, что удваивает
поверхность для рассинхронизации. Переиспользование `scans` с
добавлением `packet_id`/`method` даёт корректное обновление
`children_today`/`groups_today` **бесплатно**, через уже существующие,
проверенные триггеры — минимальный по площади и самый безопасный
вариант из рассмотренных.

**RLS** для `scan_packets`: только `SELECT` для `authenticated` (свой
пакет или admin — по аналогии с `own_group_*`, см. раздел 7); **прямой
`INSERT`/`UPDATE` от имени обычной роли (`authenticated`) не
разрешается вовсе** — запись происходит только через
`service_role`-клиент внутри Edge Function `submit-scan-packet` (раздел
2), которая сама проверяет личность вызывающего по `Authorization`-
токену (как уже делают `delete-user`/`invite-generate`), а не полагается
на RLS-политику `authenticated`-роли. Это осознанно строже, чем текущая
практика проекта — см. предупреждение в разделе 1 про
legacy-permissive-политики: для новой таблицы полностью исключаем саму
возможность повторить ту же ошибку (никакой политики вида `INSERT ...
TO authenticated USING (true)` для `scan_packets`/новых колонок `scans`
не заводится в принципе), а не полагаемся на то, что узкая политика
«победит» в OR-объединении.

# 5. `ScanPacket` как сущность — нужна

Обоснование см. разделы 2 и 4: без заголовка невозможны ни атомарная
проверка идемпотентности до вставки строк `scans` (нужен `UNIQUE
(client_packet_id)` на что-то, что существует независимо от количества
детей в пакете, в том числе для пустого/нулевого пакета), ни
пакетно-ориентированные запросы для будущего UI администратора
(«сколько пакетов получено по автобусу №2 сегодня») без `GROUP BY`
по `scans`.

# 6. Повторная отправка, идемпотентность

Edge Function `submit-scan-packet`:

1. Проверяет `Authorization`-токен вызывающего через `service_role`-
   клиент (как `delete-user`/`invite-generate`) и резолвит `author_id`
   из него (раздел 3) — не из тела запроса.
2. Проверяет: есть ли уже `scan_packets` с этим `client_packet_id`
   (обычный `SELECT` перед вставкой)?
   - Да → пакет уже обработан (это ретрай после потерянного ответа) →
     возвращает тот же результат (id существующего пакета,
     `children_count`), **не создавая ничего заново**. Идемпотентно по
     определению — за счёт `UNIQUE (client_packet_id)` + проверки перед
     вставкой, без отдельного «дедуп-кэша».
   - Нет → продолжает.
3. Выполняет **один** SQL-оператор (раздел 2, CTE-вставка): создаёт
   строку `scan_packets`, затем N строк `scans` (`packet_id` = id только
   что созданного пакета, `method` из данных ребёнка) — атомарно, как
   один statement. Каждая вставка в `scans` естественно прогоняет
   `on_scan_insert` как обычно.
4. Если оператор падает (constraint violation, невалидный `child_id` и
   т.п.) — **весь оператор откатывается целиком, включая строку
   `scan_packets`** (атомарность одного SQL-statement в Postgres).
   `client_packet_id` не считается «занятым» — легитимный повторный
   вызов с тем же `client_packet_id` после исправления данных отработает
   как первая попытка. Специального кода на откат не требуется.

**Повтор одного и того же ребёнка внутри одного пакета** (например,
случайно дважды отсканирован в режиме GROUP) специально **не
блокируется на сервере** — `scans` append-only, `on_scan_insert`
и так идемпотентно обновляет `children_today` через `ON CONFLICT`, а
для BUS-режима расчёт актуального автобуса и так берёт «последний скан»
(`useScan.getChildBusForToday`). Дедуп внутри сессии — ответственность
клиентского слоя режима (уже решено на уровне тикета 116/120: это
работа mode-обёртки, не сервера). Специально фиксирую это здесь, чтобы
в 122 не тратили время на серверный дедуп внутри пакета — он не нужен.

# 7. Изменения серверного API

- Новая Edge Function `submit-scan-packet` (`supabase/functions/submit-scan-packet/index.ts`)
  — единственная новая точка входа, по образцу существующих
  `delete-user`/`invite-generate` (`service_role`-клиент, проверка
  `Authorization`-токена в коде). Вызывается с клиента как обычный HTTP
  POST на Edge Function (как `invite-accept`), либо через
  `supabase.functions.invoke('submit-scan-packet', { body: payload })`.
- Новых RPC/PL/pgSQL-функций не требуется (см. раздел 2) — атомарность
  достигается одним SQL-оператором внутри функции, а не отдельной
  хранимой процедурой.
- Существующие `useArmband.recordChildPresence()` / `useScan.createScan()`
  не удаляются в рамках 122 — пакетный путь появляется параллельно.
  Если после 120 не останется вызывающего кода для единичной вставки —
  это решение отдельного будущего тикета, не 122.

- **Триггеры `on_scan_insert`/`on_children_today_change`** — без
  изменений (раздел 4 — ключевое архитектурное решение всего документа).
- **`HeadcountView.vue` (Kopfzählung, тикет 106)** — без изменений,
  использует отдельный путь через `useChildPresence.setPresentNow()`,
  напрямую не пересекается со `scans`/`scan_packets`.
- **`ChildrenView.vue`, `useGroups`** — без изменений, читают
  `groups_today`/`children_today`, которые продолжают обновляться как
  раньше.
- **`AdminBusView.vue`** — требует переработки (уже зафиксировано в
  `tickets/120/DECISIONS.md`, входит в объём 120, но технически
  реализуется в 122 вместе с серверной частью, см. `122.txt`, раздел
  «UI главного администратора»):
  - Существующая Realtime-подписка на `children_today`/`user_group_day`/
    `reset_events` продолжит формально работать (данные там по-прежнему
    обновляются), но перестанет быть осмысленной как «живой» индикатор —
    числа будут скачками меняться в момент отправки пакета, а не по
    одному скану.
  - Нужен новый источник для отображения «кто что прислал»: `SELECT`
    из `scan_packets` (по `date`+`bus_id`/`group_id`) — список пакетов
    с автором, временем, `children_count`. Это прямое следствие наличия
    заголовка пакета (раздел 5) — без него такой список пришлось бы
    собирать `GROUP BY packet_id` по `scans` на каждый рендер.
  - Сама реализация экрана (что именно показывать, как визуально
    группировать несколько пакетов по одному автобусу) — за рамками
    этого документа, это UI-решение тикета 122.

# 9. Вне рамок этого документа (сознательно)

Соответствует `tickets/120/DECISIONS.md`, п.2 — не проектируется здесь:

- Объединение нескольких пересчётов одного автобуса/группы, выявление
  расхождений, вычисление отсутствующих.
- Итоговый экран для Hauptbetreuer.

Хранение спроектировано так, чтобы это можно было добавить позже без
изменения уже описанной здесь схемы: `scan_packets` уже даёт группировку
«кто и когда прислал результат по какому автобусу/группе», `scans.packet_id`
даёт точную привязку каждого скана к пакету — сверка сможет читать эти
данные, не требуя новой миграции.

# 10. Развилка RPC vs Edge Function — решено

Единственный неочевидный выбор в этом документе — способ приёма пакета
(PL/pgSQL RPC или Edge Function) — вынесен на обсуждение и решён:
**Edge Function `submit-scan-packet`**, с атомарностью через один
SQL-оператор (не через PL/pgSQL-функцию и не через ручной
`BEGIN`/`COMMIT` в Deno) — см. разделы 2, 6, 7. Причины решения:
переиспользование уже принятого в проекте паттерна привилегированной
Edge Function с проверкой токена в коде (`delete-user`,
`invite-generate`), TypeScript привычнее команде, задел на будущие
внешние вызовы (уведомления и т.п.) для вынесенной за рамки 120/122
серверной сверки (раздел 9).
