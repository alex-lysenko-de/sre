# Итог

CHANGES_REQUIRED

Все семь пунктов задачи архитектурно и по объёму кода реализованы в
соответствии с `IMPLEMENTATION_PLAN.md`, но при построчном разборе
`Scanner.vue` обнаружена критическая логическая ошибка, из-за которой камера
никогда не запускается автоматически в трёх основных экранах сканирования
(Bus/Group/Checkin) — то есть основная функция приложения (сканирование
браслетов) в этих режимах полностью неработоспособна в текущем виде. Это не
было замечено разработчиком, так как ручная проверка на устройстве/в браузере
в этой сессии не проводилась (сборка и HTTP-200 роутов её не покрывают).


# Critical

**1. Автозапуск камеры (`autoStart=true`, режим по умолчанию) в `Scanner.vue`
никогда не срабатывает — Bus/Group/Checkin полностью нерабочи.**

`src/components/scanner/Scanner.vue:114`:
```js
const isTransitioning = ref(props.autoStart)
```
`src/components/scanner/Scanner.vue:229-233`:
```js
const startCamera = async () => {
  if (scannerActive.value || isTransitioning.value) {
    return
  }
  isTransitioning.value = true
  ...
```
`src/components/scanner/Scanner.vue:436-441`:
```js
onMounted(() => {
  ...
  if (props.autoStart) {
    startCamera()
  } else {
    isTransitioning.value = false
  }
})
```

`isTransitioning` инициализируется значением `props.autoStart`. Для
`ScannerBusView.vue`/`ScannerGroupView.vue`/`ScannerCheckinView.vue` проп
`autoStart` не передаётся, поэтому действует default `true` — то есть
`isTransitioning.value === true` уже в момент первого рендера, **до** вызова
`onMounted`. Когда `onMounted` вызывает `startCamera()`, собственная
guard-проверка функции (`if (scannerActive.value || isTransitioning.value)
return`) видит `isTransitioning.value === true` и немедленно завершает
работу — до создания `html5QrCode`, до `configStore.loadConfig()`, до любого
реального запуска камеры. `isTransitioning` при этом никогда не
сбрасывается в `false` (это происходит только в `finally` внутри
`startCamera`, до которого выполнение не доходит) — то есть даже кнопка
"Scan" ("камера выключена", :19-24) не появляется, так как её условие
`!scannerActive && !isTransitioning` никогда не станет истинным. Пользователь
видит только вечный спиннер "Scanner wird initialisiert..." (:14-17) —
**никакого способа запустить камеру в этих трёх экранах не существует**, ни
автоматического, ни ручного (`defineExpose.start` тоже никем извне не
вызывается — см. Minor ниже).

Подтверждено грепом (`scannerRef|\.start\(\)`) — `start()` из
`defineExpose` не вызывается ни в одном из потребителей `Scanner.vue`, кроме
самого шаблона компонента (`@click="startCamera"` внутри самого
`Scanner.vue`), который для `autoStart=true` также недостижим.

Единственный путь, где баг не проявляется — встроенная панель
`HeadcountView.vue`, так как там `:auto-start="false"` и `isTransitioning`
изначально `false`; там пользователь нажимает кнопку "Scan" сам, guard
пропускает вызов, и всё работает штатно.

**Затронуто**: `ScannerBusView.vue`, `ScannerGroupView.vue`,
`ScannerCheckinView.vue` — все три полноэкранных режима сканирования (не
только новые изменения тикета 126, а вся функциональность модуля
перекличек, тикеты 116/120). `IMPLEMENTATION_REPORT.md` заявляет только
проверку сборки (`npm run build`) и HTTP-200 роутов — ни то, ни другое не
могло обнаружить эту ошибку, так как она проявляется только при реальном
взаимодействии с камерой в браузере.


# Major

Существенных находок уровня Major, не связанных с находкой из Critical, не
обнаружено — оставшаяся часть реализации (навбар, Willkommen, настройки
сканера, Kopfzählung-события, Close, not-found-экран) соответствует плану.


# Minor

1. **`handleConfirmationBind` не обёрнут в try/catch**, в отличие от
   `onChildResolved` (:375-382) — если `props.onBindRequested` (по факту
   `router.push(...)`, `handleReset()`) выбросит исключение, оно не будет
   перехвачено, а экран подтверждения уже скрыт (`hideConfirmationScreen()`
   вызван раньше) — камера останется на паузе без визуальной обратной связи
   для пользователя. Риск низкий (текущие реализации `onBindRequested`
   синхронны и не бросают), но асимметрично по сравнению с остальным кодом
   файла.
2. **`start()` в `defineExpose` (:450) не используется ни одним
   потребителем** — фактический механизм запуска камеры в `HeadcountView.vue`
   идёт через встроенную кнопку самого `Scanner.vue`, а не через
   `scannerRef.value?.start()`, как предполагал план
   (`IMPLEMENTATION_PLAN.md:280-286` описывает оба варианта как
   допустимые, и в отчёте разработчик прямо выбрал вариант через события —
   это осознанное решение, а не недосмотр). Само по себе не ошибка, но
   стоит либо явно закомментировать, для чего `start()` остаётся публичным,
   либо убрать, если он не нужен ни одному текущему или обозримому
   потребителю.
3. **Смешение языков в UI одного и того же экрана**: кнопки
   "Cancel"/"Привязать бейдж" (`Scanner.vue:42-47`) на русском/английском
   в остальном полностью немецкоязычном интерфейсе ("Willkommen",
   "Kamera", "Anzeigedauer bei Erfolg" и т.д.). Это прямо следует из текста
   `126.txt` ("суть — по-русски «Cancel» и «Привязать бейдж»"), то есть не
   является отклонением от задачи, но с точки зрения консистентности
   продукта для конечного пользователя стоит перепроверить у заказчика,
   не была ли эта формулировка рабочей пометкой в тикете, а не финальным
   текстом кнопок.

- Перенос `DailyCheckInModal`/`showCheckInModal` из `App.vue` (монтируется
  всегда) в `MainView.vue` (монтируется только на `/main`) — риск,
  зафиксированный самим планом. Проверено повторно: единственная точка
  вызова `showCheckInModal = true` — новая кнопка на Willkommen, других
  скрытых зависимостей от постоянного монтирования модалки не найдено.
  Риск не реализовался.
- `Scanner.vue` продолжает расти в объёме ответственности (управление
  камерой через `autoStart`/`start()`/`stop()`, чтение внешних настроек,
  новая персистентная ветка confirmation) в рамках одного файла — уже
  зафиксировано как осознанный риск в `IMPLEMENTATION_PLAN.md`
  ("Риски"), актуально держать в голове при следующих правках этого
  компонента: следующая правка, которая добавит очередное состояние в
  тот же set of booleans (`scannerActive`/`isTransitioning`/`isProcessing`/
  `confirmation.*`), стоит того, чтобы вместо очередного булева флага
  выделить явный конечный автомат — Critical-находка выше как раз
  иллюстрирует, насколько легко эти флаги рассинхронизировать.
- Коммит `94785d0` ("126") объединяет изменения тикета 126 с не связанными
  с ним артефактами: `doc/utils/*.pdf` (новые бинарные файлы),
  `tickets/130/130.txt` (текст другого тикета), правки
  `tickets/124/state.txt`/`tickets/dashboard.md` по нескольким тикетам
  сразу. Не блокирует ревью 126 по существу, но затрудняет будущий
  `git bisect`/откат конкретно этого тикета.
