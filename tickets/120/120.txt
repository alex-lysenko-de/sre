# Тикет 120: Модуль перекличек — три режима сканирования


# Цель

Заменить единственный сегодняшний сканер (`/scanner`, `ScannerView.vue`)
тремя режимами меню «Scannen», каждый из которых соответствует своему
типу переклички: **пересчёт в автобусе (BUS)**, **перекличка группы
(GROUP)**, **свободные отметки (CHECKIN)**. Все три построены поверх уже
реализованного, протестированного на реальных устройствах и одобренного
заказчиком компонента `Scanner.vue` (тикет 116). Результат работы
каждого режима — пакет данных (`PresencePacket`), который целиком
отправляется на сервер по нажатию кнопки «Отправить».

# Базовая реализация

**Переиспользуется без изменений** (готово, тикет 116, статус `DONE`):
- `src/components/scanner/Scanner.vue` — камера, декод QR, резолв
  браслета в ребёнка через `useArmband.getBraceletStatus()`, звук/
  вибрация/экран подтверждения. Проп-контракт:
  `onChildResolved(result) → { title, subtitle, variant?, repeat? }`,
  исходы `invalid` / `error` / `not-found` / `found`.
- `src/composables/useScannerFeedback.js` — примитивы Web Audio/
  vibration, используются и `Scanner.vue`, и режимами (для сигнала
  «уже отсканирован», см. ниже).

`Scanner.vue` не содержит бизнес-логики, не знает о режимах и не
собирает пакет — это исключительно ответственность режимов, описанных
ниже.

**Удаляется полностью** (не архивируется, не остаётся резервным
вариантом):
- `src/views/ScannerView.vue` и маршрут `/scanner` — старый сканер.
- `src/views/ScannerPrototypeView.vue` и маршрут `/scanner-prototype`
  — вспомогательный UX-прототип тикета 116, свою роль (проверка
  интерфейса) отработал и заменяется тремя боевыми экранами.
- `useArmband.recordChildPresence()` — единственный прямой `INSERT` в
  `scans` в обход пакетной модели; единственный вызывающий
  (`ScannerView.vue`) удаляется вместе с ним.

**Не входит в этот тикет и не меняется**: `useScan.createScan()` и его
единственный вызывающий `ChildDetailView.vue` (админский ручной
пересчёт/переназначение автобуса ребёнку). Это не один из трёх
«подрежимов сканирования» — отдельный административный инструмент, вне
рамок 120.

# Пользовательский интерфейс

## Меню

В `MainView.vue` одна кнопка «Scannen» заменяется тремя (по образцу
существующих карточек-кнопок: иконка + заголовок + подпись + стрелка):

| Режим | Заголовок | Подпись | Маршрут |
|---|---|---|---|
| BUS | Bus zählen | Kinder im Bus scannen | `/scanner/bus` |
| GROUP | Gruppen-Appell | Anwesenheit der Gruppe prüfen | `/scanner/group` |
| CHECKIN | Freie Meldung | Kinder frei melden | `/scanner/checkin` |

Условия доступности (по образцу уже существующего в `MainView.vue`
паттерна предупреждения «Keine Gruppe zugewiesen»):
- BUS недоступен (задизейблен + предупреждение), если у пользователя
  нет `bus_id` (`userStore.userInfo.bus_id`).
- GROUP недоступен, если нет `group_id` (`userStore.userInfo.group_id`).
- CHECKIN доступен всем аутентифицированным без условий.

## Экраны режимов

Общий layout: камера сверху (как в 116), под ней — список/счётчик
режима, снизу — кнопки `[Reset] [Отправить]`.

**BUS** — счётчик + последний найденный ребёнок:
```
Автобус №2
Отсканировано: 37
Последний:
✓ Иванов
[Reset] [Отправить]
```
Список всех отсканированных  детей (без дублирующих записей) располагается под кнопками [Reset] [Отправить]

**GROUP** — чек-лист найденных/не найденных, счётчик `N / Total`:
```
Группа 3
16 / 18
□ Иванов
□ Петров
✓ Сидоров
✓ Кузнецов
[Reset] [Отправить]
```
Список загружается заранее (ростер группы) и обновляется по мере
сканирования. список выводится в таком порядке в каком они записаны в базе данных (order_by id). Есть ручная
отметка (тап по ребёнку в списке отмечает его найденным без
сканирования — используется, если браслет отсутствует/повреждён).

**CHECKIN** — список найденных с указанием группы:
```
Свободная отметка
Отсканировано: 2
✓ Иванов - Group 10
✓ Петров - Group 2
[Reset] [Отправить]
```

# Логика работы

Общая для всех трёх режимов, различается только контекстом (`bus_id`/
`group_id`) и наличием ростера/ручной отметки в GROUP.

1. **Начало режима**: создаётся пустой пакет — новый `client_packet_id`
   (UUID), `type` режима, `date`, `author_id` текущего пользователя,
   `bus_id`/`group_id` из контекста (где применимо). Для GROUP
   дополнительно загружается ростер группы.
2. **Сканирование**: `Scanner.vue` резолвит QR → ребёнка и вызывает
   `onChildResolved`. Если ребёнок уже есть в пакете — сигнал
   «уже отсканирован», ребёнок повторно не добавляется (дедупликация в
   рамках текущего захода). Иначе — ребёнок добавляется в пакет с
   `method: 'SCAN'` и текущим `timestamp`; для первого добавленного
   ребёнка фиксируется `started_at` пакета.
3. **Ручная отметка** (только GROUP): тап по ребёнку в ростере
   добавляет его в пакет с `method: 'MANUAL'` — эквивалентно успешному
   сканированию.
4. **Отправка**: по кнопке «Отправить» фиксируется `finished_at`,
   пакет целиком отправляется одним запросом на Edge Function
   `submit-scan-packet` (см. «Формат данных»). До этого момента ничего
   не записывается на сервер — ни по одному скану, ни частями.
5. **Успех**: локальное состояние очищается, показывается подтверждение;
   пользователю предлагается начать новый заход (эквивалент «Reset»).
6. **Ошибка** (сеть/сервер): пакет и его `client_packet_id`
   сохраняются как есть, показывается сообщение об ошибке с кнопкой
   «Повторить». Повтор — это тот же запрос с тем же `client_packet_id`;
   сервер (тикет 122) отвечает за то, чтобы повторная отправка не
   создала дублирующих данных.
7. **Reset**: текущий пакет отбрасывается, начинается новый заход с
   новым `client_packet_id`.

Пакет существует только в памяти текущего экрана ( не нужно сохранять его в
`localStorage`/LocalForage) — при перезапуске приложения посреди
захода накопленные сканы теряются, это осознанное ограничение (см.
«Важные нюансы»).

# Формат данных — PresencePacket

Тело запроса к `submit-scan-packet` (`POST`, `Authorization: Bearer
<session.access_token>`, по паттерну существующего вызова
`invite-generate` из `InviteGeneratorView.vue`):

```json
{
  "client_packet_id": "uuid",
  "type": "BUS | GROUP | CHECKIN",
  "date": "YYYY-MM-DD",
  "author_id": 123,
  "started_at": "ISO-8601",
  "finished_at": "ISO-8601",
  "bus_id": 2,
  "group_id": null,
  "children": [
    { "child_id": 456, "timestamp": "ISO-8601", "method": "SCAN" }
  ]
}
```

| Поле | Обязательность | Примечание |
|---|---|---|
| `client_packet_id` | всегда | генерируется клиентом при старте захода, не меняется при повторной отправке |
| `type` | всегда | `BUS` \| `GROUP` \| `CHECKIN` |
| `date` | всегда | текущий день |
| `author_id` | всегда заполняется клиентом | сервер игнорирует присланное значение и подставляет `author_id` из аутентифицированной сессии сам — клиент не должен полагаться на то, что переданное значение будет использовано |
| `started_at` / `finished_at` | всегда | момент первого добавленного ребёнка / момент нажатия «Отправить» |
| `bus_id` | только `type = BUS` | иначе `null`/отсутствует |
| `group_id` | только `type = GROUP` | иначе `null`/отсутствует |
| `children[].child_id` | всегда | |
| `children[].timestamp` | всегда | момент добавления в пакет |
| `children[].method` | всегда, для всех трёх типов | `SCAN` (всегда для BUS/CHECKIN) или `SCAN`\|`MANUAL` (для GROUP) |

# Границы задачи и связь с тикетом 122

Этот тикет — **чисто клиентский**. Он строит три режима, сборку пакета
и реальный (не заглушку) вызов `submit-scan-packet`, но не реализует
саму функцию, миграцию БД или переработку `AdminBusView.vue`:

- **Приём и хранение пакета на сервере** (Edge Function
  `submit-scan-packet`, таблица-заголовок пакета, идемпотентность по
  `client_packet_id`, переработка триггеров) — реализуется тикетом 122.
- **`AdminBusView.vue`** — не меняется в этом тикете. Переработка под
  отображение полученных пакетов входит в 122 (экрану физически нечего
  показывать взамен сегодняшнего realtime-по-сканам, пока не появится
  таблица-заголовок пакета из миграции 122).
- **Серверная сверка результатов** — объединение пересчётов нескольких
  вожатых, вычисление отсутствующих, выявление расхождений, итоговый
  экран для Hauptbetreuer — не входит ни в 120, ни в 122. Этой
  подсистемы в проекте пока нет вообще; выносится в отдельный, ещё не
  заведённый тикет.

**120 и 122 должны разрабатываться и вводиться в эксплуатацию в рамках
одного релиза** — до развёртывания 122 кнопке «Отправить» в 120 некуда
реально отправлять данные (на время разработки допустима работа против
мока/заглушки эндпоинта).

# Важные нюансы и ограничения

- **Батч-модель, без исключений.** Ничего не пишется на сервер до
  явного нажатия «Отправить» — ни по одному скану, ни частями. Это
  сознательное решение: near-real-time видимость для администратора
  сегодня всё равно нигде не реализована, а батч даёт офлайн-надёжность
  (понятная ошибка + повтор вместо тихого сбоя) и возможность отменить/
  начать заново.
- **Идемпотентность отправки — забота сервера.** Клиент при повторе
  после ошибки просто переотправляет тот же объект пакета с тем же
  `client_packet_id`; клиенту не нужно самостоятельно определять,
  была ли предыдущая попытка успешной.
- **Дедупликация — только в рамках текущего захода**, только в памяти,
  не переживает перезапуск приложения. Если вкладка/приложение
  закрыто посреди сканирования — накопленные сканы теряются, нужно
  начинать заново. Требование не устраняется в этом тикете.
- **BUS и CHECKIN не фильтруют по группе** — дети могут принадлежать
  любой группе; резолв браслета (`getBraceletStatus()`) уже не
  фильтрует по группе, важно не привнести такой фильтр случайно (риск
  копипасты из GROUP-режима).
- **iOS Safari mute switch / ограничения Web Audio** — унаследованный
  от 103/116 риск, не решается в этом тикете; экран подтверждения
  остаётся надёжным каналом обратной связи независимо от звука.
