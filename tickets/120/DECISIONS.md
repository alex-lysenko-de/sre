# Тикет 120 — принятые архитектурные решения

Зафиксировано по итогам обсуждения (до написания `IMPLEMENTATION_PLAN.md`).
Не заменяет план — фиксирует развилки, которые иначе пришлось бы решать
заново при следующей сессии.

## 1. Модель персистентности — полный батч

Ничего не пишется на сервер (ни в `scans`, ни в новую таблицу) до
явного нажатия кнопки **«Отправить»**. Клиент копит результаты
сканирования локально в рамках сессии режима и отправляет их одним
пакетом (`PresencePacket`, см. `tickets/120/120.txt`).

**Почему** (аргументы пользователя, признаны решающими):
- Единственное преимущество мгновенной записи — near-real-time видимость
  для администратора — на практике не реализовано: существующий экран
  `HeadcountView.vue` (тикет 106, «Meine Gruppe») не имеет realtime и
  требует ручного `Refresh`.
- Батч даёт офлайн-надёжность (понятная ошибка + повтор отправки вместо
  тихого сбоя посреди сканирования), возможность проверить список перед
  отправкой и возможность полностью отменить/начать заново, если
  сканирование пошло не так (не тот ребёнок, не привязан браслет, ошибка
  в процессе).
- Для Режима 1 (автобус) батч-по-Betreuer'у не компромисс, а более
  точное соответствие задуманной механике: концепция явно построена на
  сравнении нескольких **независимых завершённых** пересчётов одного
  автобуса ("совпадение результатов повышает достоверность"), а не на
  потоке отдельных сканов.

**Известное следствие**: `AdminBusView.vue` уже сегодня имеет живую
Supabase Realtime-подписку (индикатор "Live", видно наполнение автобуса
по каждому скану). При переходе на батч это поведение исчезает — экран
должен быть переосмыслен под пакетную модель (показывать полученные
пакеты, а не поток сканов). Это входит в объём тикета 120 (см. пункт 3
ниже), не выносится отдельно.

## 2. Объём тикета 120 — разделён

Тикет 120 включает:
- 3 клиентских режима (подрежимы меню «Scannen»): автобус, перекличка
  группы, свободные отметки.
- Формирование `PresencePacket` на клиенте + UI отправки/повтора/отмены.
- Простое серверное сохранение пакета (без интерпретации).
- Переосмысление `AdminBusView.vue` под пакетную модель (было realtime
  по сканам — станет отображением полученных пакетов).

Тикет 120 **не включает**:
- Серверную сверку: объединение пересчётов нескольких Betreuer,
  выявление расхождений, вычисление отсутствующих.
- Итоговый экран для Hauptbetreuer, показывающий результаты сверки.

Это выделено в отдельный, ещё не заведённый будущий тикет — этой
подсистемы сегодня в проекте нет вообще (ни таблиц, ни Edge Function).

## 3. Пересмотр тикета 116 (уже применено)

Тикет 116 (`ARCHITECT_DONE`, ещё не реализован) на момент обсуждения
проектировал `BraceletScanner.vue` так, что он сам вызывал
`useArmband.recordChildPresence()` при найденном ребёнке. Это
противоречило принципу «Scanner не содержит бизнес-логики» из документа
120 — решение о том, писать/копить/игнорировать, должно приниматься
слоем режима (враппером), а не слоем браслета.

**Применено**: `tickets/116/IMPLEMENTATION_PLAN.md` уже обновлён —
`BraceletScanner.vue` только резолвит QR в ребёнка (найден/не найден) и
передаёт результат вверх через обязательный проп `onChildFound(child,
bandId)`; сегодняшний `ScannerView.vue` (слой 3, единственный
реализуемый в 116 режим — групповая перекличка) сам вызывает
`recordChildPresence()` немедленно. Видимое поведение приложения не
меняется; меняется только то, в каком слое живёт код записи — благодаря
этому будущие пакетные режимы тикета 120 смогут переиспользовать
`BaseQrScanner.vue`/`BraceletScanner.vue` без изменений, заменив в
верхнем слое немедленную запись на накопление в пакет.
