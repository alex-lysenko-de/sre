# Тикет 130: Редизайн интерфейса администратора для переклички (Roll Call)

## Цель

Переосмыслить интерфейс администратора, отвечающий за управление
перекличками и учётом присутствия в автобусах/группах —
`AdminBusView.vue` (маршрут `/admin-busses`) и частично
`ChildrenView.vue` (маршрут `/children`, "Admin Übersicht"). Сейчас на
одном экране (`AdminBusView.vue`) смешаны разнородные функции: общая
статистика, ручное обновление, "Tag starten"/"Soft Reset", таблица
автобусов, история сбросов (`ResetHistoryPanel.vue`) — это визуально
перегружено и не отражает реальную последовательность действий
главного администратора в течение дня.

**Первый этап этого тикета — только UI/UX-дизайн** (wireframes/mockups
+ письменное описание концепции). Функциональная реализация (изменения
БД, композаблов, серверной логики) в объём тикета 130 **не входит** и
уйдёт в отдельный тикет после утверждения концепции — по аналогии с
парой тикетов 121 (research/архитектура) → 122 (реализация).

## Текущие проблемы

- **`AdminBusView.vue`** сочетает: общую сводку (`Kinder`/`Betreuer`,
  :16-56), кнопку "Aktualisieren" (:60-69, ручной `loadBusData()`, хотя
  экран уже подписан на Realtime — `setupRealtimeSubscription()`,
  :480-534, слушает `children_today`/`user_group_day`/`reset_events`),
  "Tag starten" (:71-81, `startNewDay()` из `useDays.js` — создаёт
  запись в `reset_events` с `event_type=1`, делает снимок присутствия и
  сбрасывает счётчики; в этом тикете это и называется **"Hard Reset"**,
  хотя в коде так не называется), "Soft Reset" (:82-92, `softReset()`,
  `event_type=2`, обнуляет только текущие счётчики без снимка),
  `ResetHistoryPanel.vue` (история событий `reset_events`) и таблицу
  автобусов с переходом в `BusDetailModal.vue`.
- В `useDays.js` есть ещё `closeDay()` ("Tag schließen"/Total Reset,
  `event_type=0`) — нигде не используется в UI (нет ни одной кнопки).
  Пересмотр меню администратора (см. ниже) должен явно решить, нужна
  ли ей кнопка, или она остаётся неиспользуемой.

- Реальное сканирование выполняют воспитатели через существующие
  режимы (тикет 120: `ScannerBusView.vue`/"Bus zählen",
  `ScannerGroupView.vue`/"Gruppen-Appell"; тикет 123:
  встроенная панель в `HeadcountView.vue`) — администратор сам не
  сканирует, а даёт команду и следит за прогрессом. Сегодня в
  приложении нет ни одной сущности "перекличка запущена/завершена" —
  есть только `reset_events` (снимки/сбросы дня) и `scan_packets`
  (тикет 122, отдельные пакеты от воспитателей, без понятия "раунда
  переклички", в который они входят).

## Рабочий процесс администратора (как должно быть)

Администратор не сканирует сам. Он запускает перекличку, следит за
прогрессом и решает, когда она завершена.

### Перекличка в автобусе (Bus Roll Call)

День начинается после посадки детей в автобусы. Администратор даёт
устную команду и сразу же запускает процесс в приложении — новое
действие **"Start Bus Roll Call"**. По нажатию:

- создаётся событие "перекличка в автобусах начата";
- открывается новый экран мониторинга переклички в автобусах.

Надо будет посмотреть в базе данных, есть ли у нас таблица с названием «переклички» или что-то похожее по смыслу. Если нету, то нужно будет добавить такую таблицу или  адаптировать одну из существующих таблиц под эти цели. например таблицу "admin_logs" или таблицу reset_events под эту задачу. Reset_events сейчас содержит только сбросы, но, по сути, их можно адаптировать как сигнал начала и конец переклички. Сигналы могут быть трех типов.  - начало переклички в автобусах, 
- начало пересчета детей в группах 
- начало ленивого  пересчета. 
То по аналогии с тремя типами сканов, используемых воспитателями см. scan_packets.type, а также симметричные им сигналы об окончании. Все пакеты, приходящие от воспитателей, принимаются только в интервалах начала и окончания переклички. Если начата перекличка в автобусе, точнее, пакеты, приходящие от воспитателей с пометкой «перекличка в автобусе», принимаются только если на данный момент есть открытая сессия «перекличка в автобусе». Соответственно, перекличка по группам, пакеты с отметкой «перекличка по группам» принимаются только когда открыта сессия переклички по группам. После закрытия такие events не принимаются просто не принимается, они отбрасываются т.е. бросается какое-то исключение с сообением "сессия не начата, разговаривайте с Hauptbetreuer."


### Мониторинг переклички в автобусах (новый экран)

Показывает текущий прогресс: автобусы, прогресс сканирования, число
отправленных пакетов (`scan_packets` от `ScannerBusView.vue`),
статус завершённости, предупреждения/несостыковки. Точная раскладка —
предмет UI-дизайна в рамках этого тикета; главное — показывать только
то, что нужно для принятия решения. Обновляется автоматически по мере
поступления данных (Realtime-инфраструктура для этого уже есть в
проекте — `AdminBusView.vue`, `stores/config.js`, `stores/user.js`
используют `supabase.channel(...).on('postgres_changes', ...)`;
если она покрывает и этот случай, отдельная кнопка "Обновить" не
нужна — проверяется на этапе реализации).

Экран мониторинга содержит два действия:

- **Finish Roll Call** — создаёт событие "перекличка в автобусах
  завершена"; подтверждает, что администратор принимает результат и
  фиксирует итог утренней переклички. В зависимости от финальной
  бизнес-логики (решается на этапе реализации, не в этом тикете) это
  действие может также фиксировать базовое число присутствующих детей
  на сегодня — то есть частично заменять собой сегодняшнюю функцию
  "Tag starten"/Hard Reset. Взаимосвязь между новым "Finish Roll Call"
  и существующим `reset_events`/"Tag starten" — открытый архитектурный
  вопрос, не решается в этом тикете, но должен быть явно поставлен в
  дизайн-концепции.
- **Cancel Roll Call** — отменяет текущую перекличку, аннулирует ранее
  созданное событие "начата" (отменой либо другим подходящим
  механизмом — конкретика также на этапе реализации).

### Перекличка по группам (Group Roll Call)

Аналогично: **"Start Group Roll Call"** создаёт событие "перекличка по
группам начата" и открывает свой экран мониторинга.

### Мониторинг переклички по группам (новый экран)

По духу — переработка существующей `ChildrenView.vue`
("Gruppenübersicht", уже показывает: статус-индикатор, группа, Morgen/
Aktuell, Betreuer, Differenz, предупреждение о недостающих детях), но
оптимизированная именно под сценарий переклички, а не под общий обзор.
Возможные поля: название группы, ответственный воспитатель, прогресс
переклички, число присутствующих/отсутствующих, статус. Цель — чтобы
администратор сразу видел, какие группы уже закончили перекличку, а
какие ещё требуют внимания. Компактно, минимум скроллинга: группы без
проблем можно сворачивать/показывать в свёрнутом виде, группы с
проблемами — выделять.

### Автообновление

Оба экрана мониторинга обновляются автоматически по мере поступления
данных — без ручного обновления администратором.

### История переклички — новый раздел "Roll Calls"

Центральная точка входа ко всем перекличкам за текущий день. Для
каждой — как минимум: время начала, время окончания, тип (Bus/Group),
текущий статус, итоговая сводка. Выбор переклички открывает её
детальный просмотр — так завершённые переклички не мешаются с активным
рабочим процессом.

### Пересмотр существующего меню администратора

Функции "Hard Reset" (= сегодняшний "Tag starten"), "Soft Reset",
"Aktualisieren" (ручное обновление), "Bus Alerts" (= предупреждение из
`ChildrenView.vue`) должны быть пересмотрены как единое целое: часть
может переехать (например, стать частью экранов мониторинга/истории
переклички), часть — упроститься, часть — вовсе исчезнуть, если
перекрывается новым процессом переклички. Цель — снизить когнитивную
нагрузку и оставить только то, что нужно в нормальной повседневной
работе.

## Явно вне рамок тикета 130

- **Функциональная реализация** (БД, композаблы, серверная логика) —
  отдельный тикет после утверждения дизайн-концепции.
- **Изменение поведения экранов сканирования у воспитателей**
  (`ScannerBusView.vue`/`ScannerGroupView.vue`) в ответ на
  Start/Finish/Cancel Roll Call — кнопки сканирования (Bus zählen/
  Gruppen-Appell) **не блокируются** и не меняют доступность в
  зависимости от статуса переклички. В этом тикете воспитатели
  продолжают сканировать так же, как сегодня.

  Зафиксирована для будущего тикета идея, обсуждённая при подготовке
  130 (не требование к нему): блокировать не кнопки сканирования, а
  саму отправку — при `submit_scan_packet()` на сервере проверять,
  есть ли для типа пакета (BUS/GROUP) открытое (начатое и ещё не
  завершённое/отменённое) событие переклички на сегодня. Если нет —
  отправка завершается ошибкой, пакет не применяется; воспитатель
  видит ошибку и может повторить отправку позже (существующий UX
  экранов сканирования уже поддерживает повтор после неудачной
  отправки — см. тикеты 120/122). Это признано более простым и
  надёжным вариантом, чем клиентская блокировка кнопок по реактивному
  статусу переклички (пришлось бы рассинхронизировать состояние между
  устройствами воспитателей и решением администратора в реальном
  времени) — но проектирование и реализация этой проверки не входят в
  130.

## Deliverables (результат этого тикета)

Несколько концепций интерфейса (wireframes/mockups), покрывающих:

- главный экран администратора (после пересмотра меню);
- мониторинг переклички в автобусах;
- мониторинг переклички по группам;
- историю переклички ("Roll Calls").

Реализация начинается только после того, как одна из концепций выбрана.

## Ожидаемый результат

Интерфейс администратора должен стать ориентированным на процесс, а не
на набор разрозненных функций — вести администратора через
последовательность дня:

1. Начать перекличку в автобусах.
2. Следить за прогрессом.
3. Завершить перекличку в автобусах.
4. Начать перекличку по группам.
5. Следить за прогрессом.
6. Завершить перекличку по группам.
7. Просмотреть завершённые переклички в истории.

Минимум действий, максимум видимости текущего статуса — чтобы
администратор сразу замечал проблемы и мог принимать решения.

## Definition of Done

- Подготовлено несколько wireframe/mockup-концепций, покрывающих все
  четыре экрана из Deliverables.
- Для каждой концепции описано, как она отражает процесс "Start →
  Monitor → Finish/Cancel" для обоих типов переклички (Bus/Group).
- Явно описан результат пересмотра существующего меню администратора
  (что происходит с Hard Reset/Soft Reset/Aktualisieren/Bus Alerts —
  переезжает, упрощается или удаляется, и куда).
- Явно поставлен (не обязательно решён) вопрос о взаимосвязи нового
  "Finish Roll Call" с существующим `reset_events`/"Tag starten".
- Зафиксирована (текстом, не реализацией) идея серверной проверки
  открытой переклички при отправке `scan_packets`, для будущего
  тикета.
- Выбрана одна концепция для дальнейшей реализации (или явно указано,
  что решение отложено) — БД/код в рамках этого тикета не меняются.
