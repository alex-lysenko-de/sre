# Отклонения от плана

Задание, полученное для этой сессии, — реализовать код/БД строго согласно
`tickets/130/IMPLEMENTATION_PLAN.md`. Это прямо противоречит явно
зафиксированному объёму самого тикета 130 и его архитектурного плана:

- `tickets/130/130.txt`: "**Первый этап этого тикета — дизайн**:
  UI/UX-концепция... Применение изменений к реальной БД, серверная логика
  (композаблы, Edge Function/триггеры) и код клиента **не входят** в 130 и
  уйдут в отдельный тикет реализации после утверждения концепции — по
  аналогии с парой тикетов 121 (research/архитектура) → 122
  (реализация)." Раздел "Явно вне рамок тикета 130" повторяет это отдельно
  для БД и для клиентского кода воспитателей. Definition of Done требует:
  "БД/код в рамках этого тикета не меняются."
- `tickets/130/IMPLEMENTATION_PLAN.md` (шапка документа): "код и БД не
  меняются в рамках 130 (по аналогии с парой тикетов 121→122)". Разделы
  «Изменения БД»/«API изменения»/«UI изменения» помечены "Не применяются
  в рамках 130" / "Ничего из этого не применяется в 130" — это
  спецификация для будущего тикета реализации, не поручение к исполнению
  сейчас. Раздел «План реализации» (10 шагов) прямо озаглавлен "Порядок
  для будущего тикета реализации (**не выполняется в 130**)".
- `tickets/130/state.txt` уже содержит `ARCHITECT_DONE` — статус
  завершённого архитектурного этапа, ожидающего отдельного тикета
  реализации (аналог связки 121 → 122, которая упоминается в самом плане
  как прецедент).

Выполнение поручения "реализовать по плану" потребовало бы одного из двух
недопустимых шагов:

1. Начать реализацию БД/кода в обход явного требования "отдельный тикет
   реализации после утверждения концепции" — то есть проигнорировать
   прямой текст задачи и её DoD;
2. Либо, чтобы вообще завершить реализацию, самостоятельно принять
   архитектурные решения по вопросам, которые сам план оставляет открытыми
   и не решает (раздел «Риски» `IMPLEMENTATION_PLAN.md`): конфликт
   создания второй Bus-переклички при открытой Bus (блокировать/
   авто-завершать — "требует подтверждения на старте реализации"),
   доступность `pg_cron` в проекте ("не подтверждено"), механизм для
   отменённых пакетов в `cancel_roll_call()` ("открытый вопрос... не
   решается") — что прямо запрещено инструкцией текущей сессии ("не
   принимай архитектурные решения самостоятельно").

Дополнительно (не блокирующее, но стоит отметить): роль сессии задана как
"Senior Python Developer", тогда как весь проект — Vue 3/Pinia/Supabase
(JS) на клиенте и PL/pgSQL на сервере; в репозитории нет Python-кода.
Похоже на шаблонную формулировку задания, не специфичную для этого
тикета/стека — самостоятельно решил не трактовать это как указание писать
код на Python, но это не главная причина остановки.

Не принимаю решение о том, какой из двух путей был бы правильным
(запускать ли отдельный тикет реализации сейчас, или это было
недоразумение в формулировке задания) — это требует подтверждения от
пользователя.
