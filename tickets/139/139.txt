# Тикет 139: Финальная сквозная проверка на устройстве + документация

Часть фазы реализации Checkpoint — см. `tickets/131/MIGRATION_PLAN.md`.
Завершающий тикет всей миграции 132–139. По итогам архитектурного ревью
(`MIGRATION_PLAN_REVIEW_RESPONSE.md`, п.1, п.15) объединяет то, что в
первой версии плана было отдельным «gate»-тикетом перед Phase 2 (141) и
финальным тикетом (144) — при отсутствии живых пользователей нет
отдельной более рискованной «Phase 2», проверка выполняется один раз, в
конце всей последовательности. Часть документации (RLS-паттерн для
`checkpoints` — тикет 132; отзыв legacy-политики на `children_today` —
тикет 138) уже обновлена по ходу, не откладывалась досюда.

## Цель

Подтвердить, что вся функциональность Checkpoint (тикеты 132–138)
работает корректно на реальной БД и реальных устройствах воспитателей/
администратора, привести `vault/`/`CLAUDE.md` в соответствие с новой
архитектурой, обновить `tickets/dashboard.md`.

## Что прочитать перед началом

- `tickets/131.txt`, Definition of Done, последний пункт — список
  сценариев сквозной проверки.
- `tickets/130/decision.md` целиком — каждый пункт модели должен быть
  подтверждён живым сценарием, а не только прочитан.
- `IMPLEMENTATION_REPORT.md`/`REVIEW_REPORT.md` тикетов 132-138 (если
  созданы) — что уже проверено по ходу реализации, чтобы не дублировать.
- `vault/00-Индекс/MOC.md` — точка входа в базу знаний, чтобы найти все
  страницы, ссылающиеся на устаревшие понятия (Roll Call, Hard/Soft
  Reset, Kopfzählung).
- `vault/04-Пользователи-и-аутентификация/stores-user.md` — свериться,
  что Checkpoint-composables (тикет 133) вписываются в описанную там
  трёхслойную архитектуру как иллюстрация паттерна, без противоречий.
- `CLAUDE.md`, раздел «Ключевые факты о модели данных» — не появилось ли
  что-то новое, обязательное для восстановления контекста после сжатия
  сессии (например, «дня не существует как отдельного действия — граница
  дня автоматическая»).

## Затрагиваемые части проекта

`vault/`, `CLAUDE.md` (только если появились новые нетривиальные факты —
см. правило файла), `tickets/dashboard.md`. Изменения кода — только
точечные багфиксы по итогам проверки, не новая функциональность.

## Файлы/подсистемы, которые будут изменены

- Страницы `vault/`, описывающие `AdminBusView.vue`/`ChildrenView.vue`/
  `HeadcountView.vue`/Hard-Soft-Reset (найти через `MOC.md`/грепом по
  `vault/`) — актуализировать или пометить как исторические.
- Новая страница `vault/.../Checkpoint-Controlnaya-tochka.md` (или в
  подходящем существующем разделе) — модель данных, RPC, три типа,
  ссылка на `tickets/130/decision.md` как на первоисточник (не дублировать
  «Aggregation Model», а ссылаться).
- `CLAUDE.md` — точечное обновление, если требуется.
- `tickets/dashboard.md` — статусы 132-139 → финальные.

## Что должно быть реализовано

1. Сквозная ручная проверка на устройстве:
   - авто-создание точки по первому пакету каждого типа (Bus/Group/Lazy),
     воспитатель ни разу не видит отказа;
   - параллельная работа Bus и Group одновременно — штатный сценарий;
   - явное создание при уже открытой точке того же типа — отклоняется;
   - Finish (baseline на первой за день точке независимо от типа),
     Reopen, Remove (каскадное удаление, повторная отправка того же
     офлайн-пакета после Remove принимается как новый);
   - Realtime-обновление всех экранов без ручной кнопки «Aktualisieren»;
   - список отличает «создана автоматически (Betreuer X)» от «создана
     администратором»;
   - смена дня (переход через полночь, после тикета 138) — вчерашняя
     зависшая `OPEN`-точка не блокирует создание сегодняшней того же
     типа;
   - `ChildDetailView.vue` (тикет 136) — привязка браслета → «Präsenz
     registrieren» → ребёнок виден в соответствующем Checkpoint-экране;
   - старые маршруты (`/admin-busses`, `/children`, `/headcount`,
     `*-prototype`) отсутствуют (тикет 137) — без регрессионной оговорки
     «должны продолжать работать», как было в первой версии плана: они
     удалены, а не сосуществуют.
2. Обновить/создать страницы `vault/`, отражающие: сущность Checkpoint,
   гибридную модель, автоматическую границу дня, новый набор экранов
   администратора, удаление Kopfzählung.
3. Пометить как исторические (не удалять историю решений) страницы,
   описывающие старый `AdminBusView.vue`/Reset-механизм/Kopfzählung, если
   такие существуют отдельно от `CLAUDE.md`.
4. `tickets/dashboard.md` — обновить статусы 130, 130_2, 131, 132-138.

## Что не входит

- Пользовательская документация конечных пользователей (тикет 109,
  отдельная задача).
- Технический долг вне Checkpoint, найденный при аудите
  (`MIGRATION_PLAN.md`, §1.5: `DaysEditView.vue`, `UsersView.vue`,
  `ArmbandConnectView.vue`) — зафиксирован там, не устраняется здесь.

## Результат выполнения тикета

- Все сценарии выше пройдены на реальных устройствах, результат
  зафиксирован в `IMPLEMENTATION_REPORT.md`.
- База знаний (`vault/`) не содержит противоречий с фактическим
  состоянием кода после 132-138.
- `tickets/dashboard.md` отражает финальный статус всей серии 130-139.
