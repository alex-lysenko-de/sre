# Тикет 132: DB — таблица `checkpoints` + `scan_packets.checkpoint_id` + RLS

Первый тикет фазы реализации «Контрольная точка» (Checkpoint) —
см. `tickets/131/MIGRATION_PLAN.md` за общей картиной и порядком
тикетов 132–144. Чисто схемное изменение, без функций/бизнес-логики
(они — тикеты 133/134) и без клиентского кода.

## Цель

Создать таблицу `checkpoints` и колонку `scan_packets.checkpoint_id` в
реальной БД проекта, с узкими RLS-политиками с самого начала — без
записи, без функций, только структура, готовая под RPC/расширение
`submit_scan_packet()` из следующих тикетов.

## Что прочитать перед началом

- `tickets/130/decision.md` — гибридная модель (для понимания, зачем
  нужен именно такой уникальный индекс).
- `tickets/131/IMPLEMENTATION_PLAN.md`, раздел «Изменения БД» — таблица
  `checkpoints` уже спроектирована там (без `CANCELLED`, `status CHECK IN
  (1,2)`), это основа для DDL этого тикета, не писать заново с нуля.
- `tickets/130/IMPLEMENTATION_PLAN.md`, раздел «Новая таблица
  `checkpoints`» — исходный DDL-набросок (устарел в части `status IN (1,2,3)`
  с `CANCELLED` — см. `tickets/131/MIGRATION_PLAN.md`, §1.3, п.2; брать
  версию `status IN (1,2)` из `131/IMPLEMENTATION_PLAN.md`).
- `doc/db/scan_packets.sql` — образец конвенции проекта: как оформлен
  файл миграции (шапка-комментарий, `IF NOT EXISTS`, RLS-блок в конце),
  этот тикет должен следовать тому же стилю.
- `vault/03-База-данных/RLS-политики.md` — пример задокументированной
  ошибки проекта («неотозванные широкие legacy-политики»), которую нужно
  не повторить.

## Затрагиваемые части проекта

Только БД. Ни один файл в `src/` не меняется этим тикетом.

## Файлы/подсистемы, которые будут изменены

- **Новый файл** `doc/db/checkpoints.sql` — DDL таблицы `checkpoints` +
  `ALTER TABLE scan_packets ADD COLUMN checkpoint_id` + RLS. Готовится по
  конвенции проекта: применяется вручную через Supabase SQL Editor/CLI,
  не автоматически в рамках этого тикета — это отдельный явно
  подтверждаемый шаг (как и миграция 122).

## Что должно быть реализовано

1. **Перед написанием DDL — сверить реальную структуру БД по живому
   проекту** (Supabase SQL Editor `\d scan_packets` или аналог), не по
   `backup/database/schema.sql` — этот дамп устарел и не содержит даже
   таблицу `scan_packets`, введённую тикетом 122 (см.
   `tickets/131/MIGRATION_PLAN.md`, §1.3, п.3). Убедиться, что
   `scan_packets` в реальной БД имеет ту же структуру, что описана в
   `doc/db/scan_packets.sql`.
2. `CREATE TABLE IF NOT EXISTS public.checkpoints` по спецификации
   `tickets/131/IMPLEMENTATION_PLAN.md` («Изменения БД», первый пункт):
   поля `id, type (smallint, 1=BUS/2=GROUP/3=LAZY), day (varchar),
   status (smallint, DEFAULT 1, CHECK IN (1,2) — без CANCELLED),
   created_by (bigint REFERENCES users), created_at, finished_at,
   finished_by, baseline_children_count`.
3. Уникальный частичный индекс «не более одной открытой контрольной
   точки на тип в день»: `CREATE UNIQUE INDEX ... ON checkpoints(day,
   type) WHERE status = 1` — центральный механизм гибридной модели
   (`decision.md`, пп. 4 и 6).
4. `ALTER TABLE public.scan_packets ADD COLUMN IF NOT EXISTS
   checkpoint_id bigint NULL REFERENCES public.checkpoints(id)`.
5. RLS для `checkpoints`: `ENABLE ROW LEVEL SECURITY`, `SELECT` для
   `authenticated` (`USING (true)`) — воспитатели должны видеть, идёт ли
   сейчас точка их типа. **Никакой** `INSERT`/`UPDATE`/`DELETE`-политики
   для `authenticated` — запись только через `SECURITY DEFINER`-функции
   из тикетов 133/134. Явно прокомментировать в файле, почему (по
   образцу комментария в конце `doc/db/scan_packets.sql`), чтобы не
   повторить ошибку `reset_events`/`children_today`/`groups_today`.
6. Файл идемпотентен (безопасно перезапускаемый): `IF NOT EXISTS`/`ADD
   COLUMN IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS`.

## Что не входит

- RPC-функции `create_checkpoint`/`finish_checkpoint`/`reopen_checkpoint`/
  `remove_checkpoint` — тикет 133.
- Расширение `submit_scan_packet()` — тикет 134.
- Любой клиентский код — тикеты 135+.
- Фактическое применение SQL к боевой БД не обязательно завершать в
  рамках этого тикета кодом ИИ-ассистента — это явно подтверждаемый
  пользователем шаг (см. `IMPLEMENTATION_REPORT.md` шаблон предыдущих
  тикетов, напр. 122).

## Результат выполнения тикета

- `doc/db/checkpoints.sql` подготовлен, идемпотентен, соответствует
  RLS-паттерну проекта.
- Таблица `checkpoints` и колонка `scan_packets.checkpoint_id`
  применены к реальной БД (после подтверждения пользователем) и
  проверены (`SELECT` из `checkpoints` работает под authenticated-сессией,
  `INSERT` под authenticated-сессией — отклоняется RLS).
- Зафиксировано в `IMPLEMENTATION_REPORT.md`, применена ли миграция к
  боевой БД в рамках этой сессии или отложена на явное подтверждение.

## Зависимости

Нет (первый тикет фазы реализации). Блокирует 133 и 134.
