# Цель

Реализовать серверную часть Checkpoint-модели (тикет 132): таблицу
`checkpoints`, колонку `scan_packets.checkpoint_id`, RLS без прав записи для
`authenticated`, четыре RPC-функции администратора (`create_checkpoint`/
`finish_checkpoint`/`reopen_checkpoint`/`remove_checkpoint`) и расширение
`submit_scan_packet()` для авто-создания/поиска точки со стороны
недоверенного пути (Edge Function `submit-scan-packet`, тикет 122, не
меняется).

Дизайн уже полностью зафиксирован в `tickets/131/IMPLEMENTATION_PLAN.md`
(«Изменения БД»), `tickets/130/decision.md` (гибридная модель) и
`src/composables/useCheckpointsMock.js` (точная форма возвращаемых
ошибок) — этот документ не пересматривает архитектурные решения, только
переводит их в один конкретный, идемпотентный SQL-файл, по конвенции
проекта (`doc/db/scan_packets.sql`, тикет 122 — один файл на
таблицу+RLS+функции).

# Анализ существующей схемы (проверено по `backup/database/schema.sql`,
`doc/db/scan_packets.sql`)

- `public.users`: `id bigint` (PK, на него ссылаются прикладные FK) отдельно
  от `user_id uuid` (= `auth.uid()`). Проверка роли admin в существующих
  RLS-политиках проекта — паттерн `EXISTS (SELECT 1 FROM users WHERE
  user_id = auth.uid() AND role = 'admin' AND active = true)`
  (`backup/database/schema.sql:6498-6500` и др.) — тот же паттерн
  используется внутри новых RPC (тикет 132.txt требует не переиспользовать
  `has_role()`/`is_admin()`, у них нет проверки `active`).
- `public.scan_packets` (тикет 122): `id, client_packet_id, type
  (1=BUS/2=GROUP/3=CHECKIN), author_id, bus_id, group_id, date,
  started_at, finished_at, received_at, children_count`. Колонка
  `checkpoint_id` отсутствует — добавляется этим тикетом.
- `submit_scan_packet(payload jsonb)` (`doc/db/scan_packets.sql:183-241`) —
  уже содержит guard на `children[]` без `child_id`, идемпотентность по
  `client_packet_id` (`ON CONFLICT (client_packet_id) DO NOTHING` +
  повторное чтение), вставку в `scans`. Payload содержит `type_code`,
  `date`, `author_id` (bigint, уже разрешённый Edge Function) — те же поля
  нужны для авто-создания/поиска checkpoint.
- `checkpoints` как таблица отсутствует — создаётся с нуля.

# План реализации

Один новый файл `doc/db/checkpoints.sql`, по образцу `doc/db/scan_packets.sql`
(шапка-комментарий, секции, `IF NOT EXISTS`/`CREATE OR REPLACE`, RLS-блок в
конце с пояснением).

1. `CREATE TABLE IF NOT EXISTS public.checkpoints`: `id bigint GENERATED BY
   DEFAULT AS IDENTITY PK`, `type smallint NOT NULL CHECK IN (1,2,3)`, `day
   varchar NOT NULL`, `status smallint NOT NULL DEFAULT 1 CHECK IN (1,2)`
   (1=OPEN, 2=FINISHED — без CANCELLED, см. `130_2` Round 1 UX-решение),
   `created_by bigint NOT NULL REFERENCES users(id)`, `created_at timestamptz
   NOT NULL DEFAULT now()`, `finished_at timestamptz NULL`, `finished_by
   bigint NULL REFERENCES users(id)`, `baseline_children_count smallint
   NULL`.
2. `CREATE UNIQUE INDEX IF NOT EXISTS checkpoints_open_type_per_day ON
   checkpoints(day, type) WHERE status = 1` — центральный механизм гибридной
   модели, единственное место, где enforced «не больше одной открытой точки
   на тип в день».
3. `ALTER TABLE public.scan_packets ADD COLUMN IF NOT EXISTS checkpoint_id
   bigint NULL REFERENCES public.checkpoints(id)`.
4. RLS `checkpoints`: `ENABLE ROW LEVEL SECURITY`, только `SELECT` для
   `authenticated USING (true)`. Комментарий в файле объясняет: запись
   только через `SECURITY DEFINER` RPC ниже — не повторять антипаттерн
   «неотозванных широких legacy-политик» (`vault/03-База-данных/
   RLS-политики.md`).
5. `create_checkpoint(p_type smallint, p_day varchar)` — `SECURITY DEFINER`,
   `SET search_path = public, pg_temp`, проверка admin/active, `RAISE
   EXCEPTION 'ALREADY_OPEN'` (с `existing_id` в `DETAIL`/через отдельный
   `SELECT`, воспроизводя форму `{error:'ALREADY_OPEN', existingId}` из
   `useCheckpointsMock.js`) при существующей открытой точке того же
   `(type, day)`, иначе `INSERT ... RETURNING`.
6. `finish_checkpoint(p_id bigint)` — `SECURITY DEFINER`, проверка admin,
   `RAISE EXCEPTION 'NOT_OPEN'` если нет строки со `status=1` и данным id.
   Шаг 1: `UPDATE ... SET status=2, finished_at=now(), finished_by=v_admin_id
   WHERE id=p_id AND status=1`. Шаг 2: если это первая `FINISHED`-точка дня
   (`NOT EXISTS (SELECT 1 FROM checkpoints WHERE day=... AND
   baseline_children_count IS NOT NULL)`) — посчитать `COUNT(DISTINCT
   scans.child_id)` через `scans JOIN scan_packets ON
   scans.packet_id=scan_packets.id WHERE scan_packets.checkpoint_id=p_id` и
   записать в `baseline_children_count`.
7. `reopen_checkpoint(p_id bigint)` — только для `status=2`, иначе
   `RAISE EXCEPTION 'NOT_FINISHED'`; если уже открыта другая точка того же
   `(type, day)` — `RAISE EXCEPTION 'ALREADY_OPEN'` (та же форма, что и
   `create_checkpoint`); иначе `UPDATE SET status=1, finished_at=NULL,
   finished_by=NULL`.
8. `remove_checkpoint(p_id bigint)` — `RAISE EXCEPTION 'NOT_FOUND'`, если
   строки нет; иначе три явных `DELETE` в одной транзакции функции: (a)
   `DELETE FROM scans WHERE packet_id IN (SELECT id FROM scan_packets WHERE
   checkpoint_id=p_id)`, (b) `DELETE FROM scan_packets WHERE
   checkpoint_id=p_id`, (c) `DELETE FROM checkpoints WHERE id=p_id`. SQL-
   комментарий: `client_packet_id` удалённых пакетов освобождается,
   повторная офлайн-отправка больше не дедуплицируется — принятый риск.
9. `submit_scan_packet()` — `CREATE OR REPLACE`, копия текущего тела
   (`doc/db/scan_packets.sql:183-241`) с вставкой между guard-проверкой и
   `INSERT INTO scan_packets`:
   - `INSERT INTO checkpoints (type, day, status, created_by) VALUES
     ((payload->>'type_code')::smallint, payload->>'date', 1,
     (payload->>'author_id')::bigint) ON CONFLICT (day, type) WHERE
     status = 1 DO NOTHING;`
   - `SELECT id INTO v_checkpoint_id FROM checkpoints WHERE day =
     payload->>'date' AND type = (payload->>'type_code')::smallint AND
     status = 1 ORDER BY id DESC LIMIT 1;`
   - `checkpoint_id` добавляется в список колонок/значений `INSERT INTO
     scan_packets`.
   - Никакого нового `RAISE EXCEPTION` — пакет никогда не отклоняется из-за
     отсутствия точки. SQL-комментарий объясняет безопасность `ON
     CONFLICT ... DO NOTHING` + повторного `SELECT` при гонке двух
     воспитателей.
10. Все новые функции — `SECURITY DEFINER`, `SET search_path = public,
    pg_temp`.
11. Весь файл безопасно перезапускаемый (`IF NOT EXISTS`/`ADD COLUMN IF NOT
    EXISTS`/`CREATE OR REPLACE FUNCTION`).
12. Короткая сноска в `vault/03-База-данных/RLS-политики.md`: `checkpoints`
    спроектирована без антипаттерна «неотозванных широких legacy-политик» с
    самого начала.

# Риски

- Расширение `submit_scan_packet()` — `CREATE OR REPLACE`, полностью
  заменяет тело существующей боевой функции. Если применение прервётся
  между `DROP`/`CREATE` (Postgres делает это атомарно для `CREATE OR
  REPLACE`, риск теоретический) — откат невозможен без повторного
  применения `doc/db/scan_packets.sql`. Смягчение: файл идемпотентен и
  оставляет старое поведение (guard/идемпотентность/вставка в `scans`)
  нетронутым, только добавляет шаги до `INSERT INTO scan_packets`.
- Уникальный частичный индекс `(day, type) WHERE status=1` — если на
  боевой БД уже существуют «аварийные» дублирующиеся открытые точки одного
  типа (не должно быть, таблица новая) — создание индекса упадёт. Не
  актуально для новой таблицы, упомянуто для полноты.
