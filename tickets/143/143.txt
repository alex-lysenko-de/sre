# Ticket 143. Исправить обновление состояния переклички (Checkpoint) в реальном времени

## Описание проблемы

На экранах переклички (`/admin/checkpoints/...`) состояние (список
отмеченных детей/групп/автобусов) не обновляется автоматически, когда
пользователи сканируют детей с других устройств.

Сценарий:

1. Несколько пользователей сканируют детей (сканы уходят пакетами через
   `submit_scan_packet()` в таблицы `scans`/`scan_packets`, что должно
   отражаться в `checkpoints`).
2. Данные успешно записываются в БД.
3. У администратора, открывшего экран переклички, отображаемое число не
   меняется.
4. Обновление происходит только после ручной перезагрузки страницы.

Ожидаемое поведение: администратор видит актуальное состояние переклички
в реальном времени, без ручного обновления страницы.

## Что уже есть в проекте (проверено, не предположение)

В коде уже реализована Realtime-подписка через Supabase (`postgres_changes`)
— это не отсутствующая, а, судя по всему, неработающая функциональность:

* `CheckpointListView.vue` (`setupRealtimeSubscription()`) подписывается
  на таблицы `checkpoints` (`day=eq.<today>`) и `scan_packets`
  (`date=eq.<today>`).
* `CheckpointBusView.vue`, `CheckpointGroupView.vue`, `CheckpointLazyView.vue`
  — каждый подписывается на `checkpoints` (`id=eq.<id>`) и `scan_packets`
  (`checkpoint_id=eq.<id>`) для своего конкретного чекпоинта.
* Во всех случаях коллбэк — `debouncedReload()`, который просто перезапускает
  обычный fetch (`fetchCheckpointsForDay`/аналоги).
* Есть также `subscribeToCheckpointsChanges()` в
  `useSupabaseCheckpoints.js`/`useCheckpoints.js` (подписка только на
  `checkpoints`) — экспортируется, но, по имеющимся данным, нигде не
  вызывается (мёртвый/неиспользуемый путь — надо перепроверить при
  исследовании).

Таким образом, подписка на изменения таблицы `scans` напрямую не
предусмотрена архитектурой: обновления идут через `scan_packets`
(пакетная модель сканов, см. `vault/02-Предметная-область/Checkpoint.md`)
и через саму таблицу `checkpoints`.

## Возможная причина (найдена при проверке, требует подтверждения)

В дампе `backup/database/schema.sql` секция `supabase_realtime`
(`ALTER PUBLICATION supabase_realtime ADD TABLE ...`) перечисляет таблицы
`children`, `children_today`, `groups_today`, `reset_events`,
`user_group_day`, `users` — но **не содержит** `checkpoints` и
`scan_packets`. Если это соответствует состоянию текущей БД, то Postgres
вообще не публикует изменения этих двух таблиц в логическую репликацию,
и клиентские подписки в коде (см. выше) никогда не получат событие —
независимо от того, насколько правильно написан клиентский код. Это
первое, что нужно проверить.

## Что нужно исследовать

Проверить весь путь от записи скана до обновления интерфейса и найти,
на каком шаге происходит разрыв:

1. Состоят ли таблицы `checkpoints` и `scan_packets` в публикации
   `supabase_realtime` в реальной (не только в бэкап-дампе) БД —
   и если нет, добавить их (`ALTER PUBLICATION supabase_realtime ADD TABLE ...`).
2. Если таблицы в публикации есть — доходит ли событие до клиента:
   проверить RLS-политики на `checkpoints`/`scan_packets` (Supabase
   Realtime требует, чтобы у клиента было право SELECT по RLS на
   затронутую строку, иначе событие тихо не доставляется), проверить
   фильтры каналов (`day=eq.<today>`, `checkpoint_id=eq.<id>` и т.д. —
   типы и формат колонок должны совпадать с фильтром).
3. Если событие доходит — почему `debouncedReload()` не обновляет
   экран (ошибка в fetch, не пробрасываемая наверх; состояние
   `loading`/данные перезаписываются, но не триггерят перерисовку; и т.п.).
4. Отдельно проверить `subscribeToCheckpointsChanges()` — используется
   ли она где-либо, и если нет, не тянет ли её существование к путанице
   (два параллельных, частично дублирующих друг друга механизма подписки).
5. Проверить стабильность самого WebSocket-соединения Supabase Realtime
   (не отваливается ли подписка при простое вкладки/потере фокуса без
   переподключения).

## Требуемый результат

1. Причина, по которой обновления в реальном времени не работают
   (или работают не всегда).
2. Точное место неисправности (БД-публикация / RLS / фильтр канала /
   клиентский код обработки события).
3. Исправление проблемы либо чёткое описание необходимых изменений,
   если исправление выходит за рамки этого тикета.
4. Краткое описание результата исследования в отчёте по тикету:
   причина, место неисправности, внесённые изменения.

## Критерии приемки

* новые сканы (через `scan_packets`), влияющие на состояние переклички,
  отображаются у администратора на всех связанных экранах
  (`CheckpointListView`, `CheckpointBusView`, `CheckpointGroupView`,
  `CheckpointLazyView`) без перезагрузки страницы;
* изменения таблицы `checkpoints` (открытие/закрытие/пересчёт) также
  корректно и без перезагрузки отражаются в интерфейсе;
* поведение стабильно воспроизводится повторно (не работает "иногда"
  после простоя вкладки/потери сети).
