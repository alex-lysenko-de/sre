# Реализованные изменения

## Диагностика (шаг 1 плана)

Основная гипотеза плана — `checkpoints`/`scan_packets` отсутствуют в
логической публикации `supabase_realtime`, поэтому Postgres не
рассылает WAL-изменения этих таблиц в Realtime независимо от
корректности клиентского кода/RLS.

Подтверждение выполнено **статическим анализом**, а не прямым запросом
`SELECT tablename FROM pg_publication_tables WHERE pubname =
'supabase_realtime'` к боевой БД: у меня в этой сессии нет инструмента
прямого доступа к БД (ни `psql`, ни MCP-сервера Supabase, ни
Management API для произвольного SQL — только сервисный ключ, который
даёт REST/PostgREST-доступ, а не выполнение произвольных SQL-команд
вроде `ALTER PUBLICATION`). Это тот же порядок работы, что и во всех
предыдущих тикетах серии 132/138: SQL-миграция готовится и кладётся в
`doc/db/`, применяет её пользователь через Supabase SQL Editor.

Что именно проверено:
- `backup/database/schema.sql:7080-7139` — секция `supabase_realtime`
  перечисляет ровно 6 таблиц (`children`, `children_today`,
  `groups_today`, `reset_events`, `user_group_day`, `users`).
  `checkpoints`/`scan_packets` в списке нет.
- Поиском по всему `doc/db/*.sql` (включая `checkpoints.sql`,
  `scan_packets.sql`) не найдено ни одного `ALTER PUBLICATION` —
  подтверждает, что этот шаг никогда не был оформлен как воспроизводимый
  SQL-скрипт для этих двух таблиц.

Дамп `backup/database/schema.sql` актуален по состоянию на тикет 138
(последнее подтверждённое побайтовое сравнение с боевой БД, тикет 139),
т.е. уже после появления `checkpoints`/`scan_packets` — если бы
публикация была включена вручную после их создания, это отразилось бы
в дампе. Гипотеза считается подтверждённой с высокой уверенностью, но
формально не верифицирована прямым запросом к живой БД (см. раздел
«Отклонения от плана»).

Вторичные гипотезы (RLS, формат фильтров, стабильность WebSocket,
необработанные ошибки в `debouncedReload()`) не проверялись — по плану
они актуальны только если первая гипотеза не подтвердится.

## Исправление

Создан `doc/db/checkpoints_realtime_publication.sql` с двумя командами
`ALTER PUBLICATION supabase_realtime ADD TABLE ...` для `checkpoints`
и `scan_packets`, по тому же оформлению, что и предыдущие SQL-скрипты
проекта (`doc/db/checkpoints.sql`, `doc/db/scan_packets.sql`) —
заголовок-комментарий с объяснением причины и пометкой «Apply manually
via the Supabase SQL editor».

## Мёртвый код

Грепом по всему репозиторию (не только `src/`) подтверждено: вызовов
`subscribeToCheckpointsChanges()` нет нигде, кроме определения/экспорта
в `useSupabaseCheckpoints.js`/`useCheckpoints.js` и упоминаний в текстах
предыдущих тикетов (132-135, 143). Функция удалена из обоих файлов
вместе с её экспортами (именованным и в `default export` объекте
`useCheckpoints.js`). Это устраняет вводящий в заблуждение неполный
параллельный механизм (не слушал `scan_packets`), не связанный с
основным исправлением.

## Документация

`vault/03-База-данных/checkpoints.md` и `scan_packets.md` дополнены
разделом «Realtime», явно фиксирующим членство в публикации
`supabase_realtime` и причину бага — раньше это нигде не было
задокументировано, что и стало причиной, почему шаг был пропущен при
создании таблиц в тикетах 122/132.

# Отклонения от плана

- **Шаг 1 плана («Подтвердить основную гипотезу на боевой БД» через
  `SELECT ... FROM pg_publication_tables`) не выполнен буквально** — в
  сессии ИИ-ассистента нет инструмента для прямого SQL-запроса к живой
  БД. Гипотеза подтверждена статическим анализом дампа (см. выше) с
  высокой, но не стопроцентной уверенностью. Требуется, чтобы
  пользователь перед/после применения миграции сам выполнил проверочный
  запрос — точный текст уже есть в комментарии
  `checkpoints_realtime_publication.sql`.
- **Шаг 3 плана («проверить эффект вручную... в двух браузерных
  сессиях/устройствах») не выполнен** — по той же причине (нет доступа
  к нескольким устройствам/браузерам и к самой возможности применить
  миграцию из этой сессии). Требует ручной проверки пользователем после
  применения SQL-скрипта.
- Вторичные гипотезы (шаг 4 плана) не исследовались — по плану они
  актуальны только при опровержении основной гипотезы, чего в рамках
  этой сессии установить не удалось (см. выше).

Всё остальное выполнено согласно `IMPLEMENTATION_PLAN.md` без
отклонений.

# Миграции

`doc/db/checkpoints_realtime_publication.sql` — **не применена к боевой
БД**. Требует ручного выполнения через Supabase SQL Editor. Команда
`ALTER PUBLICATION ... ADD TABLE` не идемпотентна (ошибка, если таблица
уже состоит в публикации) — в комментарии к файлу указан проверочный
запрос, который стоит выполнить до применения.
