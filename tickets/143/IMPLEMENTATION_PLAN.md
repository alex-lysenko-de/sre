# Цель

Найти и устранить причину, по которой экраны переклички
(Checkpoint) не обновляются в реальном времени при поступлении новых
сканов от других пользователей, вынуждая администратора вручную
перезагружать страницу.

Документ описывает диагностическую гипотезу (обоснованную анализом кода
и БД-дампа), порядок её проверки и рекомендуемое исправление. Согласно
роли Software Architect, код не пишется и не изменяется — только план.

# Анализ текущей архитектуры

## Клиентский механизм Realtime уже реализован

Вопреки формулировке задачи («предположительно, процесс должен
работать...»), в коде уже есть полноценная реализация подписки на
Supabase Realtime (`postgres_changes`), причём в двух местах:

1. **Используемый путь** — инлайн-подписки прямо во вьюхах:
   - `src/views/CheckpointListView.vue` (`setupRealtimeSubscription()`,
     строки ~215-232): канал `checkpoint-list-changes`, слушает
     `checkpoints` (`filter: day=eq.<today>`) и `scan_packets`
     (`filter: date=eq.<today>`), коллбэк — `debouncedReload()`
     (400 мс дебаунс → `load()` → `fetchCheckpointsForDay()`).
   - `src/views/CheckpointBusView.vue`,
     `src/views/CheckpointGroupView.vue`,
     `src/views/CheckpointLazyView.vue` — идентичный паттерн, канал
     `checkpoint-{type}-{id}-changes`, слушает `checkpoints`
     (`id=eq.<id>`) и `scan_packets` (`checkpoint_id=eq.<id>`).
   - Все четыре вью корректно освобождают канал в `onUnmounted()`
     (`supabase.removeChannel(realtimeChannel)`).
2. **Неиспользуемый параллельный путь** — `subscribeToCheckpointsChanges()`
   в `src/composables/useSupabaseCheckpoints.js` (строки 184-195,
   подписка только на `checkpoints`, без `scan_packets`), пробрасывается
   через `useCheckpoints.js` (строка 36, экспорт строка 624). Поиском по
   `src/views/**` и `src/components/**` ни одного вызова не найдено —
   похоже на мёртвый код, оставшийся от более раннего варианта дизайна
   (комментарий в коде ссылается на паттерн из уже удалённого тикетом 137
   `AdminBusView.vue`).

Итог: сама подписка на постгрес-события в клиентском коде архитектурно
корректна и уже соответствует описанию из `vault/02-Предметная-область/Checkpoint.md`
(«Все три детальных экрана обновляются по Realtime... без ручной кнопки
«Aktualisieren»»). Значит проблема не в отсутствии кода, а в том, что
события либо не доходят до клиента, либо (менее вероятно) доходят, но
не приводят к перерисовке.

## Основная гипотеза: таблицы не входят в публикацию `supabase_realtime`

Supabase Realtime доставляет `postgres_changes` только для таблиц,
явно добавленных в логическую публикацию `supabase_realtime`
(`ALTER PUBLICATION supabase_realtime ADD TABLE ...`) — это отдельный
шаг, не связанный с наличием кода на клиенте или с RLS.

В `backup/database/schema.sql` (актуальный дамп, последний раз
обновлён коммитом тикета 138, т.е. уже после появления `checkpoints`
и `scan_packets` в тикетах 122/132) секция публикации перечисляет:

```
ALTER PUBLICATION supabase_realtime ADD TABLE ONLY public.children;
ALTER PUBLICATION supabase_realtime ADD TABLE ONLY public.children_today;
ALTER PUBLICATION supabase_realtime ADD TABLE ONLY public.groups_today;
ALTER PUBLICATION supabase_realtime ADD TABLE ONLY public.reset_events;
ALTER PUBLICATION supabase_realtime ADD TABLE ONLY public.user_group_day;
ALTER PUBLICATION supabase_realtime ADD TABLE ONLY public.users;
```

`checkpoints` и `scan_packets` в этом списке **отсутствуют**. Дополнительно
подтверждено поиском по всему репозиторию (`doc/db/*.sql`,
`doc/supabase_install.md`) — ни один из скриптов, создававших эти две
таблицы (`doc/db/checkpoints.sql`, `doc/db/scan_packets.sql`), не
содержит `ALTER PUBLICATION`. Похоже, что для более старых таблиц
(`children`, `children_today` и т.д.) публикация была один раз включена
вручную через Supabase Dashboard («Enable Realtime» на таблице) —
шаг, который нигде не задокументирован и не воспроизведён в виде SQL-
скрипта в репозитории — и этот же ручной шаг, по всей видимости, просто
забыли выполнить, когда добавляли `checkpoints`/`scan_packets`
(тикеты 122/132).

Это полностью объясняет наблюдаемое поведение: клиент подписывается
корректно, WebSocket-соединение живо, но Postgres физически не
публикует WAL-изменения этих двух таблиц в логическую репликацию —
события никогда не приходят, независимо от корректности клиентского
кода. Ручная перезагрузка страницы работает, потому что она идёт через
обычный REST-запрос (`fetchCheckpointsForDay`), а не через Realtime.

**Эта гипотеза — вывод из статического анализа дампа БД, а не
подтверждённый факт о боевой БД.** Дамп мог устареть, либо публикация
могла быть включена позже вручную без соответствующего коммита в
`backup/`. Первый шаг реализации — обязательно проверить фактическое
состояние публикации в боевой БД (см. «План реализации»), прежде чем
считать проблему решённой.

## Вторичные гипотезы (на случай, если основная не подтвердится)

Если проверка покажет, что `checkpoints`/`scan_packets` уже в
публикации, разрыв нужно искать дальше по цепочке:

- **RLS.** Проверено: `checkpoints_select_authenticated` и
  `scan_packets_select_authenticated` — обе `FOR SELECT TO authenticated
  USING (true)`, без ограничений. Блокировки на уровне RLS маловероятны,
  но стоит перепроверить на боевой БД (RLS-политики могли разойтись с
  дампом так же, как и публикация).
- **Формат фильтров канала.** `checkpoints.day` и `scan_packets.date` —
  `character varying` (не `date`), фильтры `day=eq.<todayString()>` /
  `date=eq.<todayString()>` сравнивают со строкой в формате
  `YYYY-MM-DD` — по типам совпадает, но стоит явно сверить, что
  значения, реально записываемые в эти колонки (например, в
  `submit_scan_packet()`/триггерах), используют тот же формат даты, а
  не, например, локаль-зависимый или с другим разделителем.
  `scan_packets.checkpoint_id` — `bigint`, фильтр `checkpoint_id=eq.<id>`
  из параметра маршрута (строка) — предположительно совместимо, но
  тоже стоит подтвердить логами канала.
- **Стабильность WebSocket-соединения.** Известный класс проблем
  Supabase/браузеров — подписка молча отваливается после длительного
  простоя вкладки (потеря фокуса, засыпание вкладки/устройства) и не
  переподключается автоматически. Симптом совпадает с «работает после
  перезагрузки» и мог бы объяснить нестабильное, но не постоянное
  проявление бага.
- **Обработка ошибок в `debouncedReload()`/`load()`.** Если `load()`
  бросает исключение (например, временная сетевая ошибка), оно сейчас
  нигде не перехватывается — `loading.value = false` не выполнится, но
  экран тоже не обновится и не покажет ошибку пользователю. Маловероятная,
  но проверяемая причина «иногда не обновляется».

# Изменения существующих компонентов

Изменения в `src/` не запланированы в рамках основной гипотезы — она
решается на уровне БД. Единственное точечное изменение кода,
допустимое в рамках этого тикета (не выходит за его формулировку,
т.к. прямо служит цели «исправить обновление в реальном времени» и не
добавляет новой функциональности):

- Удаление неиспользуемой `subscribeToCheckpointsChanges()` из
  `useSupabaseCheckpoints.js`/`useCheckpoints.js`, **если** разработчик
  подтвердит грепом по всему проекту (включая тесты, если есть), что у
  неё действительно нет вызывающего кода. Это устраняет вводящий в
  заблуждение параллельный (и при этом заведомо неполный — не слушает
  `scan_packets`) механизм подписки, который мог сбить с толку при
  предыдущей отладке этой же проблемы.

Если после проверки основной гипотезы (публикация) проблема сохранится,
следующий раунд диагностики (вторичные гипотезы) может потребовать
правок в `debouncedReload()`/`load()` каждой из четырёх вью (добавить
обработку ошибок) — но это выходит за рамки данного плана и должно
рассматриваться отдельно, по факту результатов первого раунда.

# Новые компоненты

Не требуются.

# Изменения БД

Основное рекомендуемое изменение — добавить обе таблицы в
Realtime-публикацию:

```sql
ALTER PUBLICATION supabase_realtime ADD TABLE public.checkpoints;
ALTER PUBLICATION supabase_realtime ADD TABLE public.scan_packets;
```

Оформить отдельным файлом в `doc/db/` (по конвенции проекта — рядом с
`checkpoints.sql`/`scan_packets.sql`), чтобы шаг был воспроизводим и
задокументирован — в отличие от более старых таблиц, где этот шаг был,
судя по всему, сделан вручную и нигде не зафиксирован.

Никаких изменений схемы (колонок, индексов, RLS, триггеров) не
требуется — используются существующие таблицы как есть.

# API изменения

Нет — Supabase Realtime не является отдельным API-слоем проекта,
изменения происходят на уровне конфигурации БД и не затрагивают RPC
(`create_checkpoint`, `finish_checkpoint` и т.д.) или
`submit_scan_packet()`.

# UI изменения

Нет новых элементов интерфейса. Наблюдаемый пользователем эффект —
устранение необходимости вручную перезагружать страницу; существующие
экраны и их вёрстка не меняются.

# План реализации

1. **Подтвердить основную гипотезу на боевой БД.** Выполнить
   `SELECT tablename FROM pg_publication_tables WHERE pubname =
   'supabase_realtime';` (через Supabase SQL Editor или `psql`) и
   убедиться, что `checkpoints`/`scan_packets` действительно
   отсутствуют. Это первый и самый дешёвый шаг диагностики — если он
   подтверждается, вероятность того, что это и есть причина, очень
   высока (полностью объясняет все описанные в тикете симптомы).
2. Если гипотеза подтвердилась — применить `ALTER PUBLICATION` из
   раздела «Изменения БД» к боевой БД, оформить SQL-скрипт в
   `doc/db/`.
3. Проверить эффект вручную: открыть `CheckpointListView` и один из
   детальных экранов (например, `CheckpointBusView`) в двух разных
   браузерных сессиях/устройствах, выполнить скан с другого устройства,
   убедиться, что оба экрана обновляются без перезагрузки в течение
   ~1-2 секунд (с учётом 400 мс дебаунса).
4. Если после шага 2-3 проблема **не** устранена — перейти к
   вторичным гипотезам по порядку (RLS на боевой БД → формат
   фильтров/логи канала в devtools → стабильность WebSocket при
   простое вкладки → обработка ошибок в `load()`), с обязательной
   фиксацией в `IMPLEMENTATION_REPORT.md`, какая именно причина
   подтвердилась.
5. Проверить и, если подтвердится неиспользуемость,
   удалить `subscribeToCheckpointsChanges()` (мёртвый код) —
   отдельным, легко проверяемым коммитом/шагом.
6. Обновить `vault/03-База-данных/checkpoints.md` и
   `vault/03-База-данных/scan_packets.md` явным упоминанием, что обе
   таблицы состоят в публикации `supabase_realtime` (сейчас это нигде
   явно не задокументировано — именно поэтому шаг было легко забыть).

# Риски

1. **Гипотеза может не подтвердиться.** Дамп `backup/database/schema.sql`
   может быть неактуален относительно боевой БД (публикация могла быть
   добавлена позже вручную без коммита дампа). В этом случае шаг 1
   плана (SQL-запрос к живой БД) сразу это покажет, без риска
   бесполезно тратить время на применение `ALTER PUBLICATION`,
   которое ничего не изменит (сама команда идемпотентна и безопасна
   для повторного/лишнего применения — `ADD TABLE` к таблице, уже
   состоящей в публикации, вернёт ошибку, а не тихо испортит
   состояние, так что риск от «лишнего» применения минимален, но шаг
   всё равно не будет полезен).
2. **Объём Realtime-трафика.** Включение публикации на `scan_packets`
   означает, что каждое изменение пакета будет транслироваться всем
   подписанным клиентам (сейчас — до 4 канала на пользователя:
   список + до 3 детальных экрана открытых одновременно). При большом
   числе одновременно открытых админ-вкладок в пиковые моменты
   (массовое сканирование) это создаёт дополнительную нагрузку на
   Supabase Realtime и на клиентские `debouncedReload()`-запросы — но
   это именно то поведение, которое запрошено в тикете (реалтайм-
   обновление), и дебаунс в 400 мс уже смягчает избыточные перезапросы.
3. **Мёртвый код `subscribeToCheckpointsChanges()` может оказаться не
   таким уж мёртвым.** Если поиск вызовов пропустит динамический
   импорт или использование за пределами `src/` (например, в
   отдельном скрипте/тесте), удаление сломает что-то незаметное для
   грепа. Требуется тщательная проверка перед удалением; при сомнении —
   не удалять в рамках этого тикета, оставить как отдельный
   технический долг.
4. **Вторичные гипотезы не гарантируют полное покрытие.** Если
   основная гипотеза не подтвердится и ни одна из перечисленных
   вторичных причин тоже не объяснит проблему, потребуется более
   глубокое исследование (например, логирование самого Supabase
   Realtime клиента), выходящее за рамки объёма, заложенного в этот
   план.

# Definition of Done

- Подтверждено (SQL-запросом к боевой БД), состояли ли
  `checkpoints`/`scan_packets` в публикации `supabase_realtime` до
  начала работ — результат зафиксирован в `IMPLEMENTATION_REPORT.md`.
- Если гипотеза подтвердилась — `ALTER PUBLICATION` применён к боевой
  БД, соответствующий SQL-скрипт добавлен в `doc/db/`.
- Реальное обновление в реальном времени проверено вручную на всех
  четырёх экранах (`CheckpointListView`/`Bus`/`Group`/`Lazy`) сценарием
  «скан с одного устройства → появление изменения на экране
  администратора без перезагрузки» — задокументировано в
  `IMPLEMENTATION_REPORT.md` (либо явно отмечено как не выполненное,
  если нет доступа к нескольким устройствам в сессии).
- Если основная гипотеза не подтвердилась — задокументирована
  фактически найденная причина и внесённое исправление (или явно
  зафиксировано, что требуется дальнейшее исследование за рамками
  этого тикета).
- `subscribeToCheckpointsChanges()` либо удалена (если подтверждено
  как мёртвый код), либо оставлена с пометкой в
  `IMPLEMENTATION_REPORT.md`, почему её решили не трогать.
- `vault/03-База-данных/checkpoints.md`/`scan_packets.md` обновлены
  упоминанием о членстве в публикации `supabase_realtime`.
- `tickets/dashboard.md` обновлён.
