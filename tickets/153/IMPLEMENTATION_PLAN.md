# Цель

Убрать визуальное "мигание" (полное пропадание уже отрисованного контента
и замену его на полноэкранный спиннер) на четырёх Checkpoint-вью
(`CheckpointListView.vue`, `CheckpointBusView.vue`, `CheckpointGroupView.vue`,
`CheckpointLazyView.vue`) при фоновых обновлениях, вызванных Realtime
(`debouncedReload()`) или мутациями (`handleCreate`/`onFinish`/`onReopen`/
`onSetBaseline`). Полноэкранный спиннер должен показываться ровно один раз —
при самой первой загрузке экрана, когда контента ещё нет. Побочная цель
(Minor 3 из ревью 143, напрямую связана): `load()` должен гарантированно
сбрасывать `loading` в `false` даже при исключении внутри
await-последовательности (сейчас — не сбрасывает, "вечный спиннер").

Явно вне рамок (зафиксировано в 153.txt, раздел "Что решить на этапе
IMPLEMENTATION_PLAN" и подтверждено этим планом ниже):
показ пользователю текста ошибки при неудачном фоновом `load()`;
блокировка кнопок действий (`Schließen`/`Öffnen`/...) на время их
собственного `await` — не относится к мультипликации спиннера, отдельная
уже существующая (не новая) особенность поведения этих кнопок.

# Анализ текущей архитектуры

Все четыре вью не используют общий composable/компонент для состояния
"загрузка + список/деталь" — паттерн `loading`/`load()`/`debouncedReload()`/
`realtimeChannel`/`reloadDebounceTimer` продублирован по коду отдельно в
каждом файле (архитектурная особенность, унаследованная от тикетов 134/135,
не пересматривается в рамках 153 — правка ticket 153 сознательно точечная,
не рефакторинг в общий composable).

Прочитаны все четыре файла целиком, структура `load()` в каждом:

* **`CheckpointListView.vue`** (`load()`, строки 171-179): линейная
  последовательность без ветвления — `loading.value = true` →
  `fetchCheckpointsForDay()` → `summarizeCheckpoint()` на каждый checkpoint →
  `loading.value = false`. Простейший случай.

* **`CheckpointBusView.vue`** (`load()`, строки 194-218) и
  **`CheckpointGroupView.vue`** (`load()`, строки 187-209): идентичная по
  форме структура с ранним `return` — если `fetchCheckpointDetail()` вернул
  `null` (checkpoint не найден/удалён), функция сбрасывает `resultSummary`,
  ставит `loading.value = false` и выходит (строки 197-201 / 190-194) **до**
  основного `Promise.all([...])`. Экран "Checkpoint nicht gefunden"
  (`v-else` в шаблоне, за пределами `v-if="loading"`) — такой же полноценный
  результат загрузки, как и найденный checkpoint, поэтому по логике
  153.txt эта ветка тоже должна отмечаться как "уже показано что-то",
  а не заново запускать полноэкранный спиннер при повторном срабатывании
  (например, если checkpoint был удалён с другого устройства, пока экран
  открыт).

* **`CheckpointLazyView.vue`** (`load()`, строки 195-204): структурно
  отличается от Bus/Group — вместо раннего `return` здесь `if
  (checkpoint.value) { ... }`, оборачивающий вызов
  `fetchLazyCheckpointProgress()`/`summarizeCheckpoint()`, а
  `loading.value = false` стоит один раз в конце функции безусловно (уже
  после `if`). Веток два (найден/не найден), но обе сходятся в одной точке
  выхода — проще, чем в Bus/Group, учесть в реализации.

Проверено намеренно (пункт 3 из "Что решить на этапе IMPLEMENTATION_PLAN"
в 153.txt): ни в одном из четырёх файлов `loading` не используется нигде,
кроме собственного `v-if="loading"` в шаблоне того же файла. Кнопки действий
(`Schließen`/`Öffnen`/`Als Tagesreferenz festhalten`/`Entfernen`/`Neuen
Checkpoint erstellen`) не имеют `:disabled` от `loading` и не проверяют
`loading` в обработчиках — блокировки кликов на время мутации через
`loading` сегодня нет нигде из четырёх вью. Значит, вывод `loading` из-под
контроля `load()` (кроме первого раза) не отбирает у кода никакой
уже существующей защиты от повторного клика — риска регрессии по этой
линии нет, отдельный флаг `actionInProgress` не требуется (он был бы нужен,
только если бы `loading` сегодня использовался как побочный лок; это не
так — проверено чтением, а не предположением).

`checkpoint.value`/`checkpoints.value`/`results.value`/`resultSummary.value`/
`breakdownCounts.value`/`busDeltas.value`/`progress.value` — все обновляются
в `load()` полным переприсваиванием нового объекта/массива, а не
точечной мутацией. Это не проблема для устранения мигания: `v-for` в
шаблонах всех четырёх вью использует `:key` (`cp.id`/`bus.busNumber`/
`group.groupId`/`child.id`), поэтому Vue уже сегодня диффит списки по ключу
и перерисовывает только изменившиеся DOM-узлы — сама техника обновления
данных менять не требуется, единственная причина видимого "мигания" это
`v-if="loading"`, размонтирующий/монтирующий целиком блок с контентом.
Локальное UI-состояние, не связанное с `load()` напрямую (например,
`expandedBusNumber` в `CheckpointBusView.vue`) не сбрасывается в `load()`
сегодня и не должно начать сбрасываться — эта правка его не касается.

# Изменения существующих компонентов

Во всех четырёх файлах — идентичная по идее правка, только в теле функции
`load()`, плюс одна новая модульная (не `ref`) переменная рядом с уже
существующими `realtimeChannel`/`reloadDebounceTimer`:

```js
let hasLoadedOnce = false
```

**`CheckpointListView.vue`** — обернуть тело `load()` в `try/finally`,
условно выставлять `loading.value = true`, ставить `hasLoadedOnce = true`
после успешного заполнения `results.value`:

```js
async function load() {
  if (!hasLoadedOnce) loading.value = true
  try {
    checkpoints.value = await fetchCheckpointsForDay(todayString())
    const entries = await Promise.all(
        checkpoints.value.map(async cp => [cp.id, await summarizeCheckpoint(cp)])
    )
    results.value = Object.fromEntries(entries)
    hasLoadedOnce = true
  } finally {
    loading.value = false
  }
}
```

**`CheckpointBusView.vue`** / **`CheckpointGroupView.vue`** — та же схема,
но `hasLoadedOnce = true` должен быть проставлен в **обеих** ветках (найден
и не найден), так как экран "Checkpoint nicht gefunden" — тоже полноценный
результат первой загрузки (обоснование см. "Анализ текущей архитектуры").
Проще всего — не дублировать присваивание в обеих ветках, а поставить его
один раз в `finally` (симметрично `loading.value = false`), так как
`hasLoadedOnce = true` не имеет смысловой разницы между "успех" и "успех, но
пусто" — обе ветки функции достигают точки выхода без исключения:

```js
async function load() {
  if (!hasLoadedOnce) loading.value = true
  try {
    checkpoint.value = await fetchCheckpointDetail(Number(route.params.id))
    if (!checkpoint.value) {
      resultSummary.value = null
      return
    }
    const [summary, breakdown, betreuerList, deltas] = await Promise.all([...])
    // ...как сегодня...
  } finally {
    hasLoadedOnce = true
    loading.value = false
  }
}
```

(Порядок принципиален: `hasLoadedOnce = true` внутри `finally` перед
`loading.value = false`, а не после — иначе при исключении на самом первом
вызове `hasLoadedOnce` останется `false`, и следующий `debouncedReload()`
после сбоя снова покажет полноэкранный спиннер; это корректно и совпадает
с ожидаемым поведением "первая *успешная* загрузка" — если первая попытка
упала с исключением, экран ещё ничего не показал, значит следующая
попытка обязана вести себя как первая. `finally` выполняется в обоих
случаях, "успех" и "исключение", поэтому `hasLoadedOnce = true` внутри
`finally` без разбора успеха некорректен — правильная формулировка:
`hasLoadedOnce = true` ставится **в конце `try`**, а не в `finally`; в
`finally` остаётся только `loading.value = false`. Именно так и
сформулировано в примере 153.txt для `CheckpointListView.vue` — при
переносе на Bus/Group это означает `hasLoadedOnce = true` должен стоять
и в конце основной ветки, и в конце ветки "не найден", а не в общем
`finally`.)

**`CheckpointLazyView.vue`** — из-за структуры `if (checkpoint.value) {
...}` без раннего `return`, `hasLoadedOnce = true` ставится один раз, сразу
после `if`-блока, перед `finally`:

```js
async function load() {
  if (!hasLoadedOnce) loading.value = true
  try {
    const id = Number(route.params.id)
    checkpoint.value = await fetchCheckpointDetail(id)
    if (checkpoint.value) {
      progress.value = await fetchLazyCheckpointProgress(id)
      resultSummary.value = await summarizeCheckpoint(checkpoint.value)
    }
    hasLoadedOnce = true
  } finally {
    loading.value = false
  }
}
```

Общее для всех четырёх файлов:

* Сигнатура `load()` не меняется (без параметров, `async`, вызывается так
  же из `onMounted`/`debouncedReload`/`handleCreate`/`onFinish`/
  `onSetBaseline`/`onReopen`) — вызывающие места не трогаются.
* Шаблон (`v-if="loading"` / `v-else...`) — не меняется, само условие
  показа спиннера остаётся прежним; меняется только частота, с которой
  `loading` становится `true`.
* `debouncedReload()`, `setupRealtimeSubscription()`, `onUnmounted()` — не
  меняются.
* Побочный эффект `try/finally`: `loading.value = false` гарантированно
  выполняется при исключении внутри `load()` — закрывает Minor 3 из
  ревью 143 для всех четырёх файлов одновременно. Само содержимое
  обработки ошибки (сообщение пользователю, retry) — не входит, как
  зафиксировано в 153.txt.

# Новые компоненты

Не требуются. Отдельный "тихий" индикатор фонового обновления (маленький
спиннер/иконка/вспышка подсветки при изменении цифр), упомянутый в 153.txt
как рассмотренная альтернатива, — архитектурное решение этого плана:
**не реализуется в рамках тикета 153**. Обоснование: сам текст 153.txt
формулирует требование как "спиннер не показывается" (первая, приоритетная
часть пользовательского запроса), а не как "показывается иначе"; более
тонкий индикатор потребовал бы отдельной, разной по вёрстке правки под
каждый из четырёх структурно разных экранов (список карточек в List,
детальная карточка с разными блоками в Bus/Group/Lazy) — то есть отдельного
UI-дизайна, не только правки `load()`, и был бы избыточен по объёму
относительно точечного характера бага (мигание). Остаётся, как и указано в
153.txt, опциональным будущим улучшением вне этого тикета — если понадобится,
за ним должен последовать отдельный тикет с собственным UI-дизайном под
каждый экран.

# UI изменения

* Полноэкранный спиннер (`v-if="loading"`, `.spinner-border`) показывается
  один раз — сразу после открытия экрана (список чекпоинтов или детали
  одного чекпоинта), пока данных ещё нет.
* Любой последующий вызов `load()` — от Realtime (`debouncedReload()`),
  от `handleCreate`/`onFinish`/`onSetBaseline`/`onReopen` — обновляет
  данные в `ref`'ах "на месте" без показа спиннера повторно: список/деталь
  не пропадает и не перерисовывается с нуля, только изменившиеся
  текст/цифры/бейджи/строки списка обновляются (уже штатное поведение
  Vue при переприсваивании ref-значений с `:key`'ами в `v-for`, само по себе
  не требует правок).
* Никакого нового визуального индикатора фонового обновления не вводится
  (см. "Новые компоненты") — обновление происходит незаметно, как и
  выбрано в 153.txt в качестве базового варианта.
* Ветка "Checkpoint nicht gefunden" (`CheckpointBusView.vue`/
  `CheckpointGroupView.vue`/`CheckpointLazyView.vue`) при повторных
  вызовах `load()` (например, checkpoint удалён с другого устройства, пока
  экран открыт) больше не проходит через полноэкранный спиннер — сразу
  переключается на текст "не найден" без промежуточного мигания.
* Поведение кнопок действий (`Schließen`/`Öffnen`/`Als Tagesreferenz
  festhalten`/`Entfernen`/`Neuen Checkpoint erstellen`) не меняется — они и
  сегодня не блокируются на время своего `await` и не зависят от `loading`;
  эта правка не вводит и не убирает такую блокировку.

# План реализации

1. `CheckpointListView.vue`: добавить `let hasLoadedOnce = false`, обернуть
   тело `load()` в `try/finally` по образцу из 153.txt (см.
   "Изменения существующих компонентов").
2. `CheckpointBusView.vue`: та же правка, с учётом ранней ветки "не
   найден" — `hasLoadedOnce = true` ставится в обеих точках выхода из
   `try` (конец успешной ветки и конец ветки "не найден"), не в `finally`.
3. `CheckpointGroupView.vue`: идентично шагу 2 (структура `load()`
   идентична `CheckpointBusView.vue`).
4. `CheckpointLazyView.vue`: `hasLoadedOnce = true` один раз, сразу после
   `if (checkpoint.value) {...}`-блока, перед `finally`.
5. Ручная проверка в браузере/DevTools (эмуляция медленной сети —
   "Slow 3G"/"Throttling" — чтобы гарантированно застать промежуточное
   состояние) на каждом из четырёх экранов:
   * первое открытие экрана показывает спиннер один раз;
   * искусственно вызвать несколько `debouncedReload()` подряд (проще
     всего — сделать пару сканов/мутаций с другого устройства/вкладки, как
     описано в критериях приёмки 153.txt) — контент не пропадает, спиннер
     не появляется повторно, изменившиеся цифры/строки обновляются на
     месте;
   * для `CheckpointBusView.vue`/`CheckpointGroupView.vue`/
     `CheckpointLazyView.vue` — открыть существующий checkpoint, удалить
     его с другого устройства/вкладки, убедиться что экран переключается
     на "Checkpoint nicht gefunden" без промежуточного спиннера;
   * искусственно спровоцировать исключение в `load()` (например, временно
     testing-патчем сломать один из await-вызовов или отключить сеть в
     момент вызова) и убедиться, что `loading` гарантированно возвращается
     в `false`, а не зависает — только для проверки, без изменений кода
     после проверки.
6. `npm run build` — убедиться, что сборка проходит без ошибок/warning по
   всем четырём изменённым файлам.

Порядок жёсткий только в части "правки во всех четырёх файлах предшествуют
ручной проверке" — шаги 1-4 между собой независимы (разные файлы, можно в
любом порядке или параллельно).

# Риски

* **Низкий**: неверная расстановка `hasLoadedOnce = true` относительно
  `try`/`finally` (например, по ошибке внутрь `finally` без разбора
  успеха) свела бы на нет полезный побочный эффект — при первом же
  исключении экран считал бы, что "уже показано что-то", хотя реальный
  контент так и не появился, и следующий фоновый `load()` (после
  восстановления сети) прошёл бы без спиннера поверх ещё пустого экрана.
  Явно расписано в "Изменения существующих компонентов" для избежания
  этой ошибки при реализации.
* **Низкий**: `CheckpointBusView.vue`/`CheckpointGroupView.vue` имеют два
  выхода из `try` (успех / "не найден") — риск забыть проставить
  `hasLoadedOnce = true` в одной из веток. Явно указано в плане реализации
  (шаги 2-3) как отдельная проверка.
* Риска регрессии для логики выбора/мутации (`onFinish`/`onReopen`/
  `onSetBaseline`/`onRemove`/`handleCreate`) нет — эти функции не меняются,
  они лишь вызывают уже изменённый `load()` в конце; подтверждено анализом,
  что `loading` нигде не используется как блокировка кликов, значит
  убирание частых `true`/`false` переключений не открывает новых путей для
  двойных кликов, которых не было бы и сегодня.
* Риска для Realtime/дебаунса нет — `debouncedReload()` и
  `setupRealtimeSubscription()` не меняются, частота вызовов `load()`
  остаётся прежней; меняется только то, что происходит **внутри** `load()`
  с `loading`.
* Как и в остальных тикетах серии Checkpoint, автотестов для этих экранов
  в проекте нет — единственная проверка регрессии ручная (шаг 5 плана
  реализации), включая явную проверку сценария исключения в `load()`,
  так как это неочевидное для глаза изменение (пока не удастся спровоцировать
  ошибку, невозможно увидеть разницу между старым и новым поведением
  `loading` при сбое).

# Definition of Done

* После первой успешной загрузки экрана (список чекпоинтов или детали
  одного чекпоинта, включая ветку "не найден" для Bus/Group/Lazy) ни один
  последующий вызов `load()` — ни от Realtime (`debouncedReload()`), ни от
  `handleCreate`/`onFinish`/`onSetBaseline`/`onReopen` — не показывает
  полноэкранный спиннер повторно и не приводит к видимому "пропаданию"
  уже отрисованного контента.
* Полноэкранный спиннер по-прежнему показывается один раз — сразу после
  открытия экрана, пока данных ещё нет.
* Если `load()` бросает исключение (в любой момент, не только при первой
  загрузке), `loading` гарантированно возвращается в `false` во всех
  четырёх файлах — экран не зависает в состоянии "вечный спиннер".
* `npm run build` проходит без ошибок по всем четырём изменённым файлам.
* Правка ограничена телом функции `load()` и одной новой модульной
