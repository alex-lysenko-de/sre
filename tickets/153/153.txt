# Ticket 153. Убрать мигание экрана Checkpoint-вью при частых Realtime-обновлениях

## Контекст

Найдено в ревью тикета 143 ([tickets/143/review_report.md](../143/review_report.md),
раздел "Архитектурные замечания") как побочный эффект того, что тикет 143
наконец включает реально работающий Realtime (до 143 подписка была
заведена, но события не долетали — таблиц не было в публикации
`supabase_realtime`).

Во всех четырёх Checkpoint-вью (`CheckpointListView.vue`,
`CheckpointBusView.vue`, `CheckpointGroupView.vue`, `CheckpointLazyView.vue`)
один и тот же паттерн:

```js
const loading = ref(true)
...
async function load() {
  loading.value = true
  // ...await-запросы к Supabase...
  loading.value = false
}

function debouncedReload() {
  if (reloadDebounceTimer) clearTimeout(reloadDebounceTimer)
  reloadDebounceTimer = setTimeout(load, 400)
}

// realtime-подписка на checkpoints/scan_packets вызывает debouncedReload()
```

и в шаблоне:

```html
<div v-if="loading" class="text-center py-5">
  <div class="spinner-border" role="status"></div>
</div>
<div v-else>...реальный контент...</div>
```

`loading.value = true` безусловно заменяет уже отрисованный контент на
полноэкранный спиннер при **каждом** вызове `load()` — не только при
первой загрузке экрана, но и при каждом последующем `debouncedReload()`.
При ожидаемой частоте не менее ~15 пакетов в минуту (сканы прилетают от
нескольких сканеров одновременно) это означает, что список/детали
чекпоинта у администратора будет пропадать и перерисовываться с нуля
каждые несколько секунд — экран практически непрерывно "мигает". При
плохом качестве интернета эффект усиливается вдвойне: сам `await`-запрос
внутри `load()` выполняется дольше, поэтому и спиннер-заглушка держится
дольше при каждом срабатывании.

## Первопричина

`loading` в текущем коде смешивает два разных по смыслу состояния:

1. "На экране вообще ещё нечего показать" (первая загрузка сразу после
   `onMounted` — единственный случай, когда полноэкранный спиннер
   оправдан и ожидаем пользователем).
2. "На экране уже есть актуальные (на момент предыдущей загрузки) данные,
   сейчас идёт их фоновое обновление" (любой `debouncedReload()` от
   Realtime, а также `handleCreate()`/`onFinish()`/`onReopen()` и другие
   вызовы `load()` после мутации) — в этом случае блокировать/скрывать уже
   отрисованный контент не нужно и вредно для UX: пользователь смотрит на
   список/детали, а не на пустой экран с крутилкой.

Оба случая сегодня используют один и тот же флаг и один и тот же
`v-if="loading"`, который отличает не "первая загрузка/фоновое
обновление", а исключительно "запрос выполняется/не выполняется".

Отдельно (Minor 3 из ревью 143, не блокирующий, но напрямую связанный):
`load()` ни в одном из четырёх вью не обёрнут в `try/catch` — при
исключении внутри `await`-цепочки `loading.value = false` не выполнится,
и экран зависнет в состоянии "вечный спиннер" без сообщения об ошибке.
Особенно вероятно именно при "плохом качестве интернета", то есть в тех
же условиях, что усиливают и мигание.

## Предлагаемое решение

Простое и локальное для каждого из четырёх вью: спиннер показывается
**только один раз** — при самой первой успешной загрузке экрана, когда
показывать ещё действительно нечего. Любой последующий вызов `load()`
(от Realtime, от `debouncedReload()`, от `handleCreate`/`onFinish`/
`onReopen` и т.п.) обновляет данные в реактивных `ref`'ах "на месте", не
трогая `loading` — Vue сам перерисует только изменившиеся куски DOM
(текст/цифры/бейджи), без полного размонтирования списка/карточки.
Экран не пропадает и не мигает ни разу после первой отрисовки.

Реализуется без изменения сигнатур `load()`/`debouncedReload()` и без
изменения вызывающих мест — минимальная правка внутри самой функции
`load()` в каждом из четырёх файлов:

```js
const loading = ref(true)
let hasLoadedOnce = false

async function load() {
  if (!hasLoadedOnce) loading.value = true
  try {
    checkpoints.value = await fetchCheckpointsForDay(todayString())
    const entries = await Promise.all(
        checkpoints.value.map(async cp => [cp.id, await summarizeCheckpoint(cp)])
    )
    results.value = Object.fromEntries(entries)
    hasLoadedOnce = true
  } finally {
    loading.value = false
  }
}
```

(пример для `CheckpointListView.vue`; для `CheckpointBusView.vue`/
`CheckpointGroupView.vue` — та же идея, `hasLoadedOnce = true` ставится
сразу после успешного `fetchCheckpointDetail(...)`, **до** ветки
"checkpoint не найден", так как отображение "не найден" — тоже
полноценный, а не пустой экран).

Побочный эффект такой формулировки (`try/finally` вместо голого
`loading.value = true/false` россыпью по функции) — заодно закрывает
Minor 3 из ревью 143: `loading` теперь гарантированно сбрасывается в
`false` даже при исключении внутри `load()`, вместо зависания в
"вечном спиннере". Само содержимое `catch`/сообщение об ошибке
пользователю в это исправление не входит (см. "Что решить на этапе
IMPLEMENTATION_PLAN") — это отдельный, более широкий вопрос
error-handling, специально не смешиваем с точечным фиксом мигания.

`hasLoadedOnce` — обычная модульная переменная (как уже существующие
`realtimeChannel`/`reloadDebounceTimer` в этих же файлах), не `ref` —
она не используется в шаблоне и не должна быть реактивной.

### Почему не отдельный «тихий» индикатор обновления

Рассматривался вариант с отдельным лёгким индикатором (маленький
спиннер/иконка в углу карточки) на время фонового `load()`, не
затрагивающим сам контент — технически он ближе ко второй фразе
пользовательского запроса ("показывается, но экран не мигает"). Он
возможен как последующее улучшение, но требует персональной вёрстки под
каждый из четырёх разных по структуре вью (список карточек в List,
детальная карточка в Bus/Group/Lazy) — то есть не такое простое и
единообразное решение, как вариант выше (первая фраза запроса — "спиннер
не показывается", применительно к фоновым обновлениям). Оставляем как
опциональное улучшение на будущее, а не часть этого тикета — см. "Что
решить на этапе IMPLEMENTATION_PLAN".

## Затронутые части

* `src/views/CheckpointListView.vue`
* `src/views/CheckpointBusView.vue`
* `src/views/CheckpointGroupView.vue`
* `src/views/CheckpointLazyView.vue`

Правка в каждом файле — только тело функции `load()` + одна новая
модульная переменная `hasLoadedOnce`. Шаблоны (`v-if="loading"`),
`debouncedReload()`, realtime-подписки, остальные функции — не меняются.

## Что решить на этапе IMPLEMENTATION_PLAN

* Нужен ли пользователю какой-либо, пусть минимальный, визуальный сигнал
  о том, что фоновое обновление вообще произошло (например, короткая
  вспышка подсветки изменившейся карточки/цифры) — или достаточно того,
  что цифры просто обновляются сами по себе без индикации, как решено
  выше.
* Осознанно оставляем вне рамок этого тикета: показ пользователю ошибки
  при неудачном фоновом `load()` (сейчас — тихо игнорируется, только не
  зависает спиннер) — это Minor 3 из ревью 143 в полном объёме
  (retry-логика/toast/сообщение), а не только утечка `loading`.
* Проверить, не полагается ли где-то ещё в этих же вью на побочный эффект
  `loading.value = true` от `load()` как на способ временно спрятать
  контент во время мутации (например, чтобы пользователь не кликнул на
  ещё не актуальные данные во время `onFinish()`/`onReopen()`) — если да,
  для таких мест стоит отдельный явный флаг (например, `actionInProgress`
  для блокировки кнопок), а не общий `loading`.

## Критерии приемки

* После первой успешной загрузки экрана (список чекпоинтов или детали
  одного чекпоинта) ни один последующий вызов `load()` — ни от Realtime
  (`debouncedReload()`), ни от `handleCreate`/`onFinish`/`onReopen` — не
  показывает полноэкранный спиннер повторно и не приводит к видимому
  "пропаданию" уже отрисованного контента.
* Полноэкранный спиннер по-прежнему показывается один раз — сразу после
  открытия экрана, пока данных ещё нет.
* Если `load()` бросает исключение (в любой момент, не только при первой
  загрузке), `loading` гарантированно возвращается в `false` — экран не
  зависает в состоянии "вечный спиннер".
* `npm run build` проходит.
* Ручная проверка на устройстве/в браузере: держать открытым
  `CheckpointListView.vue` (или один из детальных экранов), выполнить
  подряд несколько сканов с другого устройства/вкладки в течение минуты
  — экран не должен ни разу "мигнуть" (пропасть и появиться), только
  цифры/список должны обновляться на месте.
