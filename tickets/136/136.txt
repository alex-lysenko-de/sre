# Тикет 136: Entity-слой на реальных данных (Child/Betreuer/Group карточки, универсальный список)

Часть фазы реализации Checkpoint — см. `tickets/131/MIGRATION_PLAN.md`.
Переносит «энтити-центрированную» часть UI-прототипа (UX-фидбек Раунд 4
тикета 130_2 — принципы 1–5 из `tickets/130/decision.md`, «Child /
Group / Betreuer как самостоятельные сущности со своей карточкой и
маршрутом») на реальные данные `children`/`users`/`user_group_day`.

## Цель

Заменить mock-источники (`useChildEntityMock.js`, `useBetreuerEntityMock.js`,
`useGroupEntityMock.js`, `useScanHistoryMock.js`) реальными Supabase-
запросами, сохранив набор переиспользуемых presentational-компонентов
(`ChildLink`/`BetreuerLink`/`GroupLink`/`CountLink`/`EntityListCard`) и
экранов (Child card/edit, Betreuer card, Group entity, универсальный
список), уже согласованных и принятых в 130_2.

## Что прочитать перед началом

- `src/composables/useChildEntityMock.js`, `useBetreuerEntityMock.js` —
  эталонные сигнатуры (`getChildById`, `getChildrenByGroup`,
  `updateChild`, `getBetreuerById`, `getBetreuerByName`) и комментарий о
  том, какие поля мока не имеют реального аналога (родители/телефон
  ребёнка — не переносить; email/phone Betreuer — **есть** в реальной
  таблице `users`, см. `tickets/131/MIGRATION_PLAN.md`, §1.3, п.5).
- `src/components/checkpoints-prototype/{ChildLink,BetreuerLink,GroupLink,
  CountLink,EntityListCard}.vue` — переиспользуемые компоненты, переезжают
  почти без изменений (только источник данных у вызывающих экранов).
- `src/views/{ChildCardPrototypeView,ChildEditPrototypeView,
  BetreuerCardPrototypeView,GroupEntityPrototypeView,
  EntityListPrototypeView}.vue` — экраны-эталоны.
- `src/views/ChildDetailView.vue`, `src/views/ChildEditView.vue` — уже
  существующие реальные экраны карточки/редактирования ребёнка (не в
  namespace прототипа) — реальная схема полей `children`
  (`age`/`schwimmer`/`band_id`/`notes`/`group_id`/`bus_id`, без
  родителей/телефона) уже используется здесь, ориентир для полей
  реальной Checkpoint-карточки ребёнка.
- `src/composables/useChildren.js`, `fetchChildDetailsAndScans(childId)`
  — готовая функция для истории сканирований ребёнка, заменяет
  `useScanHistoryMock.js`.
- Реальная схема таблиц `children` (id, name, age, schwimmer, status,
  notes, group_id, band_id, bus_id), `users` (id, email, phone,
  display_name, role, active), `user_group_day` (user_id, group_id,
  bus_id, day) — `backup/database/schema.sql:3650-3662, 3899-3910,
  3938-3950` (сверить с живой БД, дамп может отставать, см.
  `tickets/131/MIGRATION_PLAN.md`, §1.3, п.3).

## Затрагиваемые части проекта

Новые файлы под `src/components/checkpoints/` и продолжение
`src/views/*` без суффикса `Prototype`. Существующие
`ChildDetailView.vue`/`ChildEditView.vue` не меняются — Checkpoint-карточка
ребёнка ведёт кнопкой «Bearbeiten» на уже существующий `/child-edit/:id`,
а не дублирует его (`131/IMPLEMENTATION_PLAN.md`, «UI изменения»).

## Файлы/подсистемы, которые будут изменены

- Компоненты `src/components/checkpoints/{ChildLink,BetreuerLink,
  GroupLink,CountLink,EntityListCard}.vue` — копии из
  `checkpoints-prototype/`, без изменений логики (только импорт
  реальных composables вместо мока в вызывающих экранах, сами эти
  компоненты в основном presentational и получают данные через props).
- Новые экраны: `src/views/ChildCardView.vue`, `src/views/BetreuerCardView.vue`,
  `src/views/GroupEntityView.vue`, `src/views/EntityListView.vue`
  (`ChildEditPrototypeView.vue` **не переносится** — см. «Что не входит»).
- Новый файл `src/composables/useBetreuerEntity.js` (реальный, читает
  `users` с фильтром `role != 'admin'` либо без фильтра — на усмотрение
  реализации, см. открытый вопрос ниже).
- `useChildren.js` — используется как есть для карточки ребёнка,
  возможно, дополняется недостающей функцией списка по группе (если
  `fetchGroupDetails()` из `useGroups.js` уже покрывает это — оценить по
  месту, не дублировать).

## Что должно быть реализовано

1. `getChildById(id)`/`getChildrenByGroup(groupId)` — реальные запросы к
   `children`, без полей `parentA`/`parentB`/`phone` (не существуют в
   реальной схеме — карточка ребёнка эти поля просто не показывает, как
   уже сделано в `ChildDetailView.vue`).
2. Реальный аналог `getBetreuerById(id)`/`getBetreuerByName(name)` —
   запрос к `users`. **Открытый вопрос для решения по месту**: должен ли
   список ограничиваться `role != 'admin'`, или показывать всех
   пользователей — сверить с тем, как сегодня формируется список
   Verantwortliche/Betreuer в `AdminBusView.vue`/`ChildrenView.vue`, не
   изобретать новый критерий.
3. `EntityListView.vue` — универсальный список (переезд из
   `EntityListPrototypeView.vue`), источник данных переключается на
   реальные `children`/`users` в зависимости от типа сущности.
4. Карточка ребёнка вызывает `useChildren.fetchChildDetailsAndScans(childId)`
   напрямую для истории сканирований, вместо `useScanHistoryMock.js`.
5. Кнопка «Bearbeiten» на реальной карточке ребёнка ведёт на уже
   существующий `/child-edit/:id` (`ChildEditView.vue`) — не создавать
   параллельный редактор.
6. Маршруты — по аналогии с прототипом, но без суффикса `-prototype`;
   точные пути финализируются вместе с тикетом 137 (общий namespace
   `/admin/checkpoints/...`), не обязательно фиксировать в этом тикете
   изолированно.

## Что не входит

- `ChildEditPrototypeView.vue` не переносится вообще (см. п.5 выше).
- Сами Checkpoint-экраны (List/Bus/Group/Lazy) — тикеты 137–140,
  используют компоненты этого тикета, но реализуются отдельно.
- Изменение реальной схемы `children`/`users` — полям
  «родители»/«телефон ребёнка» из мока не добавляется реальный аналог.

## Результат выполнения тикета

- Presentational-компоненты и entity-экраны работают на реальных
  Supabase-данных, визуально эквивалентны прототипу 130_2 (с поправкой
  на реальные, не выдуманные поля).
- `npm run build` проходит без ошибок.
- Ручная проверка на устройстве/в браузере: открытие карточки реального
  ребёнка/Betreuer/группы показывает корректные данные.

## Зависимости

Не требует 132–134/135 напрямую (работает с уже существующими таблицами
`children`/`users`/`user_group_day`) — может выполняться параллельно с
132–135. Мягкая связь: если экраны 137–140 к моменту готовности этого
тикета уже используют `useCheckpoints.js` (135) для сводных данных,
интеграция entity-ссылок с этими экранами требует и 135. Блокирует 137,
138, 139, 140 (все используют `ChildLink`/`BetreuerLink`/`GroupLink`).
