## Critical

### 1. Раздел «03-База-данных» описывает устаревшую схему; 6 таблиц не задокументированы вовсе

`vault/03-База-данных/Обзор-схемы-БД.md:9-13` заявляет: «Постоянного каталога
`supabase/migrations/` в репозитории нет — источником истины по схеме служат
`doc/table_structure.md`... применяемые вручную». Это неверно: в репозитории
уже есть авторитетный, свежий источник — `backup/database/schema.sql`
(pg_dump реальной БД, коммит `17e206d`, тикет 111), закоммиченный **до**
коммита `56476d7` (тикет 108). Он не упомянут ни разу ни в
`IMPLEMENTATION_PLAN.md`, ни в самих заметках раздела 03 (grep по vault на
`schema.sql`/`backup/database`/`pg_dump` — 0 совпадений в разделе 03; файл
упомянут вскользь только в `Сборка-и-деплой.md` как «инструмент бэкапа»,
без использования как источника схемы).

Сверка `vault/03-База-данных/*.md` с `backup/database/schema.sql` (реальный
`CREATE TABLE public.*`, строки 3593–3990):

- **Отсутствуют целиком** 6 таблиц из `public` и не упомянуты вообще:
  `admin_logs`, `calendar`, `invites`, `scan_type`, `sessions`,
  `webauthn_challenges` (плюс `auth.webauthn_credentials`). `calendar`
  активно используется в `src/views/DaysEditView.vue`, `invites`/`sessions`/
  `webauthn_*` — в `supabase/functions/{auth,invite-generate,invite-accept}`.
  Это не «мёртвая» схема — это часть системы, о которой в базе знаний нет ни
  строки.
- `children.md` — DDL пропускает реальные колонки `last_scan_at
  timestamp with time zone` и `bus_id smallint` (обе есть в
  `public.children`, schema.sql:3650-3662).
- `config.md` — DDL пропускает `description`, `access_level smallint
  DEFAULT 1`, `name`. `access_level` — не мелочь: на нём построена RLS-политика
  `"Public read access" ON public.config FOR SELECT USING ((access_level = 3))`
  (schema.sql:6446) — заметка о конфиге не может объяснить, кто что видит,
  без этого поля.
- `reset_events.md` — DDL пропускает колонку `children_count integer
  DEFAULT 0` и указывает `user_id smallint`, тогда как реально `user_id

  присутствует/подтверждено»). В реальной таблице такого поля нет вообще —

### 2. Раздел «Модель аутентификации» не отражает реальную систему аутентификации — целый подслой пропущен

`vault/04-Пользователи-и-аутентификация/Модель-аутентификации.md:6-8`
описывает аутентификацию исключительно как «Supabase Auth» с двумя ролями
поверх `auth.users`. Но реальная схема (см. находку #1) содержит
полноценный дополнительный слой: `public.sessions` (кастомные токены сессий,
`token_hash`, `device_id`, `revoked`), `public.invites` (инвайт-токены с
ролью и сроком действия), `public.webauthn_challenges` +
`auth.webauthn_credentials` (WebAuthn/passkey), и функции
`is_session_valid()`, `has_role()`, `is_admin()`, `update_last_seen()`
(schema.sql:748-1037). Этому соответствует edge-функция
`supabase/functions/auth/index.ts` — **413 строк**, явно не сводящихся к
«серверным операциям аутентификации» одной строкой в таблице
(`Обзор-Edge-Functions.md:20`).

Разработчик сам зафиксировал в `IMPLEMENTATION_REPORT.md` («Отклонения от
плана»), что `supabase/functions/*/index.ts` не читались построчно «по
явному выбору владельца проекта» — но описывает это как экономию на
технической точности одной заметки о Edge Functions. По факту пропущен не
частный технический нюанс, а отдельный архитектурный слой аутентификации
(passkey/WebAuthn + собственные сессии поверх/вместо Supabase Auth),
который прямо входит в пункт тикета «Модель учета пользователей» и является
частью DoD плана («модель аутентификации» как отдельный обязательный пункт
покрытия). Это следует зафиксировать явно (аналогично находке про
`groups`/`buses`) как отдельную секцию или заметку, а не оставлять
implicit-пропуском.

## Major

### 3. RLS-политики.md переоценивает фактическую строгость RLS

`vault/03-База-данных/RLS-политики.md:34-53` описывает модель доступа к
`children_today` как «запись — либо владелец контекста (своя группа на
сегодня), либо admin» (политики `own_group_update_presence_now` /
`own_group_insert_presence_now`, тикет 106). Это верно только отчасти:
реальная БД (schema.sql:6278-6376) содержит **более старые, не отозванные**
permissive-политики того же типа операции — `"Allow authenticated users to
update children_today" ... USING (true) WITH CHECK (true)`, аналогично
insert/delete для `children_today`, `groups_today`, `reset_events`, а также
`update`/`insert` для `children` и `days` (`USING (true)`). В PostgreSQL RLS
несколько permissive-политик на одно действие объединяются через **OR** —
значит для этих таблиц узкая «своя группа» политика ничего не ограничивает:
любой `authenticated` может писать в любую строку, потому что старая
`USING (true)`-политика её всё равно разрешает.

Заметка утверждает обратное: «RLS — единственная граница, которая реально
исполняется сервером на каждый запрос» (строка 59-60) — это верно
концептуально, но в применении к `children_today` создаёт ложное ощущение,
что запись ограничена группой Betreuer, хотя фактически это не так. Раз
заметка претендует быть источником истины для новых участников команды и
объяснения архитектурных решений (явная цель тикета 108), эта неточность
имеет прямые последствия для security-репутации документа: инженер,
доверившийся заметке, ошибочно предположит более узкую поверхность атаки,
чем есть на самом деле.

**Требуется:** либо зафиксировать явно, что legacy-политики `USING (true)`
всё ещё активны и делают `own_group_*`-ограничение декоративным (с
рекомендацией удалить дублирующие широкие политики), либо, если это
намеренное поведение — объяснить почему.

### 4. `?id=`/`?n=` редирект описан как применимый к «любому маршруту», хотя фактически работает только для `/main` и `/info`

`vault/06-Маршруты-и-URL/Карта-маршрутов.md:45-49` и
`QR-код-URL.md:12-15` утверждают: роутер перехватывает `id`/`n` «как
query-параметр **любого** маршрута». Однако в `src/router/index.js:186-235`
блок `if (to.meta.requiresAuth) { ... return next(...) }` возвращается на
каждой ветке (успех, ошибка авторизации, неактивный пользователь, отказ
admin-проверки) — код после этого блока (строки 238-242, сама проверка
`to.query.id || to.query.n`) физически недостижим для любого маршрута с
`requiresAuth: true`. Публичные маршруты (`meta.public: true`) тоже
возвращаются раньше (строка 181-183). Проверка `id`/`n` реально срабатывает
только для маршрутов с `requiresAuth: false` и без `meta.public` — в
текущей карте это исключительно `/main` и `/info`.

На практике это совпадает с основным сценарием (короткая QR-ссылка ведёт на
`/` → редирект на `/main`), поэтому баг не в поведении приложения, а в
точности документации — но именно этот механизм тикет 108.md явно называет
контрольным пунктом («используемые URL и маршруты... публичные QR-код
URL»), так что неточность здесь особенно нежелательна.
