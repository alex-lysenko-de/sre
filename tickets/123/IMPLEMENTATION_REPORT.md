# Измененные файлы

- `src/composables/useChildren.js` — `fetchChildrenByGroup(groupId)`:
  сортировка `.order('name', { ascending: true })` заменена на
  `.order('id', { ascending: true })` (п. 3 требования — стабильный
  порядок, не зависящий от переименования ребёнка). Единственный
  потребитель функции (проверено `grep` по `src/`) — `HeadcountView.vue`,
  никакой другой экран не затронут.
- `src/views/HeadcountView.vue` — полностью переработан согласно плану:
  карточно-списочная раскладка заменена на плотную таблицу (Концепт A,
  выбран пользователем перед началом кода — см. «Отклонения от плана»),
  добавлены кнопка «Scan» и выезжающая панель со встроенным `Scanner.vue`.
  Бизнес-логика загрузки данных (`Promise.all(fetchChildrenByGroup,
  getTodayGroupPresence)`) и ручной отметки (`onTogglePresentNow()` →
  `setPresentNow()`) перенесены без изменений в сигнатуре/семантике.
  Переведён с Options API на `<script setup>` (тот же паттерн, что уже
  использует `MainView.vue`/три `Scanner*View.vue`) — необходимо для
  чистой интеграции нового composable без раздувания `data()`/`methods`.
- `src/router/index.js` — маршрут `/headcount` переведён со статического
  импорта на ленивый (`component: () => import(...)`), по тому же
  паттерну, что уже используют маршруты `/scanner/*` (тикет 120). Это не
  предусмотрено планом буквально («router/index.js не затрагивается»),
  но потребовалось из-за побочного эффекта, обнаруженного при сборке —
  см. «Отклонения от плана».

# Реализованные изменения

Реализовано строго по `tickets/123/IMPLEMENTATION_PLAN.md`, шаги 3–6
(шаги 1 и 2 — см. «Отклонения от плана», шаги 7–8 — см. «Проверки»):

1. **Сортировка ростера** — `useChildren.fetchChildrenByGroup()` теперь
   упорядочивает по `id`, тот же принцип, что уже применяется в
   `useArmband.getChildrenByGroupOrderedById()` (тикет 120) — решение
   согласовано с уже принятым в проекте подходом, не вводит новый.
2. **Табличная раскладка (Концепт A)** — `table table-sm` без
   карточки-обёртки и внешних отступов, порядковый номер, столбцы
   Morgens (только чтение, `<input type="checkbox" disabled>`) и Jetzt
   (обычный чекбокс, `@change` → `setPresentNow()`), строки с
   `Jetzt = false` подсвечены `bg-danger-subtle`. Столбец Morgens
   скрывается целиком, если ни у одного ребёнка группы ещё нет
   `presence_morning = 1` за сегодня (эвристика по плану, приближённая —
   см. «Риски» плана, не переопределяется этим отчётом).
3. **Панель сканера** — кнопка «Scan» полноширинная над таблицей;
   выезжающая сверху панель (`<transition>` + `max-height`) с
   `Scanner.vue` внутри без изменений его контракта; панель ограничена
   `max-height: 50vh` (`overflow-y: auto`) — попадает в требуемый
   диапазон «примерно верхняя четверть-половина экрана»; таблица
   остаётся видимой ниже (не модальное затемнение).
4. **Обработка скана** — `onChildResolved` панели подключён к
   `useGroupScanSession.handleResolved`: успешный скан «своего» ребёнка
   немедленно переключает `presentNow` соответствующей строки таблицы,
   дубликат внутри раунда — стандартный «успех» с `repeat: true` (тот же
   паттерн, что `ScannerGroupView.vue`), чужая группа — та же
   бизнес-ошибка `variant: 'error'`.
5. **Автозакрытие** — 5 секунд без нового успешного скана закрывают
   панель (`Scanner.vue` размонтируется через `v-if`, что останавливает
   камеру в его собственном `onBeforeUnmount`), кнопка «Scan» появляется
   заново; закрытие инициирует фоновую `submitPacket()`; повторное
   открытие панели начинает новую сессию (`createPacket()` с новым
   `client_packet_id`).
6. **Ошибка фоновой отправки** — компактное сообщение
   (`alert alert-danger`) рядом с кнопкой «Scan» с действием
   «Wiederholen», переиспользующим идемпотентность `submitPacket()` (тот
   же `client_packet_id`/`finished_at`), без отдельного экрана и без
   отката уже выставленных в таблице отметок — тот же принятый в
   `ScannerGroupView.vue`/тикете 120 риск.

# Отклонения от плана

**Шаг 1 плана реализации («Ревью и выбор одного из двух табличных
концептов... контрольная точка с заказчиком... до начала кода»)** —
не мог быть выполнен мной самостоятельно (явное указание общей
инструкции «не принимай архитектурные решения самостоятельно»). Перед
началом любого кода пользователю был задан прямой вопрос с превью обоих
концептов (A/B) и вариантом «согласованная комбинация»; выбран
**Концепт A** («классическая таблица»). Реализация выполнена строго по
описанию Концепта A из плана.

**Шаг 2 плана реализации («Подтвердить, что серверная инфраструктура
120/122 реально развёрнута»)** — на момент начала этой сессии уже
подтверждено в рамках отдельного обращения по тикету 122: SQL-схема
`scan_packets` применена, Edge Function `submit-scan-packet` задеплоена
и проверена (`curl`, `OPTIONS` → `200`) — см.
`tickets/122/IMPLEMENTATION_REPORT.md`, раздел «Деплой и исправление
после сообщения об ошибке». Риск, которым план обосновывал этот шаг,
снят до начала работы над 123, поэтому шаг не блокировал переход к
шагам 3–6.

**`src/router/index.js` изменён, хотя план прямо указывает, что этот
файл не затрагивается.** Причина — обнаруженный при сборке побочный
эффект, не предусмотренный планом: маршрут `/headcount` был
статически импортирован (`import HeadcountView from ...`), и после
встраивания `Scanner.vue` (тянущего `html5-qrcode`) в этот экран
основной чанк `index-*.js` вырос с ~657 кБ до ~1011 кБ — весь код
сканера стал грузиться на **каждой** странице приложения, а не только
на `/headcount`. Три существующих маршрута `/scanner/*` (тикет 120) уже
используют ленивый импорт именно по этой причине. Изменение — замена
статического импорта на `component: () => import('@/views/HeadcountView.vue')`,
без изменения пути/имени маршрута/meta. Это не архитектурное решение и
не новая функциональность, а исправление конкретного измеримого
регресса (см. «Проверки»), в том же уже принятом в проекте паттерне.
Прочие пункты раздела «Не затрагиваются» плана (маршруты `/scanner/*`,
схема БД, Edge Function, `AdminBusView.vue`/`GroupDetailModal.vue`/
`BusDetailModal.vue`) действительно не изменены.

Других отклонений от плана нет.
