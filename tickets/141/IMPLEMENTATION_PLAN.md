# Цель

После успешной (или неуспешной) отправки пакета сканирования («Senden»)
в режимах `ScannerBusView`/`ScannerGroupView`/`ScannerCheckinView` окно
сканирования визуально остаётся открытым и камера продолжает
показывать картинку, но новые сканы больше не распознаются и не
попадают в список — продолжить работу без перезапуска экрана
невозможно.

Цель тикета — устранить причину зависания декодирования после
«Senden» так, чтобы модуль сканирования оставался полностью
работоспособным после отправки (первый вариант из 141.txt) **либо**,
если это окажется избыточно рискованным, гарантированно приводить
модуль в рабочее состояние эквивалентным по надёжности способом.
Функциональность сканирования (форматы пакетов, режимы BUS/GROUP/
CHECKIN, бизнес-правила) не меняется — это исправление конкретно
цикла камеры вокруг «Senden».

# Анализ текущей архитектуры

Общий сканер `Scanner.vue` (тикет 116, не менявшийся тремя режимами
120) инкапсулирует камеру/декод через библиотеку `html5-qrcode`
(`^2.3.8`) и не знает о режимах — общается с вызывающей стороной
только через проп `onChildResolved` и через `defineExpose({ start,
stop, showMessage })`.

Внутри `Scanner.vue` есть два независимых цикла паузы/возобновления
одного и того же `html5QrCode`/`<video>`-инстанса:

1. **Обычный цикл скана** (`onScanSuccess` → `showConfirmationScreen`
   → `wait()` → `resumeAfterConfirmation()`, `Scanner.vue:326-404`) —
   на каждый скан: `html5QrCode.pause(true)`, экран результата,
   `html5QrCode.resume()`.
2. **Внешнее сообщение** (`showExternalMessage`, `Scanner.vue:413-434`,
   единственный вызывающий — `scannerRef.value.showMessage(...)` из
   `handleSend()` всех трёх View, и в success-, и в error-ветке) —
   независимо повторяет тот же паттерн: `pause(true)` → экран
   «Gesendet»/«Fehler beim Senden» → `wait()` → `resume()`.

Оба цикла управляют **одним и тем же** `html5QrCode`-инстансом и его
`<video>`-элементом, но не координируются друг с другом и не проверяют
состояние друг друга — `isProcessing`, которым защищён путь (1),
никак не учитывается путём (2).

## Разбор `html5-qrcode` (`node_modules/html5-qrcode/esm/html5-qrcode.js`, `camera/core-impl.js`)

Чтение исходников библиотеки показывает конкретный механизм, который
объясняет ровно наблюдаемый симптом («картинка есть, декод не
работает»):

- `foreverScan()` (`html5-qrcode.js:553`) — бесконечный цикл через
  `setTimeout`, управляется только флагом `this.shouldScan` (снимается
  единственно в `stop()`). Он **всегда** перерисовывает кадр в canvas,
  независимо от паузы — отсюда «камера продолжает работать, изображение
  отображается».
- `scanContext()` (`:536`) — реальный декод — в самом начале делает
  `if (this.stateManagerProxy.isPaused()) return Promise.resolve(false)`.
  То есть декод полностью отключается, пока внутренний FSM
  (`stateManagerProxy`) находится в состоянии `PAUSED`, а видеопоток
  при этом продолжает рисоваться.
- `Html5Qrcode.prototype.resume()` (`:202`) — если
  `renderedCamera.isPaused()` (обёртка над нативным `<video>.paused`)
  верно, переход FSM обратно в `SCANNING` происходит **не сразу**, а
  внутри колбэка `RenderedCameraImpl.prototype.resume()`
  (`camera/core-impl.js:216`):
  ```js
  RenderedCameraImpl.prototype.resume = function (onResumeCallback) {
      ...
      var onVideoResume = function () { setTimeout(onResumeCallback, 200); ... };
      this.surface.addEventListener("playing", onVideoResume);
      this.surface.play();
  };
  ```
  FSM переходит в `SCANNING` **только если у нативного `<video>`
  успеет сработать событие `"playing"`**. Это событие — известное
  слабое место HTML5 video API: не гарантировано срабатывает при
  быстро следующих друг за другом/пересекающихся `play()`/`pause()` на
  одном и том же элементе (прерванный `play()`-промис, повторный
  `play()` при уже играющем видео и т.п., особенно на мобильных
  браузерах). Если событие не срабатывает — колбэк `resume()`
  **никогда** не вызывается: не бросается исключение, не отклоняется
  промис — просто тишина. FSM необратимо застревает в `PAUSED`, декод
  выключен навсегда, а `foreverScan()` продолжает рисовать кадры как
  ни в чём не бывало.

Ключевой вывод: **у сбоя `resume()` нет наблюдаемого сигнала ошибки** —
ни исключения, ни отклонённого промиса. Поэтому оборачивание
существующего `resume()` в try/catch (как уже сделано в коде) в
принципе не может обнаружить и исправить этот сбой.

Наиболее вероятный триггер именно «после Senden»: `handleSend()`
вызывает `showMessage()` сразу после сети (`submitPacket()`), в момент,
когда предыдущий цикл (1) от последнего реального скана мог ещё не
завершить свой `wait()`/`resumeAfterConfirmation()` (пользователь часто
жмёт «Senden» сразу после последнего скана, не дожидаясь автоскрытия
экрана подтверждения). Тогда циклы (1) и (2) накладываются друг на
друга и оба вызывают `pause()`/`play()`/`resume()` на одном и том же
`<video>` почти одновременно — это ровно тот сценарий пересекающихся
`play()`/`pause()`, в котором событие `"playing"` по опыту чаще всего
не срабатывает по одному из вызовов.

Дополнительно (не обязательный, но подтверждающий факт): экран
подтверждения — это непрозрачный `position:absolute; inset:0` блок
сплошного цвета (`.proto-confirmation.success`/`.error`,
`Scanner.vue:539-547`), полностью перекрывающий камеру визуально. То
есть `shouldPauseVideo = true` (реальная пауза `<video>`) в
`showExternalMessage()` не даёт никакого видимого эффекта — экран и
так полностью закрывает картинку с камеры. Единственная причина
паузы — не декодировать во время показа сообщения. Эта настоящая
пауза видео и есть источник риска, но не источник пользы.

Для сравнения: `startCamera()`/`html5QrCode.start()` (используется при
каждом монтировании `Scanner.vue` и уже проверено работающим) resolve-ится
из `camera.render(...).then(renderedCamera => { ...; resolve(null) })`
(`html5-qrcode.js:167-178`) — без зависимости от события `"playing"` на
уже существующем `<video>`. Это принципиально более надёжный путь,
чем `resume()`.

# Изменения существующих компонентов

## `Scanner.vue` — `showExternalMessage()`

Сегодня (упрощённо):

```js
const showExternalMessage = async (variant, display, durationMs) => {
  const wasActive = scannerActive.value
  if (wasActive) { await html5QrCode.pause(true) }
  showConfirmationScreen(variant, display)
  await wait(durationMs || durationFor(variant))
  hideConfirmationScreen()
  if (wasActive) { html5QrCode.resume() }   // <-- ненадёжный шаг
}
```

Меняется последний шаг: вместо `resume()`, зависящего от недетектируемо
падающего события `"playing"`, — гарантированный холодный перезапуск
камеры через уже существующие в этом же файле функции `stopScanning()`
и `startCamera()` (используют тот же путь инициализации, что и при
монтировании экрана — уже проверенно рабочий):

```js
const showExternalMessage = async (variant, display, durationMs) => {
  const wasActive = scannerActive.value
  if (wasActive) { await html5QrCode.pause(true) }
  showConfirmationScreen(variant, display)
  await wait(durationMs || durationFor(variant))
  hideConfirmationScreen()
  if (wasActive) {
    await stopScanning()
    await startCamera()
  }
}
```

Существенно:

- `stopScanning()` уже сегодня опирается на `stateManagerProxy`-проверку
  `isScanning()`, которая (в отличие от `isStrictlyScanning()` в
  `pause()`) верна и для `SCANNING`, и для `PAUSED` — то есть отработает
  корректно вне зависимости от того, застрял ли FSM в `PAUSED` или нет.
  Ошибку `.stop()` `stopScanning()` уже сегодня перехватывает и в
  `finally` всё равно сбрасывает `scannerActive.value = false` — то
  есть последующий `startCamera()` не заблокируется её guard'ом
  (`if (scannerActive.value || isTransitioning.value) return`).
- `startCamera()` — тот же путь, что при первом открытии экрана;
  показывает уже существующий оверлей «Scanner wird initialisiert...»
  (`isTransitioning`), так что для пользователя это выглядит как
  короткая, объяснимая перезагрузка камеры, а не необъяснимое
  зависание.
- Правка полностью локальна для `Scanner.vue` — три `ScannerXxxView.vue`
  не меняются, их контракт с `showMessage()` не меняется.

Разбор эксплицитно НЕ выбранной альтернативы (обёртка `resume()` в
watchdog/таймаут с последующим fallback на restart) — рассмотрена и
отклонена: как показано в анализе, сбой `resume()` не порождает ни
исключения, ни отклонённого промиса, только зависший колбэк — значит,
единственный надёжный способ понять «резюм не сработал» — это
завести отдельный таймер и следить за `html5QrCode.getState()` (не
экспортируется сегодня из компонента, пришлось бы дополнительно
импортировать `Html5QrcodeScannerState` только ради сравнения статусов).
Это сложнее, добавляет условную логику и время ожидания (нужно ждать
таймаут watchdog'а, прежде чем понять, что нужен restart), а выигрыш —
только в том, что в «удачном» случае не будет короткого мигания
камеры. Учитывая, что тикет прямо допускает более простое и грубое
решение («закрыть весь экран»), безусловный restart — простое решение
из того же семейства, но с меньшим ухудшением UX (не покидает экран
режима сканирования), поэтому предпочтителен.

# План реализации

1. Внести правку в `showExternalMessage()` (`Scanner.vue`), как описано
   выше.
2. Обновить/добавить комментарий над функцией, фиксирующий причину
   (ссылка на конкретную проблему `resume()`/событие `"playing"` в
   `html5-qrcode`), чтобы не потерялось обоснование при будущих правках
   компонента.
3. `npm run build` — убедиться, что сборка проходит (правка не меняет
   публичный контракт компонента).
4. Ручная проверка на устройстве (обязательна, так как первопричина —
   гипотеза по чтению стороннего кода библиотеки, не воспроизведена
   живым тестом в рамках архитектурного этапа):
   - для каждого из трёх режимов (Bus/Group/Checkin): отсканировать
     несколько человек, нажать «Senden» **сразу** после последнего
     скана (не дожидаясь исчезновения экрана подтверждения) —
     воспроизводит наиболее вероятный триггер гонки;
   - после экрана «Gesendet» — попытаться отсканировать ещё одного
     человека и убедиться, что он корректно добавляется в новый пакет;
   - то же самое для error-ветки (например, временно отключив сеть) —
     убедиться, что после экрана «Fehler beim Senden» сканер тоже
     остаётся рабочим;
   - убедиться, что короткое мигание/перезапуск камеры после «Senden»
     не воспринимается как баг/зависание (заметно, но объяснимо —
     тот же оверлей, что при первом открытии экрана).
5. Обновить `tickets/141/state.txt` и `tickets/dashboard.md` по факту
   выполнения реализации (вне рамок архитектурного этапа — на этапе
   `IMPLEMENTATION_REPORT.md`).

# Риски

1. **Гипотеза без живого воспроизведения.** Причина установлена чтением
   исходников `html5-qrcode` (`node_modules`), а не отладкой на живом
   устройстве/эмуляторе — ни у одной из предыдущих реализаций в этом
   проекте нет доступа к браузеру/устройству на этапе ИИ-сессии (см.
   `tickets/139` — сквозная device-проверка тоже не выполнена). Возможно,
   после правки симптом воспроизведётся не полностью или обнаружится
   дополнительная причина — обязателен пункт 4 плана реализации.
2. **UX-стоимость restart.** Полный `stop()+start()` тяжелее, чем
   `resume()`: заново запрашивается `getUserMedia`, короткая задержка
   (доли секунды — ~1-2 c) и видимый оверлей инициализации после
   *каждого* «Senden» (успешного и неуспешного), а не только когда
   реально нужно восстановление. Ticket 141 явно допускает более грубое
   решение (полное закрытие экрана) как приемлемое — restart отдельного
   компонента строго легче этого допустимого запасного варианта, но
   всё равно стоит подтвердить на устройстве, что задержка не
   раздражает.
3. **Тот же класс уязвимости в обычном цикле скана.** `onScanSuccess`/
   `resumeAfterConfirmation()` (путь 1) использует тот же
   `pause(true)`/`resume()` для каждого отдельного скана и теоретически
   подвержен тому же риску зависания `"playing"`, если пользователь
   умудрится наложить два скана почти одновременно (быстрое повторное
   поднесение бейджа). Тикет 141 по тексту описывает проблему именно
   «после Senden» — фикс объёма тикета намеренно ограничен
   `showExternalMessage()`; если тот же симптом (без Senden, просто при
   быстром сканировании подряд) когда-либо будет замечен, потребуется
   отдельный тикет на путь (1) по тому же принципу (restart вместо
   resume либо явная сериализация двух циклов через общий lock).
4. **Повторный `stop()` сразу после (возможно) уже не полностью
   отработавшего предыдущего цикла.** Если гонка была именно между
   циклами (1) и (2) (см. «Анализ»), `stopScanning()`, вызванный из
   (2), теоретически может столкнуться с тем, что `html5QrCode`
   находится в промежуточном состоянии из-за незавершённого `resume()`
   цикла (1). `stopScanning()` уже сегодня оборачивает `.stop()` в
   try/catch и гарантированно сбрасывает `scannerActive` в `finally` —
   независимо от исхода `.stop()`, `startCamera()` после него не
   заблокируется; худший случай — лишняя (безвредная) попытка
   остановки уже неактивной камеры.

# Definition of Done

- `showExternalMessage()` в `Scanner.vue` восстанавливает камеру после
  показа сообщения об отправке через гарантированный перезапуск
  (`stop()+start()`), а не через `resume()`, зависящий от
  недетектируемо ненадёжного события `"playing"`.
- Контракт `Scanner.vue` (пропсы, `defineExpose`) и все три
  `ScannerXxxView.vue` не изменены.
- `npm run build` проходит.
- Ручная проверка на устройстве (п. 4 плана реализации) подтверждает:
  после «Senden» (успех и ошибка), во всех трёх режимах, новые сканы
  снова корректно распознаются и добавляются в список без
  необходимости покидать/перезаходить на экран.
- Если ручная проверка опровергнет гипотезу (симптом сохранится) —
  зафиксировать это в `IMPLEMENTATION_REPORT.md` и вернуться к
  архитектурному этапу для пересмотра (например, реализация запасного
  варианта из 141.txt — автозакрытие экрана после отправки).
