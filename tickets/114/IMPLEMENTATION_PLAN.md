# Цель

Исправить два прямых дефекта в коде экранов авторизации, из-за которых
пользователь после успешного входа по логину/паролю или после успешной
регистрации по invite-ссылке попадает на `/info` вместо домашней страницы
`/main`. Редирект на `/info` должен по-прежнему срабатывать только для
гостей без активной сессии (см. `router/index.js`) и оставаться доступным
через явную ссылку в меню.

Задача не предполагает изменений в логике `router.beforeEach` — она уже
проверена и не содержит каскадных редиректов (см. раздел «Анализ текущей
архитектуры»).

# Анализ текущей архитектуры

Аутентификация и маршрутизация описаны в
`vault/04-Пользователи-и-аутентификация/Модель-аутентификации.md` и
`vault/06-Маршруты-и-URL/Карта-маршрутов.md`. Ключевые факты, релевантные
этой задаче:

- `/main` (`meta.requiresAuth: false`, без `public`) — фактическая
  домашняя страница приложения; `/` — это `redirect: '/main'`.
- `/info` (`meta.requiresAuth: false`, без `public`) — публичная страница
  для гостей без активной сессии; также доступна авторизованным
  пользователям через явную ссылку в меню (`App.vue:91`,
  `MainView.vue: goToInfo()` → `router.push('/info')` — эта навигация
  корректна и не относится к дефекту).
- `router.beforeEach` (`src/router/index.js:156-261`) уже устроен так, что
  каждая ветка логики завершается ровно одним `next(...)`/`return
  next(...)`; веток, последовательно вызывающих несколько редиректов друг
  за другом (каскад), не найдено. Прочитан построчно для проверки этого
  пункта задачи — дополнительных изменений в guard не требуется.
- Гостевая логика (строки 181-192) уже корректно пропускает `/main` и
  `/info` для незарегистрированных гостей и не участвует в дефекте:
  проблема — не в guard'е, а в двух местах, где код экрана сам,
  программно, вызывает `router.push('/info')` после успешной
  аутентификации.

Найдены ровно два места, вызывающие дефект (оба подтверждены чтением
текущего кода, совпадают с описанием в `tickets/114/114.txt`):

1. `src/views/LoginView.vue:171-173` — функция `redirectToHome()`:
   ```js
   async function redirectToHome() {
     await router.push('/info')
   }
   ```
   Вызывается в двух местах: `onMounted()` (строка 106, при обнаружении
   уже активной сессии) и в конце `handleLogin()` (строка 161, после
   успешного входа по паролю).

2. `src/views/WelcomeView.vue:223` — внутри `setTimeout`-колбэка
   авто-логина после `invite-accept`, сразу после `setAuthItem
   ('sre_user_registered', 'true')`:
   ```js
   await router.push('/info')
   ```

Оба вызова исторически ведут не туда, куда должны по названию/смыслу
(`redirectToHome` → `/info` вместо home; авто-логин после регистрации →
`/info` вместо `/main`).

# Затрагиваемые модули

- `src/views/LoginView.vue`
- `src/views/WelcomeView.vue`

`src/router/index.js` — не затрагивается (изменений не требует, только
использован для анализа/проверки).

# Изменения существующих компонентов

## `src/views/LoginView.vue`

- Функция `redirectToHome()` (строка 172): заменить `router.push('/info')`
  на `router.push('/main')` (либо `router.push('/')`, что эквивалентно
  благодаря `redirect: '/main'` в `router/index.js:38-40` — предпочтителен
  прямой `/main`, чтобы не полагаться на цепочку redirect и не создавать
  косвенность, не соответствующую названию функции).
- Саму функцию переименовывать не обязательно — имя `redirectToHome` уже
  корректно отражает намерение и станет соответствовать поведению после
  исправления целевого пути. Единственное необходимое изменение — сам
  путь.
- Вызовы `redirectToHome()` в `onMounted()` (строка 106) и в конце
  `handleLogin()` (строка 161) не требуют изменений — они уже вызывают
  правильную функцию, дефект был только в её теле.

## `src/views/WelcomeView.vue`

- В обработчике авто-логина внутри `handleRegister()` (строка 223):
  заменить `router.push('/info')` на `router.push('/main')`, сразу после
  `setAuthItem('sre_user_registered', 'true')` (строка 220) — порядок
  операций (сначала флаг, потом редирект) сохраняется без изменений.
- Соседняя ветка обработки ошибки авто-логина (строка 226,
  `router.push('/login')`) не относится к дефекту и не меняется.

Оба изменения — замена одного литерала пути в уже существующей строке
кода, без изменения окружающей логики, сигнатур функций или структуры
компонентов.

# План реализации

1. `src/views/LoginView.vue`: заменить `'/info'` на `'/main'` в
   `redirectToHome()` (строка 172).
2. `src/views/WelcomeView.vue`: заменить `'/info'` на `'/main'` в
   обработчике авто-логина (строка 223).
3. Ручная проверка (по DoD исходного тикета, порядок соответствует
   перечисленным там сценариям):
   - Вход существующего пользователя по email/паролю → ожидается `/main`.
   - Регистрация нового пользователя по invite-ссылке (авто-логин по её
     завершении) → ожидается `/main`.
   - Гость без активной сессии сканирует браслет / открывает приложение
     впервые → по-прежнему `/info` (проверить, что это поведение не
     сломано изменениями — код `router.beforeEach` не менялся, но
     регрессионная проверка нужна, так как оба сценария используют общий
     маршрут `/info`).
   - Уже активная сессия при повторном открытии `/login` напрямую
     (`onMounted()` в `LoginView.vue`) → ожидается немедленный переход на
     `/main`, а не на `/info`.
   - Явная ссылка «Info» в меню (`App.vue`) и `goToInfo()` в
     `MainView.vue` — убедиться, что они по-прежнему работают и ведут на
     `/info` (эта функциональность не должна была измениться, но стоит
     проверить, что её не задело смежными правками).
4. Обновить `tickets/114/state.txt` и `tickets/dashboard.md` по итогам
   реализации (следующий этап, вне рамок этого архитектурного плана).

Изменения не имеют внутренних зависимостей друг от друга — оба шага (1 и
2) независимы и могут выполняться в любом порядке или параллельно.

# Риски

- **Низкий риск регрессии**: изменения — это замена строкового литерала
  пути в двух местах, без изменения условий/ветвлений. Вероятность
  побочных эффектов минимальна.
- **Кэш `sre_user_registered` на реальном устройстве (тикет 112)**: логика
  флага не меняется этой задачей, но ручное тестирование сценария
  «уже активная сессия» в `LoginView.onMounted()` стоит проводить с учётом
  того, что флаг и реальная сессия Supabase — не одно и то же (см.
  `vault/04-Пользователи-и-аутентификация/Модель-аутентификации.md`,
  раздел про тикет 112). Тестировать нужно именно с реальной активной
  сессией Supabase, а не полагаясь только на значение флага в
  LocalForage.
- **Явная ссылка на `/info` в меню не должна быть перепутана с
  дефектными вызовами**: при внесении правки важно не задеть
  `MainView.vue: goToInfo()` (строка 218) и `App.vue:91`
  (`router-link to="/info"`) — они ведут на `/info` намеренно и не входят
  в объём этой задачи.
- **Отсутствие автоматических тестов** на редиректы после логина/
  регистрации: проверка целиком ручная (см. План реализации, п. 3);
  риск того, что регресс в этой области останется незамеченным при
  будущих изменениях, сохраняется и после этой задачи — принято как
  фоновый риск проекта, не требующий решения в рамках данного тикета.
