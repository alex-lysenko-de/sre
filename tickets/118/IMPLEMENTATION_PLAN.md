# Цель

Убрать из `doc/` файлы, чьё содержание теперь полностью или почти полностью дублируется базой знаний `vault/` (тикет 108), — так, чтобы не осталось двух конкурирующих источников правды. Дополнительно создать `CLAUDE.md` в корне репозитория: плотную, ориентированную на ИИ-ассистента сводку проекта, которая автоматически подхватывается Claude Code в начале каждой сессии и служит быстрой точкой восстановления контекста после его очистки, со ссылкой на `vault/00-Индекс/MOC.md` как на полную базу знаний.

Ожидаемый результат: `doc/` содержит только (а) файлы, не покрытые `vault/` по существу, и (б) рабочие артефакты, не являющиеся документацией (SQL, бинарники, скрипты) — они не подпадают под эту задачу вообще. Плюс — новый `CLAUDE.md` в корне.

Это задача документационного рефакторинга — код проекта не меняется.

# Затрагиваемые модули

Не код, а исключительно документация:

- `doc/` (каталог с техническими заданиями и заметками) — источник ревизии.
- `vault/` (Obsidian-база знаний, тикет 108) — эталон для сравнения, не изменяется в рамках этого тикета (кроме одного точечного риска, см. раздел «Риски»).
- Корень репозитория — добавляется один новый файл `CLAUDE.md`.
- `tickets/dashboard.md` — обновление статуса по завершении.

# Новые компоненты

## `CLAUDE.md` (корень репозитория)

Не код — плотный справочный markdown-файл. Рекомендуемая структура разделов (без прозы, списками):

1. Одна строка о предметной области проекта (учёт детей и переклички на мероприятиях, Stadtranderholung).
2. Стек — одной строкой со ссылкой на `package.json`, без дублирования деталей (Vue 3, Pinia, Supabase, LocalForage, Vite/PWA).
3. Нетривиальные архитектурные соглашения: слоистая структура `stores/useXXX/useSupabaseXXX` (state / бизнес-логика / доступ к Supabase — см. `vault/04-Пользователи-и-аутентификация/stores-user.md`).
4. Ключевые факты о модели данных, которые не выводятся тривиально чтением схемы:
   - `group_id`/`bus_id` в `userInfo` — поля **на сегодня** из `user_group_day`, не персистентные атрибуты пользователя;
   - таблиц `groups`/`buses` не существует — это просто smallint-номера `1..config.total_groups`/`1..config.total_buses`;
   - целевая архитектура (API-адаптер, Cloud/Local Mode) пока не реализована — фронтенд обращается к Supabase напрямую.
5. Активное ограничение (дословно): 3 файла с секретами — `doc/sb_install_keys.bat`, `doc/supabase_install.md`, `doc/users.sql` — не менять, не удалять, не копировать содержимое никуда.
6. Конвенция работы с тикетами: `tickets/<N>/<N>.txt` → `IMPLEMENTATION_PLAN.md` → `IMPLEMENTATION_REPORT.md` → `REVIEW_REPORT.md`, статус в `state.txt`; после любого создания тикета или смены статуса — обновить `tickets/dashboard.md`.
7. Предостережение про номера тикетов: номер тикета иногда используется в тексте git-коммита независимо от наличия папки в `tickets/` (см. коммит `17e206d "111: add DB backup tooling"` — коллизия обнаружена и исправлена при работе над этим самым тикетом, см. `tickets/dashboard.md`) — перед тем как присвоить новый номер, стоит свериться и с `tickets/`, и с `git log --oneline --grep`.
8. Финальная строка: точка входа в полную базу знаний — `vault/00-Индекс/MOC.md`, не пересказывать её содержимое здесь.

Формат — списки/таблицы фактов, не развёрнутая проза; общий объём должен оставаться небольшим (справочник, а не документация).

# Риски

- **Потеря backlog-идей.** `AdminBusView_TechTask.md` — единственный документ, а `doc/db/adminBusView.md` частично его повторяет — с содержательным списком нереализованных фич. Прямое удаление без извлечения раздела «Предложения по доработке» безвозвратно потеряет эти идеи (см. шаг 1 последовательности).
- **Неточная атрибуция в `vault/`.** `vault/04-Пользователи-и-аутентификация/Кэширование-LocalForage.md` цитирует `doc/migration_guide.md` как источник обоснования перехода `localStorage` → `LocalForage` (тикет 105). Фактическое содержимое `doc/migration_guide.md` на момент этой ревизии — исключительно «Migration Checklist» рефакторинга store/composable-слоёв, про `localStorage` там ни слова. После удаления `doc/migration_guide.md` эту цитату в `vault/` будет невозможно перепроверить по первоисточнику. Рекомендация — либо поправить атрибуцию в `Кэширование-LocalForage.md` на реальный источник (вероятно, сам `src/modules/storage.js` и история тикета 105), либо явно принять этот разрыв как известный, задокументированный в `IMPLEMENTATION_REPORT.md`. Это правка `vault/`, выходящая за пределы простого DoD «файлы удалены», — решение по объёму остаётся за разработчиком/архитектором на следующем шаге.
- **Секреты.** Любое неосторожное массовое действие (например, `git add -A` или скрипт, проходящий по всем файлам `doc/`) рискует задеть 3 secret-файла. Обязательна точечная проверка перед коммитом (шаг 4 последовательности).
- **Устаревание `backup/database/schema.sql`.** Обоснование удаления `table_structure.md` частично опирается на актуальность `schema.sql` (добавлен коммитом `17e206d`, до появления `vault/` в этом виде) — если `schema.sql` перестанет обновляться, этот аргумент со временем ослабнет; сам `vault/03-База-данных/*` остаётся основным обоснованием независимо от судьбы `schema.sql`.
- **Процессный риск с номерами тикетов (обнаружен в ходе этой самой архитектурной сессии).** Номер тикета может быть уже занят в тексте git-коммита без соответствующей папки в `tickets/` (пример — коммит `17e206d`, использовавший номер 111 для несвязанной задачи backup-тулинга, из-за чего исходный тикет 118 пришлось переномеровать с 111). `tickets/` не под версионным контролем в этом репозитории, поэтому единственный способ проверить номер перед использованием — `git log --oneline --grep <номер>` вручную. Рекомендуется зафиксировать это как пункт в `CLAUDE.md` (см. раздел 7 выше) — не требует отдельного тикета, это уже часть данного тикета.
