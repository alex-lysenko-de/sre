# Цель

На странице настроек сканера (`ScannerSettingsView.vue`, `/scanner-settings`)
добавить живое видео-превью выбранной камеры с рамкой распознавания QR —
сейчас список камер (`settings.cameraList`) только перечисляет названия
устройств, ни одно из них никогда не показывается пользователю. Нужно:
запускать `Html5Qrcode` на выбранной камере и показывать её поток в
квадратной области на странице; корректно переключать поток при смене
выбора; гарантированно останавливать камеру при уходе со страницы.
Реакция на успешно распознанный QR-код в этом превью — вне рамок тикета
(явно указано в `152.txt`, п. 4): достаточно, что поток отображается и
корректно живёт по жизненному циклу экрана.

# Анализ текущей архитектуры

`ScannerSettingsView.vue` сегодня не содержит никакой A/V-логики: список
камер наполняется вызовом `settings.loadCameraList()` →
`Html5Qrcode.getCameras()` (`useScannerSettings.js:92-95`) — системный
метод, который только перечисляет `MediaDeviceInfo` (спрашивая разрешение
камеры ради меток устройств), не открывает поток и не связан ни с каким
`<video>`. Выбор камеры (`settings.setPreferredCameraId(id)`) — чисто
персистентность в `localStorage` через модуль-глобальный `ref` (общий с
`Scanner.vue`, см. комментарий в шапке `useScannerSettings.js:6-10`), без
побочных эффектов на поток.

Единственное существующее место в проекте, где `Html5Qrcode` реально
запускает видеопоток — `src/components/scanner/Scanner.vue`. Он:

* создаёт `new Html5Qrcode('qr-reader-proto')` и вызывает
  `html5QrCode.start(deviceId | {facingMode}, SCANNER_CONFIG,
  onScanSuccess, onScanError)` (`Scanner.vue:240-284, 303-337`);
  `SCANNER_CONFIG.qrbox` (250×250) — это и есть "рамка распознавания",
  её рисует сама библиотека `html5-qrcode` поверх `<video>`, отдельного
  кастомного рисования нет;
* останавливает поток через `html5QrCode.stop()` (`stopScanning()`,
  `Scanner.vue:286-297`) и делает это в `onBeforeUnmount` (`Scanner.vue:546-552`),
  используя флаг `isComponentMounted`, чтобы не трогать камеру после
  размонтирования, если асинхронный вызов ещё в процессе (введено
  тикетом 141_2 как фикс, `Scanner.vue:122-126`);
* после **успешного скана** переходит в развитый цикл
  `pause()` → показ экрана подтверждения → `wait()` →
  `restartCameraReliably()` (`resume()`, подтверждаемый опросом
  `getState()`, с откатом на `stop()+start()`) — весь этот механизм
  (`Scanner.vue:174-235, 403-481`) существует из-за тикетов 141/141_2 и
  решает конкретно проблему "продолжить поток после того, как решение
  по распознанному коду принято и показано пользователю".

Важный вывод для этого тикета: `Scanner.vue` не является "камерой в
чистом виде" — это тесно связанный с бизнес-логикой распознавания
компонент с обязательным `props.onChildResolved` (резолвинг браслета,
звук/вибрация, экран подтверждения, очередь циклов). Настройки камеры
(`152.txt`) явно требуют **не** реагировать на распознанный код —
значит, весь цикл `pause()/restart​CameraReliably()/подтверждение`
(строки 355-481 `Scanner.vue`) для этой задачи не нужен и не должен
запускаться: превью, которое никогда не вызывает `pause()`, структурно
не подвержено классу бага из тикета 141 (тот возникал именно на стыке
`pause()` → `resume()`, зависящем от нативного события `<video>`
`"playing"`). Актуальная часть прецедента 141/141_2 для этого тикета —
не сам `resume()`-фикс, а более общий урок: асинхронные вызовы
`start()/stop()` на `Html5Qrcode`-инстансе нужно защищать от гонок и от
обращения к нему после размонтирования компонента (флаг вроде
`isComponentMounted`).

`ScannerSettingsView.vue` уже читает `settings.preferredCameraId` и
`settings.cameraList` реактивно (общий модуль-глобальный `ref`,
`useScannerSettings.js:40-45`) — значит, превью может реагировать на
смену выбора либо через `watch()`, либо напрямую из обработчика клика по
пункту списка; выбор между ними — architecture-level решение этого
плана (см. "План реализации").

`src/views/ScannerSettingsView.vue`:

* В `<template>`, в блоке `<div class="mb-4">` с меткой "Kamera"
  (строки 19-53), добавить новый квадратный контейнер предпросмотра

  распознавания, которой здесь нет):
  * пустой `<div>`-контейнер с уникальным id (например,
    `#qr-settings-preview`), в который `Html5Qrcode` монтирует
    `<video>`/`<canvas>`;
  * состояние "камера не выбрана" (`preferredCameraId === null`,
    режим "Automatische Kamerawahl") — вместо потока текстовая
    подсказка внутри того же контейнера (например, "Vorschau nicht
    verfügbar im automatischen Modus" — обоснование см. ниже, раздел
    "UI изменения");
  * состояние ошибки запуска потока — текст ошибки внутри контейнера,
    по аналогии с уже существующим `cameraLoadError` для списка камер
    (тот же стиль `.alert alert-danger`), не блокирует остальную
    страницу.
* В `<script setup>`:
  * новая локальная (не в composable) переменная модуля функции —
    инстанс `let html5QrCode = null`, создаваемый один раз при первом
    запуске превью (`new Html5Qrcode('qr-settings-preview')`), по
    аналогии с `Scanner.vue:102, 309-310`;
  * новые локальные `ref`ы состояния превью: `previewState` (`'idle' |
    'starting' | 'active' | 'error'`) и `previewError` (строка);
  * функция `startPreview(cameraId)` — запускает
    `html5QrCode.start(cameraId, PREVIEW_CONFIG, () => {}, () => {})`;
    `PREVIEW_CONFIG` — та же форма, что `SCANNER_CONFIG` в
    `Scanner.vue:104-108` (`fps: 10, qrbox: { width: 250, height: 250 },
    aspectRatio: 1.0`), но собственная константа в этом файле (не
    импортируется из `Scanner.vue` — см. "Новые компоненты" насчёт
    отказа от связывания файлов). Оба callback'а декода — пустые
    функции: успешный скан осознанно ни к чему не приводит (152.txt,
    п. 4), `onScanError` как и в `Scanner.vue:495-497` штатно
    игнорируется (шум при каждом кадре без распознавания);
  * функция `stopPreview()` — `await html5QrCode.stop()` с тем же
    паттерном `try/catch/finally`, что `stopScanning()` в
    `Scanner.vue:286-297` (метод `stop()` может бросить исключение,
    если поток уже не активен — не должно ронять страницу настроек);
  * функция-диспетчер `switchPreview(cameraId)` — гарантированно
    останавливает текущий поток (если был) и запускает новый; вызовы
    сериализуются (см. "Риски" — защита от гонки при быстром
    переключении), синхронизируется с `preferredCameraId` через
    `watch(() => settings.preferredCameraId.value, ..., { immediate: true
    })`, а не из обработчиков клика по кнопкам списка — так превью
    автоматически показывает уже сохранённую в `localStorage` камеру
    сразу при открытии страницы (см. "UI изменения"), без дублирования
    логики в двух местах (`@click` на "Automatische Kamerawahl" и на
    `cam in settings.cameraList.value`);
  * `watch` также должен реагировать на `settings.cameraList.value`
    (или проверяться после `loadCameras()` в `onMounted`) — превью для
    ранее сохранённой камеры может запуститься только когда список
    камер уже загружен и подтверждено, что устройство с этим `id` всё
    ещё существует (тот же паттерн `preferredCameraStillExists`, что в
    `Scanner.vue:322-324`); если устройства с сохранённым `id` больше
    нет — превью остаётся в состоянии "idle"/ошибки, `preferredCameraId`
    не сбрасывается автоматически (вне рамок тикета — то же поведение,
    что и сегодня для самого запуска сканирования в `Scanner.vue`);
  * флаг `isComponentMounted` (по аналогии с `Scanner.vue:126`) и
    `onBeforeUnmount`, вызывающий `stopPreview()` — гарантия из
    критерия приёмки 3.
* `<style scoped>`: добавить блок для контейнера превью — тот же приём,
  что `Scanner.vue:579-592` (`#qr-settings-preview :deep(video),
  #qr-settings-preview :deep(canvas) { width/height: 100% !important;
  object-fit: cover }`, квадратная `aspect-ratio: 1 / 1`, `background:
  #000`).

# Новые компоненты

Новый компонент/composable не создаётся — логика запуска/остановки
превью реализуется локально в `ScannerSettingsView.vue`.

Рассмотрен и отклонён вариант "переиспользовать `Scanner.vue` напрямую
(например, через новый `previewOnly`-режим/проп)":

* `Scanner.vue` — не универсальная "голая камера", а зрелый компонент с
  обязательным `props.onChildResolved`, встроенной очередью циклов
  `enqueueCycle()`, звуком/вибрацией и экраном подтверждения — вся эта
  часть (`Scanner.vue:355-533`) для настроек камеры не нужна и её
  пришлось бы принудительно отключать новым условным флагом внутри уже
  сложного файла, прошедшего несколько раундов фиксов гонок (141,
  141_2). Это увеличивает риск регрессии в реально используемых экранах
  сканирования (`ScannerBusView`/`GroupView`/`CheckinView`) ради
  фичи на отдельной странице настроек, которая используется не во время
  самой переклички.
* Сам тикет (`152.txt`, п. "Требуется") формулирует задачу как
  "по тому же принципу" ("Html5Qrcode-инстанс, контейнер... рамка
  распознавания"), а не как "переиспользовать компонент" — то есть
  сходство подразумевается на уровне паттерна использования библиотеки,
  а не общего кода.
* Единственное место использования — эта одна страница; выделение
  общего переиспользуемого компонента "чистая камера без бизнес-логики"
  было бы преждевременной абстракцией на один вызов (тот же принцип,
  что уже применялся в плане тикета 150 к списку детей в
  `ArmbandView.vue`).

Минимальное дублирование constants (`qrbox`/`fps`/`aspectRatio`,
CSS-приём `:deep(video/canvas)`) между `Scanner.vue` и
`ScannerSettingsView.vue` — сознательно принятая цена этой развязки, а
не недосмотр.

# UI изменения

* На `/scanner-settings`, в блоке "Kamera", под списком камер —
  квадратная область предпросмотра с живым видео выбранной камеры и
  рамкой распознавания QR (визуально в духе `Scanner.vue`, но без
  оверлеев подтверждения/кнопки "Scan").
* Выбор конкретной камеры из списка (`@click="settings.setPreferredCameraId(cam.id)"`,
  уже существующая кнопка) приводит к запуску/переключению превью на
  эту камеру — без дополнительного клика или кнопки "Показать превью".
* Выбор "Automatische Kamerawahl" (`preferredCameraId === null`) —
  архитектурное решение: превью в этом режиме **не запускается**,
  область показывает нейтральную подпись (например, "Kamera wird beim
  Scannen automatisch gewählt"). Обоснование: "автоматический" режим не
  указывает на конкретное физическое устройство — сам `Scanner.vue`
  решает это в момент старта сканирования эвристикой `facingMode` +
  подбором по названию (`startScanningWithFacingMode()`/
  `startScanningWithDeviceListFallback()`, `Scanner.vue:246-284`), т.е.
  результат может отличаться от раза к разу и не привязан к id из
  списка `settings.cameraList`; показ здесь превью произвольно выбранной
  из списка камеры (например, первой) вводил бы пользователя в
  заблуждение, будто именно эта камера гарантированно будет
  использована при сканировании. Это решение — на усмотрение
  реализации, не жёсткое требование тикета (в `152.txt` не описано
  поведение для "Automatische Kamerawahl"), и должно быть явно
  зафиксировано в `IMPLEMENTATION_REPORT.md`.
* При открытии страницы, если камера уже была выбрана ранее
  (`preferredCameraId` из `localStorage` не `null`) — превью запускается
  автоматически, без необходимости заново кликать по камере в списке.
* Переключение на другую камеру — старый поток корректно останавливается
  до/во время старта нового (нет наложения двух потоков камеры).
* Уход со страницы (роутинг на другой экран) — камера гарантированно
  останавливается, фонового доступа к ней не остаётся.
* Ошибка запуска потока (например, устройство занято другим приложением,
  либо `NotFoundError` если ранее выбранное устройство отключено) —
  показывается текстом внутри области превью, не блокирует остальную
  страницу (ползунки длительностей и т.д. остаются работоспособны).

# План реализации

1. В `ScannerSettingsView.vue` добавить в `<script setup>` константу
   `PREVIEW_CONFIG`, `ref`ы `previewState`/`previewError`, переменные
   `html5QrCode`/`isComponentMounted`, функции `startPreview()`/
   `stopPreview()`/`switchPreview()` (пустые no-op callback'и декода).
2. Добавить в `<template>` контейнер превью (`#qr-settings-preview`) с
   тремя визуальными состояниями (idle/автоматический режим, активный
   поток, ошибка) и соответствующие классы в `<style scoped>`
   (квадратная область, `:deep(video/canvas)`).
3. Подключить `watch(() => settings.preferredCameraId.value, ...,
   { immediate: true })`, зависящий также от готовности
   `settings.cameraList.value` (ждать завершения `loadCameras()` из
   `onMounted`, чтобы корректно проверить `preferredCameraStillExists`
   для уже сохранённой камеры) — вызывает `switchPreview()`.
4. Добавить `onBeforeUnmount`, выставляющий `isComponentMounted = false`
   и вызывающий `stopPreview()` — по аналогии с `Scanner.vue:546-552`.
5. Ручная проверка на устройстве/в браузере:
   * открыть `/scanner-settings` без ранее сохранённой камеры — превью
     в состоянии "автоматический режим", без потока;
   * выбрать конкретную камеру из списка — появляется живой поток с
     рамкой распознавания;
   * переключиться на другую камеру несколько раз подряд (в том числе
     быстро, до завершения предыдущего переключения) — нет наложения
     двух потоков, нет зависшего "starting", итоговый активный поток
     соответствует последнему клику;
   * перейти на другой экран (например, `/main`) во время активного
     превью, затем проверить через `chrome://settings` / индикатор
     камеры ОС, что доступ к камере отпущен;
   * закрыть/переоткрыть `/scanner-settings` при ранее сохранённой
     камере — превью стартует само, без клика.
6. `npm run build` — убедиться, что сборка проходит без ошибок/warning
   по изменённому файлу.

Порядок жёсткий только в части "код превью и `watch` — до ручной
проверки"; порядок шагов 1-2 между собой не важен.

# Риски

* **Гонка при быстром переключении камер**: пользователь кликает по
  второй камере до того, как `switchPreview()` для первой завершил
  `start()`. Без явной сериализации возможно наложение потоков или
  попытка `stop()` на ещё не полностью запущенном инстансе. Решение —
  тот же принцип, что уже применён в `Scanner.vue` для параллельных
  циклов (`enqueueCycle()`, `Scanner.vue:184-198`), но в упрощённом виде:
  либо цепочка промисов (`switchQueue = switchQueue.then(() =>
  doSwitch(id))`), либо токен последнего запроса с проверкой актуальности
  после каждого `await` внутри `switchPreview()`, отбрасывающий устаревший
  результат. Конкретный механизм — на усмотрение реализации, но должен
  быть протестирован сценарием "быстрое переключение" (см. план,
  шаг 5).
* **Обращение к камере после размонтирования**: переход на другой экран
  во время незавершённого `start()`/`stop()`. Смягчается флагом
  `isComponentMounted`, тем же паттерном, что `Scanner.vue:122-126,
  227-234` — обязателен к переносу, не факультативен (это прямое
  требование критерия приёмки 3).
* **`getCameras()`/`start()` при отказе в доступе к камере**: уже
  частично обрабатывается сегодня для списка камер (`cameraLoadError`);
  для самого превью `html5QrCode.start()` может бросить исключение
  отдельно от списка (например, устройство исчезло между
  `getCameras()` и `start()`, либо занято другим приложением/вкладкой) —
  обрабатывается локальным `try/catch` в `startPreview()`, не должно
  ронять остальной функционал страницы (ползунки длительностей).
* **Дублирование констант/CSS-приёма с `Scanner.vue`** — принятый и
  осознанный риск рассинхронизации (например, изменится `qrbox` в одном
  файле, но не в другом); не устраняется в рамках этого тикета (см.
  "Новые компоненты" — обоснование, почему шаринг кода с `Scanner.vue`
  сознательно не делается).
* **`html5-qrcode` не позволяет держать два параллельных инстанса на
  разных `<div>`** с одним и тем же физическим устройством одновременно
  без конфликта потоков браузера — актуально, если в будущем понадобится
  превью параллельно с работающим сканированием на другом экране; для
  этого тикета не актуально (`ScannerSettingsView.vue` — самостоятельная
  страница, `Scanner.vue`-инстансы других экранов размонтируются при
  переходе на `/scanner-settings`).
* Регрессионных рисков для существующего функционала (список камер,
  ползунки длительностей, `Scanner.vue` и реальные экраны сканирования)
  нет — изменения строго аддитивны в пределах одного файла, ничего
  существующего не удаляется и не меняет поведения.

# Definition of Done

* На `/scanner-settings`, при выборе конкретной камеры из списка, в
  квадратной области на странице отображается её живой видеопоток с
  рамкой распознавания QR (не просто список названий, как сейчас).
* Переключение выбранной камеры в списке корректно меняет отображаемый
  поток — без наложения двух потоков, без зависания в промежуточном
  состоянии (проверено сценарием быстрого переключения).
* При уходе со страницы настроек (переход на другой маршрут) камера
  гарантированно останавливается — нет фонового доступа к камере после
  ухода с экрана (проверено вручную через системный индикатор камеры).
* Режим "Automatische Kamerawahl" и ошибки запуска потока показывают
  осмысленное состояние в области превью, не ломая остальную страницу.
* Успешное распознавание QR-кода в превью ни к чему не приводит (нет
  побочных действий) — соответствует явному ограничению `152.txt`, п. 4.
* `npm run build` проходит без ошибок.
* Правка ограничена файлом `src/views/ScannerSettingsView.vue` —
  `Scanner.vue`, `useScannerSettings.js`, БД/API не затронуты.
