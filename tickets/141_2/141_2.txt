# Ticket 141_2. Устранить гонку между циклом скана и showExternalMessage() в Scanner.vue

## Контекст

Follow-up к тикету 141. Ревью 141 ([tickets/141/REVIEW_REPORT.md](../141/REVIEW_REPORT.md),
Major 1) показало, что исходная гонка не устранена, а лишь смягчена для
одной из двух сторон:

* **Путь 1 (обычный скан)** — `onScanSuccess()` → `pause()` → показ экрана
  подтверждения → собственный независимый таймер `wait(durationFor(variant))`
  → `resumeAfterConfirmation()` → `hideConfirmationScreen()` +
  `html5QrCode.resume()`. **Не менялся тикетом 141**, всё ещё использует
  `resume()` — тот самый примитив, ненадёжность которого была
  диагностирована как первопричина исходного бага 141.
* **Путь 2 (кнопка "Senden")** — `showExternalMessage()` → `pause()` (если
  камера активна) → показ экрана подтверждения → свой независимый таймер
  `wait(durationMs)` → `hideConfirmationScreen()` + `stopScanning()` +
  `startCamera()`. Правка тикета 141 — заменила `resume()` на надёжный
  `stop()+start()`, но только здесь.

Оба пути управляют одним и тем же `html5QrCode`-инстансом и одним и тем же
реактивным объектом `confirmation`, но никак не координируются между собой:
`isProcessing` выставляется и проверяется только путём 1, путь 2 его не
трогает вообще. Если пользователь жмёт "Senden" сразу после скана, не
дожидаясь исчезновения экрана подтверждения, оба таймера могут сработать
почти одновременно и наложить свои `hide/pause/resume/stop/start` друг на
друга — сценарий воспроизведён чтением кода в ревью 141 (Major 1, шаги 1-4),
не на устройстве.

## Первопричина (структурная)

Два независимых стейт-машины "пауза → показ → таймер → возобновление"
работают над одним общим ресурсом (`html5QrCode` + `confirmation`) без
единой точки взаимного исключения. `isProcessing` — это соглашение
("не забудь проверить/выставить флаг"), а не гарантия: путь 2 уже один раз
забыл, и то же самое может повториться для любого будущего третьего
вызывающего (например, будущего тикета).

Отдельно от гонки — путь 1 сам по себе всё ещё не защищён от исходного
бага 141 (зависание `resume()` без исключения), просто до сих пор не было
independent репорта именно про путь 1.

## Предлагаемое решение

Две ортогональные правки, обе нужны, чтобы устранить проблему уверенно, а
не только для одного пути:

### A. Единая сериализованная очередь вместо двух независимых таймеров

Вместо флага `isProcessing`, который каждый вызывающий обязан не забыть
проверить/выставить, — единая точка входа для *любого* цикла
"пауза → показ подтверждения → ожидание → возобновление камеры":

```js
let queueLength = 0
let tail = Promise.resolve()

function enqueueCycle(task) {
  queueLength++
  isProcessing.value = true
  const settle = () => {
    queueLength--
    if (queueLength === 0) isProcessing.value = false
  }
  tail = tail.then(task, task).then(settle, settle)
  return tail
}
```

* `onScanSuccess()`: синхронная проверка `if (isProcessing.value) return` в
  начале остаётся как дешёвый быстрый guard (новый скан во время паузы
  камеры и так физически не должен прийти). Само тело "показать
  результат → подождать → скрыть → возобновить камеру" оборачивается в
  `enqueueCycle(...)`.
* `showExternalMessage()`: **весь** цикл (включая собственную `pause()`)
  переносится внутрь `enqueueCycle(...)` — без предварительной проверки
  `isProcessing` на входе, вызов должен встать в очередь безусловно.
  Результат "Senden" нельзя терять/пропускать — если путь 1 в этот момент
  ещё выполняется, путь 2 просто выполнится следующим по очереди, а не
  параллельно.

`isProcessing` перестаёт быть флагом, который вручную выставляют/сбрасывают
в нескольких разных местах (сейчас: `resumeAfterConfirmation()`,
`handleConfirmationBind()`) — он становится производным от состояния
очереди, что устраняет саму возможность забыть его сбросить/выставить в
новом месте.

### B. Не полагаться на `resume()` вслепую ни в одном из путей

Простая замена `resume()` на `stop()+start()` в пути 1 (как предлагает
ревью 141, Major 1, "минимальное закрытие") сама по себе устранила бы
проблему, но ценой заметного визуального моргания камеры **после каждого
без исключения скана**, а не только после "Senden" (как сейчас, тикет
141) — сегодня быстрый `resume()` в подавляющем большинстве случаев
срабатывает без сбоев и без видимого перезапуска потока.

Предлагается сохранить `resume()` как быстрый путь, но перестать ему
слепо доверять — подтверждать результат опросом реального состояния
`html5QrCode.getState()` и откатываться на надёжный `stop()+start()`
только если возобновление не подтвердилось за короткое время:

```js
async function restartCameraReliably() {
  try {
    html5QrCode.resume()
    if (await confirmResumed()) return
  } catch (error) {
    console.warn('resume() fehlgeschlagen, Fallback auf Kaltstart:', error)
  }
  await stopScanning()
  await startCamera()
}

async function confirmResumed(retries = 3, delayMs = 100) {
  for (let i = 0; i < retries; i++) {
    await wait(delayMs)
    if (html5QrCode?.getState?.() === Html5QrcodeScannerState.SCANNING) {
      return true
    }
  }
  return false
}
```

Оба пути (завершение обычного скана и завершение `showExternalMessage()`)
в конце своей задачи в очереди вызывают **один и тот же**
`restartCameraReliably()` — это одновременно закрывает найденную ревью
асимметрию ("путь 1 не менялся") и убирает необходимость выбирать между
"быстро, но рискованно" и "надёжно, но с миганием при каждом скане":
быстрый путь остаётся основным, тяжёлый — только как подтверждённый
fallback для действительно зависшего `resume()`.

### Почему очередь, а не просто флаг-семафор

Флаг (`isProcessing`) уже применялся в проекте и не спас: путь 2 просто не
стал его проверять — обычная ошибка при добавлении нового вызывающего.
Очередь (`enqueueCycle`) физически не позволяет второму циклу начать
манипуляции с камерой, пока не завершился первый — это гарантия на уровне
структуры кода, а не соглашение, которое можно случайно нарушить в
следующем тикете, трогающем `Scanner.vue`.

## Затронутые части

* `src/components/scanner/Scanner.vue` — вся правка локальна:
  `onScanSuccess()`, `resumeAfterConfirmation()`, `showExternalMessage()`,
  новые `enqueueCycle()`/`restartCameraReliably()`/`confirmResumed()`.
* Публичный контракт компонента (`start()`/`stop()`/`showMessage()` через
  `defineExpose`, события `camera-started`/`camera-stopped`) не меняется —
  три `ScannerXxxView.vue` и `useScanPacket.js` не затрагиваются.

## Критерии приемки

* Сценарий "скан → сразу Senden, не дожидаясь исчезновения экрана
  подтверждения скана" (сценарий Major 1 из ревью 141) не приводит ни к
  преждевременному скрытию чужого экрана подтверждения, ни к
  перезапуску камеры посреди ещё не завершившегося цикла — оба сообщения
  показываются полностью и последовательно, каждое положенное ему время.
* Ни один из двух путей (обычный скан, `showExternalMessage()`) не может
  зависнуть в `PAUSED` без восстановления — при неудаче `resume()` в любом
  из путей происходит гарантированный `stop()+start()`.
* Новые сканы после "Senden" по-прежнему корректно добавляются в список
  (регрессия критерия приёмки тикета 141 недопустима).
* `npm run build` проходит.
* Ручная проверка на устройстве по сценарию из чек-листа
  [tickets/141/IMPLEMENTATION_PLAN.md](../141/IMPLEMENTATION_PLAN.md)
  (п. 4), с явным добавлением сценария "Senden сразу после скана".
