# Реализованные изменения

## A. Единая сериализованная очередь вместо двух независимых таймеров

В `Scanner.vue` добавлен `enqueueCycle(task)` (переменные `queueLength`/`tail`,
локальные для экземпляра компонента — объявлены на верхнем уровне
`<script setup>`, который выполняется заново при каждом монтировании
компонента, поэтому нет риска смешать очереди двух одновременно
смонтированных `Scanner.vue`). Реализация — точно по коду из
`141_2.txt`/`IMPLEMENTATION_PLAN` (которого не существовало отдельным
файлом — см. «Отклонения от плана»).

* `onScanSuccess()` разделён на синхронный быстрый guard (`if
  (isProcessing.value) return`) и `runScanCycle(decodedText)` — тело
  прежнего `onScanSuccess` (pause → сигналы → resolve → показ →
  wait/persistent-ветка → restart), обёрнутое в `enqueueCycle(() =>
  runScanCycle(decodedText))`.
* `showExternalMessage()` стал тонкой обёрткой `enqueueCycle(() =>
  runExternalMessageCycle(...))` — весь цикл, включая собственный
  `pause()`, теперь внутри очереди, без предварительной проверки
  `isProcessing` на входе (вызов не теряется, просто встаёт следующим в
  очередь, если путь 1 ещё выполняется — ровно требование плана).
* `isProcessing` больше нигде не выставляется/не сбрасывается вручную —
  это теперь производное состояние `enqueueCycle` (`queueLength === 0`).
  Ручные присвоения `isProcessing.value = true/false` убраны из всех мест,
  где они были (`onScanSuccess`, `resumeAfterConfirmation`,
  `handleConfirmationBind`).

### Персистентная ветка (Armband nicht zugeordnet)

Персистентный экран ("Armband nicht zugeordnet" с кнопками
Abbrechen/"Armband zuordnen") не завершает `runScanCycle` сразу — вместо
этого `runScanCycle` дожидается `await new Promise(resolve => {
pendingPersistentResolve = resolve })`. `handleConfirmationCancel()`
(теперь `async`, вызывает `restartCameraReliably()` и затем разрешает
промис) и `handleConfirmationBind()` (разрешает промис без перезапуска
камеры — как и раньше, это дело вызывающей стороны) вызываются напрямую
по клику, а не через новый `enqueueCycle()` — они не начинают новый цикл,
а продолжают/завершают уже стоящий в очереди `runScanCycle`. Это и есть
решение открытого в `141_2.txt` вопроса «нужно ли использовать
`enqueueCycle()` также для этих веток» — не нужно, они физически являются
продолжением уже занимающего место в очереди задания, а не новым
конкурентным циклом; обёртывание их в отдельный `enqueueCycle()` было бы
избыточным и мешало бы порядку (очередь и так уже блокирована на этом
промисе). Побочный эффект: если во время показа персистентного экрана
нажать "Senden", `showExternalMessage()` корректно встаёт в очередь и
выполняется только после того, как администратор нажмёт
Abbrechen/"Armband zuordnen" — что и требовалось (единая точка
взаимного исключения для камеры).

## B. `resume()` подтверждается опросом состояния, а не принимается вслепую

Добавлены `confirmResumed()` и `restartCameraReliably()` — по коду из
плана, с одним отличием: число попыток и задержка между ними не
захардкожены (`retries = 3, delayMs = 100`), а читаются из
`useScannerSettings()` (см. ниже) на каждый вызов, чтобы значение из
`/scanner-settings` подхватывалось без перезагрузки.

Оба цикла (`runScanCycle`, `runExternalMessageCycle`) в конце вызывают
один и тот же `restartCameraReliably()` вместо раздельных
`resumeAfterConfirmation()`/`stopScanning()+startCamera()` — асимметрия
"путь 1 не менялся" из ревью 141 закрыта: путь 1 больше не полагается на
`resume()` вслепую.

## Открытый вопрос: параметры `confirmResumed()` → меню настроек

Согласно резолюции в `141_2.txt` ("решение: установку этих параметров
вынести в меню настроек сканера `/scanner/settings`"):

* `useScannerSettings.js` дополнен полями `confirmResumeRetries`
  (по умолчанию 3, диапазон 1–10) и `confirmResumeDelayMs` (по умолчанию
  100 мс, диапазон 50–500 мс, шаг 25 мс), с персистентностью в том же
  `localStorage`-ключе `scanner_settings`, что и существующие настройки
  (обратная совместимость: `??` на чтении подставляет дефолт для старых
  сохранённых объектов без этих полей). Диапазоны экспортированы как
  `CONFIRM_RESUME_RETRIES_RANGE`/`CONFIRM_RESUME_DELAY_MS_RANGE`.
* `ScannerSettingsView.vue` дополнен двумя новыми `<input type="range">`
  в том же стиле, что уже существующие "Anzeigedauer bei
  Erfolg/Fehler" — под разделителем `<hr>`.

## Открытый вопрос: защита от размонтирования

Согласно резолюции в `141_2.txt` ("решение принимает разработчик.
Критерий: отсутствие побочных эффектов, чистота кода, простая и ясная
архитектура") — добавлен один простой флаг `isComponentMounted` (обычная
переменная, не `ref`, реактивность не нужна), выставляемый в `false` в
начале `onBeforeUnmount()`. Единственная точка проверки — внутри
`restartCameraReliably()`, перед `stopScanning()` и перед `startCamera()`
(именно те два вызова, которые реально трогают камеру/DOM и были указаны
как риск в Minor 1 ревью 141). Выбрана одна точка проверки в общей
функции вместо дублирования guard'а в обоих циклах — минимальный код,
закрывает риск для обоих путей одновременно.

# Отклонения от плана

**`tickets/141_2/IMPLEMENTATION_PLAN.md` как отдельный файл не
существовал** на момент начала реализации (создан не был — в отличие от
всех прочих тикетов проекта). Сам `tickets/141_2/141_2.txt` уже содержит
полностью проработанную архитектуру (разделы "Первопричина", "Предлагаемое
решение" с частями A/B, точным псевдокодом) и оба открытых на момент
постановки вопроса резолвированы прямо в тексте пометками "решение" —
по факту это и есть согласованный план, просто оформленный в файле
постановки задачи, а не в отдельном `IMPLEMENTATION_PLAN.md`. Реализация
выполнена строго по этому тексту, без каких-либо самостоятельных
архитектурных решений сверх двух явно делегированных разработчику
пунктов (параметры `confirmResumed()` → в настройки; защита от
unmount — минимальный guard), которые описаны выше. Каких-либо иных
расхождений с описанным в `141_2.txt` решением нет.
