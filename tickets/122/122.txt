# Тикет 122: Серверная логика обработки пакетов сканирования

Серверный аналог тикета 120, выполняется в рамках **одного релиза** с
ним — до совместного развёртывания кнопке «Отправить» в 120 некуда
реально отправлять данные.

Входные документы, на которых основан этот тикет и которые он **не
дублирует**: `tickets/120/120.txt` (итоговый клиентский контракт
`PresencePacket`) и `tickets/121/IMPLEMENTATION_PLAN.md` (архитектурное
исследование и принятое решение по модели хранения). Детальная
техническая проработка этого тикета (точные DDL, код функции БД, код
Edge Function) уже выполнена и зафиксирована в
`tickets/122/IMPLEMENTATION_PLAN.md` — этот документ описывает задачу
на уровне требований и ссылается на план за реализационными деталями,
не повторяя их.

# Назначение задачи

После реализации 120 клиент больше не пишет в БД по одному скану —
вместо этого он копит результаты локально и по нажатию «Отправить»
отправляет один пакет (`PresencePacket`) целиком. На сегодня сервер
понятия «пакет» не имеет: единственный существующий способ записи
результата — прямой `INSERT` в `scans` по одному ребёнку за раз.

Задача 122 — научить сервер принимать, атомарно и идемпотентно
сохранять такие пакеты, не нарушая при этом корректности уже
существующих производных данных о присутствии (`children_today`/
`groups_today`) и экранов, которые их читают, и дать администратору
возможность видеть «кто, когда и что прислал» на уровне пакета, а не
только на уровне отдельных сканов.

Место в архитектуре: 122 — связующий серверный слой между новой
клиентской пакетной моделью (120) и существующими read-моделями
присутствия, который должен сделать переход на пакетную отправку
незаметным для этих read-моделей.

# Зависимости — что уже решено и не пересматривается этим тикетом

Ниже перечислены решения, принятые в 120 и 121, на которые 122
опирается как на данность. Обоснования и рассмотренные альтернативы —
в соответствующих документах, здесь не воспроизводятся.

- **Формат `PresencePacket`** (поля, типы, обязательность) — зафиксирован
  в `tickets/120/120.txt`. 122 обязан принимать данные строго в этом
  формате, не вводя собственных полей и не меняя семантику существующих.
- **Модель хранения** — исследование 121 рекомендует и фиксирует
  вариант «заголовок пакета (новая сущность) + переиспользование
  `scans` для отдельных результатов», а не полностью независимую схему
  и не JSONB-документ. 122 реализует именно этот вариант.
- **Точка приёма** — согласовано и зафиксировано в 121: Edge Function
  `submit-scan-packet` (по образцу уже существующих в проекте
  привилегированных функций), а не PL/pgSQL RPC как единственная точка
  входа.
- **Идемпотентность** — принцип зафиксирован в 121: уникальный на
  стороне БД `client_packet_id`, сгенерированный клиентом один раз на
  заход; повторная отправка с тем же `client_packet_id` не создаёт
  дублей.
- **Пакетная (не построчная) переработка триггеров** — обязательное
  условие, зафиксированное в 121: без него вставка пакета из 35+ детей
  вызывает 35-кратный каскад пересчёта. Это требование к реализации, а
  не факультативная оптимизация.
- **`author_id`** сервер определяет сам из аутентифицированной сессии;
  присланное клиентом значение всегда игнорируется — согласовано в 121.

# Что реализует этот тикет (охват)

1. Новая сущность «заголовок пакета сканирования» в БД.
2. Атомарная идемпотентная функция приёма пакета (заголовок + все
   результаты по детям — одной операцией, либо целиком, либо ничего).
3. Edge Function `submit-scan-packet` — публичная точка входа,
   аутентификация, валидация, вызов функции приёма.
4. Переработка существующих триггеров пересчёта присутствия на
   пакетную обработку (устранение N-кратных каскадов).
5. Видимость пакетов в интерфейсе администратора: у автобусов (через
   уже существующий `AdminBusView.vue`/`BusDetailModal.vue`) и у групп
   (для которых сегодня нет отдельного экрана деталей — минимально
   необходимый новый компонент).

Точный список новых/изменяемых файлов и их сигнатур — в
`tickets/122/IMPLEMENTATION_PLAN.md`, разделы «Затрагиваемые модули»,
«Новые компоненты».

# Модель данных

Требуется:

- Таблица-заголовок пакета: клиентский идентификатор пакета (уникален
  — основа идемпотентности), тип пакета, автор, привязка к автобусу
  или группе (в зависимости от типа), дата, время начала/окончания
  сбора на клиенте, время получения сервером, количество результатов,
  поле отмены (задел на будущее — см. «Границы задачи», отмена сама не
  реализуется).
- `scans` дополняется ссылкой на заголовок пакета и способом получения
  результата (скан / ручная отметка), обратно совместимо со
  существующими строками (значения по умолчанию для старых данных).

Точные названия колонок, типы, индексы и текст миграций — в
`tickets/122/IMPLEMENTATION_PLAN.md`, раздел «Изменения БД» (единственный
источник истины на уровне реализации, здесь не дублируется).

# Идемпотентность и производительность вставки

- Пакет применяется атомарно: одним составным оператором вставки
  (заголовок + все дочерние результаты), не последовательностью
  отдельных вызовов — от этого напрямую зависит и корректность
  идемпотентности при гонке двух одновременных повторов одного и того
  же пакета, и работоспособность пакетной переработки триггеров ниже.
- Повторная отправка того же `client_packet_id` не создаёт новых
  строк — сервер обнаруживает существующий пакет и возвращает тот же
  результат.
- Триггеры, обновляющие производные данные присутствия
  (`children_today`, `groups_today`), переводятся с построчной на
  постатементную обработку — обязательное требование, без которого
  вариант хранения (см. «Зависимости») не может считаться реализованным
  корректно. Итоговый набор данных в `children_today`/`groups_today`
  после этой переработки не должен отличаться от того, что дал бы
  сегодняшний построчный вариант — меняется только количество
  срабатываний, не результат.

# API — Edge Function `submit-scan-packet`

Требования к реализации:

- Аутентификация и проверка активности пользователя — по образцу уже
  существующих привилегированных функций проекта (проверка токена
  через анонимный клиент, проверка роли/активности через
  `service_role`-клиент).
- `author_id` в ответе/сохранённых данных — всегда из проверенной
  личности вызывающего; значение из тела запроса не используется ни
  при каких обстоятельствах.
- Валидация обязательных полей тела запроса (форма — по контракту
  120.txt/121, см. «Зависимости»); при нарушении — ошибка `400` с
  описанием проблемы.
- Успешный ответ — идентификатор сохранённого (или уже существовавшего
  при повторе) пакета и признак «создан впервые» / «уже существовал»;
  оба случая клиент трактует как успех (это уже решено на стороне 120,
  здесь не пересматривается).
- Ошибки аутентификации/авторизации/сервера — коды `401`/`403`/`500`
  со структурированным телом, по образцу существующих функций проекта.

Точный контракт запроса/ответа, включая маппинг текстовых значений типа
пакета в служебное представление для хранения — в
`tickets/122/IMPLEMENTATION_PLAN.md`, раздел «API изменения».

# UI администратора

- `AdminBusView.vue` (существующий экран) — добавляется видимость
  полученных пакетов (общий список и по конкретному автобусу через уже
  существующий `BusDetailModal.vue`). Существующая realtime-подписка на
  производные данные присутствия не удаляется (эти данные продолжают
  обновляться), но её индикатор должен перестать подразумевать
  поштучную, пер-скановую живость — обновления теперь приходят пакетами.
- Для групп аналогичного экрана деталей сегодня не существует. Минимально
  необходимо добавить точку входа и экран, показывающий пакеты,
  полученные по конкретной группе — по образцу уже существующего
  решения для автобусов, без пересмотра существующей сводной таблицы
  групп.
- Экраны и композаблы, не читающие `scans`/пакеты напрямую (сводная
  таблица присутствия по группам, Kopfzählung), изменений не требуют —
  это прямое следствие того, что пакетная переработка триггеров не
  меняет итоговый состав производных данных, которые эти экраны читают.

# Ограничения, которые нужно соблюдать

- Существующий административный путь ручного пересчёта/переназначения
  автобуса ребёнку (вне трёх режимов сканирования 120) не входит ни в
  120, ни в 122 и не должен быть сломан переработкой триггеров —
  требуется регрессионная проверка, что он продолжает корректно
  обновлять производные данные присутствия без изменений в его
  собственном коде.
- Ссылка на пакет в `scans` вводится как допускающая отсутствие
  значения (для совместимости с этим оставшимся путём и с уже
  существующими строками) — превращение её в обязательную не входит в
  этот тикет и выполняется отдельным, более поздним шагом, только
  после отдельного решения о судьбе оставшегося прямого пути записи.
- Право записи в новую сущность заголовка пакета должно принадлежать
  исключительно серверной привилегированной логике — не обычной роли
  пользователя. В проекте уже есть прецедент, когда широкая политика
  доступа «на всякий случай» делает более узкую политику для той же
  таблицы бессмысленной — для новой сущности такую политику создавать
  нельзя.

# Границы задачи (что не входит)

- Клиентская часть — экраны режимов сканирования, сборка пакета,
  вызов `submit-scan-packet` — реализована тикетом 120, здесь не
  переделывается и не переопределяется.
- Серверное объединение нескольких независимых пересчётов одного
  автобуса/группы, вычисление расхождений и отсутствующих детей,
  итоговый экран для главного распорядителя (Hauptbetreuer) — не
  входит ни в 120, ни в 122; для этого функционала пока не заведён
  отдельный тикет.
- Функция отмены уже отправленного пакета — не реализуется в 122;
  требуется только не исключать такую возможность будущей схемой
  (задел — поле отмены в заголовке пакета).
- Перевод ссылки на пакет в `scans` в обязательную (`NOT NULL`) — не
  входит в 122, выполняется отдельным будущим шагом после решения
  судьбы оставшегося прямого пути записи (см. «Ограничения»).

# Definition of Done

- Новая сущность-заголовок пакета создана; повторная отправка одного и
  того же пакета (тот же клиентский идентификатор) не создаёт
  дублирующих данных ни в заголовке, ни в результатах по детям.
- Приём пакета атомарен: любая ошибка в процессе сохранения не
  оставляет частично применённого пакета (ни заголовка без результатов,
  ни результатов без заголовка).
- Edge Function `submit-scan-packet` развёрнута и доступна клиенту 120;
  отклоняет запросы без валидного токена, от неактивных пользователей и
  с неполным телом запроса; во всех случаях сама определяет автора,
  игнорируя присланное клиентом значение.
- Пакет с большим числом детей (проверено на пакете от автобуса, 35+
  записей) вызывает один цикл пересчёта производных данных присутствия,
  а не по одному на каждого ребёнка — подтверждено вручную.
- Существующий административный путь ручного пересчёта продолжает
  корректно работать после переработки триггеров без изменений в
  собственном коде — подтверждено регрессионной проверкой.
- Экраны и композаблы, не работающие с пакетами напрямую (сводная
  таблица присутствия по группам, Kopfzählung), показывают корректные
  данные без изменений в их собственном коде.
- `AdminBusView.vue`/`BusDetailModal.vue` показывают полученные пакеты
  по автобусам; появился аналогичный по возможностям экран для групп.
- Сквозная ручная проверка выполнена совместно с реализованным тикетом
  120: все три режима сканирования успешно отправляют пакеты, данные
  появляются в admin-экранах, повторная отправка после сетевого сбоя
  не создаёт дублей.
