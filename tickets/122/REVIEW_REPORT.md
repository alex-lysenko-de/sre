Код структурно реализует утверждённый план (модель хранения, идемпотентность,
атомарность, постатементные триггеры, Edge Function, admin UI) без
архитектурных отклонений. Изначально был обнаружен реальный функциональный
регресс в переработке триггера `on_scan_insert` (Major 1) и пробел во входной
валидации `submit_scan_packet()` (Major 2) — по обсуждению с автором задачи

уже загруженного на клиенте ростера) — решение: не городить graceful-обработку
несуществующего случая, а реагировать на него громким `RAISE EXCEPTION`
(тот же паттерн, что уже использовался в исходном построчном триггере до
этого тикета). Оба места исправлены минимальными guard-проверками, см. ниже.

Ни один пункт Definition of Done, требующий реального окружения (применение
DDL, деплой функции, ручные и регрессионные проверки), по-прежнему не
выполнен — это ожидаемо для этой сессии (нет доступа к Supabase) и не
блокирует код-ревью, но означает, что заявленные в отчёте гарантии («один
цикл пересчёта», «идемпотентность подтверждена») пока не верифицированы
фактически.

При первой реальной попытке применить `doc/db/scan_packets.sql` к Supabase
(вне этой сессии) обнаружился ещё один дефект, уже не логический, а
синтаксический — Postgres отклонил `CREATE TRIGGER trg_on_children_today_change
... AFTER INSERT OR UPDATE ... REFERENCING NEW TABLE AS new_table` с ошибкой
`0A000: transition tables cannot be specified for triggers with more than one
event`. Это ограничение Postgres не было учтено ни планом (`IMPLEMENTATION_PLAN.md`,
раздел «Изменения БД»), ни первоначальной реализацией — соответствующий SQL
физически не мог быть применён ни разу, что означает: строка «`npm run build`
— успешно... без ошибок» в `IMPLEMENTATION_REPORT.md` подтверждает только
компиляцию клиентского кода, а не работоспособность SQL-скрипта — тот при
первом же реальном запуске падал на этом операторе, до `submit_scan_packet()`
и RLS-политик включительно (они шли в скрипте после сломанного триггера и не
были применены). Исправлено тем же способом, которым Postgres требует
обходить это ограничение — триггер с двумя событиями и transition table разбит
на два триггера с одним событием каждый (`trg_on_children_today_insert`/
`trg_on_children_today_update`), оба вызывают ту же функцию
`on_children_today_change_batch()`. См. «Правки после ревью».

## Major 1 — `on_scan_insert_batch` тихо теряет защитную проверку «у ребёнка нет группы» — ИСПРАВЛЕНО

`doc/db/scan_packets.sql`, функция `on_scan_insert_batch()`
(`JOIN children c ON c.id = s.child_id`).

Текущая построчная версия (`doc/db_triggers.sql`, `on_scan_insert()`) делает:

```sql
SELECT group_id INTO v_group_id FROM children WHERE id = NEW.child_id;
IF v_group_id IS NULL THEN
  RAISE EXCEPTION 'Child with id % does not exist', NEW.child_id;
END IF;
```

`v_group_id IS NULL` истинно в двух случаях: (а) ребёнка не существует —
невозможно на уровне `on_scan_insert_batch`, т.к. `scans.child_id` имеет
`FOREIGN KEY REFERENCES children(id)` (`backup/database/schema.sql:6070-6071`),
и любой несуществующий `child_id` в пакете уронит весь `INSERT INTO scans`
целиком, откатив всю функцию `submit_scan_packet` (это часть работает
корректно, атомарность сохранена); и (б) **ребёнок существует, но
`children.group_id IS NULL`** (колонка нигде не `NOT NULL`,
`backup/database/schema.sql:3658`, `children_today.group_id` тоже nullable,
`:3686`) — сегодня это активно и намеренно блокируется построчным триггером
через `RAISE EXCEPTION`.

Новая `on_scan_insert_batch()` использует `JOIN children c ON c.id =
s.child_id` без проверки `c.group_id IS NOT NULL` и без `RAISE EXCEPTION`.
Для ребёнка без назначенной группы это не удаляет и не блокирует вставку —
строка `s` из `new_table` по-прежнему проходит `JOIN` (просто `c.group_id`
будет `NULL`) и **тихо** попадает в `children_today` с `group_id = NULL`.
Ошибка не возникает нигде — ни в `submit_scan_packet()`, ни в Edge Function,
ни в UI. Далее `on_children_today_change_batch()` явно фильтрует
`WHERE group_id IS NOT NULL`, так что такая строка никогда не появится ни в
одной групповой агрегатной таблице (`groups_today`) — присутствие ребёнка
физически зафиксировано (`scans`, `children_today`), но невидимо ни в одном
экране, читающем по группам (`HeadcountView`, `ChildrenView`).

**Файл**: `doc/db/scan_packets.sql`
**Сценарий отказа**: Betreuer сканирует/чек-инит ребёнка, которому по какой-то
причине (ещё) не назначена группа (`children.group_id IS NULL` — валидное
состояние по схеме). Раньше это надёжно и явно ломало вставку (Betreuer видел
ошибку и мог исправить назначение группы прежде, чем данные потеряются).
Теперь пакет «успешно» принимается (`created: true`), `scans`/`children_today`
получают строку, но ребёнок нигде не всплывает как присутствующий/отсутствующий
на уровне группы — тихая рассинхронизация данных, которую сложно диагностировать
постфактум.

Это прямое нарушение собственного инварианта задачи (`122.txt`, раздел
«Идемпотентность и производительность вставки»): «Итоговый набор данных в
`children_today`/`groups_today` после этой переработки не должен отличаться
от того, что дал бы сегодняшний построчный вариант — меняется только
количество срабатываний, не результат» — для этого конкретного случая
результат меняется.

**Как исправлено**: по обсуждению с автором задачи — «ребёнок без группы»
признан невозможным в реальной эксплуатации состоянием (группа назначается
при занесении ребёнка в базу и далее не меняется), поэтому вместо попытки
как-то «обработать» этот случай (например, пропустить строку, дописать её в
отдельный лог, показать в UI как «бесхозную») перед `INSERT` в
`on_scan_insert_batch()` добавлена явная проверка, которая делает
`RAISE EXCEPTION` при обнаружении такой строки в `new_table` — тот же
контракт, что и у построчной версии до этого тикета, просто перенесённый на
уровень батча (одна проверка на весь `new_table`, а не N раз).

## Major 2 — Edge Function не валидирует форму элементов `children[]` — ИСПРАВЛЕНО (на уровне БД)

`supabase/functions/submit-scan-packet/index.ts`, шаг 3 (валидация тела).

Валидируются только поля верхнего уровня (`client_packet_id`, `type`, `date`,
`finished_at`, условно `bus_id`/`group_id`). Массив `children` передаётся в
`submit_scan_packet()` без проверки, что каждый элемент содержит `child_id`
(и что он вообще является числом). В `submit_scan_packet()`:

```sql
(c->>'child_id')::bigint
```

Если у элемента массива отсутствует ключ `child_id` (испорченный клиент,
баг сериализации, ошибка в будущей версии клиента 120), `c->>'child_id'`
даёт SQL `NULL`. Колонка `scans.child_id` нигде не `NOT NULL`
(`backup/database/schema.sql:3851`), и FK на nullable-колонке не блокирует
`NULL` — вставка в `scans` со строкой `child_id = NULL` пройдёт без ошибки.
`on_scan_insert_batch()`: `JOIN children c ON c.id = s.child_id` — `NULL`
никогда не матчится ни с одним `id`, строка тихо не попадает в
`children_today`, но «пустой» скан на `child_id = NULL` остаётся в `scans`
навсегда, ни разу не всплыв ни в одной ошибке.

Это тот же класс проблемы, что и Major 1 (тихая рассинхронизация вместо явной
ошибки `400`), но на уровне валидации входных данных, а не бизнес-правила
триггера. Требование `122.txt` («Валидация обязательных полей тела запроса
… при нарушении — ошибка 400») по букве относится к пакету в целом, но не
исключает элементы `children[]`, которые тоже часть тела запроса.

**Как исправлено**: не на уровне Edge Function (не добавляли валидацию формы
`children[]` в `index.ts`), а на уровне `submit_scan_packet()` — по решению
автора задачи оба варианта нереалистичны в реальной эксплуатации (`child_id`
в пакет попадает только из уже загруженного клиентом ростера), поэтому вместо
«мягкого» `400` от Edge Function добавлен явный `RAISE EXCEPTION` в начале
`submit_scan_packet()` при обнаружении элемента `children[]` без `child_id` —
атомарно ничего не создаётся, ошибка долетает до Edge Function как `500` с
текстом причины. Это осознанно проще, чем дублировать валидацию формы
элементов на клиенте Edge Function и на сервере БД.

# Minor

## Minor 1 — `TYPE_CODE[body.type]` уязвим к обращению к унаследованным свойствам `Object.prototype`

`supabase/functions/submit-scan-packet/index.ts`:

```ts
const TYPE_CODE = { BUS: 1, GROUP: 2, CHECKIN: 3 }
...
if (!body.client_packet_id || !TYPE_CODE[body.type] || !body.date || !body.finished_at)
  return json(400, { error: "Missing required packet fields" })
```

`TYPE_CODE` — обычный объектный литерал, у него в цепочке прототипов есть
`Object.prototype` со свойствами `constructor`, `toString`, `valueOf`,
`hasOwnProperty` и т.д. — все они функции, то есть «истинные» значения.
`body.type = "constructor"` (или `"toString"`, `"valueOf"`, ...) проходит
проверку `!TYPE_CODE[body.type]` как `false` (не отсутствует), хотя это не
валидный тип пакета. Дальше `body.type === 'BUS'`/`'GROUP'` — строгое
сравнение, не совпадёт ни с одним значением, поэтому проверки
`bus_id`/`group_id required` тоже не сработают. `type_code: TYPE_CODE[body.type]`
получит функцию; при сериализации в JSON для RPC-вызова свойство с
функцией-значением просто выпадает из тела запроса, `payload->>'type_code'`
на стороне БД — `NULL`, вставка в `scan_packets.type` (`NOT NULL`) упадёт —
результат: `500` вместо ожидаемого чистого `400` для заведомо некорректного
входа. Практических последствий для целостности данных нет (`author_id`
по-прежнему берётся только из проверенного профиля, констрейнты БД в итоге
всё равно блокируют вставку), но валидация не выполняет свою декларируемую
роль и выдаёт вводящий в заблуждение код ответа.

**Рекомендация**: `Object.prototype.hasOwnProperty.call(TYPE_CODE, body.type)`,
либо `Object.create(null)`/`Map` для `TYPE_CODE`, либо просто
`['BUS','GROUP','CHECKIN'].includes(body.type)`.

## Minor 2 — Смешанные окончания строк в `src/views/ChildrenView.vue`

Диф файла в коммите `a3c0fbd` показывает переписывание всех 338 строк
(`-338/+375`), хотя по факту изменения — это одна кнопка в таблице + одно

eol=lf`, если такая проблема уже возникала раньше в проекте).

# Архитектурные замечания

- Разделение `useScanPacket.js` (клиент, тикет 120, единственное число) и
  `useScanPackets.js` (админ-чтение, этот тикет, множественное число) — я
  бы не выбрал такую близкую пару имён сам, но выбор осознанно
  задокументирован в обоих местах (комментарий в файле, план, отчёт), и не
  создаёт двусмысленности при чтении кода. Не является замечанием к
  исправлению.
- `submit_scan_packet()` не помечена `SECURITY DEFINER` — это корректно и
  осознанно: функция вызывается только через `service_role`-клиент внутри
  Edge Function, который сам уже обходит RLS; `SECURITY DEFINER` здесь был
  бы избыточным повышением привилегий без необходимости.
- Пропуск `error` из `SELECT id, active FROM users WHERE user_id = ...`
  (только `!profile?.active`, без проверки `error`) маскирует настоящую
  ошибку БД под `403 Account inactive` — но это дословно тот же паттерн, что
  и в обоих прецедентах (`delete-user/index.ts`, `invite-generate/index.ts`),
  так что это не отклонение, внесённое этим тикетом, а унаследованный
  технический долг всего семейства привилегированных Edge Function проекта.
  Не требует исправления в рамках 122, но стоит иметь в виду, если этот
  паттерн будет пересматриваться отдельно.
- RLS `scan_packets_select_authenticated` (`USING (true)`) даёт любому
  аутентифицированному пользователю читать пакеты всех автобусов/групп, не
  только своих, — это совпадает с существующим паттерном проекта для
  `children_today`/`groups_today`/`reset_events` (`SELECT — любой
  authenticated`, см. `vault/03-База-данных/RLS-политики.md`), а не новое
  ослабление, специфичное для 122.
