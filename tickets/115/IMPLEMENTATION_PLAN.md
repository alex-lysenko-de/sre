# Цель

Исправить архитектурный дефект: пользователь без назначенной на сегодня
группы (`group_id === null`) может открыть экран `/group-edit` и работать
с несуществующей группой "null" — добавлять в неё детей, запускать для
неё пересчёт и т.п. Задача решает это тремя связанными изменениями:

1. Даёт пользователю возможность указать группу заранее — уже на экране
   регистрации по invite-ссылке (`WelcomeView.vue`), опционально.
2. Блокирует на уровне UI действия, требующие группы (`/group-edit` и
   производные кнопки), если эффективная группа не определена — кроме
   случая, когда группа передана явно (`:id`), что естественным образом
   покрывает сценарий администратора.
3. Делает выбор/смену группы доступной без обязательного предварительного
   подтверждения "Ich fahre heute mit!" (ежедневный check-in).

Отдельно задача фиксирует архитектурное решение по открытому вопросу,
поднятому в `tickets/115/115.txt` (варианты (а)/(б) — см. ниже).

# Анализ текущей архитектуры

Актуальная модель зафиксирована в `CLAUDE.md`, `vault/03-База-данных/
user_group_day.md`, `vault/04-Пользователи-и-аутентификация/stores-user.md`
и `vault/02-Предметная-область/Группы-и-рабочий-день.md`: `group_id`/
`bus_id` в `userInfo` — это поля из таблицы `user_group_day` **на
сегодня**, а не персистентный атрибут пользователя. Персистентной
"домашней группы" в БД нет.

## Существующий механизм переноса группы между днями

`useUser.fetchUserFromSupabase()` (`src/composables/useUser.js:71-112`) уже
реализует fallback: если записи `user_group_day` на сегодня нет, вызывается
`fetchLastKnownSchedule()` (`useSupabaseUser.js:97-112` — `ORDER BY day DESC
LIMIT 1`, без ограничения на прошлое/будущее), и `group_id`/`bus_id` из
последней известной записи попадают в `userInfo.group_id` (см. `useUser.js:
100-101`, `combinedData.group_id = scheduleData?.group_id || lastKnownGroup`).
Это значит: если хотя бы одна строка `user_group_day` с `group_id` для
пользователя когда-либо существовала, `userInfo.group_id` будет заполнен
даже без сегодняшнего check-in. Этот механизм — ключевой строительный блок
для архитектурного решения ниже.

Подтверждено также, что `src/composables/useDays.js` (`startNewDay()`,
`softReset()`) вообще не обращается к `user_group_day` (grep не дал
совпадений) — старт нового дня/сброс не затирают историю назначений,
`fetchLastKnownSchedule()` продолжает находить любую прошлую запись
бессрочно.

## Точное место дефекта "группа null"

Прочитаны и прослежены end-to-end:

- `GroupEditView.vue`, `created()` (строки 134-150): если `route.params.id`
  отсутствует, код берёт `groupId = this.userStore.userInfo.group_id` —
  **без проверки на `null`** — и присваивает его `this.groupNumber` как
  есть.
- Шаблон (строки 26-71) рендерит полный UI (список детей, кнопка "Neues
  Kind hinzufügen") независимо от значения `groupNumber`. Кнопка передаёт
  `:group-id="parseInt(groupNumber)"` (строка 79) в `AddEditChildModal.vue`.
- `AddEditChildModal.vue` объявляет `groupId` как `required: true, type:
  Number` (строки 113-117), но никак не валидирует его значение;
  `handleSubmit()` (строка 225) кладёт `group_id: this.groupId` в
  `childData` без проверки на `NaN`.
- `useChildren.saveChild()` (`src/composables/useChildren.js:200-245`)
  отправляет `payload` в Supabase без какой-либо валидации `group_id`.

Итог цепочки: `parseInt(null) === NaN` → при сериализации в JSON-тело
запроса (`JSON.stringify(NaN) === 'null'`) Supabase получает `group_id:
null` → в таблицу `children` реально попадает строка с `group_id = null`.
Это буквально дефект, названный в заголовке тикета.

## Единственное место, реально привязывающее выбор группы к check-in

`App.vue`, строка 27:
```html
<div v-if="!isCheckInRequired && userStore.userInfo.isPresentToday" ...>
  <!-- кнопки "Gruppe ändern" / "Bus ändern" -->
```
`isCheckInRequired` определён в `stores/user.js:29` как `!!userInfo.id &&
!userInfo.isPresentToday`. Для аутентифицированного пользователя (`id`
всегда truthy) это алгебраически `!isCheckInRequired ⇔ isPresentToday`, то
есть всё условие в App.vue сводится к `isPresentToday && isPresentToday` —
кнопки открытия `GroupChangeModal`/`BusChangeModal` видны **только после**
подтверждения "Ich fahre heute mit!". Это единственный реальный барьер,
который нужно снять для выполнения пункта 3 тикета — сам механизм записи
(`GroupChangeModal`/`assignUserToGroup`) уже готов и ничего менять не
требует.

Важно: пункт 3 тикета говорит только о **группе** ("Сделать выбор группы
доступным...") — про автобус там речи нет. Развязывать индикатор автобуса
от check-in не нужно, и делать этого не следует — см. следующий пункт.

## `bus_id` — не инертное поле, в отличие от `group_id` (найдено при
## обсуждении плана)

В отличие от `group_id` (который вне `/group-edit` больше нигде не
используется без фильтра `isPresentToday=1`, см. выше), `bus_id`
используется в `ScannerView.vue` **без какой-либо проверки
`isPresentToday`**:

```js
// src/views/ScannerView.vue:462-467
await armbandComposable.recordChildPresence(
    userStore.userInfo.id,
    child.id,
    bandId,
    userStore.userInfo.bus_id   // ← без проверки isPresentToday
)
```

Каждый скан ребёнка помечается тем `bus_id`, который в данный момент лежит
в `userInfo`, независимо от того, подтвердил ли пользователь сегодняшнее
участие. Сейчас это безопасно только потому, что единственные два места,
где `bus_id` вообще устанавливается (`DailyCheckInModalView.vue` — поле
"Bus" там `required`, и `BusChangeModal.vue`, кнопка которого в `App.vue`
сегодня видна только при `isPresentToday`), всегда идут в связке с
подтверждённым check-in. Если развязать видимость индикатора автобуса от
`isPresentToday` так же, как индикатор группы, появляется реальный
сценарий: пользователь из любопытства выбирает автобус, не собираясь
сегодня ехать, затем (сам или по ошибке) делает скан в `ScannerView.vue` —
скан привяжется к автобусу, на котором пользователь по факту не работает,
искажая присутствие в этом автобусе. Это не гипотетический риск, а прямое
следствие уже существующего кода — поэтому пункт 3 тикета реализуется
**только для группы**, индикатор/смена автобуса остаются привязаны к
`isPresentToday`, как сегодня.

(Отдельно, вне рамок этого тикета: кнопка "Scannen" в `MainView.vue`
видна вообще любому аутентифицированному пользователю — `v-if=
"isAuthenticated"`, без проверки `group_id`/`isPresentToday` — то есть
доступ к сканированию сегодня в принципе не завязан на check-in. Это
существующий, самостоятельный от тикета 115 пробел; в рамках данной
задачи не устраняется, но стоит держать в уме, если позже будет отдельный
тикет на ужесточение доступа к `/scanner`.)

## Архитектурное решение по открытому вопросу (а)/(б)

Выбран вариант **(б)**: при регистрации с указанной группой сразу писать
строку `user_group_day` на сегодняшнюю дату через уже существующий
`assignUserToGroup(groupId)` / `upsertScheduleField()`, **без** нового
столбца `users.default_group_id` (вариант (а)).

Обоснование:

- Вариант (б) полностью переиспользует уже работающий и уже описанный выше
  fallback `fetchLastKnownSchedule()` — новый источник истины для
  `group_id` не создаётся, приоритеты между "сегодняшняя запись / последняя
  известная запись / дефолтное поле" не нужно проектировать и тестировать.
- Не требует миграции БД.
- `upsertScheduleField(userId, date, { group_id })` обновляет только поле
  `group_id`, не трогая `isPresentToday`/`bMustWorkToday` (оба остаются
  `0` по умолчанию в `insertScheduleRecord()`, `useSupabaseUser.js:157-170`)
  — запись группы при регистрации не может быть ошибочно интерпретирована
  как подтверждение присутствия.
- Подтверждено выше (`useDays.js`), что записи `user_group_day` не
  затираются стартом/сбросом дня — запись, созданная в день регистрации,
  остаётся находимой `fetchLastKnownSchedule()` на любую будущую дату.
- Это ровно та же самая операция записи, которую сегодня для обычного
  пользователя с ролью `user` выполняют `DailyCheckInModalView.vue` и
  `GroupChangeModal.vue` — не требуется новая или отдельная RLS-политика.
- Вариант (а) создал бы второй, постоянно расходящийся источник "группы
  пользователя" (колонка в `users` vs. история в `user_group_day`),
  который пришлось бы согласовывать во всех местах чтения `group_id` — это
  архитектурное усложнение, не оправданное требованиями тикета.

   - Администратор (`role='admin'`, `group_id` всегда `null`): доступ к

# Риски

- **Соблазн симметрично развязать и автобус**: при реализации важно не
  "выровнять" условия для группы и автобуса в `App.vue` из соображений
  единообразия кода — они должны остаться разными намеренно (см. «`bus_id`
  — не инертное поле» в разделе «Анализ...»). Если кто-то в будущем
  скопирует условие группы для автобуса по аналогии, `bus_id` начнёт
  устанавливаться без подтверждённого присутствия и потенциально исказит
  привязку сканов в `ScannerView.vue:462-467` к автобусу — тест-сценарий на
  это явно включён в план реализации (п. 5).
- **RLS при первой записи в `user_group_day` сразу после регистрации**:
  `assignUserToGroup()` вызывается сразу после самого первого в жизни
  аккаунта `signInWithPassword()`. Сама операция (`insertScheduleRecord`
  для несуществующей ещё записи дня) идентична обычному ежедневному
  check-in новой строки для любого пользователя — но рекомендуется явно
  проверить на реальном инвайте, что RLS не завязана неявно на «уже была
  хотя бы одна предыдущая сессия/запись».
- **Гонка `signInWithPassword()` → `getSession()`**: между подтверждённым
  входом и фактической видимостью новой сессии в `supabase.auth.
  getSession()` теоретически возможна задержка (аналогичная уже
  чинившимся в тикетах 112/114 для PWA/iOS). Если `userStore.loadUser(true)`
  не увидит сессию, `assignUserToGroup()` бросит `'User not loaded'`;
  поскольку вызов обёрнут в некритичный `try/catch` (см. План реализации,
  п. 2), регистрация не прерывается, но группа в этом редком случае не
  сохранится с первого раза — пользователь сможет установить её позже
  через "Gruppe ändern" (после этой задачи доступную без check-in).
- **Путаница «эффективная группа» vs `route.params.id`**: важно не
  перепутать admin-путь (`/group-edit/:id`, явный id из `/children`) с
  обычным путём Betreuer (`/group-edit` без id, использующий `userInfo.
  group_id`) — блокировка должна срабатывать только при отсутствии ОБОИХ
  источников одновременно, иначе сломается один из двух легитимных
  сценариев.
- **Отсутствие серверной валидации диапазона `group_id`** (таблица
  `children`, `saveChild()` в `useChildren.js`) — не входит в объём этой
  задачи: тикет 115 фокусируется на UI-блокировке при отсутствующей
  группе, а не на серверной валидации допустимого диапазона `1..
  total_groups`. Отмечено как фоновый риск, не решаемый в рамках этого
  тикета.
- **Отсутствие автоматических тестов** на новую логику блокировки/
  предзаполнения группы — проверка целиком ручная (см. План реализации,
  п. 5); риск регресса при будущих изменениях остаётся фоновым, как и в
  предыдущих тикетах.
