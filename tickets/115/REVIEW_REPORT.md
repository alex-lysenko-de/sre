CHANGES_REQUIRED

Реализация в целом следует утверждённому `IMPLEMENTATION_PLAN.md` и решает
основной сценарий бага (регистрация с выбором группы, блокировка
`/group-edit` без группы, разблокировка кнопки "Gruppe ändern" от
check-in). Но найден один реальный функциональный баг, возникающий именно
из комбинации двух изменений этого тикета (п.2 + п.3), и один пункт DoD
("кроме администратора"), который фактически не обеспечен кодом, а
опирается на случайность структуры навигации, а не на проверку роли.
Ручная проверка сценариев из плана, судя по `IMPLEMENTATION_REPORT.md`,
не проводилась.

# Critical

Не найдено.

# Major

## 1. `noGroupAssigned` не сбрасывается реактивно → блокирующий экран «залипает» после выбора группы через шапку

`src/views/GroupEditView.vue:132-138`:

```js
watch : {
  'userStore.userInfo.group_id'(newGroupId) {
    if (!this.$route.params.id && newGroupId) {
      this.groupNumber = newGroupId
      this.loadInitialData()
    }
  }
}
```

Этот watcher существовал до тикета, но именно тикет 115 впервые создаёт
условия, при которых он срабатывает на уже смонтированной, заблокированной
странице `/group-edit`: пользователь без группы открывает `/group-edit`,
видит блокирующее сообщение (`noGroupAssigned = true`), затем — благодаря
именно этому тикету — кнопка "Gruppe ändern" в шапке (`App.vue:29`) теперь
доступна без check-in, открывает `GroupChangeModal`, пользователь выбирает
группу, `App.vue.onGroupChanged()` вызывает `userStore.loadUser(true)`.
Store обновляет `userInfo.group_id`, watcher в `GroupEditView` срабатывает,
подгружает детей через `loadInitialData()` — но **не** делает
`this.noGroupAssigned = false`. В шаблоне порядок `v-if/v-else-if` таков,
что `noGroupAssigned` по-прежнему перекрывает блок со списком детей
(`GroupEditView.vue:26-31` vs `:31`) — пользователь продолжает видеть
"Ihnen ist heute keine Gruppe zugewiesen…", хотя группа уже назначена и
данные фактически загружены в фоне. Нужна перезагрузка страницы, чтобы
увидеть список.

Это прямое следствие сочетания изменений тикета (разблокировка группы без
check-in + блокировка `/group-edit`) и не покрыто ручным тестированием
(см. `IMPLEMENTATION_REPORT.md`, раздел «Проверки» — ручная проверка не
проводилась). План реализации явно предусматривал тест-сценарий "открывает
Gruppe ändern ДО check-in", но не сценарий "делает это, уже находясь на
заблокированном `/group-edit`".

**Требуется исправить**: в watcher также сбрасывать `noGroupAssigned = false`
при появлении `newGroupId`.

## 2. Исключение "кроме администратора" не проверяет роль — только наличие `route.params.id`

`src/views/GroupEditView.vue:143-157` трактует любое непустое
`route.params.id` как "administrator path" и полностью пропускает проверку
`noGroupAssigned`. Но маршрут объявлен как:

```js
// src/router/index.js:73-77
{
    path: '/group-edit/:id?',
    name: 'GroupEdit',
    component: GroupEditView,
    meta: { requiresAuth: true, requiresAdmin: false }
}
```

`requiresAdmin: false` — то есть любой аутентифицированный пользователь с
ролью `user`, вручную набравший `/group-edit/7` в адресной строке (зная
или подобрав номер чужой группы), получает полный доступ на просмотр,
добавление и удаление детей группы 7, даже если сам он не привязан к этой
группе сегодня — блокировка `noGroupAssigned` в этом случае вообще не
срабатывает, т.к. `route.params.id` truthy.

Это не новый регресс — до тикета 115 такого же кода блокировки не было
вовсе, поведение по этому конкретному вектору не изменилось. Но
`IMPLEMENTATION_PLAN.md` (раздел «Изменения GroupEditView.vue») прямо
утверждает: *«Явное наличие `route.params.id` … всегда пропускается без
блокировки — этим и выражается исключение "кроме администратора" из
тикета»* — это утверждение неверно: наличие `:id` не эквивалентно роли
`admin`, это два разных условия, которые сейчас случайно совпадают только
потому, что единственная сегодняшняя ссылка с `:id` (`ChildrenView.vue:103`)
находится на admin-only странице `/children`. Прямой URL это не
блокирует. Дополнительно ослабляется тем, что RLS на `children`
(`vault/03-База-данных/RLS-политики.md`, раздел про legacy permissive
policies — `"Allow authenticated users to modify children"`,
`USING/WITH CHECK (true)`) тоже не ограничивает запись по группе/роли —
то есть проблема не только на уровне UI, но и не блокируется на уровне
данных.

Так как п. 2 DoD тикета явно требует блокировку "кроме администратора", а
реализация фактически не проверяет роль, этот пункт нельзя считать
выполненным строго по формулировке DoD — рекомендуется либо явно
подтвердить (с учётом реального состояния RLS), что эта задача сознательно
не устраняет данный вектор (и зафиксировать это как принятый фоновый риск,
аналогично уже сделанному для `children`/`saveChild()` в плане), либо
добавить проверку `userStore.isAdmin` рядом с проверкой `route.params.id`.

# Minor

- Дублирование разметки/логики выпадающего списка групп между
  `WelcomeView.vue:97-113` и `GroupChangeModal.vue:44-59` (разные семантики
  дефолтной опции: в одном месте `:value="null"` выбираемая "Keine Angabe",
  в другом — `disabled` placeholder). Не блокирует, но потенциальный
  источник расхождений при будущих правках (например, диапазона групп).
- `WelcomeView.vue:180-189` — `configStore.loadConfig()` вызывается
  безусловно в `onMounted()`, включая случай отсутствующего
  `inviteToken` (когда форма вообще не показывается, см. `v-if="!inviteToken"`
  в шаблоне) — лишний сетевой запрос в сценарии "битая ссылка". Низкое
  влияние (публичный кэшируемый эндпоинт, TTL 5 мин), но нет практической
  необходимости грузить конфиг, когда форма не будет показана.
- `App.vue:29,35` — индикатор "Gruppe {{ ... || '?' }}" теперь показывается
  и администратору (`userStore.userInfo.id` truthy для любой роли), у
  которого по определению домена нет группы (`115.txt`: «Работать с
  приложением без привязки к группе может только Администратор») — кнопка
  открывает `GroupChangeModal` и позволяет админу назначить себе группу,
  что не было предусмотрено ни тикетом, ни планом. Не ломает функциональность,
  но не по назначению — стоит решить, нужно ли скрывать этот индикатор для
  `isAdmin`.
- Отсутствуют автотесты на новую логику блокировки/предзаполнения — риск
  признан в `IMPLEMENTATION_PLAN.md`/`IMPLEMENTATION_REPORT.md` как фоновый,
  согласуется с практикой предыдущих тикетов.

# Архитектурные замечания

- Архитектурное решение (б) (запись группы при регистрации через уже
  существующий `assignUserToGroup()`/`upsertScheduleField()` без нового
  постоянного поля) обосновано корректно и полностью соответствует ранее
  задокументированной модели `group_id` как "поля на сегодня" — согласен с
  выбором, реализация ему не противоречит.
- Осознанное решение НЕ развязывать индикатор/логику автобуса от
  `isPresentToday` (в отличие от группы) корректно обосновано в плане
  прямой связью `bus_id` со сканами в `ScannerView.vue:462-467` — согласен,
  реализация в `App.vue` этому следует.
- См. Major 2 выше: формулировка плана "`route.params.id` ⇒ администратор"
  смешивает два независимых понятия (наличие параметра маршрута и роль
  пользователя) — стоит скорректировать понятийно в будущих ADR/планах,
  чтобы не закрепить это как архитектурный паттерн для других экранов.
