# Major

## 1. `noGroupAssigned` не сбрасывается реактивно → блокирующий экран «залипает» после выбора группы через шапку

`src/views/GroupEditView.vue:132-138`:

```js
watch : {
  'userStore.userInfo.group_id'(newGroupId) {
    if (!this.$route.params.id && newGroupId) {
      this.groupNumber = newGroupId
      this.loadInitialData()
    }
  }
}
```

Этот watcher существовал до тикета, но именно тикет 115 впервые создаёт
условия, при которых он срабатывает на уже смонтированной, заблокированной
странице `/group-edit`: пользователь без группы открывает `/group-edit`,
видит блокирующее сообщение (`noGroupAssigned = true`), затем — благодаря
именно этому тикету — кнопка "Gruppe ändern" в шапке (`App.vue:29`) теперь
доступна без check-in, открывает `GroupChangeModal`, пользователь выбирает
группу, `App.vue.onGroupChanged()` вызывает `userStore.loadUser(true)`.
Store обновляет `userInfo.group_id`, watcher в `GroupEditView` срабатывает,
подгружает детей через `loadInitialData()` — но **не** делает
`this.noGroupAssigned = false`. В шаблоне порядок `v-if/v-else-if` таков,
что `noGroupAssigned` по-прежнему перекрывает блок со списком детей
(`GroupEditView.vue:26-31` vs `:31`) — пользователь продолжает видеть
"Ihnen ist heute keine Gruppe zugewiesen…", хотя группа уже назначена и
данные фактически загружены в фоне. Нужна перезагрузка страницы, чтобы
увидеть список.

Это прямое следствие сочетания изменений тикета (разблокировка группы без
check-in + блокировка `/group-edit`) и не покрыто ручным тестированием
(см. `IMPLEMENTATION_REPORT.md`, раздел «Проверки» — ручная проверка не
проводилась). План реализации явно предусматривал тест-сценарий "открывает
Gruppe ändern ДО check-in", но не сценарий "делает это, уже находясь на
заблокированном `/group-edit`".

**Требуется исправить**: в watcher также сбрасывать `noGroupAssigned = false`
при появлении `newGroupId`.

# Архитектурные замечания

- Архитектурное решение (б) (запись группы при регистрации через уже
  существующий `assignUserToGroup()`/`upsertScheduleField()` без нового
  постоянного поля) обосновано корректно и полностью соответствует ранее
  задокументированной модели `group_id` как "поля на сегодня" — согласен с
  выбором, реализация ему не противоречит.
- Осознанное решение НЕ развязывать индикатор/логику автобуса от
  `isPresentToday` (в отличие от группы) корректно обосновано в плане
  прямой связью `bus_id` со сканами в `ScannerView.vue:462-467` — согласен,
  реализация в `App.vue` этому следует.
- **Модель разрешений (уточнено автором задачи после первой версии этого
  отчёта):** правильная модель — два независимых признака, применяемых
  одинаково ко всем ролям: `group_id === null` ⇒ операции с группой
  недоступны; `bus_id === null` ⇒ операции пересчёта в автобусе
  недоступны. Никакого отдельного ACL-исключения "кроме администратора"
  не нужно — админ является обычным бетройером и подчиняется тем же
  правилам null-проверки; отличие роли только в дополнительных пунктах
  меню (`/children`, `/config` и т.п.), а не в бизнес-логике блокировки.
  С этой точки зрения формулировка `IMPLEMENTATION_PLAN.md` — *«наличие
  `route.params.id` … этим и выражается исключение "кроме администратора"»*
  — вводит в заблуждение терминологически (это не ACL-исключение, а
  просто явно заданный контекст группы, доступный технически кому угодно
  по URL), но по факту не противоречит уточнённой модели: раз группа
  задана явно (≠ null), операции разрешены — независимо от роли, как и
  требуется. Возвращаться к этому пунктом обязательных исправлений не
  нужно (снято из Major, см. `IMPLEMENTATION_REPORT.md`-историю правок
  этого отчёта).
- Отдельно от ACL для группы: правило «`bus_id === null` ⇒ пересчёт в
  автобусе недоступен» в текущем кодовой базе пока не к чему применять —
  функции «пересчёт детей в автобусе» (по аналогии с `HeadcountView.vue`
  для группы) в проекте ещё нет; `AdminBusView.vue` — это админский обзор
  всех автобусов сразу, не завязанный на `userInfo.bus_id` конкретного
  пользователя. Не требует изменений в рамках тикета 115, но стоит держать
  в уме при проектировании будущей функции пересчёта по автобусу (см.,
  например, тикет 116).
- Пре-существующий и не относящийся к этому тикету технический риск:
  маршрут `/group-edit/:id?` объявлен с `requiresAdmin: false`
  (`src/router/index.js:73-77`), и RLS на `children`
  (`vault/03-База-данных/RLS-политики.md`, раздел про legacy permissive
  policies) не ограничивает запись по группе — то есть по уточнённой
  модели это не баг (группа явно задана ⇒ доступ по правилам разрешён), но
  стоит зафиксировать, что фактическая граница доступа к «чужой» группе
  сегодня — не ACL и не RLS, а исключительно то, что ссылка с `:id` сейчас
  есть только на admin-only странице `/children`. Вне объёма ticket 115.
