# Архитектурные замечания

- Архитектурное решение (б) (запись группы при регистрации через уже
  существующий `assignUserToGroup()`/`upsertScheduleField()`, без нового
  постоянного поля) обосновано и реализовано корректно.
- Осознанное решение НЕ развязывать индикатор/логику автобуса от
  `isPresentToday` (в отличие от группы) обосновано прямой связью
  `bus_id` со сканами в `ScannerView.vue:462-467` — реализация в
  `App.vue` этому следует, регрессий не внесено.
- Модель разрешений (уточнена автором задачи между раундами ревью): два
  независимых признака — `group_id === null` ⇒ операции с группой
  недоступны, `bus_id === null` ⇒ пересчёт в автобусе недоступен —
  применяются одинаково ко всем ролям, без отдельного ACL-исключения для
  администратора; роль влияет только на видимость пунктов меню. С этой
  точки зрения текущая реализация (`route.params.id` как явно заданный,
  отличный от `null`, контекст группы) уже соответствует модели — не
  потому что это «исключение для админа», а потому что группа явно
  задана. Терминология в `IMPLEMENTATION_PLAN.md` («исключение кроме
  администратора») по-прежнему неточна, но это не влияет на корректность
  поведения кода. Правило про `bus_id === null` пока не к чему применять:
  функции «пересчёт детей в автобусе» в кодовой базе ещё нет
  (`AdminBusView.vue` — сводный админский обзор, не завязанный на
  `userInfo.bus_id`); учесть при проектировании такой функции в будущем
  (например, тикет 116).

# Изменения со времени предыдущего ревью

Проверен `git diff` — из файлов проекта в этом раунде изменён только
`src/views/GroupEditView.vue`, на одну строку:

```diff
   watch : {
     'userStore.userInfo.group_id'(newGroupId) {
       if (!this.$route.params.id && newGroupId) {
         this.groupNumber = newGroupId
+        this.noGroupAssigned = false
         this.loadInitialData()
       }
     }
   },
```

Проверка логики: строка добавлена до вызова `this.loadInitialData()` (не
после), синхронно с обновлением `groupNumber`, внутри того же условия
(`!route.params.id && newGroupId`) — то есть срабатывает ровно в том
сценарии, где раньше проявлялся баг (пользователь получает `group_id` на
уже смонтированной, ранее заблокированной странице `/group-edit`).
Порядок веток `v-if/v-else-if` в шаблоне (`loadingInitialData` →
`!isConfigLoaded` → `noGroupAssigned` → `v-else` со списком) теперь
корректно приводит к показу списка детей после того, как
`loadInitialData()` завершится, без необходимости перезагрузки страницы.
Других мест, где `noGroupAssigned` мог бы аналогично «зависнуть», не
найдено — `created()` — единственное место, где флаг устанавливается в
`true`, и единственный watcher, который может сделать группу доступной
реактивно после монтирования, теперь сбрасывает его корректно.

Побочных эффектов не обнаружено:
- `route.params.id`-путь (admin/явный переход из `/children`) watcher не
  затрагивает (`!this.$route.params.id` в условии) — поведение для этого
  пути не изменилось.
- Изменение не затрагивает `App.vue`/`WelcomeView.vue` — оба файла
  идентичны состоянию предыдущего раунда ревью (подтверждено `git diff`),
  поэтому все выводы предыдущего ревью по этим файлам (кроме уже
  скорректированной трактовки Major 2 — см. «Архитектурные замечания»)
  остаются в силе без повторной проверки построчно.
- `npm run build` по отчёту разработчика проходит успешно (322 модуля).

Второй пункт прошлого списка обязательных исправлений («выполнить ручную
проверку сценариев из плана») разработчик закрыл не изменением кода
(что и ожидалось — это не дефект кода), а явной фиксацией статуса
тестирования в `IMPLEMENTATION_REPORT.md`; поскольку сама правка
однострочная и низкорисковая, отсутствие интерактивной Supabase-проверки
не блокирует PASS, но перенесено в Minor как рекомендация перед боевым
релизом.
