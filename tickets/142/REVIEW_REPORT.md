следствие того, как в этом же тикете переиспользован `error.value`/

# Major

**1. Ошибка при удалении ребёнка с `/child/:id` оставляет пользователя в тупиковом состоянии без навигации.**

`ChildDetailView.vue:12-20` — шаблон использует взаимоисключающую цепочку
`v-if="isLoading"` / `v-else-if="error"` / `v-else-if="child"`. Блок
ошибки (`:13-17`) содержит только заголовок и текст — ни кнопки «Zurück»,
ни какой-либо другой навигации в нём нет:

```html
<div v-else-if="error" class="alert alert-danger" role="alert">
  <h4 class="alert-heading">⚠️ Fehler</h4>
  <p>{{ error }}</p>
  <hr>
</div>
```

До этого тикета `error.value` на этом экране выставлялся только в
`loadChildDetails()` (`:162-180`) — то есть до того, как карточка вообще
успевала отрисоваться (сеть недоступна / ребёнок не найден); в этот
момент показывать пустой экран с одной ошибкой было приемлемо, деградации
навигации по сути не было (карточка и так ещё не показывалась).

Новая функция `removeChild()` (`:217-234`, добавлена этим тикетом)
переиспользует тот же `error.value` при неудачном
`childrenComposable.deleteChild(...)` (`:230-232`) — но теперь ошибка
происходит **после** того, как карточка уже была показана и
пользователь взаимодействовал с ней. Из-за `v-else-if` весь `<div
v-else-if="child">` (включая кнопки «Zurück», «Bearbeiten», «Entfernen»,
всю информацию о ребёнке) немедленно перестаёт рендериться и
заменяется на голый блок ошибки — без кнопки «Zurück» или повторной
попытки. Единственный выход — браузерная навигация назад/вручную
изменённый URL; для установленного PWA (см. `vite.config.js`,
`registerType`) этот путь может быть не всегда очевиден или доступен.

Сценарий: RLS/сетевая ошибка при `DELETE` (риск 4 плана — «требует
подтверждения вручную», то есть сам план признаёт эту ветку
неполностью проверенной) → пользователь застревает на экране без единой
кнопки.

Это не отклонение от плана — план (`IMPLEMENTATION_PLAN.md:167-169`)
прямо предписывает «показать ошибку тем же способом, что уже принят на
этой странице (`error.value = ...`, тот же блок `alert-danger`)», то
есть дефект уже заложен на уровне плана, а реализация просто следует
ему буквально. Затрагивает именно новую функциональность тикета, а не
уже существовавшее поведение — поэтому не наследуемый долг, а новый
баг.

Рекомендация: не использовать во `removeChild()` тот же `error.value`,
что и для `loadChildDetails()` (у которого действительно нет смысла
показывать карточку без данных) — либо завести отдельное состояние
ошибки удаления и показывать его поверх/рядом с уже отрисованной
карточкой (как это уже делает `alert-danger` внутри самой карточки на
других экранах проекта, например `AddEditChildModal.vue`), либо как
минимум продублировать кнопку «Zurück» в блоке ошибки.

# Minor

**1. Нет блокировки повторного нажатия «Entfernen» на время запроса.**

`removeChild()` (`ChildDetailView.vue:217-234`) не выставляет никакого
флага занятости (`isDeleting`/аналог) на время `await
childrenComposable.deleteChild(...)`, кнопка не получает `:disabled`.
Между подтверждением `confirm()` и завершением запроса пользователь
теоретически может ещё раз нажать «Entfernen», получить второй
`confirm()` и запустить повторный `deleteChild()` для уже удаляемого
(или уже удалённого) ID. Риск невысокий (требует быстрого повторного
клика в узком окне), но это тот же класс проблемы, что уже отмечался в
ревью 141 (гонки из-за отсутствия блокировки повторного действия) —
стоит взять за общий паттерн для новых async-обработчиков кнопок в
проекте.

**2. `AddEditChildModal.vue` сохраняет полностью неиспользуемую ветку `isEditing`.**

План (раздел «Риски», п.1) сам заранее фиксирует это как осознанно
отложенную уборку, не входящую в объём тикета — не блокирует ревью,
но подтверждаю находку: после этого тикета ни один вызывающий не
передаёт `AddEditChildModal` непустой `child-data` (единственный
оставшийся потребитель — `GroupEditView.vue::openAddChildModal()`,
всегда с `selectedChild = null`), то есть ветки `isEditing` в шаблоне и
скрипте компонента стали недостижимым кодом. Технический долг,
осознанно принят планом — упомянут здесь для полноты, отдельного
исправления в рамках 142 не требует.

# Архитектурные замечания

- Повторное использование единственного `error.value` + жёсткого
  `v-if/v-else-if` для «ошибка загрузки страницы» и «ошибка действия
  на уже загруженной странице» — источник Major 1. Это общий паттерн
  риска: любое новое действие на этой странице, которое в будущем
  тоже начнёт писать в `error.value` (например, если понадобится
  показать ошибку и от `editChild()`), унаследует тот же дефект.
  Стоит рассмотреть отдельное состояние ошибки, не завязанное на
  `v-else-if` всего тела карточки, как общий паттерн для «view-level
  load error» vs. «in-place action error».
- Перенос удаления с `/group-edit` (список, ошибка — временный toast
  `showAlert`, список остаётся видимым) на `/child/:id` (единственная
  карточка, ошибка — подмена всего экрана) — сам по себе логичный
  результат требования тикета («редактирование/удаление — со страницы
  просмотра»), но два разных экрана теперь используют для одной и той
  же операции (`deleteChild`) два разных, несовместимых по UX способа
  сообщать об ошибке. Не блокирует тикет, но стоит держать в уме при
  дальнейшей унификации UI ошибок в проекте.
