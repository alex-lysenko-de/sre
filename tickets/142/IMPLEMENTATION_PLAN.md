# Цель

Привести сценарий «просмотр/привязка/редактирование ребёнка» в
соответствие с текущей бизнес-логикой:

1. Убрать возможность отметить присутствие ребёнка сразу после привязки
   Armband — присутствие регистрируется только через перекличку
   (сканирование ребёнка в рамках Checkpoint), так как только там
   можно указать сопутствующие данные (например, номер автобуса).
2. Привести список детей на `/group-edit` к паттерну «список
   виджетов»: убрать точечные кнопки «изменить»/«удалить» из строки
   списка, сделать саму строку кликабельной ссылкой на страницу
   просмотра ребёнка (`/child/:id`); редактирование и удаление
   переносятся на страницу просмотра (кнопка «bearbeiten» уже есть,
   рядом с ней добавляется «entfernen»).

Функциональность сканирования/переклички, БД-схема присутствия и сама
процедура привязки Armband к ребёнку (выбор ребёнка из группы) не
меняются — тикет затрагивает только то, что происходит **после**
успешной привязки и просмотр/переходы в списке `/group-edit`.

# Анализ текущей архитектуры

В проекте существуют **два разных экрана просмотра ребёнка** с разной
аудиторией и разным назначением — важно не перепутать их:

| Маршрут | Компонент | Назначение | Используется из |
|---|---|---|---|
| `/child/:id` (`ChildDetail`) | `ChildDetailView.vue` | «Моя группа»/руки на местах: карточка ребёнка обычного Betreuer'а | `ArmbandView.vue` (после привязки и когда бейдж уже привязан), `/group-edit` (после этого тикета) |
| `/admin/checkpoints/child/:id` (`CheckpointChildCard`) | `ChildCardView.vue` | Админ-контекст Checkpoint: карточка ребёнка со scan-историей, `GroupLink`/`BetreuerLink` (тикет 133) | `ChildLink.vue`/`EntityListCard.vue` из `GroupEntityView.vue` и других Checkpoint-admin экранов |

Тикет 142 целиком про первый экран (`ChildDetailView.vue`, маршрут
`/child/:id`) — именно на него ссылается пример из 142.txt
(«/child/19»), и именно он замыкает сценарий `/group-edit` →
просмотр → редактирование. `ChildCardView.vue` и Checkpoint-admin
маршруты этим тикетом не затрагиваются (другая аудитория, другой
набор данных — там нет ни кнопки регистрации присутствия, ни
удаления, трогать нечего).

## Текущий поток «привязка → предложение отметить присутствие»

`ArmbandView.vue` (маршрут `/armband/:id`, открывается со сканера при
статусе `not-found` через «Привязать бейдж», см. `Scanner.vue`/тикет
126 п.7) после `assignArmband()` уже сегодня **напрямую** переходит на
`{ name: 'ChildDetail', params: { id } }` (`ArmbandView.vue:203-211`) —
отдельного «предложения отметить присутствие» в самом `ArmbandView.vue`
нет. Источник «предложения» — сам экран `ChildDetailView.vue`, на
который производится переход: там сразу под заголовком располагается
акцентный блок «Heute noch nicht anwesend» + кнопка «✅ Präsenz
registrieren» (`ChildDetailView.vue:45-57`), открывающая
`ChildPresenceModal.vue` с чекбоксом «Bus-Nummer hinzufügen»
(`ChildPresenceModal.vue:42-53`) — это и есть «галочка», о которой
говорит 142.txt. Проверено: `ChildPresenceModal.vue` используется
**только** из `ChildDetailView.vue` (второго потребителя нет).

Итог: специфичного кода в `ArmbandView.vue` для требования 1 нет —
достаточно убрать «предложение» на самом `ChildDetailView.vue`
(что дословно совпадает и с требованием 2.3 тикета — это одно и то же
изменение, описанное с двух сторон: бизнес-обоснование в п.1 и
конкретное расположение в UI в п.2.3).

## Текущий список `/group-edit`

`GroupEditView.vue` (маршрут `/group-edit/:id?`, имя `GroupEdit`) рисует
`<li>` на каждого ребёнка с двумя кнопками — «Bearbeiten» (открывает
`AddEditChildModal.vue` в режиме редактирования, `editChild()`) и
«Entfernen» (`removeChild()` → `useChildren().deleteChild()` через
`confirm()`-диалог, `GroupEditView.vue:205-220`). Перехода на отдельную
страницу просмотра нет вообще — редактирование только через модалку.

Добавление нового ребёнка («Neues Kind hinzufügen» →
`openAddChildModal()` → та же `AddEditChildModal.vue` в режиме
создания) тикетом не затрагивается и остаётся как есть.

### Про «список виджетов»

В проекте уже существует паттерн «список виджетов» (`EntityListCard.vue`
+ `ChildLink.vue`, тикет 133) — но он используется только в
Checkpoint-admin разделе и `ChildLink.vue` **жёстко** ведёт на
`/admin/checkpoints/child/:id` (`ChildLink.vue:5`, без пропа для
переопределения маршрута). Прямое переиспользование этих компонентов
в `/group-edit` увело бы пользователя на чужой (админский) экран
просмотра, что противоречит требованию тикета (пример в 142.txt —
именно `/child/19`, т.е. `ChildDetail`). Поэтому здесь заимствуется
только **концепция** (строка списка целиком кликабельна, без точечных
кнопок действий в строке) — реализуется прямо в разметке
`GroupEditView.vue`, без импорта компонентов из
`src/components/checkpoints/`, которые концептуально принадлежат
Checkpoint-admin слою, а не «моей группе» обычного Betreuer'а.

# Риски

1. **`AddEditChildModal.vue` остаётся с неиспользуемым режимом
   редактирования.** После этого тикета никто не вызывает модалку с
   непустым `childData` — `isEditing`-ветка (`:137-139`,
   `:158-166`) становится мёртвым, но не удалённым кодом. Тикет не
   просит трогать этот компонент (используется для добавления), и его
   удаление — отдельное решение с более широким обоснованием (может ли
   он ещё понадобиться, например, если `ArmbandConnectView.vue` когда-
   нибудь будет реализован по своему TODO, который явно ссылается на
   «ту же форму, что в GroupEditView»). Оставлено как есть, зафиксировано
   здесь для будущей уборки.
2. **`presenceInfo`/баннер статуса остаётся без явного запроса в
   тикете.** Формально 142.txt просит убрать только кнопку/предложение
   регистрации, а не сам показ статуса. Решение оставить баннер — не
   расширение объёма (баннер уже существовал), но при ревью стоит
   явно сверить с автором задачи, что информационный (не
   призывающий к действию) баннер присутствия допустим на этом экране,
   либо убрать и его, если весь блок присутствия должен исчезнуть
   целиком.
3. **Место возврата после удаления ребёнка.** `ChildDetailView.vue`
   открывается не только из `/group-edit`, но и из `ArmbandView.vue`
   (после привязки). Выбранный редирект после удаления —
   `GroupEdit` (с `group_id` удалённого ребёнка, если есть) — логичен
   для основного сценария (просмотр из списка группы), но не является
   буквальным «вернуться туда, откуда пришли» (`router.back()`) — после
   удаления ребёнка «назад» на `ArmbandView.vue` того же бейджа не имеет
   смысла (ребёнка, которому его привязали, больше не существует),
   поэтому переход на список группы — осознанный выбор, а не
   недосмотр.
4. **RLS/права на `DELETE children`.** Кнопка удаления просто
   переезжает на другой экран — существующие права уже проверены тем,
   что кнопка сегодня работает на `/group-edit`; риск регрессии прав
   минимален, но стоит подтвердить вручную (тот же Betreuer, что мог
   удалять ребёнка своей группы из списка, должен мочь сделать то же
   самое с экрана просмотра).

- `npm run build` проходит, нет мёртвых импортов удалённого

- Ручная проверка в браузере (п.6 плана реализации) подтверждает все
