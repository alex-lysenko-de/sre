# Итог

CHANGES_REQUIRED

Реализация в целом соответствует плану (ревизия 2): `getSession()` теперь вызывается всегда,
флаг `sre_user_registered` понижен до подсказки для redirect-таргета, добавлено самовосстановление
флага, `LogoutConfirmModal` + `clearAllAuthStorage()` реализованы, `npm run build` проходит без
ошибок (318 модулей, проверено повторно при ревью). Найдено два конкретных бага, один из которых
напрямую касается сценария, ради которого написан этот тикет (ненадёжная запись в LocalForage на
iOS), и один — прямое расхождение между кодом и явно задокументированным намерением плана/отчёта.
Оба воспроизводимы по коду без необходимости физического iPhone.

# Найденные проблемы

## Critical

Нет.

## Major

### 1. `clearAllAuthStorage()` стирает `app_config_cache` и другие данные, вопреки явно
   задокументированному намерению

`src/modules/storage.js:43-46`:

```js
export async function clearAllAuthStorage() {
    await authLocalForage.clear()
    window.localStorage.clear()   // <-- стирает ВСЁ, не только legacy auth-ключи
}
```

И план (`IMPLEMENTATION_PLAN.md`, риск №5), и отчёт (`IMPLEMENTATION_REPORT.md`), и обновлённый
`vault/.../Кэширование-LocalForage.md` явно утверждают: «`app_config_cache` (`stores/config.js`)
этой функцией сознательно не затрагивается». Это неверно на практике:

- `src/stores/config.js:95` пишет конфиг-кэш через **обычный** `localStorage.setItem(CONFIG_CACHE_KEY, ...)`
  (`CONFIG_CACHE_KEY = 'app_config_cache'`), а не через LocalForage.
- `src/views/ScannerView.vue:348` таким же образом хранит выбор камеры пользователем
  (`localStorage.setItem('scanner_preferred_camera_id', ...)`).

`window.localStorage.clear()` не различает «legacy auth-ключи read-through-миграции тикета 105» и
любые другие ключи в том же origin — он стирает буквально весь `localStorage`. То есть при выходе
с чекбоксом «Auch lokale Daten löschen» пользователь неожиданно теряет закешированный конфиг
приложения (будет перезапрошен — не критично) и **выбор камеры сканера** (UX-регрессия, не
относящаяся к авторизации и не упомянутая в чекбоксе).

**Как исправить:** заменить `window.localStorage.clear()` на точечное удаление только тех ключей,
которые реально относятся к legacy auth read-through-миграции (например, перечислить конкретные
ключи, как это уже делает `removeAuthItem()`), либо явно задокументировать и согласовать с
заказчиком, что очистка теперь шире, чем было заявлено.

### 2. Успешный автологин после регистрации может привести к редиректу на `/login` из-за
   сбоя записи флага — то есть именно тот сценарий, который тикет должен устранять

`src/views/WelcomeView.vue:210-228`:

```js
setTimeout(async () => {
  try {
    const { error: signInError } = await supabase.auth.signInWithPassword({...})
    if (signInError) throw signInError

    // Flag wird erst nach bestätigtem Login gesetzt
    await setAuthItem('sre_user_registered', 'true');   // <-- await внутри общего try
    console.log('...');

    await router.push('/info')
  } catch (err) {
    console.error('Fehler bei der automatischen Anmeldung:', err)
    await router.push('/login')     // <-- срабатывает и при сбое setAuthItem, не только signIn
  }
}, 1500)
```

`setAuthItem()` находится в том же `try`, что и `signInWithPassword()`. Если запись в LocalForage
на этом шаге не удалась (а именно такая ненадёжность на iOS — центральная гипотеза всего тикета,
см. `112.txt` и план), пользователь получает `catch` и уходит на `/login`, **несмотря на то что
`signInWithPassword()` только что успешно отработал и сессия Supabase реально существует**. Это
воспроизводит симптом тикета в модифицированном виде: не постоянная поломка устройства (флаг
самовосстановится в `App.vue` при следующем подтверждении сессии — архитектурно это исправлено
верно), но одноразовый, лишний экран логина сразу после успешной регистрации — худший первый
UX-опыт именно там, где задача была его улучшить.

**Как исправить:** вынести `setAuthItem` из-под `try/catch`, относящегося к `signInWithPassword`, и
сделать её fire-and-forget по образцу самовосстановления в `App.vue`
(`setAuthItem(...).catch(err => console.error(...))`), не блокируя переход на `/info` в случае её
сбоя — ровно то поведение, которое ключевой принцип плана уже реализует в `App.vue`, но не в этом
конкретном месте `WelcomeView.vue`.

## Minor

### 3. Дублирование логики проверки сессии между `router/index.js` и `App.vue`

Теперь `supabase.auth.getSession()` и `getAuthItem('sre_user_registered')` вызываются на **каждую**
навигацию дважды независимо друг от друга: один раз в `router.beforeEach` (для решения о редиректе)
и второй раз в `App.vue` (`checkAuth()` по `watch(route.path)` либо `initializeApp()` при монтировании)
для самовосстановления флага и загрузки `userStore`. Раньше вызов `getSession()` в guard был
условным (только при `isRegistered && meta.requiresAuth`), сейчас — безусловный на каждой странице,
включая полностью публичные (`/login`, `/welcome`). Само по себе решение осознанное (см. план), но
having почти идентичную auth-логику в двух местах — риск рассинхронизации при будущих изменениях
(например, правило "гость → только Welcome/Main/Info" сейчас продублировано только в
`router/index.js`, `App.vue` его не знает и полагается, что guard уже отработал раньше). Не блокирует
приёмку, но стоит учитывать как технический долг.

### 4. Ручная регрессия на Android/десктопе не выполнена

Отчёт честно фиксирует: пункт 6 плана (регрессия логина/восстановления сессии/обоих вариантов
выхода на доступных устройствах) отмечен как невыполненный из-за отсутствия окружения с реальным
Supabase-бэкендом. Изменение redirect-таргета (`/info` → `/login` для «флаг есть, сессии нет»)
задокументированно как затрагивающее всех пользователей, не только iPhone (риск №3 плана) — то есть
это единственный пункт DoD, оставшийся полностью непроверенным вручную, а не только на iPhone.
Рекомендуется выполнить перед мерджем либо явно перенести на отдельный шаг после мерджа с owner'ом
задачи.

# Архитектурные замечания

- Корневая причина (раздельное/ненадёжное хранилище Safari vs standalone PWA на iOS) не была
  подтверждена диагностикой на реальном устройстве — это осознанный и явно задокументированный риск
  плана (риск №1 и №6), не упущение реализации. Если после релиза проблема на iPhone сохранится
  (например, если реальная причина — что `authLocalForage`, где лежит и сессия Supabase, и сама
  сессия физически недоступна в standalone-режиме, а не только ненадёжна разово), придётся вернуться
  к варианту с диагностикой на устройстве — план это прямо предвидит.
- Ключевое архитектурное решение — сессия как источник истины, флаг как подсказка для redirect —
  реализовано корректно и именно там, где должно быть (`router/index.js`, `App.vue`). Самовосстановление
  флага fire-and-forget по аналогии с `last_seen_date` — хороший, консистентный с существующим кодом
  паттерн.
- Порядок операций в `logout()` (`signOut()` → `clearUserCache()` → опционально
  `clearAllAuthStorage()`) корректно соответствует риску №2 плана (revoke до стирания токена).

# Рекомендации

1. Исправить оба Major-пункта перед мерджем — они конкретны, легко воспроизводимы по коду и
   недороги в исправлении (несколько строк).
2. Явно перечислить в `clearAllAuthStorage()` (или в отдельной функции) ключи, которые
   действительно относятся к legacy read-through-миграции, вместо блан­кетного
   `window.localStorage.clear()`.
3. Перед закрытием тикета выполнить хотя бы минимальную ручную регрессию на Android/десктопе
   (пункт 6 плана), особенно для изменения redirect-таргета `/info` → `/login`, — это затрагивает
   всех пользователей, не только iPhone.

# Список обязательных исправлений

1. `src/modules/storage.js` — заменить `window.localStorage.clear()` в `clearAllAuthStorage()` на
   точечную очистку только legacy auth-ключей, чтобы не стирать `app_config_cache`
   (`stores/config.js`) и `scanner_preferred_camera_id` (`ScannerView.vue`), как и было
   задокументировано в плане/отчёте/vault.
2. `src/views/WelcomeView.vue` — вынести `await setAuthItem('sre_user_registered', 'true')` из-под
   `try/catch`, ловящего ошибки `signInWithPassword()`, и сделать запись fire-and-forget, чтобы
   сбой этой записи не редиректил только что успешно вошедшего пользователя на `/login`.

# Список необязательных улучшений

1. Устранить дублирование auth-логики между `router/index.js` и `App.vue` (например, вынести общую
   проверку «сессия есть / флаг говорит X» в один переиспользуемый модуль), чтобы избежать
   рассинхронизации правил в будущем.
2. Выполнить и задокументировать ручную регрессию на Android/десктопе (пункт 6 плана) до закрытия
   тикета, а не только при следующей возможности.
