# IMPLEMENTATION_PLAN — Тикет 112: Сохранение авторизации в PWA на iPhone (Safari / Add to Home Screen)

> Ревизия 2. Обсуждена с заказчиком после версии 1: диагностический тестовый
> режим (временное логирование + отдельный экран для просмотра логов без
> Mac) отклонён как непропорционально сложный при отсутствии физического
> iPhone для тестирования. Вместо диагностики-с-подтверждением заказчик
> выбрал прямое упрощение архитектуры, осознанно принимая риск того, что
> поведение на Android может незначительно измениться. Это план исправления,
> код не пишется.

---

## Ключевые принципы (зафиксированы в обсуждении, определяют весь план)

1. **Пользователь логинится один раз.** Успешно авторизовавшись (логин+пароль),
   пользователь больше не должен вводить их снова — ни на веб-сайте, ни в
   установленном PWA. Это должно работать одинаково на всех платформах.
2. **Система обязана отличать гостя от залогиненного пользователя.**
   Сканирование браслета гостем ведёт на `/info` и никуда больше (кроме
   `/login`) — этот экран не должен превращаться в полноценный проходной портал.
   Способ различения — либо флаг `sre_user_registered`, либо непосредственно
   факт наличия сессии; в обоих случаях главное требование — надёжность на
   iPhone, а не конкретный механизм.
3. **Пользователь должен иметь возможность полностью стереть локальные
   данные** (например, при продаже/передаче телефона) — после этого его
   устройство должно быть неотличимо от устройства гостя, который никогда не
   регистрировался.

Направление хранения — **в сторону LocalForage/IndexedDB, не обратно к
`localStorage`** (см. `doc/migration_guide.md`, тикет 105: `localStorage`
уже признан менее надёжным вариантом и был сознательно заменён). План не
предлагает откат к `localStorage` ни в каком виде — только исправление того,
как и когда используется LocalForage.

---

## Диагностика причины (обновлено)

Версия 1 плана предполагала обязательную диагностическую фазу с временным
логированием на реальном iPhone перед любым исправлением. Заказчик отклонил
этот подход — устройства для тестирования нет, эмуляторы дают ограниченную
достоверность, а сама diagnostic-инфраструктура добавляет сложность в и без
того переусложнённую auth-цепочку. Вместо этого выбран путь прямого
упрощения кода, который снижает количество точек отказа независимо от того,
какая именно причина (раздельное хранилище Safari/standalone, зависание
IndexedDB, ITP-вытеснение) окажется основной — потому что все три найденные
ниже проблемы являются реальными архитектурными дефектами вне зависимости от
специфики WebKit.

### Найдено при разборе кода (наиболее вероятная главная причина)

`sre_user_registered` пишется в `WelcomeView.vue` **сразу после успешного
`invite-accept`, до подтверждения входа** (строка `await setAuthItem(...)`
идёт раньше отложенного на 1.5 сек `signInWithPassword()`). Если запись этого
флага на iPhone ненадёжна (что и является предполагаемой причиной всего
бага), то и последующий фактический логин её не чинит — `LoginView.vue`
записывает флаг только при явном ручном логине через форму, а не при
автологине после регистрации, и ничто в коде не перезаписывает флаг повторно
при последующих успешных проверках сессии. Итог: одна неудачная запись в
LocalForage в момент регистрации перманентно "ломает" устройство — оно ведёт
себя как незарегистрированное при каждом следующем запуске, даже если сама
сессия Supabase восстанавливается нормально.

Это объясняет симптом точнее, чем гипотеза "разное хранилище Safari/PWA": не
обязательно нужен переход через границу браузер→установленное приложение —
хватает одной сбойной записи в любой момент, и флаг после этого никогда не
восстанавливается сам.

## Затрагиваемые модули

- `src/router/index.js` (`beforeEach`) — гейт "сначала флаг, потом сессия".
- `src/App.vue` (`initializeApp()`, `checkAuth()`, `logout()`) — тот же гейт;
  здесь же добавляется самовосстановление флага и вызов нового диалога выхода.
- `src/views/WelcomeView.vue` — момент и порядок записи флага при
  регистрации по invite.
- `src/views/LoginView.vue` — момент записи флага при обычном логине
  (уже корректен по времени, изменений по существу не требует).
- `src/modules/storage.js` — точка добавления `clearAllAuthStorage()` для
  функции "удалить локальные данные" при выходе.
- `src/stores/user.js` (`clearUserCache`) — переиспользуется/расширяется для
  выхода с полной очисткой.
- Новый компонент `src/components/LogoutConfirmModal.vue` (по аналогии с уже
  существующими `GroupChangeModal.vue`/`BusChangeModal.vue`).

## Изменения в существующих модулях

### 1. `src/router/index.js` + `src/App.vue` — сессия проверяется всегда, флаг — не блокирующий гейт

Сейчас: если `sre_user_registered` не читается как `'true'`, код вообще не
вызывает `supabase.auth.getSession()` — рабочая сессия, если она есть,
никогда не проверяется.

Меняем порядок: **всегда** вызывать `supabase.auth.getSession()` в
`beforeEach` и в `App.vue.initializeApp()/checkAuth()`, независимо от
значения `sre_user_registered`. Логика становится:

- Есть активная сессия → пользователь авторизован, обычный поток (плюс —
  см. пункт 3 — самовосстановление флага).
- Сессии нет **и** флаг `sre_user_registered !== 'true'` → гость →
  `/info`/публичные страницы, как сейчас.
- Сессии нет, но флаг `'true'` (устройство когда-то логинилось, сессия сейчас
  недействительна/просрочена) → это уже не "случайный прохожий", разумно
  вести на `/login`, а не на `/info` — с `/info` у пользователя сейчас нет
  пути обратно к логину (`InfoView.vue` не содержит ссылки на `/login`,
  проверено чтением файла — там только номер телефона для находки ребёнка).

Флаг, таким образом, не убирается, а **понижается в правах**: раньше он был
обязательным условием для проверки сессии вообще, теперь — только подсказка
для выбора страницы в единственном случае "сессии сейчас нет".
Ошибочное значение флага в этом сценарии не ломает основной обещание
принципа №1 (залогиненный пользователь остаётся залогиненным) — оно влияет
только на то, куда именно попадёт пользователь без сессии.

### 2. `src/views/WelcomeView.vue` — флаг пишется только после подтверждённого входа

Текущий порядок: `invite-accept` успешен → `setAuthItem(flag)` →
`setTimeout(1500) → signInWithPassword()`.

Новый порядок: `invite-accept` успешен → `signInWithPassword()` → **только
при успехе** → `setAuthItem(flag)` → редирект на `/info`. Если автологин не
удался (`catch` уже редиректит на `/login`), флаг не пишется — устройство не
помечается как "известное" по факту, которого не произошло.

### 3. Самовосстановление флага при каждой подтверждённой сессии

В `App.vue` (`handleAuthentication()`/`checkAuth()`), там же, где уже
выполняется fire-and-forget обновление `last_seen_date` (тот же паттерн уже
есть в `router/index.js`), добавить fire-and-forget
`setAuthItem('sre_user_registered', 'true')` каждый раз, когда
`getSession()` подтвердил активную сессию. Это устраняет корневой сценарий,
описанный выше: даже если запись флага в момент регистрации на iPhone не
удалась, при первом же успешном чтении сессии флаг будет восстановлен без
участия пользователя. Дешёвая операция (idempotent bool), не блокирует UI.

### 4. `src/modules/storage.js` — `clearAllAuthStorage()`

Новая функция, дополняющая существующие `getAuthItem`/`setAuthItem`/
`removeAuthItem`:

```js
export async function clearAllAuthStorage() {
    await authLocalForage.clear()
    window.localStorage.clear() // legacy-ключи, оставшиеся от read-through-миграции (тикет 105)
}
```

Отличие от уже существующего `removeAuthItem()` — тот удаляет один конкретный
ключ, `clearAllAuthStorage()` полностью очищает весь `auth`-store LocalForage
(сессию, `sre_user_registered`, `user_info_cache`) разом. `app_config_cache`
(`stores/config.js`) использует отдельный, не связанный с auth механизм
кэширования — сознательно не затрагивается этой функцией (см. «Риски»).

### 5. `src/App.vue` (`logout()`) — подтверждение выхода вместо мгновенного signOut

Кнопка "Abmelden" вместо немедленного вызова `logout()` открывает новый
`LogoutConfirmModal`. Порядок действий при подтверждении:

1. `supabase.auth.signOut()` — **сначала**, пока сессия ещё физически на
   месте (SDK должен успеть прочитать текущий refresh-токен для корректного
   server-side revoke; вызывать после стирания хранилища нельзя — signOut
   ничего не найдёт для отзыва).
2. `userStore.clearUserCache()` — как сейчас (существующий метод).
3. Если отмечен чекбокс "Auch lokale Daten löschen" — дополнительно
   `clearAllAuthStorage()`. После этого шага `sre_user_registered` тоже
   стёрт — устройство при следующем запуске неотличимо от гостевого.
4. Редирект на `/main`, как сейчас.

## Новые компоненты

### `src/components/LogoutConfirmModal.vue`

По образцу `GroupChangeModal.vue`/`BusChangeModal.vue` (те же пропсы `show`/
события `close`/`saved`, тот же визуальный паттерн модалки Bootstrap).
Содержимое: подтверждающий текст выхода + чекбокс (немецкий текст интерфейса,
по умолчанию **не отмечен**, например: `Auch lokale Daten von diesem Gerät

регистрация/приглашение для повторного входа с этого устройства) + кнопки
"Abmelden" / "Abbrechen". Один компонент, без отдельного роута `/logout` —
это укладывается в уже принятый в проекте паттерн модалок поверх текущей
страницы вместо отдельных экранов для второстепенных диалогов.

## Последовательность реализации

1. `router/index.js` + `App.vue` — всегда вызывать `getSession()`, флаг
   использовать только как подсказку для redirect-таргета при отсутствии
   сессии (`/login`, если флаг `true`, иначе `/info`).
2. `WelcomeView.vue` — перенести запись флага после успешного
   `signInWithPassword()`.
3. `App.vue` — добавить самовосстановление флага при каждой подтверждённой
   сессии (fire-and-forget, по образцу `last_seen_date`).
4. `storage.js` — добавить `clearAllAuthStorage()`.
5. `LogoutConfirmModal.vue` — новый компонент; подключить вместо прямого
   `logout()` на кнопке "Abmelden" в `App.vue`.
6. Ручная регрессия на доступных устройствах (Android/десктоп-браузер):
   логин, автоматическое восстановление сессии между запусками, выход без
   чекбокса (сессия сброшена, флаг остался), выход с чекбоксом (флаг тоже
   стёрт, следующий запуск ведёт себя как у гостя).
7. Проверка на iPhone — по мере появления доступа к устройству; не
   блокирует внедрение (см. «Риски», пункт 1), но должна быть выполнена и
   задокументирована при первой возможности.

## Риски

1. **Нет физического iPhone для проверки на момент реализации.** Заказчик
   осознанно принимает этот риск в обмен на упрощение архитектуры — план
   фиксирует это явно, чтобы не считать отсутствие проверки на iPhone
   упущением при закрытии тикета. Проверка остаётся открытым пунктом до
   появления устройства.
2. **Порядок операций при выходе с очисткой важен.** `signOut()` должен
   выполняться до `clearAllAuthStorage()` — иначе Supabase SDK не сможет
   прочитать токен для server-side revoke. Ошибка в порядке — не критична для
   пользователя (устройство всё равно будет очищено локально), но оставит
   "подвисшую" активную сессию на сервере до её естественного истечения.
3. **Смена redirect-таргета (`/info` → `/login`) для случая "флаг есть,
   сессии нет" — затрагивает всех пользователей, а не только iPhone.**
   Требует регрессии на Android/десктопе (шаг 6 последовательности).
4. **Самовосстановление флага — новая операция записи при каждом успешном
   старте.** Дешёвая и idempotent, но должна быть fire-and-forget (не
   блокировать рендер), по аналогии с уже существующим обновлением
   `last_seen_date`.
5. **`clearAllAuthStorage()` не трогает `app_config_cache`.** Это осознанное
   решение (отдельный, не auth-связанный кэш конфигурации, `stores/config.js`)
   — стоит явно прописать в `IMPLEMENTATION_REPORT.md`, чтобы не восприняли
   как забытый пункт при следующем ревью.
6. **Без диагностики на реальном устройстве корневая причина остаётся
   неподтверждённой, только наиболее вероятной по анализу кода.** Если после
   внедрения этого исправления проблема на iPhone сохранится, потребуется
   отдельный проход — вероятно, тогда придётся вернуться к диагностике с
   реальным устройством (версия 1 плана), которая была отложена, а не
   отменена навсегда.
